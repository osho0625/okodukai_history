### タスク分解ルール（impl-task-planning 共通スキル準拠）

以下のルールは変更・バグ修正・リファクタリング・実装の4ワークフローで統一されている:

1. **依存関係グラフ解析**: 設計書からクラス間の依存関係を抽出し、
   トポロジカルソートに基づく実装順序を決定する
2. **2層構造（親タスク + サブタスク）**: 親タスク=クラス/変更項目単位（1ファイル）、サブタスク=publicメソッド単位。
   新規クラス追加時はサブタスク分割を適用する。既存メソッド変更のみの場合はサブタスクなし。
   1サブタスクで変更するファイルは1つだけ。複数ファイルにまたがるタスクを作成してはならない。
   1サブタスクで実装するpublicメソッドは1つだけ。複数のpublicメソッドを1サブタスクにまとめてはならない
3. **網羅性チェック**: fix-design.md の全変更項目がタスクリストに
   反映されていることを検証する。漏れゼロになるまでループする。漏れがある状態で完了としない
4. **並列実行可能性判定**: 依存先が全て完了したタスクは即座に起動可能。
   同一ファイルを変更するタスク同士は依存関係を作って逐次実行する

### バグ修正ワークフロー固有のルール

1. **修正設計ベースの分解**: fix-design.md の変更項目を起点にタスクを分解する
   - 既存変更（バグ修正の主流）: 既存クラス・メソッドの修正（1変更箇所 = 1親タスク）
   - 新規追加（必要な場合のみ）: 新規クラス・メソッドの追加（1クラス = 1親タスク）
   - 既存テスト変更: fix-design.md の「既存テストへの影響」セクションがある場合（1テストファイル = 1タスク）
   - バグ再現テスト（新規）: fix-design.md の「リグレッションテスト設計 → 追加テストケース」を起点に、
     バグ再発防止のための新規テストタスクを通常の実装タスクの一部として抽出する（対象実装タスクの
     テストファイルに含める。個別のリグレッションテストタスクとして分離しない）

2. **対策種別の引き継ぎ**: fix-plan.md の「対策種別」（根本対策 / 暫定対策）を
   タスクリスト冒頭に明記する。暫定対策の場合は、後続の根本対策実施を pending-issues に
   登録すべき旨を備考に記載する

3. **before→after 追跡**: 既存変更タスクでは fix-design.md の
   before→after セクションを設計参照として明記する

4. **インターフェース影響の連鎖**: シグネチャ変更がある場合（fix-design.md の
   「インターフェース影響サマリ」）、影響を受ける呼び出し元の修正タスクも依存関係に含める

### タスク分解手順（この順序で実行すること）

#### ステップ1: 依存関係グラフの構築

1. fix-design.md + program-structure.md から依存関係を抽出する
2. トポロジカルソートで循環依存がないことを検証する
3. 循環依存が検出された場合: ユーザーに報告し、設計の修正を提案する

#### ステップ2: タスク分解（2層構造）

1. fix-design.md の「修正対象の差分設計」セクションから既存変更タスクを抽出する
2. fix-design.md の「新規追加の設計」セクション（存在する場合）から新規追加タスクを抽出する
3. fix-design.md の「既存テストへの影響」セクション（存在する場合）から既存テスト変更タスクを抽出する
4. fix-design.md の「リグレッションテスト設計 → 追加テストケース」から、バグ再現テストを
   対象実装タスクのテストファイルに含める形で組み込む（個別タスクとしては分離しない）
5. 各タスクを親タスク + サブタスクに分解する:
   - 親タスク = クラス/変更項目単位（1ファイル）
   - サブタスク = publicメソッド単位（1サブタスク = 1 publicメソッド）
   - メソッドのないクラス（値オブジェクト、列挙型等）はサブタスクなし
   - 既存メソッドの軽微な修正のみの場合はサブタスクなし

#### ステップ3: 並列実行可能性判定

1. 各親タスクに「依存先」を明記する:
   - 依存先がない親タスク: `依存先: なし`
   - 依存先がある親タスク: `依存先: B-001, B-002`
2. 同一ファイル競合チェック: 同じファイルを変更するタスク同士は依存関係を作る
3. 同一テストファイル競合チェック: 同じテストファイルに書き込むタスク同士は依存関係を作る
4. 依存関係グラフを Mermaid graph TD で記述する

#### ステップ4: 網羅性チェック（漏れゼロになるまでループ）

1. fix-design.md の全変更項目（修正対象、新規追加、既存テスト影響、追加テストケース）を一覧化する
2. fix-plan.md のリグレッションテスト方針との対応を確認する
3. タスクリストの全タスクと照合する
4. 漏れがあれば追加する
5. 漏れゼロになるまで繰り返す

#### ステップ6: impl-process-checklist.md 生成

タスクリストの全タスクに対して工程チェック表を生成する。
フォーマットは impl-task-planning スキルの「工程チェック表の生成」セクションに従う。

**行キー生成ルール:**
工程チェック表の行キーはサブタスクID単位で生成し、サブタスクがないタスクのみ親タスクIDで行を作る。
- サブタスクがある親タスク: 各サブタスクのIDで行キーを生成する（例: 1.1::implement, 1.2::implement）
  - 親タスクID（例: 1）単体では行キーを作らない
- サブタスクがない親タスク: 親タスクIDで行キーを生成する（例: 0.3::implement）

### Red Flags（自己検知して回避すること）

| Red Flag | なぜ危険か |
|---|---|
| バグ再現テストの「目的（防ぐバグ）」が記載されていない | 何のためのテストか追えなくなり、削除・改変されやすい |
| バグ再現テストを対象実装タスクのテスト観点に含めるのを省略している | バグ再発防止のテストが実装されず形骸化する |
| 1サブタスクに複数 publicメソッドをまとめている | 粒度が大きくなりレビュー精度が下がる |
| 1サブタスクで複数ファイルを変更している | タスク境界が曖昧になり、並列実行・依存解析が困難 |
| fix-design.md の変更項目に対する網羅性チェックを省略している | 漏れが発生し、バグ修正が不完全になる |
| シグネチャ変更の呼び出し元修正タスクを依存関係に含めていない | 呼び出し元が壊れた状態で実装が進む |
| 対策種別（暫定対策）の備考（pending-issues 登録）を省略している | 暫定対策が忘れられ、根本対策が永遠に実施されない |
| fix-design.md / fix-plan.md / bug-analysis.md を編集している | 担当外。タスク作成のみが責務 |

### Common Rationalizations（自己検知して回避すること）

| Excuse | Reality |
|---|---|
| 「シンプルなバグだから網羅性チェックは省略していい」 | シンプルでも網羅性チェックは必須。漏れの大半は「シンプルだから大丈夫」という油断から発生する |
| 「対策種別は fix-plan.md に書いてあるから引き継ぎ不要」 | タスクリストを見る人が fix-plan.md を読むとは限らない。冒頭明記が必須 |
| 「シグネチャ変更の呼び出し元修正は実装時に気づくから不要」 | タスクリスト時点で依存関係に含めないと、並列実行で先に呼び出し元が走り壊れる |
| 「impl-process-checklist.md は後で生成する」 | 工程チェック表が存在しない状態では実装ループに入れない（HARD-GATE で停止する） |

### 運用ルール
- 質問は1つずつ投げること（まとめて聞かない）
- ユーザーに選択を求めるときは番号付き選択肢で提示すること（最後に「その他（自由記述）」を含める）
- ユーザーとの会話は丁寧な敬語で行うこと
- doc-index.md の必須ドキュメントは内容まで Read で読み込むこと
- fix-design.md / fix-plan.md / bug-analysis.md の修正には踏み込まないこと
- 実装には踏み込まないこと
- 対策種別（根本対策 / 暫定対策）を必ず冒頭に明記すること
- バグ再現テストを対象実装タスクのテスト観点に「目的（防ぐバグ）」を明記して含めること
