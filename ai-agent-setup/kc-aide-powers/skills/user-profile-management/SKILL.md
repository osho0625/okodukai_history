# user-profile-management

## Overview

ユーザーの技術レベルを会話から推定し、コミュニケーションの粒度を動的に調整せよ。直接聞くな、観察して推定しろ。プロファイルに基づいて、説明の深さ・専門用語の使用・選択肢の提示方法を含む会話内容全体を調整せよ。

**Core principle:** user-profile-management は、ユーザーとの対話を通じて技術レベル（ドメイン知識・プログラミング・システム/インフラの3軸×5段階）を推定・記録し、コミュニケーションスタイルを動的に調整するスキルである。ユーザーに「あなたのレベルは？」と直接聞くのではなく、会話の中で使用する用語、質問の具体性、理解の深さから自然に推定する。

## 評価軸の定義

### ユーザー識別

- `git config user.email` を実行してメールアドレスを取得し、個別識別子として使用する
- 取得できない場合は `git config user.name` をフォールバックとして使用する
- それも取得できない場合は、ユーザーに識別情報を確認する
- 同じプロジェクトを複数人が扱う可能性があるため、プロファイルはユーザーごとに管理する

### 3軸×5段階の評価テーブル

| 軸 | 観点 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| **ドメイン知識** | ビジネスロジックの把握度 | 業務未経験 | 概要は知っている | 業務経験あり | 業務の詳細を把握 | 業務設計可能 |
| **プログラミング** | プログラミング知識レベル | 未経験 | 基本概念は理解 | 基本的なコーディング可能 | 設計パターンを理解 | アーキテクチャ設計可能 |
| **システム/インフラ** | DB・外部サービス・インフラの知識 | 未経験 | 概念は理解 | 利用経験あり | 設定・構築経験あり | 構築・運用経験あり |

### 5段階の基準（共通パターン）

| レベル | 共通的な意味 |
|---|---|
| 0 | 初期値（不明）。プロファイル未作成時、または初回対話中のデフォルト値 |
| 1 | 未経験・知識なし |
| 2 | 概念レベルの理解（聞いたことがある程度） |
| 3 | 実務経験あり（基本的な操作・作業が可能） |
| 4 | 詳細な理解（設計・設定レベルの判断が可能） |
| 5 | エキスパート（設計・構築・運用を主導できる） |

## Process

**プロファイル未作成時のデフォルト動作:**
- user-profile.md が存在しない場合は全軸スコア0（不明）として安全側デフォルトで進行
- apply モード実行時にプロファイルが存在しなければ自動で作成する

**Adapt to context:**
- プロジェクトの性質に応じて3軸の重み付けを調整してよい
- ユーザーが複数人いる場合は主要な対話相手のプロファイルを管理する
- 技術レベルが明らかな場合（自己紹介等）はその情報を初期スコアに反映してよい

### モード判定

| モード | トリガー |
|---|---|
| apply | ユーザーに説明・質問・提案するとき（常時）。プロファイル未作成なら自動で作成 |
| update | 会話中にスコアと実態の差異を検知した / ワークフロー終了時 |

### update モード（プロファイル更新）

**Step 1:** 現在のスコアとの比較
- 新たな情報が現在のスコアと矛盾するか確認
- 矛盾なし → 更新不要
- 矛盾あり or より正確な情報 → Step 2へ

**Step 2:** スコアの更新
- 該当軸のスコアを変更、変更根拠を記録

**Step 3:** apply モードを再調整

### apply モード（会話内容の調整・常時適用）

**プロファイルが存在しない場合（自動作成）:**

1. ユーザー識別
   - `git config user.email` → 取得できなければ `git config user.name`
   - 既存 user-profile.md に該当ユーザーが存在する → update モードへ
2. 会話内容からの推定
   - 使用する用語の専門性、質問の具体性・抽象度、技術概念への理解度、業務知識の深さ
3. 3軸×5段階のスコア設定
   - 各スコアに推定根拠を記録
4. user-profile.md の作成
   - プロジェクトの設計書ディレクトリに保存

**プロファイルに基づく調整（常時適用）:**

| 調整観点 | スコア0〜2 | スコア3 | スコア4〜5 |
|---|---|---|---|
| **専門用語** | 避ける。具体例や比喩で説明 | 基本的な用語は使用。必要に応じて補足 | そのまま使用。補足不要 |
| **説明の深さ** | 背景から丁寧に説明。前提知識を仮定しない | 要点を説明。必要に応じて背景を補足 | 結論から簡潔に。詳細は求められたら |
| **選択肢の提示** | 推奨を明示し、判断を助ける | 選択肢を並列提示。メリット・デメリットを添える | 選択肢のみ提示。判断はユーザーに委ねる |
| **質問の仕方** | 具体的な例を挙げて質問 | 一般的な質問形式 | 技術的な議論形式 |
| **設計判断の説明** | 「なぜこうするか」を平易に説明 | 設計原則を引用して説明 | 設計原則名のみで通じる |

**軸ごとの独立適用:** 各軸のスコアは独立して適用する。

**プログラミング軸スコア0〜2の場合の判断代行ルール:**

ユーザーに判断する力量がない場合、**より安全な選択肢を選ぶ**:
- 設計原則・アーキテクチャルール・コーディング規約を厳守する方
- 技術的負債を生まない方
- 将来の保守性・拡張性を優先する方

**禁止:** AIの都合で楽な方（実装が簡単、変更量が少ない、早く終わる）に誘導すること。

## user-profile.md テンプレート

```markdown
# ユーザープロファイル

## ユーザー: {user.name}
- 識別子: {user.email}
- 取得手段: git config user.email
- 初回対話日: {YYYY-MM-DD}

### 技術レベル（3軸×5段階）

| 軸 | スコア | 根拠 |
|---|---|---|
| ドメイン知識 | {1-5} | {推定根拠} |
| プログラミング | {1-5} | {推定根拠} |
| システム/インフラ | {1-5} | {推定根拠} |

### 更新履歴

| 日時 | 軸 | 変更 | 根拠 |
|---|---|---|---|
| {YYYY-MM-DD} | — | 初期作成 | {初回対話の内容から推定} |
```

1つの user-profile.md ファイル内に複数ユーザーのプロファイルをセクションとして管理する。

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。プロファイル管理を怠ろうとしている。

| Red Flag | なぜ危険か |
|---|---|
| 「ユーザーに直接技術レベルを聞こう」 | ユーザーは自分のレベルを正確に自己評価できないことが多い。会話から推定する方が正確 |
| 「全員に同じ説明粒度でいい」 | 専門用語だらけの説明は初心者を混乱させ、平易すぎる説明はエキスパートの時間を浪費する |
| 「プロファイルの更新は面倒だから初期値のまま」 | ユーザーの理解度は会話を重ねるにつれて明らかになる。初期推定は不正確な場合がある |
| 「スコア変更の根拠は記録しなくてよい」 | 根拠なきスコア変更は恣意的になる。引き継ぎ時に「なぜこのスコアか」が説明できない |
| 「このユーザーはエンジニアだから全軸5でいい」 | エンジニアでもドメイン知識が低い場合がある。各軸を独立して評価する |
| 「プロファイルは企画ワークフローだけで使うもの」 | 設計ワークフロー以降でもユーザーとの対話は発生する。プロファイルは全ワークフローで活用すべき |
| 「ユーザーが判断できないから簡単な方にしよう」 | プログラミング知識が低いユーザーの判断を代行する場合、もしくは推奨（recommend）を設定する場合、安全側（堅実・ルール準拠）を選ぶ。AIの都合で楽な方に流れてはならない |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「ユーザーが自分でエンジニアだと言ったからプログラミング=5」 | 自己申告は過大・過小評価の可能性がある。会話内容から実際のレベルを推定する |
| 「プロファイル作成に時間をかけたくない」 | 初回対話の中で自然に推定するだけ。追加の時間はほぼかからない |
| 「設計フェーズではプロファイルは不要」 | 設計フェーズでもユーザーへの説明・確認が発生する。プロファイルに基づく説明粒度の調整は常に有効 |
| 「スコアが変わるたびに更新するのは手間」 | 更新は「新たな情報が得られたとき」のみ。毎回の会話で更新する必要はない |
| 「変更量が少ない方がユーザーにとっても良い」 | 変更量の大小は安全性の指標ではない。変更が大きくても、ルールに則った堅実な選択肢の方がユーザーにとって長期的に有益 |

## Integration

**Required workflow skills:**
- なし（このスキルは他のスキルに依存しない）

**Called by:**
- 企画ワークフロー — 初期プロファイル作成、全フェーズでの更新、引き継ぎ時の所感記載
- 設計ワークフロー — 引き継ぎ資料としての読み込み、説明粒度の調整
- 全ワークフロー — ユーザーとの対話時のコミュニケーションスタイル調整（推奨）

**Related skills:**
- `doc-index-maintenance` (aide-powers skill) — user-profile.md 作成時に `doc-index.md` に登録する
