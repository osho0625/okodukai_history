# doc-index-maintenance

## Overview

`doc-index.md` は、プロジェクトの全設計書の一覧と状態を管理する唯一の情報源（Single Source of Truth）である。設計書ゲート（design-gate (aide-powers skill)）は `doc-index.md` を読んで設計書の完了状態を判定する。`doc-index.md` が不正確であれば、設計書ゲートが正しく機能しない。

**Core principle:** ドキュメントを作ったら、必ずインデックスに登録しろ。登録なきドキュメントは存在しないのと同じ。

## The Iron Law

```
NO DOCUMENT CREATION WITHOUT INDEX UPDATE.
ドキュメントの作成・更新・削除なしに、インデックスを放置してはならない。
```

## Process

**Exceptions:**
- 作業中ドキュメント（変更/バグ修正/リファクタリングの中間成果物）はインデックスに登録しない。設計書本体に反映されるまで作業中扱いとする

### プロセスA: ドキュメント作成時のインデックス更新

**Step 1:** インデックスの存在確認
- 存在しない → Step 1aへ: インデックスを新規作成する（テンプレート: ドキュメント一覧テーブル + 参照ガイドセクション）
- 存在する → Step 2へ

**Step 2:** 作業中ドキュメント判定
- 作成されたドキュメントは作業中ドキュメントか？（変更/バグ修正/リファクタリングの中間成果物）
- 作業中ドキュメント → 登録しない。終了
- 設計書本体 → Step 3へ

**Step 3:** エントリの追加
- ファイル名（相対パスリンク付き）
- 用途（1行の説明）
- 作成タイミング（フェーズ番号等）
- ステータス（✅ 完了）

**Step 4:** 参照ガイドの更新
- 「ドキュメント参照ガイド」セクションを必要に応じて更新する

### プロセスB: ドキュメント更新時のインデックス更新

**Step 1:** 該当エントリの確認
- インデックスに該当ドキュメントのエントリが存在するか確認する
- 存在しない → エントリを追加する（プロセスAのStep 3へ）
- 存在する → Step 2へ

**Step 2:** エントリの最新化
- 用途・説明が最新かを確認し、必要なら修正する
- ステータスが変わった場合は更新する

**Step 3:** 参照ガイドの更新
- 必要に応じて更新する

### プロセスC: ドキュメント削除時のインデックス更新

**Step 1:** 該当エントリの除去
- インデックスから削除されたドキュメントのエントリを除去する

**Step 2:** 参照ガイドの更新
- 該当参照を除去する

### プロセスD: インデックスの新規作成

**Step 1:** テンプレートからインデックスを作成する
- ドキュメント一覧テーブル（ファイル名、用途、作成タイミング、ステータス）
- ドキュメント参照ガイドセクション

**Step 2:** 最初のドキュメントのエントリを追加する

### プロセスE: ワークフロー定義との整合性チェック

**Step 1:** 既存エントリのフェーズ番号を確認する
- ワークフロー定義の最新フェーズ番号と一致するか？
- 一致する → 修正不要
- ずれがある → フェーズ番号を修正する。進捗管理ファイルが存在する場合も同様に修正する

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。インデックス更新を忘れようとしている。

| Red Flag | なぜ危険か |
|---|---|
| 「ドキュメントを作ったが、インデックス更新は後でやる」 | 「後で」は忘れる。作成直後に更新すること |
| 「小さなドキュメントだからインデックスに登録しなくてよい」 | ドキュメントの大小に関わらず、全てのドキュメントを登録する。登録なきドキュメントは設計書ゲートで認識されない |
| 「作業中ドキュメントもインデックスに登録しておこう」 | 作業中ドキュメント（変更/バグ修正/リファクタリングの中間成果物）は登録しない。設計書本体に反映されるまで作業中扱い |
| 「設計書反映が完了したが、インデックスは変わっていないはず」 | 設計書反映で新規ドキュメントが追加されたり、既存ドキュメントの用途が変わる可能性がある。必ず確認する |
| 「revertしたが、インデックスはそのままでよい」 | revertで削除されたドキュメントのエントリを除去しないと、設計書ゲートが不正確になる |
| 「フェーズ番号がずれているが、大した問題ではない」 | フェーズ番号のずれは、ワークフローの進捗管理に混乱を招く。発見したら即座に修正する |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「インデックス更新は手間がかかる」 | 1エントリの追加は数秒の作業。更新忘れによる設計書ゲートの誤判定の方がはるかにコストが高い |
| 「誰もインデックスを見ていない」 | 設計書ゲート（design-gate (aide-powers skill)）がインデックスを読んで設計書の完了状態を判定する。インデックスが不正確なら設計書ゲートが機能しない |
| 「ドキュメントのファイル名を見ればわかる」 | ファイル名だけでは用途・ステータス・作成タイミングがわからない。インデックスは設計書の全体像を把握するための唯一の情報源 |
| 「設計書反映後のインデックス更新は設計書反映エージェントがやるべき」 | 設計書反映エージェントはインデックスを更新しない（読み取り専用）。インデックスの管理はワークフロー管理者（オーケストレーター）の責務 |

## Integration

**Required workflow skills:**
- なし（doc-index-maintenance は独立して動作する）

**Called by:**
- 設計ワークフロー（各フェーズ完了後）
- 企画ワークフロー（各成果物作成後、フェーズ3最終化時）
- 逆引きワークフロー（各フェーズ完了後）
- 変更ワークフロー（フェーズ9完了後）
- バグ修正ワークフロー（フェーズ6完了後）
- リファクタリングワークフロー（フェーズ5完了後）
- revert処理時

**Related skills:**
- `design-gate (aide-powers skill)` — インデックスを「読む」側。doc-index-maintenance が「書く」側。この2つで読み書き分離を実現する
- `pending-issues-management (aide-powers skill)` — design-gate (aide-powers skill) が FAIL した場合に issue を登録する。doc-index-maintenance が正確にインデックスを管理することで、design-gate (aide-powers skill) の判定精度が保たれる
- `design-sync (aide-powers skill)` — 設計書と実装の乖離が発生した場合の同期手順。設計書が更新された場合、doc-index-maintenance でインデックスも更新する
