# 実装タスク分解

## Overview

**Core principle:** 設計書を依存関係グラフとして解析し、「常にテスト済みの部品だけを使って次の部品が作れる」順序でタスクを分解せよ。タスクは2層構造（親タスク=クラス/ファイル単位、サブタスク=publicメソッド単位）で生成する。設計書の全定義がタスクリストに反映されるまで完了としない。

impl-task-planning は、4つのワークフロー（実装・変更・バグ修正・リファクタリング）で共通利用されるタスク分解スキルである。設計書から依存関係を機械的に抽出し、トポロジカルソートに基づく実装順序を決定し、並列実行可能性を判定し、網羅性を検証する。

## 絶対ルール

以下の4つのルールは、いかなる状況でも破ってはならない:

1. **2層構造（親タスク + サブタスク）**: タスクリストは「親タスク=クラス単位（1ファイル）」と「サブタスク=publicメソッド単位」の2層構造で生成する。メソッドのないクラス（値オブジェクト、列挙型、例外クラス等）はサブタスクなしで親タスク自体が実装単位となる。micro-impl-agent はサブタスク単位（または サブタスクなしの親タスク単位）で呼び出される
2. **1サブタスク=1ファイル=1 publicメソッド**: 1つのサブタスクで変更するファイルは1つだけ、実装するpublicメソッドは1つだけ。複数ファイルにまたがるタスクを作成してはならない。複数のpublicメソッドを1サブタスクにまとめてはならない
3. **網羅性チェック必須**: 設計書の全定義がタスクリストに反映されていることを検証する。漏れゼロになるまでループする。漏れがある状態でユーザーに提示しない
4. **依存関係に基づく順序**: 依存先を先に実装してから本体を実装する順序を守る。依存関係を無視した順序でタスクを並べてはならない

## Process

impl-task-planning は「ルール提供型」の共通スキルであり、自身が制御フローを持つのではなく、呼び出し元のフェーズスキルが制御フローを管理する。本スキルは以下の共通ルール・手順を提供する。

**Step 1:** 依存関係グラフの構築
- 設計書からクラス/モジュール間の依存関係を抽出する
  - コンストラクタ引数の型
  - メソッド引数・戻り値の型ヒント
  - import 関係
  - インターフェース実装関係
- ★ 型ヒントの依存関係を最優先する:
  - インターフェースがドメインモデル（エンティティやVO）を引数・戻り値の型に使う場合、そのVO/エンティティをインターフェースより先に実装すること

**Step 2:** 依存関係グラフの検証
- 依存関係グラフのトポロジカルソートで循環依存がないことを検証する
- ※ 「レベル」の概念は使用しない。依存先が全て完了したタスクは即座に起動可能
- ★ 循環依存が検出された場合: ユーザーに報告し、設計の修正を提案する

**Step 3:** タスクへの分解（2層構造）
- 各クラス/変更項目を親タスク + サブタスクに分解する
  - 親タスク = クラス単位（1ファイル）。メタ情報（ファイルパス、依存先、設計参照等）を持つ
  - サブタスク = publicメソッド単位。micro-impl-agent が実際に呼ばれる単位
  - メソッドのないクラス（値オブジェクト、列挙型、例外クラス等）はサブタスクなし。親タスク自体が実装単位
  - 初回サブタスク（クラス新規作成時）は、コンストラクタ（__init__）+ 最初のpublicメソッド1つまで
  - テストファイルは実装ファイルと同じ親タスクに含める
  - インターフェース（ABC）の「定義」と「実装」は別親タスク

**Step 4:** 並列実行可能性の判定（依存グラフ生成）
- 各親タスクの依存関係を以下のチェックで確定する:
  1. 同一ファイル競合チェック: 同じファイルを変更する親タスク同士は依存関係を作って逐次実行する（並列禁止）
  2. 同一テストファイル競合チェック: 同じテストファイルに書き込む親タスク同士は依存関係を作って逐次実行する
  3. 依存グラフでの表現（cline Kanban 準拠）:
     - Mermaid graph TD で各親タスクのノードと依存エッジを記述
     - 実行リンク（`A → B, A → C` 形式）で並列スタート・依存連鎖を明示
     - 依存先のない親タスク = 並列スタート可能
     - 矢印の左が完了したら右を開始
     - [並列可] / [逐次] マーカーは廃止
  4. 各親タスクに「依存先」を明記する（必須）:
     - 依存先がない親タスク: `依存先: なし`
     - 依存先がある親タスク: `依存先: D-001, D-002`（タスク番号をカンマ区切りで列挙）
     - この「依存先」表記により、実装フェーズが「今すぐ実行可能なタスク」を即座に判定できる
  5. 「レベル」の概念は使用しない:
     - 依存先が全て完了した親タスクは即座に起動可能
     - 同レベルの無関係なタスクの完了を待つ必要はない
     - 最大並列度 = 依存先が全て完了済みの親タスクの数
  6. サブタスクの実行順序:
     - 同一親タスク内のサブタスクは上から順に逐次実行する（並列不可）
     - サブタスク間の依存関係は親タスク内で暗黙的に成立する（前のサブタスクが完了してから次のサブタスクを実行）

**Step 5:** 網羅性チェック（漏れゼロになるまでループ）
- REPEAT:
  1. 設計書の全定義を一覧化する
  2. タスクリストの全タスクと照合する
  3. 漏れがある場合:
     - 漏れた項目ごとにタスクを追加する
     - 追加タスクは依存関係に基づき適切なレベルに挿入する
     - 追加タスクに並列実行可能性を判定する
  4. 漏れがない場合: ループ終了
- UNTIL 漏れ = 0

**Step 6:** 完了 — タスクリストを呼び出し元に返す

### 依存関係グラフ解析の詳細ルール

**抽出対象（設計書から機械的に抽出）:**

| 依存関係の種類 | 抽出元 | 例 |
|---|---|---|
| コンストラクタ引数の型 | クラス定義の `__init__` 引数 | `def __init__(self, repo: IRepository)` → IRepository に依存 |
| メソッド引数の型ヒント | publicメソッドの引数型 | `def process(self, data: InputData)` → InputData に依存 |
| メソッド戻り値の型ヒント | publicメソッドの戻り値型 | `def get() -> Result` → Result に依存 |
| インターフェース実装 | クラスの継承関係 | `class Impl(IInterface)` → IInterface に依存 |
| import 関係 | program-structure.md のimportルール | レイヤー間の依存方向 |

**依存方向の原則（レイヤードアーキテクチャ準拠）:**

```
ドメイン層（依存なし）
  ^
  |
アプリケーション層（ドメイン層に依存）
  ^
  |
インフラストラクチャ層 / プレゼンテーション層（アプリケーション層・ドメイン層に依存）
```

**型ヒント最優先ルール:**
- インターフェースがドメインモデル（エンティティやVO）を引数・戻り値の型に使う場合、そのVO/エンティティをインターフェースより先に実装する
- レベル分類上はインターフェースが「完全独立」に見えても、型ヒントで参照するクラスが未実装なら後回しにする

### 2層構造ルールの詳細

**親タスク（クラス単位）:**

| ルール | 説明 |
|---|---|
| 1親タスク = 1ファイル | `src/domain/entity.py` と `tests/domain/test_entity.py` のペアが1親タスク |
| 複数クラスが同一ファイルに配置される場合 | 同一ファイル内の全クラスを1親タスクにまとめる |
| インターフェース定義と実装は別親タスク | `IRepository`（定義）と `JsonRepository`（実装）は別親タスク・別ファイル |
| 既存ファイルの変更は1変更箇所=1親タスク | 同一ファイルへの複数変更は1親タスクにまとめる（ファイル競合防止） |

**サブタスク（publicメソッド単位）:**

| ルール | 説明 |
|---|---|
| 1サブタスク = 1 publicメソッド | 1つのpublicメソッド + 関連するprivateメソッド・ヘルパーが最大単位 |
| 初回サブタスク | クラス新規作成時は、コンストラクタ（`__init__`）+ 最初のpublicメソッド1つまで |
| メソッドのないクラス | 値オブジェクト、列挙型、例外クラス等。サブタスクなし、親タスク自体が実装単位 |
| micro-impl-agent の呼び出し単位 | サブタスク1つ（またはサブタスクなしの親タスク1つ）= micro-impl-agent 1回の呼び出し |
| 1サブタスクで変更するファイルは1つだけ | 複数ファイルへの変更が必要な場合は別タスクに分割する |

### 網羅性チェックの詳細

**新規作成モードのチェック対象:**
- クラス定義（コンストラクタ含む）
- 全publicメソッド
- 定数の塊（モジュールレベルの定数定義）
- 列挙型の全メンバー
- インターフェース定義（ABC）
- 設計書に記載されたヘルパー関数・ユーティリティ関数

**差分モードのチェック対象:**
- 差分設計書の全変更項目（新規追加・既存変更・削除）
- import関係の変更
- テストの変更

**チェック結果の記録フォーマット:**

```markdown
## 網羅性チェック結果
- チェック回数: {N}回
- 設計書の総定義数: {A}件
- タスクリストの総タスク数: {B}件
- 最終結果: 漏れなし
```

## 実行可能タスクの判定手順（実装フェーズ向け）

実装フェーズは以下の手順で「今すぐ実行可能なタスク」を特定し、全て同時に起動すること。

### 基本原則

- **依存先がないタスク → すぐに実装できる**
- **依存先があるタスク → その全ての依存先の実装が完了したら実装できる**

### 具体的な手順

1. タスクリストの未完了タスクを全て走査する
2. 各タスクの「依存先」を見る
3. 実行可能なタスクを全て抽出する:
   - 依存先が「なし」→ すぐに実装できる
   - 依存先が全て完了済み → すぐに実装できる
   - 依存先に1つでも未完了がある → まだ実装できない（待機）
4. 実行可能なタスクを全て、それぞれ別のサブエージェントに委譲し、同時に起動する
5. いずれかのタスクが完了したら、1に戻る
6. 全タスク完了まで繰り返す

### 例

タスク一覧:
- D-001: 依存先: なし ← すぐに実装できる
- D-002: 依存先: なし ← すぐに実装できる
- D-003: 依存先: D-001 ← D-001 が完了したら実装できる
- D-004: 依存先: D-001, D-002 ← D-001 と D-002 の両方が完了したら実装できる
- D-005: 依存先: D-003 ← D-003 が完了したら実装できる

実行の流れ:
- 時点1: D-001, D-002 を同時起動（依存先なし → すぐに実装できる）
- 時点2: D-001 完了 → D-003 を起動（D-001 が完了したので実装できる）
- 時点3: D-002 完了 → D-004 を起動（D-001, D-002 の両方が完了したので実装できる）
- 時点4: D-003 完了 → D-005 を起動（D-003 が完了したので実装できる）

### 禁止事項

- 依存先がないタスクを順番に1つずつ実行すること（全て同時起動すべき）
- 依存関係を確認せずに「とりあえず最初のタスクから」と順番に実行すること
- 無関係なタスクの完了を待ってから次のタスクを起動すること
- 「依存先がある」だけで実行不可と判断すること（依存先が全て完了済みなら実行可能）

## 完了条件

以下の全てを満たすこと:

1. 設計書から依存関係グラフが構築されている
2. トポロジカルソートで循環依存がないことが検証されている
3. 全タスクが2層構造（親タスク=クラス/ファイル単位、サブタスク=publicメソッド単位）の粒度を満たしている
4. 全タスクが依存グラフ（Mermaid + 実行リンク）で表現され、同一ファイル競合がない
5. 網羅性チェックで漏れゼロが確認されている
6. 循環依存が検出されていない（検出された場合はユーザーに報告済み）
7. 工程チェック表（impl-process-checklist.md）が生成されている

## 工程チェック表の生成（必須）

タスクリスト生成と同時に、`impl-process-checklist.md` を生成する。これは fs-impl-phase4-execution (aide-powers skill) が各タスクの工程漏れを防ぐためのチェック表である。

工程チェック表は **「1 工程 = 1 行」構造**で生成する。同一タスク内で「実装」と「テスト実装」を並列起動、「設計準拠レビュー」と「コード品質レビュー」を並列起動しても、各工程の担当サブエージェントが**別々の物理行**を更新するため、同一行への同時書き込み衝突が構造的に発生しない。状態管理は task-orchestration スキルの状態管理表方式（4 状態・担当本人による 3 段階更新）に合わせる。

### 生成ルール

1. タスクリストの全タスクに対して、「タスク × 工程」を 1 行ずつ持つ工程行を生成する（1 工程 = 1 行）
2. プログラムコードのタスクは 5 工程（実装 / テスト実装 / テスト実行 / 設計準拠レビュー / コード品質レビュー）の行を生成する。非プログラム成果物は「実装」「設計準拠レビュー」を実工程行として生成し、「テスト実装」「テスト実行」「コード品質レビュー」は `➖ skip` 行として生成する（output に成果物種別の判定理由を記入。理由なき簡略化を禁止）
3. 表はタスク番号順、同一タスク内は工程キーの順（implement → write_test → run_test → spec_review → quality_review）に並べる
4. 各工程行の「状態」は初期値 `⬜ todo`（`➖ skip` 行を除く）、「実行エージェント」は初期値 `—`、「output」は初期値 `—` とする

### 工程キーと担当エージェント（固定対応）

| 工程キー | 工程名（表示） | 担当エージェント | 前提工程（✅ done で起動可） |
|---|---|---|---|
| `implement` | 実装 | micro-impl-agent (aide-powers agent) | なし |
| `write_test` | テスト実装 | micro-impl-agent (aide-powers agent) | なし（implement と並列） |
| `run_test` | テスト実行 | micro-impl-agent (aide-powers agent) | implement ＋ write_test |
| `spec_review` | 設計準拠レビュー | design-review-agent (aide-powers agent) | run_test |
| `quality_review` | コード品質レビュー | code-review-agent (aide-powers agent) | run_test |
| `parent_check` | 親タスク完了チェック | design-review-agent (aide-powers agent) | 当該親タスクの全サブタスクの全工程 ✅ done（実行時に追加生成） |

> 行キーは `{task_id}::{工程キー}`（例: `1.1::implement`）。親タスク完了チェック行は `{parent_task_id}::parent_check`。チェック表全体で一意。

### フォーマット

各工程行は「状態」「実行エージェント」「output」を持つ。実行エージェントは、状態が `🔄/✅/❌` のとき、その工程キーに対応する担当エージェント（上表）かつホワイトリスト（micro-impl-agent (aide-powers agent) / design-review-agent (aide-powers agent) / code-review-agent (aide-powers agent)）のいずれかでなければならない。

```markdown
# 工程チェック表

## 状態凡例
- ⬜ todo : 未着手（初期状態）
- 🔄 in-progress : 実行中（担当本人が作業開始直後に設定）
- ✅ done : 完了（PASS。担当本人が output に結果サマリを記入）
- ❌ failed : 失敗（FAIL。担当本人が output にエラー／指摘を記入）
- ➖ skip : 対象外（生成時に確定。非プログラム成果物でスキップする工程。output に判定理由）

## プログラムコードタスク

| 行キー | タスクID | タスク | 工程 | 状態 | 実行エージェント | output |
|--------|---------|--------|------|------|----------------|--------|
| 1.1::implement | 1.1 | UserService | 実装 | ⬜ todo | — | — |
| 1.1::write_test | 1.1 | UserService | テスト実装 | ⬜ todo | — | — |
| 1.1::run_test | 1.1 | UserService | テスト実行 | ⬜ todo | — | — |
| 1.1::spec_review | 1.1 | UserService | 設計準拠レビュー | ⬜ todo | — | — |
| 1.1::quality_review | 1.1 | UserService | コード品質レビュー | ⬜ todo | — | — |

## 非プログラム成果物タスク

| 行キー | タスクID | タスク | 工程 | 状態 | 実行エージェント | output |
|--------|---------|--------|------|------|----------------|--------|
| 0.3::implement | 0.3 | 設定ファイル | 実装 | ⬜ todo | — | — |
| 0.3::spec_review | 0.3 | 設定ファイル | 設計準拠レビュー | ⬜ todo | — | — |
| 0.3::write_test | 0.3 | 設定ファイル | テスト実装 | ➖ skip | — | 非プログラム成果物（実行ロジックなし）のためテスト工程は対象外 |
| 0.3::run_test | 0.3 | 設定ファイル | テスト実行 | ➖ skip | — | 非プログラム成果物のため対象外 |
| 0.3::quality_review | 0.3 | 設定ファイル | コード品質レビュー | ➖ skip | — | 非プログラム成果物のため対象外 |
```

完了時の記入例（1 行ずつ担当本人が更新する）:
```
| 1.1::implement | 1.1 | UserService | 実装 | ✅ done | micro-impl-agent | publicメソッド register を実装。DONE |
| 1.1::spec_review | 1.1 | UserService | 設計準拠レビュー | ✅ done | design-review-agent | 設計準拠 PASS（差分0件） |
```

### 担当本人による 3 段階更新（衝突回避）

各工程の担当サブエージェント本人が、**自分の工程行（1 物理行）のみ** を str_replace で更新する。各担当が別行を書くため、対象文字列が物理的に重ならず、並列実行でも衝突しない。

1. 【作業開始直後】 自分の行の 状態 `⬜ todo → 🔄 in-progress`、実行エージェントを自分の名前に
2. 【完了（PASS）】 状態 `🔄 in-progress → ✅ done`、output に結果サマリ
3. 【失敗（FAIL）】 状態 `🔄 in-progress → ❌ failed`、output にエラー／指摘内容

**オーケストレータ（起動元）が代理で `✅ done` を書くこと（実施していない工程をやったことにする）は禁止。** 更新前に impl-process-checklist.md を Read で読み直し、自分の行のみ最小編集する。

### 監査ルール（ホワイトリスト強制）

- 各工程行の「実行エージェント」は、状態が `🔄/✅/❌` のとき、その工程キーに対応する担当エージェント（上表「工程キーと担当エージェント」）であり、かつホワイトリスト3エージェント（micro-impl-agent (aide-powers agent) / design-review-agent (aide-powers agent) / code-review-agent (aide-powers agent)）のいずれかでなければならない
- 工程キーと実行エージェントの対応が不一致、またはホワイトリスト以外の場合は ❌ FAIL 扱いとする
- ユーザーが事後監査で各工程行の実行エージェント列を確認し、違反を検出する
- 違反が検出された場合は、該当工程行を正しいエージェントで再実行する

### 状態記号

| 記号 | 意味 | 設定者 |
|------|------|--------|
| `⬜ todo` | 未着手 | 生成時 |
| `🔄 in-progress` | 実行中 | 担当本人（開始直後） |
| `✅ done` | 完了（PASS） | 担当本人（完了時、output 記入） |
| `❌ failed` | 失敗（FAIL） | 担当本人（失敗時、output 記入） |
| `➖ skip` | 対象外（生成時確定） | 生成時（output に判定理由） |

> 旧フォーマットの「`[!]` FAIL（修正中）」と「修正/再レビュー」列は廃止。FAIL は当該工程行を `❌ failed`／`⬜ todo` に戻して再実行する状態遷移で表現する（差し戻し先の決定規則は coding-test-2review SKILL.md の「レビュー FAIL 時の再実行ルール」を参照）。

## ワークフロー別差異

本スキルは4ワークフロー共通のルールを定義する。各ワークフロー固有のルールは以下の通り:

| 観点 | 実装WF（新規作成モード） | 変更・バグ修正・リファクタリングWF（差分モード） |
|---|---|---|
| 入力設計書 | object-design-*.md, program-structure.md 等 | delta-design.md / fix-design.md / refactoring-design.md |
| タスク構造 | 2層構造（親タスク=クラス単位 + サブタスク=publicメソッド単位） | 2層構造（親タスク=変更項目/クラス単位 + サブタスク=publicメソッド単位）。新規クラス追加時はサブタスク分割を適用。既存メソッド変更のみの場合はサブタスクなし |
| 依存グラフ | クラス階層に基づく依存グラフ（最大並列度） | 変更項目間の依存グラフ（最大並列度） |
| グループ化 | ユースケース単位（フェーズ0: 共通基盤 + フェーズ1-N: ユースケース別） | フラット |
| 網羅性チェック対象 | 全クラス・全publicメソッド・全定数・全列挙型 | 差分設計の全変更項目 |
| ユーザー試験マイルストーン | あり（各フェーズ末尾） | なし |
| リグレッションテスト（既存テスト全実行） | なし | どのWFでも実装タスクとしては計画しない（動作確認Stepで1回実施する設計に統一） |

**実装WF固有の詳細手順:**
- `impl-planner-prompt.md`（本スキルディレクトリに配置）を参照

**差分モード固有の詳細手順:**
- 各フェーズスキルのプロンプトテンプレートに記載（impl-task-planning 共通スキルのルールを前提として参照する形式）

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。impl-task-planning のルールを逸脱しようとしている。

| Red Flag | なぜ危険か |
|---|---|
| 「1タスクで複数ファイルを変更した方が効率的」 | 1サブタスク=1ファイル=1 publicメソッドは絶対ルール。効率性は理由にならない。並列実行可能性の判定が破綻する |
| 「1サブタスクで複数のpublicメソッドをまとめた方が効率的」 | 1サブタスク=1 publicメソッドは絶対ルール。レビュー・テストの粒度が粗くなり品質低下の原因 |
| 「依存関係は自明だから解析不要」 | 依存関係は設計書から機械的に抽出する。「自明」という思い込みは漏れの原因 |
| 「網羅性チェックで漏れがあるが、後で追加すればいい」 | 漏れゼロになるまでループする。漏れがある状態でユーザーに提示しない |
| 「並列実行は使わないから判定不要」 | 並列実行可能性の判定は必須。使うかどうかは実装フェーズが決める |
| 「タスクが多すぎるからまとめた方がいい」 | タスクの統合は品質低下の原因。2層構造のルールを守る |
| 「循環依存があるが無視して進めよう」 | 循環依存は設計の問題。ユーザーに報告し、設計の修正を提案する |
| 「テストファイルは別タスクにした方がいい」 | テストファイルは実装ファイルと同じ親タスクに含める。実装と即テストのループを維持する |
| 「メソッドが少ないからサブタスク分割は不要」 | publicメソッドが1つでもあればサブタスクとして分割する。メソッドのないクラスのみサブタスクなし |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「変更が少ないからタスク分解は不要」 | 変更が1件でもタスクリストは作成する。依存関係の明示と網羅性チェックが目的 |
| 「依存関係グラフは大げさ」 | 依存関係グラフは実装順序の根拠。規模に関わらず作成する |
| 「網羅性チェックは時間がかかる」 | 網羅性チェックは品質保証の核心。漏れがあると実装フェーズで手戻りが発生する |
| 「タスクの粒度はプログラマーが判断すればいい」 | 粒度ルール（親タスク=クラス単位、サブタスク=publicメソッド単位）は統一基準。個人の判断に委ねない |
| 「並列実行可能性は実装時に判断すればいい」 | 並列実行可能性はタスク分解時に判定する。実装時の判断では遅い |
| 「差分モードではサブタスク分割は不要」 | 新規クラス追加時はサブタスク分割を適用する。既存メソッド変更のみの場合はサブタスクなし |
