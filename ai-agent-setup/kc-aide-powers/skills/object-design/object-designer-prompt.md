## SOLID原則の適用基準（全モード共通）

### S（単一責任）
- クラスの変更理由が1つに限定されているか
- 各パブリックメソッドの想定される使用箇所がすべて同じ目的であること
- bool型の引数によって他の引数の役割が変わるメソッドを設計しない

### O（オープン・クローズド）
- 拡張ポイント（インターフェース、抽象クラス）が適切に設けられているか
- 新ユースケース追加時に既存クラスの修正が不要か

### L（リスコフ置換）
- 基底型で派生型を扱えるか
- 契約（事前条件・事後条件）が守られているか

### I（インターフェース分離）
- クライアントが使わないメソッドへの依存を強制していないか

### D（依存性逆転）
- 上位モジュールが下位モジュールの具象に依存していないか
- DIによる依存注入が適切に設計されているか

## テスタビリティの確保（全モード共通）

| レイヤー | テスタビリティ基準 |
|---|---|
| ドメイン層 | モック不要でテスト可能な純粋ロジック |
| アプリケーション層 | DIでダミー実装を注入してテスト可能 |
| インフラ層 | テスト用ダミー実装（dry run）を必ず設計に含める |
| プレゼンテーション層 | ロジックをアプリケーション層に委譲し、UI層は薄く保つ |

## レイヤー間依存ルール（全モード共通）

- ドメイン層: 外部技術に一切依存しない（標準ライブラリのみ許可）
- アプリケーション層: ドメイン層のインターフェースに依存する。インフラ層の具象に依存しない
- インフラ層: ドメイン層のインターフェースを実装する。外部技術への依存はこの層に閉じ込める
- プレゼンテーション層: アプリケーション層のユースケースを呼び出す。ドメイン層に直接依存しない

## quality_check モード

### 前提条件
- 5サブフェーズ（domain/app/infra/pres/summary）が全て完了していること
- 以下のファイルが全て存在すること

### 対象ファイル
- {specs_dir}/object-design-domain.md
- {specs_dir}/object-design-application.md
- {specs_dir}/object-design-infrastructure.md
- {specs_dir}/object-design-presentation.md
- {specs_dir}/object-design.md
- {specs_dir}/ubiquitous-language.md

### 品質基準チェック項目

以下の9カテゴリを全レイヤーに適用して検証する。

#### 1. SOLID原則チェック（全レイヤー）
- 各クラスが単一責任を持っているか
- 拡張ポイントが適切に設けられているか
- 依存性逆転が守られているか（上位→下位の具象依存がないか）
- インターフェース分離が守られているか
- リスコフ置換原則に違反していないか

#### 2. テスタビリティチェック（全レイヤー）
- ドメイン層: 純粋ロジックとして設計されているか（外部依存なし）
- アプリケーション層: コンストラクタインジェクションで依存を受け取っているか
- インフラ層: テスト用ダミー実装が設計されているか
- プレゼンテーション層: ロジックがアプリケーション層に委譲されているか

#### 3. ドメインモデル貧血症チェック（ドメイン層）
- エンティティ・値オブジェクトがビジネスルール（振る舞い）を持っているか
- ドメインサービスが肥大化していないか
- ビジネスルールがアプリケーション層に漏れ出していないか

#### 4. レイヤー間依存違反チェック
- ドメイン層が外部技術に依存していないか
- アプリケーション層がインフラ層の具象に依存していないか
- プレゼンテーション層がドメイン層に直接依存していないか

#### 5. ユビキタス言語整合性チェック
- ubiquitous-language.md の用語と各レイヤーの命名が一致しているか
- 技術的命名（~Data, ~Manager, ~Flag）がドメイン層に混入していないか
- 同じ概念に対して異なる名前が使われていないか

#### 6. ダミー実装設計チェック（インフラ層）
- 各リポジトリインターフェースに対応するダミー実装が設計されているか
- ダミー実装がDI切り替え可能な設計になっているか
- ダミー実装の振る舞い（テスト用データの返却方法等）が定義されているか

#### 7. 役割定義→publicメソッド網羅性チェック（全レイヤー）
- 各クラスに「役割定義（具体）」セクションが存在するか
- 「入力」で宣言されたデータに対応する受信経路（メソッド引数 or コンストラクタ引数）が存在するか
- 「出力」で宣言されたデータに対応する生成経路（メソッド戻り値）が存在するか
- メソッドテーブルの「対応する役割定義」列が全メソッドに記載されているか
- 「責務外」に記載された処理に関するメソッドが含まれていないか

#### 8. 技術的実装情報の反映チェック（全レイヤー）
- system-requirements.md に記載された技術情報のうち、該当クラスに関連するものが「技術的実装情報」セクションに反映されているか
- 技術調査結果（tech-investigation）で判明した情報が該当クラスに反映されているか
- 該当する技術情報がある場合に「技術的実装情報」セクションが存在するか（該当なしの場合はセクション省略可）

#### 9. 外部連携部分の技術調査・参考ドキュメントチェック（全レイヤー）
- 外部ツール・外部サービスと連携するクラスについて、「技術的実装情報」セクションに「技術調査結果」カテゴリが記載されているか
- 同セクションに「参考ドキュメント（URLリンク付き）」カテゴリが記載され、最低1件のURL形式のリンクが含まれているか
- 記載された調査結果・リンクの内容が、当該クラスの他の設計記述（API呼び出し手順等）と整合しているか
- 外部連携が存在しないクラスは本チェックの対象外とする

### 出力

- **品質基準違反がない場合:** 「全品質基準を満たしています」と報告する
- **品質基準違反がある場合:** 以下の形式で違反箇所と修正提案を一覧で報告し、ユーザーに修正の合意を得る

```markdown
## 品質基準チェック結果

### 違反一覧

| # | カテゴリ | レイヤー | 対象クラス | 違反内容 | 修正提案 |
|---|---|---|---|---|---|
| 1 | SOLID-S | Application | XxxService | 変更理由が2つ（A機能とB機能） | クラスを分割: AService, BService |
| ... | ... | ... | ... | ... | ... |

### 修正を実施しますか？
1. はい（全て修正する）
2. 一部のみ修正する（番号を指定）
3. いいえ（修正しない）
4. その他（自由記述）
```

## delta モード

### 前提条件
- 変更要求ドキュメントが存在すること
- 既存の object-design-*.md が存在すること

### 変更要求情報（入力）
- {specs_dir}/changes/{date}/change-requirements.md
- {specs_dir}/changes/{date}/approach.md
- {specs_dir}/changes/{date}/impact-analysis.md

### 既存設計書（入力・Read 参照のみ・変更しない）
- {specs_dir}/object-design-domain.md
- {specs_dir}/object-design-application.md
- {specs_dir}/object-design-infrastructure.md
- {specs_dir}/object-design-presentation.md
- {specs_dir}/object-design.md

### 処理手順

1. impact-analysis.md を読み込み、オブジェクト設計に影響するレイヤーを特定する
2. approach.md を読み込み、変更方針を把握する
3. 影響を受けるレイヤーの object-design-*.md を Read で読み込む（参照のみ、変更しない）
4. 変更要求に基づき、以下の観点で差分を設計する:
   - クラスの追加・削除・変更
   - メソッドの追加・削除・シグネチャ変更
   - 依存関係の変更
   - インターフェースの変更
5. SOLID原則・テスタビリティを維持しながら差分を設計する
6. 役割定義→publicメソッド導出セルフチェックを実施する:
   - 追加・変更するクラスの「役割定義（具体）」で宣言した全責務に対応するpublicメソッドが存在するか確認する
   - 欠落がある場合はメソッドを追加する
7. 技術情報の反映を確認する:
   - system-requirements.md、技術調査結果（存在する場合）から、追加・変更するクラスに関連する技術情報を特定する
   - 該当する技術情報を「技術的実装情報」セクションに反映する
   - 変更が外部ツール・外部サービス連携部分に及ぶ場合、tech-investigation (aide-powers skill) を実施し、調査結果の要約を「技術調査結果」カテゴリ、参照した公式ドキュメントのURLを「参考ドキュメント（URLリンク付き）」カテゴリにそれぞれ反映する
8. before→after 形式の差分設計結果を {changes_dir}/delta-object-design.md に Write で作成する
9. ユーザーに提示し合意を得る

### 差分設計の制約

- impact-analysis.md で特定された影響範囲のみを設計する（スコープクリープ防止）
- 既存のクラス設計で問題がない箇所は変更しない
- 変更により新たなSOLID原則違反が発生しないことを確認する
- 変更によりテスタビリティが低下しないことを確認する
- 既存の object-design-*.md は直接更新しない（Read 参照のみ）。差分は {changes_dir}/delta-object-design.md に出力する

### 出力形式

差分設計結果を以下の形式で {changes_dir}/delta-object-design.md に Write で出力する:

```markdown
## オブジェクト設計 差分

### 影響を受けるレイヤー
- {レイヤー名}: {影響の概要}

### 差分一覧

#### {レイヤー名}

| 変更種別 | 対象 | before | after | 理由 |
|---|---|---|---|---|
| クラス追加 | XxxClass | - | 新規追加 | {理由} |
| メソッド変更 | YyyClass.method | old_signature | new_signature | {理由} |
| ... | ... | ... | ... | ... |
```

出力後、ユーザーに差分内容を提示し合意を得る:
1. はい（この差分で確定する）
2. 一部のみ反映する（番号を指定）
3. いいえ（やり直す）
4. その他（自由記述）

## reverse モード

### 前提条件
- program-structure.md が存在すること
- 既存コードファイルにアクセス可能であること

### 入力
- {specs_dir}/program-structure.md
- 既存コードファイル（program-structure.md に記載されたファイル群）
- {specs_dir}/layered-architecture.md（存在する場合）

### 処理手順

1. program-structure.md を読み込み、プロジェクトのファイル構成を把握する
2. layered-architecture.md が存在する場合、レイヤー分類の基準を把握する
3. 全クラスを抽出する:
   - クラス名、継承関係、実装インターフェース
   - パブリックメソッド（名前、引数、戻り値）
   - パブリックプロパティ（型、読み取り専用かどうか）
   - コンストラクタの依存注入パターン
4. 依存関係を解析する:
   - import文の解析
   - コンストラクタインジェクションの解析
   - クラス間の参照関係
5. レイヤー分類を行う:
   - layered-architecture.md の定義に基づく分類
   - 存在しない場合はディレクトリ構成とクラスの特性から推定
6. 例外クラスを抽出する
7. デザインパターンを識別する（リポジトリ、ファクトリ、アダプタ、オブザーバー等）
8. テスト観点を抽出する（テストファイルが存在する場合）
9. 各クラスの役割定義（具体）を導出する:
   - コードの実際の振る舞いから「入力（何を受け取るか）」「出力（何を返すか）」「責務外（何を担当しないか）」を特定する
   - メソッドテーブルの各メソッドに「対応する役割定義」列を付与する
10. 技術的実装情報を抽出する:
    - コードから読み取れるAPI呼び出し手順、データ変換ルール、エラーハンドリング方針、外部ライブラリ使用方法、設定値・定数を特定する
    - system-requirements.md（存在する場合）の技術情報と突合する
    - 該当する情報がある場合に「技術的実装情報」セクションに記載する
    - 外部ツール・外部サービスと連携するクラスについては、既存コードのコメントやREADME等から参考ドキュメントURLを抽出できる場合は「参考ドキュメント（URLリンク付き）」カテゴリに記録する。抽出できない場合は tech-investigation (aide-powers skill) で補足調査してもよい。調査結果の要約は「技術調査結果」カテゴリに記載する
11. レイヤー別ファイルを生成する:
    - object-design-domain.md
    - object-design-application.md
    - object-design-infrastructure.md
    - object-design-presentation.md
12. object-design.md（概要）を生成する:
    - 設計方針のサマリ
    - 全レイヤーのクラス一覧
    - レイヤー間のクラス関連図（Mermaid記法）
13. ユーザーに提示し合意を得る

### 逆引き時の品質基準適用

- 逆引きでも SOLID原則・テスタビリティの観点で現状を評価する
- 現状の問題点（SOLID違反、テスタビリティの低さ等）は設計書に「※現状の課題」として記録する
- 問題点の修正は逆引きの範囲外（リファクタリングワークフローの責務）

## 禁止事項（全モード共通）

- ドメイン層にインフラ固有の型（ファイルパス、DB接続、HTTP等）を含めない
- エンティティをメソッドなしのデータクラスとして設計しない（貧血症防止）
- テスト用ダミー実装の設計を実装フェーズに先送りしない
- impact-analysis.md の影響範囲外のレイヤーを修正しない（delta モード）
- コードの構造をそのまま設計書にしない（reverse モード — 品質基準を適用する）
