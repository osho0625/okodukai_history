# Overview

タスクリスト・工程チェック表・doc-index.md・実装に必要な設計資料 を受け取り、タスクリストの全てのタスクについて、設計書に従って各工程を実行する。同一タスク内では「実装」と「テスト実装」を並列起動し、両者の PASS 後に「テスト実行」を実施し、テスト実行 PASS 後に「設計準拠レビュー」と「コード品質レビュー」を並列起動する。設計準拠レビューとコード品質レビューは、実装コードとテストコードをまとめて検証する（工程効率化）。工程チェック表は「1 工程 = 1 行」構造で管理し、各工程の担当サブエージェント本人が自分の工程行を 3 段階（開始 🔄 / 完了 ✅ / 失敗 ❌）で更新する。タスクリストはタスク完了と同時に更新する。


# The Iron Law

```
1 タスクの 1 工程 = 1 サブエージェント。1 ウェーブ最大 6 タスクを並列実行する（上限はタスク本数で数える）。
同一タスク内では「実装」と「テスト実装」を並列起動し、「設計準拠レビュー」と「コード品質レビュー」を並列起動する。
実装・テスト・2レビューの全工程を通さないタスクを完了にしてはならない。
親タスクの全サブタスクが全工程 PASS になったら、親タスク完了チェックを通すまで親タスクを完了にしてはならない。
手順を逸脱（省略・一括実行・簡易手順・不正確な実行）する場合は、実行前にユーザー承認と品質低下リスク説明を必須とする。
```

- **1呼び出し = 1タスクの1工程**: 1つのサブエージェントに複数タスク、または同一タスクの複数工程を束ねて渡してはならない。タスク内工程の並列化により 1 タスクが複数のサブエージェントを同時に起動しうるが、束ね禁止の本意（1 サブエージェント＝独立した 1 作業単位）は維持する
- **タスク間並列実行（上限不変）**: 同一ウェーブ内の複数タスク（最大6）は、それぞれ別のサブエージェントに同時にアサインして並列実行する。**ウェーブの上限カウントはタスク本数（最大6）で数える。** タスク内で同時起動される工程サブエージェント数（実装＋テスト実装＝2、または 2 レビュー＝2）はこの 6 タスク上限のカウント対象外（別レイヤー）
- **タスク内工程の並列起動（新規）**: 同一タスク内の「実装（implement）」と「テスト実装（write_test）」は単純並列で同時起動する（テスト実装は設計書のテスト観点を起点に書けるため実装非依存）。「設計準拠レビュー（spec_review）」と「コード品質レビュー（quality_review）」は、対象タスクの実装・テスト実装・テスト実行が PASS した後に単純並列で同時起動する
- **工程依存の維持**: テスト実行（run_test）は実装とテスト実装の両方が PASS した後に実施する（並列対象外）。2 レビューはテスト実行 PASS の後に並列起動する。この前後依存（実装・テストが揃っていることが前提）は維持する
- **FAIL は前工程を fix で再実行**: レビュー FAIL のタスクは、指摘起因に応じて当該工程行（実装／テスト実装）を未PASS（`❌ failed`／`⬜ todo`）に戻し、micro-impl-agent の fix / fix_test モードで修正して PASS まで再実行する（詳細は「レビュー FAIL 時の再実行ルール（共通）」）
- **手順逸脱時の実行前承認＋リスク説明必須**: 確実な手順の省略・一括実行・簡易手順・不正確な実行を行う場合は、**実行前に**ユーザー承認を取得し、その際に品質低下リスク（不具合の混入・コードの設計書からの乖離）を必ず説明する。事後報告は不可。詳細は「手順逸脱時のユーザー承認とリスク説明」節（承認なしの手順逸脱を禁止する）
- **親タスク完了チェック必須**: ある親タスクの全サブタスクが全工程 PASS になったら、その親タスクの設計参照セクション全体と実装ファイル群を design-review-agent に holistic 照合させ、設計項目の実装漏れ（サブタスク化されていなかった定義・メソッド等）がないことを確認してから親タスクを完了にする。漏れが見つかったら新規サブタスクとして追加して再実行する

# 出力

| 項目 | 説明 |
|---|---|
| 全タスク処理結果 | 全タスクのID と最終状態（完了 / 未完了＋理由） |
| status | DONE（全実行可能タスク完了） / BLOCKED（続行不能、理由付き） |

# Process

タスクリストを確認し、次の条件を満たす **実行可能タスク** の一覧(.aide/tmp/do_task_list-(重複排除用のpostfix).txt)を作成する:
   - タスクの状態が未完了（タスクリスト上で未完了）
   - かつ「依存先: なし」または「依存先のタスクが全て完了済み」（タスク間依存原則は不変）

**実行可能タスク** の各々について、工程チェック表（1 工程 = 1 行）から、状態が `⬜ todo` かつ前提工程が全て `✅ done` の工程行（＝今すぐ実行可能な工程）を特定する。工程の前提は次のとおり:
   - 実装（implement） / テスト実装（write_test）: 前提なし。**同一タスク内で同時に並列起動できる**
   - テスト実行（run_test）: 実装・テスト実装の両方が `✅ done`（並列対象外）
   - 設計準拠レビュー（spec_review） / コード品質レビュー（quality_review）: テスト実行が `✅ done`。**両者は同時に並列起動できる**

実行可能な「タスク × 工程」のペアを集め、**タスク本数で最大 6 タスク**になるよう選ぶ（タスク内で同時起動される工程サブエージェント数は 6 の上限カウントに含めない）。各ペアごとに 1 サブエージェントをアサインして同時に起動する。例として、依存先のない非依存タスク A／B の起動初期には、実装A・テスト実装A・実装B・テスト実装B の 4 サブエージェントを同時起動できる（タスク本数は 2 で上限内）。
全てのサブエージェントの実行が完了すれば**実行可能タスク** の一覧を削除し、再評価する。

タスク内の全ての工程行が `✅ done`（または `➖ skip`）となったら、タスクリスト内の該当タスク（サブタスク）の進捗チェック欄を更新する

ある親タスクに属する**全サブタスクが全工程 PASS** になったら、その親タスクについて「親タスク完了チェック」工程を実行する（後述）。漏れが検出されたら不足分を新規サブタスクとして追加し（工程チェック表にも該当タスクの工程行を追加し）、次ウェーブで通常通り処理する。漏れなしなら親タスクを完了としてマークする。

全ての工程行が PASS となるまで繰り返す。
レビュー工程で FAIL となった場合、FAIL を出したサブエージェントの指摘起因（実装／テスト実装）に従って、該当する工程行を未PASS（`⬜ todo`）に戻して再実行対象とする（「レビュー FAIL 時の再実行ルール（共通）」を参照）。

実行可能タスクが無くなったら（未完了タスクが残っていない）、全タスクの処理結果とともに status: DONE を返して終了する。未完了タスクが残っているが依存先未完了で着手できず進行中もない場合は、デッドロックとして status: BLOCKED で理由とともに報告する。

## 各工程のサブエージェント実行

「タスク × 工程」のペアごとに **1ペア = 1サブエージェント** をアサインする（タスク本数で最大 6 タスク。タスク内工程の同時起動は上限カウント対象外）。各サブエージェントには下記「エージェント呼び出しペイロード」の項目を渡し、**実行後（および開始直後）に当該工程の工程チェック表の行を当該エージェント自身に更新させる**（自分が担当した工程の行のみ最小編集。CF-5 の 3 段階更新）。

工程の実行順序は工程チェック表の**工程行の前提依存**に従う（上記の前提一覧）。各タスクについて「状態が `⬜ todo` かつ前提工程が全て `✅ done` の工程行」を実行可能な工程として全て選ぶ（同一タスク内に複数あれば並列起動する）。

### 工程: 実装
- エージェント: `micro-impl-agent (aide-powers agent)`（mode: implement）
- プロンプト: 本スキルディレクトリの `implementer-prompt.md`（mode: implement）
- **起動タイミング**: タスク着手と同時（前提工程なし）。同一タスクの「テスト実装」と並列起動してよい
- 工程チェック表: micro-impl-agent に **自分の `implement` 工程行** を 3 段階（開始 🔄 / 完了 ✅＋output / 失敗 ❌＋output）で更新させる
- 判定: 報告ステータスが DONE / DONE_WITH_CONCERNS → PASS。NEEDS_CONTEXT → 不足情報を補い再実行。BLOCKED → 当該タスクを停止し理由を記録（以降の工程に進めない）

### 工程: テスト実装
- エージェント: `micro-impl-agent (aide-powers agent)`（mode: write_test）
- プロンプト: `implementer-prompt.md`（mode: write_test）。テスト観点は設計書から転記
- **起動タイミング**: 前提工程なし（設計書のテスト観点起点で実装非依存）。同一タスクの「実装」と並列起動してよい
- 工程チェック表: micro-impl-agent に **自分の `write_test` 工程行** を 3 段階で更新させる
- 判定: DONE / DONE_WITH_CONCERNS → PASS

### 工程: テスト実行
- エージェント: `micro-impl-agent (aide-powers agent)`（mode: run_test）
- プロンプト: `implementer-prompt.md`（mode: run_test）。対象テスト
- **起動タイミング**: 同一タスクの「実装」と「テスト実装」の両工程行が `✅ done` の後に実施する（**並列対象外**）。実行結果をもとに、テスト構成（設計書のテスト観点を網羅しているか・テスト構成が妥当か）のチェックも micro-impl-agent に依頼する
- 工程チェック表: micro-impl-agent に **自分の `run_test` 工程行** を 3 段階で更新させる
- 判定: 全テストがパスし、かつテスト構成チェックが妥当 → PASS。テスト失敗、またはテスト構成に不備（観点の取りこぼし・無意味なテスト等）→ FAIL（実装またはテスト実装の工程行を `⬜ todo` に戻して再実行対象とする）

### 工程: 設計準拠レビュー（実装＋テストをまとめてレビュー）
- エージェント: `design-review-agent (aide-powers agent)`
- プロンプト: 本スキルディレクトリの `spec-reviewer-prompt.md`
- **実装コードとテストコードをまとめて1回でレビューする**（工程効率化）。実装の設計準拠（クラス/メソッドシグネチャ/内部ロジック意図/不変条件/import ルール）と、テストの網羅性（設計書のテスト観点を全てカバーしているか）を一括で検証する。target_file と test_file の両方を渡す
- **起動タイミング**: 対象タスクの「テスト実行」工程行が `✅ done` の後（＝実装・テストが揃っている）。**「コード品質レビュー」と並列起動する**
- 工程チェック表: design-review-agent に **自分の `spec_review` 工程行** を 3 段階で更新させる
- 判定: 差分（実装の設計不一致＋テスト網羅漏れ）0件 → PASS。1件以上 → FAIL
- FAIL の場合（明らかな実装誤り）: 従来通り、指摘内容に従い当該タスクの「実装」工程行（テストに起因する指摘なら「テスト実装」工程行）を `⬜ todo`（未PASS）に戻して再実行対象とする
- FAIL_PENDING の場合（種別未確定の差分）: 乖離種別を即時確定せず、FAIL_PENDING 保留状態とする
  - FAIL_PENDING 詳細（差分内容）を工程チェック表の当該タスク備考欄に記録する
  - 当該タスクは FAIL_PENDING 保留状態のまま、他の実行可能タスクの処理を続行する
  - 乖離種別確定トリガー（以下のいずれか早い方）:
    - 全タスクの実装が完了した時点
    - FAIL_PENDING 保留タスクへの依存により後続タスクが実行不可能になった時点
  - トリガー到達後、蓄積された FAIL_PENDING 差分を 1件ずつユーザーに提示し種別を確定する:
    - 実装誤りと確定: 当該タスクの「実装」工程行を `⬜ todo` に戻して fix→再レビュー
    - 設計漏れと確定: `design-sync (aide-powers skill)` で設計書を更新（fix モード）→ 再レビュー

### 工程: コード品質レビュー（実装＋テストをまとめてレビュー）
- エージェント: `code-review-agent (aide-powers agent)`
- プロンプト: 本スキルディレクトリの `code-quality-reviewer-prompt.md`
- **実装コードとテストコードをまとめて1回でレビューする**（工程効率化）。実装のコード品質・エラーハンドリングと、テストの方針準拠（命名規則・独立性・モック禁止・境界値・異常系）を一括で検証する。target_file と test_file の両方を渡す
- **起動タイミング**: 対象タスクの「テスト実行」工程行が `✅ done` の後（＝実装・テストが揃っている）。**「設計準拠レビュー」と並列起動する**
- 工程チェック表: code-review-agent に **自分の `quality_review` 工程行** を 3 段階で更新させる
- 判定: ERROR（実装品質＋テスト方針）0件 → PASS。1件以上 → FAIL
- FAIL の場合: 指摘内容に従い、当該タスクの「実装」工程行（テストコードに起因する指摘なら「テスト実装」工程行）を `⬜ todo`（未PASS）に戻して再実行対象とする

### レビュー FAIL 時の再実行ルール（共通）

レビュー工程（設計準拠レビュー / コード品質レビュー）が FAIL になったら、FAIL を出したサブエージェントの指摘の**起因**に応じて、差し戻す工程行を一意に決め、未PASS（`⬜ todo`）に戻す。各工程が独立した行（1 工程 1 行）で状態管理されるため、差し戻し（状態変更）も工程行単位で衝突なく行える。

**単独レビュー FAIL の場合:**
- 実装起因の指摘 → `implement` 工程行を `⬜ todo` に戻す
- テスト（テスト実装）起因の指摘 → `write_test` 工程行を `⬜ todo` に戻す

**両レビューが同時に FAIL した場合（AC-002-3）:**
- 両レビューの指摘が**同一工程**を指す（例: 双方とも実装起因）→ 当該工程行を **1 回だけ** `⬜ todo` に戻し、両レビューの指摘を**統合して** fix（micro-impl-agent の fix / fix_test）で対応する
- 実装起因とテスト起因が**混在**する → `implement` 工程行と `write_test` 工程行の**両方**を `⬜ todo` に戻す

**再実行の連鎖:**
- 差し戻した `implement` / `write_test` を次ウェーブで再実行（micro-impl-agent の fix / fix_test。本人が工程行を 🔄 → ✅ に更新）したら、実装・テストが変わったため `run_test` 工程行も `⬜ todo` に戻して再実行し、その PASS 後に `spec_review` / `quality_review` 工程行を `⬜ todo` に戻して**両レビューを再度（並列で）実行**する
- これにより並列化後も「FAIL 工程を未PASSに戻して再実行する」原則が一貫して成立し、FAIL 時の扱いが曖昧化しない
- 実装の修正自体は `micro-impl-agent`（mode: fix / fix_test）で行い、レビュー指摘内容をそのまま転記して渡す

> 差し戻し（工程行を `⬜ todo` へ戻す）の操作は、再実行スケジューリングとして起動元が行ってよい（実施していない工程を `✅ done` にする代理チェック禁止には抵触しない — done を偽る行為ではなく未完了へ戻す行為のため）。再実行後の 🔄 / ✅ / ❌ は必ず担当本人が書く。

## 工程: 親タスク完了チェック（親タスク単位の局所網羅チェック）

ある親タスクに属する**全サブタスクが全工程（実装〜コード品質レビュー）PASS** になったタイミングで、その親タスク1つを対象に実行する。これは「サブタスク=publicメソッド単位の実装」と「親タスク=クラス単位の網羅」を両立させる**局所チェック**であり、ワークフロー末尾の大域監査とは別物である。

- エージェント: `design-review-agent (aide-powers agent)`（holistic 照合: セクション全体 vs 実装ファイル群）
- 照合対象:
  - **設計参照セクション全体**: `design_doc_paths` のうち当該親タスクに対応するセクション**全体**（個々のサブタスクに絞った `design_refs` ではなく、親タスクのセクション全体を渡す）
  - **実装ファイル群**: その親タスクに属する全実装ファイル（サブタスクが生成したファイル）
- 目的: 設計項目の実装漏れ（サブタスク化されていなかった定義・メソッド・定数・分岐等）を holistic に検出する
- 判定:
  - **漏れなし** → 親タスクを完了としてマークする（タスクリストの親タスク進捗欄を更新）
  - **漏れあり** → 不足分を**新規サブタスクとして task_list に追加**し、工程チェック表（process_checklist）にも当該サブタスクの**工程行一式**（プログラム成果物なら implement / write_test / run_test / spec_review / quality_review の 5 行、非プログラム成果物なら実工程＋ `➖ skip` 行）を追加する。追加サブタスクは次ウェーブで通常通り並列起動（実装∥テスト実装 → テスト実行 → 設計準拠レビュー∥コード品質レビュー）を実行する。全追加サブタスクが PASS したら親タスク完了チェックを再実行し、漏れなしになるまで繰り返す
- 親タスク完了チェック自体は工程チェック表に `{parent_task_id}::parent_check` 行（工程名「親タスク完了チェック」、担当 design-review-agent）として記録し、design-review-agent 本人が 3 段階で更新する（output にチェック日時・漏れ件数を記入）

### 親タスク完了チェックのエージェント呼び出しペイロード

- **parent_task_id**: 親タスクID
- **parent_task_title**: 親タスクのタイトル（対象クラス/ファイル単位）
- **design_section_refs**: `design_doc_paths` の該当親タスクの**セクション全体**のパス + セクション名（サブタスク単位に絞らない）
- **implementation_files**: その親タスクに属する全実装ファイルのパス
- **task_list_path**: タスクリストのパス（漏れ検出時に新規サブタスクを追加するため）
- **process_checklist_path**: 工程チェック表のパス（新規サブタスク行の追加・チェック結果の記録用）
- **pending_issues_path**: pending-issues.md のパス（holistic 照合で設計同期では対応しきれない設計欠陥を発見した場合の記録用）

## 作業中の問題記録（随時）

実装・テスト・レビューの各工程中に、以下のいずれかを発見した場合、その工程を担当した各サブエージェント（`micro-impl-agent` / `design-review-agent` / `code-review-agent`）が `pending-issues-management (aide-powers skill: record)` で **`pending_issues_path` に随時記録する**。

- 設計書の考慮漏れが発覚した場合（設計同期で対応しきれない範囲の問題）
- 実装中に動作不良・不具合が発見された場合（実装中に発見した別件不具合を含む）
- テスト実行で設計の期待と矛盾する結果が出た場合（設計同期で対応した後も残る問題）
- レビューで設計自体の根本的な不備が指摘された場合
- その他、現在のタスクのスコープ外の問題を発見した場合

各サブエージェントには呼び出しペイロードで `pending_issues_path` を渡し、記録先を明示する。これは旧 fs-impl-phase4-execution の「作業中の問題記録（随時）」に相当する責務であり、本スキルへ1回呼び出し方式へ移行したことに伴い、各サブエージェント側の随時記録として整理したものである。

**絶対禁止**: 作業中に発見した問題を理由として、現在のワークフローを中断し変更・バグ修正・リファクタリングワークフローを起動すること。問題は pending-issues に記録し、現在の実装を最後まで完遂すること。

## プログラム成果物 / 非プログラム成果物の工程差

各タスクの成果物種別を判定する（拡張子だけで判定しない。内容で判断し、迷う場合はプログラムコードとして扱う＝安全側）。

- **プログラム成果物**: 全工程を実施する（実装 → テスト実装 → テスト実行 → 設計準拠レビュー → コード品質レビュー）
- **非プログラム成果物**（設定ファイル・ドキュメント・データ定義等、実行されるロジックを含まないファイル）: **「実装 → 設計準拠レビュー」のみ**を実施する。テスト実装・テスト実行・コード品質レビューはスキップする
  - スキップする工程は工程チェック表で `➖ skip` 行として記録する（CF-3 の状態記号 `➖ skip` / CF-7 の非プログラム成果物の扱い）
  - 成果物種別の判定理由を該当 `➖ skip` 工程行の output に明記する（理由なき簡略化を禁止）

## エージェント呼び出しペイロード（全工程共通の必須項目）

各サブエージェントには、対象タスク1つ分の以下の情報だけを渡す（最小化）:

- **task_id**: タスクリストのサブタスクID
- **task_title**: サブタスクのタイトル
- **target_file**: 対象ファイル（1ファイルのみ）
- **test_file**: テストファイル（プログラムコードの場合）
- **design_refs**: **design_doc_paths の該当設計書ファイルパス + セクション名**（doc_index_path で所在を確認し、該当タスクのセクションだけに絞る。設計書全体を渡さない）
- **test_perspectives**: テスト観点（設計書から転記）
- **dependencies**: 依存先（既に完了済みのクラス/モジュールのファイルパス）
- **reference_files**: 参照ファイル（既存規約。同レイヤーの既存コード。命名・エラーハンドリング・スタイルの参考。doc_index_path / program-structure.md から特定）
- **dev_environment**: dev-environment.md のパス（doc_index_path から特定）
- **process_checklist_path**: 工程チェック表のパス（**自分が担当した工程行**の 3 段階更新用。行キーは `{task_id}::{工程キー}`）
- **process_row_key**: 当該サブエージェントが更新すべき工程行の行キー（例: `1.1::implement`）。担当本人はこの行のみを最小編集する
- **pending_issues_path**: pending-issues.md のパス（工程中に発見したスコープ外の問題・設計欠陥・別件不具合の随時記録先）
- **task_kind**: タスク種別（normal / bugfix / change / refactoring）

## 工程チェック表更新の衝突回避（1 工程 1 行による構造的解消）

工程チェック表は「1 工程 = 1 行」構造（共通仕様 CF-1〜CF-9）であり、同一タスク内で並列起動される各工程（実装 / テスト実装、または 設計準拠レビュー / コード品質レビュー）の担当はそれぞれ**別の物理行**を更新する。これにより、同一行への同時 str_replace 衝突（旧フォーマットで同一タスク行の別セルを 2 担当が同時に書くことで生じた、旧文字列不一致による更新失敗・後勝ちによるロストアップデート）が**構造的に発生しない**。

- 各エージェントは **自分が担当した工程の行（行キー `{task_id}::{工程キー}`）のみ** を更新する。他工程・他タスクの行は触らない
- 各エージェントは更新前に impl-process-checklist.md を Read で読み直し、自分の工程行のみを最小編集する（CF-5 の 3 段階更新）
- **オーケストレータ（起動元）が代理でチェック（特に `✅ done`）を書くことは禁止。** チェック表の状態更新は「その工程を実施したサブエージェント本人」が証跡として書くのが大原則である（実施していない工程を「やったことにする」誤りを防ぐ既存の歯止めを堅持）。起動元による書き込み主体一本化（集約）案は採らない
- 例外的に、起動元は再実行スケジューリングとして工程行を `⬜ todo` に**戻す**ことができる（done を偽る代理チェックではないため禁止に抵触しない。CF-6）

## 手順逸脱時のユーザー承認とリスク説明

本スキルの定められた手順（工程順序・並列起動の前提・レビュー・工程チェック表更新・親タスク完了チェック等）を逸脱する場合は、**実行前に**ユーザー承認を取得し、その際に品質低下リスクを必ず説明しなければならない。

### 手順逸脱の定義

次のいずれかを「手順逸脱」とする:
- 確実な手順の**省略**（例: テスト実行・レビュー・親タスク完了チェックを飛ばす）
- 複数工程・複数タスクの**一括実行**（束ね）による簡略化
- 定義された手順と異なる**簡易手順**での実行
- その他、本スキルを**正確に実行しない**こと

### 実行前ユーザー承認の必須化（REQ-C-003 / AC-003-1・AC-003-2・AC-003-3）

- 手順逸脱を行う場合は、**逸脱した手順を実行する前に**ユーザーの承認を取得すること。承認は番号付き選択肢で諾否を問う形で求める
- **事後報告は不可。** 「逸脱して実行した後で報告する」ことは禁止する
- ユーザー承認なしの手順逸脱を禁止する

### 品質低下リスク説明の必須化（REQ-C-004 / AC-004-1・AC-004-2・AC-004-3）

- 上記の承認を求める際は、**品質低下リスクを必ず説明**したうえで承認を求めること
- 説明すべきリスクには、少なくとも次を具体的に含める:
  - **不具合の混入**（手順簡略化により欠陥が検出されないまま残るおそれ）
  - **コードの設計書からの乖離**（レビュー省略等により実装が設計書と食い違うおそれ）
- **リスク説明と承認取得は一体の必須手順である。** リスク説明を伴わない承認取得は無効とする

## Red Flags - STOP

| Red Flag | 対処 |
|---|---|
| 「複数タスク、または同一タスクの複数工程を1サブエージェントにまとめて速くしよう」と考えた | STOP。1 タスクの 1 工程 = 1 サブエージェント。束ねは禁止（並列化しても各工程は独立サブエージェント） |
| 「依存先が未完了だが先に始めよう」と考えた | STOP。依存先が全完了したタスクのみ実行可能（タスク間依存原則は不変） |
| 「テスト実行やレビューを、実装・テスト実装が揃う前に始めよう」と考えた | STOP。テスト実行は実装＋テスト実装の PASS 後、2 レビューはテスト実行 PASS 後。並列化してよいのは 実装∥テスト実装 と 設計準拠レビュー∥コード品質レビュー のみ |
| 「レビューFAILだが軽微だから次工程へ」と考えた | STOP。FAIL は該当工程行を `⬜ todo` に戻し fix で修正、PASS まで再実行する |
| 「両レビューが同時にFAILしたが、どちらの工程を差し戻すか曖昧だから片方だけ直そう」と考えた | STOP。指摘起因で差し戻し先を決める（実装起因→実装行 / テスト起因→テスト実装行 / 混在→両行）。AC-002-3 の再実行ルールに従う |
| 「7タスク以上を1ウェーブで並列起動しよう」と考えた | STOP。1ウェーブ最大6タスク（上限はタスク本数で数える。タスク内工程の同時起動数は上限カウント対象外） |
| 「自分の担当でない工程行や、起動元として `✅ done` を代理で書こう」と考えた | STOP。状態更新は工程を実施した本人のみ。起動元の代理チェック（done の偽記入）は禁止 |
| 「手順を省略・一括実行・簡易手順で速くしよう（ユーザー承認なしで）」と考えた | STOP。手順逸脱は実行前にユーザー承認が必須。承認なしの逸脱は禁止（事後報告も不可） |
| 「手順逸脱の承認を、品質低下リスクを説明せずに取ろう」と考えた | STOP。リスク説明（不具合の混入・コードの設計書からの乖離）と承認取得は一体。リスク説明なしの承認は無効 |
| 「設計書全体をエージェントに渡そう」と考えた | STOP。design_refs はセクションを絞って渡す（※親タスク完了チェックは例外で、当該親タスクのセクション全体を渡す） |
| 「全サブタスクが PASS したから親タスクをそのまま完了にしよう」と考えた | STOP。親タスク完了チェック（セクション全体 vs 実装の holistic 照合）を通すまで親タスクを完了にしてはならない |
| 「親タスク完了チェックで漏れが見つかったが軽微だから記録だけして完了にしよう」と考えた | STOP。漏れは新規サブタスクとして task_list と工程チェック表に追加し、次ウェーブで通常工程を通す |
| 「スコープ外の問題を見つけたが現在のタスクで直してしまおう」と考えた | STOP。pending_issues_path に記録し、現在の実装を完遂する。別ワークフロー起動も禁止 |

## Integration

**Called by:**
- 実装ループを持つフェーズスキルの実装フェーズ（例: `fs-change-phase2-impl` Step 10）

**Required agents（agents/ 配下の aide-powers agent）:**
- `micro-impl-agent (aide-powers agent)` — 実装（implement）・テスト実装（write_test）・修正（fix / fix_test）・工程チェック表更新
- `design-review-agent (aide-powers agent)` — 設計準拠レビュー（mode: implementation）・**親タスク完了チェック（holistic: セクション全体 vs 実装ファイル群）**・工程チェック表更新
- `code-review-agent (aide-powers agent)` — コード品質レビュー（mode: implementation）・工程チェック表更新

**Calls:**
- `design-sync (aide-powers skill)` — 設計準拠レビューで設計漏れ（FAIL_PENDING→種別確定後）を検出した場合の設計書同期
- `pending-issues-management (aide-powers skill: record)` — 実装・テスト・レビュー・親タスク完了チェック中に発見した「設計書の考慮漏れ」「動作不良・別件不具合」「設計の根本不備」等のスコープ外問題を各サブエージェントが `pending_issues_path` に随時記録（旧 phase4 の「作業中の問題記録（随時）」相当）

**プロンプトテンプレート（本スキルディレクトリ配下）:**
- `implementer-prompt.md` — micro-impl-agent 用（mode: implement / write_test / run_test〔テスト実行＋構成チェック〕/ fix / fix_test）
- `spec-reviewer-prompt.md` — design-review-agent 用（mode: combined＝実装の設計準拠＋テスト網羅性を一括）
- `code-quality-reviewer-prompt.md` — code-review-agent 用（mode: combined＝実装の品質・エラーハンドリング＋テスト方針を一括）

**Global rules:** `.aide/references/global-rules.md` を厳守
