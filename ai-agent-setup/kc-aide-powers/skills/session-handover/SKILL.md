# session-handover

## Overview

セッションのコンテキストが大きくなった際に、新しいセッションへのスムーズな引き継ぎを実現する。
引き継ぎファイルの自動生成・更新・読み込み・old リネームを管理する。

**Core principle:** セッション切り替え時に作業状態を失わない。引き継ぎファイルは常に最新状態を維持し、新セッション開始時に即座に作業を再開できる状態を保証する。

## .gitignore 保証（常時）

session-handover スキルが activate されたら、プロセス実行の前に必ず以下を確認する:

1. ワークスペースのルートに `.gitignore` が存在するか確認する
2. `.gitignore` 内に `session-handover` 関連のパターン（`**/session-handover*.md` 等）が含まれているか確認する
3. **含まれていない場合** → `.gitignore` の末尾に以下を追記する:

```
# Session handover files (aide-powers: local working files, not for repository)
**/session-handover*.md
```

4. `.gitignore` 自体が存在しない場合 → 新規作成して上記を記載する

**この処理はプロセス1〜4のどれが実行される場合でも、最初に1回だけ実行する。**
既に登録済みなら何もしない。

## Process

**Exceptions:**
- サブエージェントとして派遣された場合はこのスキルを実行しない

### 索引（状況別ガイド）

| 状況 | 参照すべきプロセス | 他のプロセスは読まなくてよい |
|---|---|---|
| **新セッション開始時**（引き継ぎファイルがある） | プロセスA: 新セッション開始時の読み込み | プロセスB〜C は不要 |
| **フェーズ完了時**（セッション切り替え判断） | プロセスB: コンテキスト使用量確認 → プロセスC: 引き継ぎファイル生成（書く前合意 + プロンプト提示含む） | プロセスA は不要 |
| **ユーザーから明示的に引き継ぎ指示** | プロセスC（書く前合意 + プロンプト提示含む） | プロセスA は不要 |

## 【セッション開始時】

### プロセスA: 新セッション開始時の読み込み

**トリガー:** 新セッション開始時に session-handover.md が存在する場合

#### ⛔ 全文読み込み必須ルール

> **引き継ぎ不備による不具合が頻発している。以下を厳守すること。**
>
> session-handover.md を読み込む際は、**全てのセクション・全ての行を漏れなく把握すること。**
> 一部だけ読んで作業を開始することを絶対に禁止する。
>
> **禁止パターン:**
> - 「現在の状態」セクションだけ読んで作業開始
> - 「次セッションで継続する作業（ユーザー確認済み）」を読み飛ばす（前回ユーザーが望んだ作業を取りこぼす）
> - 「未完了作業」だけ見て他のセクションを無視
> - 「追加作業ルール・ユーザー指示」を読み飛ばす
> - 「実行証跡」セクションを無視して後処理を実行
> - 「確定した設計判断」を把握せずに設計作業を開始
>
> **必須:** 全セクションを読み込み、内容を把握してから作業を開始すること。
> 特に「追加作業ルール・ユーザー指示」と「実行証跡」は見落としが致命的。

**Step 1:** session-handover.md の存在確認
- パス: .aide/specs/{feature_name}/session-handover.md
- 存在しない → 通常のセッション開始（このプロセスは終了）
- 存在する → Step 2へ

**Step 2:** session-handover.md を **全文** 読み込む
- 全セクションの内容を把握する（一部だけ読んで作業開始することを禁止）

**Step 3:** session-handover-old.md にリネーム
- session-handover.md → session-handover-old.md
- session-handover-old.md が既に存在する場合は上書き（削除してから移動）
- ⚠️ 連番ファイルを作ってはならない。古い old は問答無用で上書き削除する

**Step 4:** 作業状態の復元
- **最初に `using-aide-powers` スキルを activate する。** activate せずに作業を開始することを絶対に禁止する
- **最優先:** 「次セッションで継続する作業（ユーザー確認済み）」セクションを読む。前セッションでユーザーが合意した「次にやること」がここにある。**これが今回の作業の起点**
- ⚠️ このセクションには「実行するフェーズスキル」「実行するStep」「実行するサブスキル/サブエージェント」が指定されている。**オーケストレーターが直接タスクを実行してはならない。** 指定されたフェーズスキルを activate し、そのフェーズスキルの指示に従って作業を進めること
- 前セッションのワークフロー・フェーズを把握
- 未完了作業の確認
- 追加ルール・ユーザー指示の適用
- 読むべきファイルの把握（必要に応じて読み込み）

**Step 5:** ユーザーへの報告
- 「次セッションで継続する作業（ユーザー確認済み）」の内容を引用し、**前回のやり取りの続きとして**何を継続するかを提示する:
- 「前回のセッションから引き継ぎました。`using-aide-powers` スキルに従い作業を進めます。現在の状態: {ワークフロー名} フェーズ{N}。前回のやり取りの続きとして、`{フェーズスキル名}` を activate し、Step {N} にて `{サブスキル/サブエージェント名}` で作業を継続します。進めてよろしいですか？」
  1. はい（前回の続きから再開）
  2. 別の作業をする
  3. その他（自由記述）

- ユーザーが「1」→ **指定されたフェーズスキルを activate して作業を開始する。** オーケストレーターが直接タスクを実行することを禁止する

## 【セッション終了時】

### プロセスB: コンテキスト使用量確認とセッション切り替え判断

**トリガー:** フェーズスキルが1つ完了した時点

> **Kiro IDE の場合:** チャットパネルにコンテキスト使用量メーターが表示される。
> 80% に達すると Kiro が自動的に会話を要約する。
> AI 側からプログラム的にコンテキスト使用率を取得する手段は現時点で存在しない。

**Step 1:** ユーザーにコンテキスト使用量メーターの確認を依頼する
- 「コンテキスト使用量メーターを確認してください。セッションを切り替えますか？」
  1. まだ大丈夫（次フェーズに進む）
  2. 切り替える（引き継ぎ生成してセッション終了）

**Step 2:** ユーザーの回答に従う
- 「まだ大丈夫」→ 次フェーズに進む。**無理に引き継ぎ作業を行わない**
- 「切り替える」→ プロセスC（引き継ぎファイル生成 + プロンプト提示）へ
- ユーザーから確認なしに「コンテキストが大きくなってきた」と指摘 → 即座にプロセスCへ

**禁止:** ユーザーが「まだ大丈夫」と言っているのに無理に引き継ぎ作業を行うこと

### プロセスC: 引き継ぎファイルの生成・更新

**トリガー:**
- プロセスBでユーザーが「切り替える」と回答
- ユーザーの明示的指示
- ユーザーから「コンテキストが大きくなってきた」と指摘

#### 引き継ぎ生成ルール

> コンテキストが限界に達してから慌てて引き継ぎを書くと、記述が簡素化され、
> 実行証跡が不十分になり、次セッションで compliance-check write が FAIL する。
> コンテキストに余裕がある段階で丁寧に書くこと。
> 実行証跡は実行直後に記録する（後から思い出して書くと不正確になる）。

#### ⛔ このプロセスの最重要原則: 「書く前にユーザーと次作業を合意する」

> **引き継ぎファイルが「ざっくり」しか書かれず、「ユーザーがこれからやってほしいこと」が
> 抜け落ちる不具合が頻発している。** 原因は、AI が自分の作業ログだけを頼りに
> いきなりファイルを書き、ユーザーが本当に望んでいる「次にやること」を取りこぼすこと。
>
> これを防ぐため、**ファイルを書く前に、直近のやり取りから読み取った「次セッションで継続実行すること」を
> ユーザーに提示し、合意を得てから書く。** 合意なしにファイルを書き始めてはならない（Step 2）。

**Step 1:** 直近のやり取りの精読と「次にやること」の言語化（最優先・省略禁止）

> このステップを飛ばして作業ログだけで引き継ぎを書くことを禁止する。
> ユーザーの「次にやってほしいこと」は作業ログではなく直近の会話に現れる。

- セッション終盤（直近5〜10ターン、または最後のユーザー指示が出てから現在まで）の会話を**逐語的に振り返る**
- 以下を抽出する:
  - ユーザーが最後に出した指示・依頼の**原文に近い表現**
  - ユーザーと合意した「次にやること」（まだ着手していない依頼を含む）
  - ユーザーが最後に整理・提示した作業状態（テーブル・リスト等）があれば**そのまま**控える（要約しない）
  - 「このやり取りの続きとして次セッションで何を継続するか」を言語化する
- **FS/Step/サブスキルの特定（必須）:**
  - 現在のワークフローとフェーズ進行状況から、次セッションで activate すべきフェーズスキル名を特定する
  - そのフェーズスキル内のどの Step から再開するかを特定する
  - その Step で使用するサブスキルまたはサブエージェント名を特定する
  - 特定できない場合は `progress-resume-check` の結果とフェーズスキルの定義を確認する
- 中断作業がある場合は「中断時点で何をしていたか」「次の1操作」も併せて言語化する

**Step 2:** 書く前のユーザー合意（次作業の確認 — 省略禁止・このプロセスの核心）

> ⛔ このステップを省略して Step 3 のファイル生成に進むことを絶対に禁止する。
> AI の作業ログは「やったこと」しか持たない。ユーザーだけが「次に何をやってほしいか」を正確に知っている。
> 書いてから直すのではなく、**書く前に合意する**。

Step 1 で言語化した内容を、以下の形式でユーザーに提示する:

「直近のやり取りを次のように理解しました。**次のセッションでは、このやり取りの続きとして以下を継続実行します。**これで合っていますか？」

提示する内容（箇条書きで簡潔に）:
- **直近のユーザー指示（私の理解）:** {原文に近い表現で}
- **次セッションで継続実行すること:**
  - 実行するフェーズスキル: `{fs-xxx-phaseN-xxx}` (aide-powers skill)
  - 実行するStep: Step {N} ({ステップ名})
  - 実行するサブスキル/サブエージェント: `{skill名}` または `{agent名}`
  - タスク概要: {何を完了させるか — 参考情報。FSのStep定義に従う}
- **中断作業がある場合:** 中断時点の状況と次の1操作

> ⚠️ **FS指定の重要性:** ここで指定した「実行するフェーズスキル」「Step」「サブスキル/サブエージェント」が、
> 新セッションのオーケストレーターに対する **実行ルート指示** となる。
> 新セッションでは、オーケストレーターが直接タスクを実行するのではなく、
> 指定されたFSを activate → 指定された Step に進む → 指定されたサブスキル/サブエージェントで実行する。
> これを明確にするため、「タスク概要」は参考情報に過ぎず、実行手順はFS定義に委ねることを明記する。

選択肢:
1. はい（この理解で引き継ぎファイルを作成する）
2. 違う / 不足がある（正しい次作業を教えてください）
3. その他（自由記述）

- ユーザーが「1」→ Step 3（ファイル生成）へ。**合意した「次セッションで継続実行すること」を、テンプレートの「次セッションで継続する作業（ユーザー確認済み）」セクションと「未完了作業と次のアクション」テーブルに必ず反映する**
- ユーザーが「2」または「3」→ 指摘内容で理解を修正し、再度 Step 2 で確認する（合意できるまで繰り返す。ファイルは書かない）

**Step 3:** 現在の作業状態を収集し session-handover.md を生成

- 以下の項目を全て収集する（空の場合は「なし」と明記）:
  1. **次セッションで継続する作業（Step 2 でユーザー合意済み）** ← 最優先。合意内容をそのまま記載する
  2. 現在のワークフロー名とフェーズ番号
  3. 完了済み作業のサマリー
  4. 未完了作業の一覧と次のアクション（項目1の合意内容を反映する）
  5. 読むべきファイルの一覧（なぜ読む必要があるかも記載）
  6. 今回のセッションで確定した設計判断
  7. 発見した問題点（pending-issues 登録済み/未登録を区別）
  8. 追加作業ルールやユーザー指示（セッション中にユーザーが指定したルール・制約）
  9. 中断作業の詳細な再開手順（後述の「中断作業の記述ルール」に従う）
  10. 実行証跡（後述の「実行証跡の記載ルール」に従う）
- 出力先: .aide/specs/{feature_name}/session-handover.md
- テンプレートに従って全セクションを記述する
- ※ 既存の内容は全て上書き（差分更新ではない）

**Step 4:** 自己検証（生成後の品質チェック — 省略禁止）

生成した session-handover.md を以下の4観点で検証し、違反があれば修正してから次に進む:

#### 検証1: 問題点・状態の正確性

- 「完了済み作業」に書いた内容は、実際に成果物ファイルが存在するか？
- 「未完了作業」に書いた内容は、本当に未完了か？（部分完了を「未完了」と書いていないか）
- エラーや問題を記載する場合、**エラーメッセージの原文**または**具体的な症状**を含めているか？
- 「〜が問題」ではなく「〜が〜という理由で〜という状態になっている」レベルで書いているか？

**禁止:** 「うまくいかなかった」「問題があった」等の曖昧な記述。具体的な事象・原因・状態を書く。

#### 検証2: 関連ファイルの網羅性

- 「読むべきファイル」に、以下の全カテゴリを確認したか？
  1. 現在のフェーズスキルが参照する設計書（フェーズスキルの Input from caller を確認）
  2. 現在編集中・生成中のファイル
  3. 進捗管理ファイル（design-progress.md 等）
  4. pending-issues.md（問題点がある場合）
  5. dev-environment.md（実装フェーズの場合）
  6. 前フェーズの成果物（次フェーズの入力になるもの）
- 「なぜ読む必要があるか」が具体的か？（「参考のため」は禁止。「Step 3 で〜を確認するため」レベルで書く）

**禁止:** 「主要なファイルを列挙」で済ませること。フェーズスキルの Input/Output を確認して網羅する。

#### 検証3: パスの正確性

- 全てのファイルパスについて、以下を確認したか？
  1. `.aide/specs/{feature_name}/` のプレフィックスが正しいか（`{feature_name}` が実際の値に置換されているか）
  2. ファイル名のスペルが正しいか（`design-progress.md` を `progress.md` と略していないか）
  3. サブディレクトリが正しいか（`testing/manual-test-plan.md` を `manual-test-plan.md` と書いていないか）
  4. 実際にそのパスにファイルが存在するか（存在しないファイルを「読むべき」に入れていないか）
- パスは **ワークスペースルートからの相対パス** で統一する

**禁止:** `{feature_name}` 等のプレースホルダーを実際の値に置換せずに残すこと。ファイル名を略称で書くこと。

#### 検証4: 次のアクションの粒度

- 「未完了作業と次のアクション」の「次のアクション」列は、**新セッション開始後の最初の1〜2操作**に限定されているか？
- 以下の粒度基準を満たしているか？
  - ✅ OK: 「`fs-impl-phase4-execution` を activate し、Step 3 にて `micro-impl-agent` でタスク1.1を実装する」
  - ✅ OK: 「`fs-change-phase2-impl` を activate し、Step 2 にて `coding-test-2review` で差分実装を実行する」
  - ✅ OK: 「`skills/session-handover/SKILL.md` の行120付近にある Step 2 の後に検証ステップを追加する」
  - ❌ NG: 「プロセスCを改善してテンプレートを更新してRed Flagsも追加する」（複数ステップをまとめている）
  - ❌ NG: 「設計を完成させてQAレビューを通す」（フェーズ全体を書いている）
  - ❌ NG: 「object-design-domain.md に不変条件を追記する」（FS/Step/サブスキル指定なし → オーケストレーターが直接実行してしまう）
- 「次のアクション」は **FS activate → Step指定 → サブスキル/サブエージェント指定** の形式で書く

**禁止:** 次のアクションに2ステップ以上先の作業を書くこと。フェーズ全体のゴールを「次のアクション」に書くこと。

#### 検証5: ユーザー合意した次作業の反映（最重要）

- Step 2 でユーザーが合意した「次セッションで継続実行すること」が、テンプレートの **「次セッションで継続する作業（ユーザー確認済み）」** セクションに記載されているか？
- **FS/Step/サブスキルの指定が具体的か？**
  - ✅ OK: `fs-impl-phase4-execution` → Step 3 → `micro-impl-agent`
  - ✅ OK: `fs-change-phase2-impl` → Step 2 → `coding-test-2review`
  - ❌ NG: 「実装を続ける」「設計を完成させる」（FSもStepもサブスキルも不明）
  - ❌ NG: フェーズスキル名だけでStepやサブスキルが未指定
- その合意内容が **「未完了作業と次のアクション」** テーブルにも反映されているか？（2箇所で齟齬がないか）
- ユーザー指示の **原文に近い表現** が残っているか？（AI が勝手に言い換えて意図を変えていないか）
- Step 2 で提示した内容とファイルの記載が一致しているか？（合意後に内容が変質していないか）
- **「タスク概要」が参考情報である旨が明記されているか？** （新セッションのオーケストレーターが直接実行しないよう）

**禁止:** ユーザー合意した次作業を AI の作業ログ由来の内容で上書きすること。Step 2 の合意を省略してこの検証を「合格」とみなすこと。FS/Step/サブスキルを特定せずに「タスク概要」だけで済ませること。

---

**全5検証に合格してから Step 5 に進む。1つでも違反があれば session-handover.md を修正する。**

**Step 5:** ユーザーへの報告 + 新セッション用プロンプト提示（統合ステップ — 分離禁止）

> ⛔ このステップは「報告」と「プロンプト提示」の **両方を1回の応答で出力する** こと。
> 「報告だけ出して次のターンでプロンプトを出す」ことを禁止する。
> 以下のテンプレートを **そのまま** 出力すること。

以下を **1回の応答で全て** ユーザーに提示する:

## 実行証跡の記載ルール

> **記載条件:** フェーズの後処理（phase-report-check write）がまだ完了していない状態でセッションを切り替える場合に記載する。
> 後処理が完了済み（進捗ファイルに記録済み）の場合は記載不要。

### なぜ必要か

`phase-report-check (write)` は進捗ファイルの更新を行う。セッションを跨ぐ場合、前セッションの実行状態は新セッションのAIには見えないため、引き継ぎファイルに明示的に記録しておく必要がある。

### 記載すべき内容

1. **前処理の実行結果** — progress-resume-check の結果、phase-compliance-check verify の結果（実行コマンドと出力を含む）
2. **各ステップの実行内容** — 何を読み込んだか、何を実行したか、何が生成されたか
3. **サブエージェント呼び出し履歴** — 呼び出し先エージェント名、モード、渡した主要パラメータ、結果
4. **後処理の実行済み分** — doc-index-maintenance の結果、中間コミットのハッシュ等

## Red Flags - STOP

| Red Flag | なぜ危険か |
|---|---|
| **「引き継ぎの次作業にFS/Step/サブスキル指定なしでタスク内容だけ書く」** | **新セッションのオーケストレーターがFSを activate せずに直接タスクを実行してしまう。FSのプロセス（レビュー・品質チェック等）が全てスキップされ、品質が担保されない。これが最も頻発する構造的不具合** |
| **「直近のやり取りを読まず、作業ログだけで引き継ぎを書く」** | **ユーザーが次にやってほしいことは作業ログではなく直近の会話に現れる。作業ログだけで書くと「ユーザーが望む次作業」が抜け落ち、引き継ぎが機能しない。これが最頻発の不具合原因** |
| **「次作業をユーザーに確認せず、いきなりファイルを書く」** | **AI の作業ログは「やったこと」しか持たない。書く前に Step 2 で合意しないと、ユーザーの意図とずれた引き継ぎになる。書いてから直すのは二度手間で、かつ取りこぼしに気づけない** |
| 「引き継ぎファイルの一部だけ読めば十分」 | 全セクションを読まないと追加ルール・実行証跡・設計判断が失われ、作業の重複・矛盾・compliance-check FAIL が発生する |
| 「引き継ぎファイルの更新は後でまとめてやる」 | フェーズ完了時に更新しないと、セッション切断時に情報が失われる |
| 「コンテキストはまだ大丈夫」だとAIが勝手に判断する | AI にはコンテキスト使用量を確認する手段がない。ユーザーにメーターを確認してもらうこと |
| 「ユーザーがまだ大丈夫と言っているが念のため引き継ぎする」 | ユーザーが「まだ大丈夫」と言っているなら無理に引き継ぎ作業を行わない。ユーザーの判断を尊重する |
| 「前回の引き継ぎファイルは参考程度」 | 引き継ぎファイルの内容は正確に復元する。「参考程度」で済ませると作業が重複する |
| 「old リネームは忘れてもいい」 | リネームしないと次回更新時に前セッションの情報が上書きされ、履歴が失われる |
| **「プロンプト提示は省略してもいい」** | **引き継ぎファイルを作っても、ユーザーが新セッションで何を貼り付ければいいか分からない。引き継ぎが機能しない。Step 4 のテンプレート出力を省略することは、プロセスC未完了と同義。** |
| 「session-handover-old.md が既にあるから 2.old を作る」 | 連番ファイルは管理が煩雑になる。古い old は上書き削除する |
| 「セクションが空だから省略する」 | 空のセクションも「なし」と明記する。省略すると情報が欠落しているのか未記載なのか区別できない |
| 「ユーザー指示は覚えているから書かなくていい」 | 新セッションでは記憶がリセットされる。明示的に記録しないと失われる |
| **「問題があった、とだけ書けば伝わる」** | **新セッションのAIは文脈を持たない。「何が」「なぜ」「どういう状態か」の3点がないと正確に再現できず、誤った対処をする** |
| **「主要なファイルだけ書けば十分」** | **フェーズスキルの Input を確認せずに書くと、次セッションで必要なファイルを読み忘れ、不整合な成果物を生成する** |
| **「パスは大体合っていればいい」** | **1文字でも間違うとファイルが見つからず、新セッションで無駄な調査が発生する。存在確認してから書く** |
| **「次のアクションにフェーズのゴールを書いておけば方向性が伝わる」** | **新セッションのAIは「最初に何をすべきか」が分からず、間違った順序で作業を始める。直近1操作に限定する** |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「FS指定しなくてもタスク概要があれば次セッションで分かる」 | タスク概要だけ書くとオーケストレーターが直接実行する。FS/Step/サブスキルの3点指定が必須。実行ルートを明示しなければFSのプロセスが全てスキップされる |
| 「次にやることは自分の作業ログを見れば分かる」 | 作業ログは「やったこと」。ユーザーが望む「次にやってほしいこと」は直近の会話にある。両者は一致しない |
| 「書いてからユーザーに見せて直せばいい」 | 書く前に合意しないと、AI が取りこぼした項目には気づけない。ユーザーは「書かれた内容」しかレビューできない |
| 「まだセッションは続けられる」 | 兆候が出ているなら提案する。ユーザーが判断する |
| 「引き継ぎファイルを書く時間がもったいない」 | 引き継ぎなしの再開は、状態把握に倍以上の時間がかかる |
| 「前回と同じ作業だから引き継ぎは不要」 | 同じ作業でも、どこまで完了したかの情報は必要 |
| 「pending-issues に書いてあるから引き継ぎには不要」 | pending-issues は問題の詳細。引き継ぎはサマリーと次のアクションを提供する |

## Integration

**Called by:**
- 全ワークフローのフェーズスキル（フェーズ完了時の自動更新）
- using-aide-powers/SKILL.md（新セッション開始時の読み込み判定）
- ユーザーの明示的指示

**Related skills:**
- `pending-issues-management (aide-powers skill)` — 問題点の記録（session-handover は問題点の「サマリー」を記載、詳細は pending-issues.md）
- `doc-index-maintenance (aide-powers skill)` — session-handover.md は doc-index.md には登録しない（一時的なファイルのため）
- `user-profile-management (aide-powers skill)` — **ユーザーとやり取りが発生するフェーズでは必ず activate して user-profile.md を確認し、会話内容の指針にすること。** apply モード: user-profile.md を読み込み（未作成なら会話から技術レベルを推定して作成）、説明粒度・専門用語・選択肢の提示方法をスコアに基づいて調整する。update モード: 会話中にスコアと実態の差異を感じたらスコアを更新する
