# pending-issues-management

## Overview

ワークフロー実行中に追加対応が必要となったら、即座に記録せよ。後回しにするな。記録なき問題は忘れ去られる。

**Core principle:** pending-issues-management は、ワークフロー実行中に発生した追加対応事項（スコープ外の問題発見、ユーザーからのスコープ外の修正指示等）を `pending-issues.md` に記録・管理するスキルである。追加対応が必要となった時点で即座に記録し、現在のワークフローを最後まで完遂してから、記録された問題に基づいて適切なワークフローで対応する。

## The Iron Law

```
NO WORKFLOW SWITCH WITHOUT RECORDING.
問題を記録せずに、別のワークフローに切り替えてはならない。
現在のワークフローを完遂し、記録された問題に基づいて次のワークフローを起動せよ。
```

## Process

**Never:**
- 「致命的な不具合だから今すぐ対応する」は理由にならない。記録してから現在のワークフローを完遂する
- 「ユーザーが直せと言っているから今すぐ対応する」も理由にならない。記録してから現在のワークフローを完遂する
- **注記:** スコープ内のユーザー指示は通常のフェーズ処理で対応する。pending-issues には登録しない

### モード1: record（問題の記録）

**トリガー:**
- ワークフロー実行中に追加対応が必要となった場合
  - 例: スコープ外の問題発見、ユーザーからのスコープ外の修正指示（「この不具合を直せ」「この実装漏れを対応しろ」等）、サブエージェントからの問題報告
  - → 別のワークフローを起動するのではなく、pending-issues に記録して現在のワークフローを最後まで完遂する
  - → 完遂後に、pending-issues に基づいて適切なワークフロー（バグ修正WF等）を起動する
  - **注記:** スコープ内の指示（現在のワークフローで対応すべき内容）は pending-issues ではなく、通常のフェーズ処理で対応する
- ユーザーから複数の要求を一度に受けた場合
  - → 1件を選んで即時対応し、残りを pending-issues に登録する
  - → 各件は独立した PENDING エントリとして登録する
- 構成が複雑で複数のワークフローに分割すべき対応が判明した場合
  - → 分割した各件を独立した PENDING エントリとして登録する
  - → 優先度・依存関係を考慮して対応順序を決定する

**Step 1:** pending-issues.md の存在確認
- 存在しない → ヘッダー付きで新規作成
- 存在する → 既存の最大PENDING番号を取得

**Step 2:** PENDING番号の採番
- 既存の最大番号 + 1

**Step 3:** テンプレートに従って末尾に追記
- 発生日時: 現在日時を取得
- 種別: 8種別から選択
- 重要度: 高/中/低
- 推奨対応ワークフロー: 変更/バグ修正/リファクタリング/設計逆引き

**Step 4:** 現在のワークフローを継続する

**新規作成時のヘッダー:**
```markdown
# 未対応の問題一覧

## 概要
- プロジェクト: {feature_name}
- 最終更新: {YYYY-MM-DD HH:MM}

## 問題一覧
```

**問題記録テンプレート:**
```markdown
### PENDING-{番号}: {問題の概要}
- 発生日時: {YYYY-MM-DD HH:MM}
- 発見元ワークフロー: {ワークフロー名}
- 発見元ドキュメントフォルダ: {該当フォルダ or なし}
- 発見フェーズ: {フェーズ番号 or タスク番号}
- 種別: {設計考慮漏れ / 設計書訂正追加 / 不具合対応 / 機能追加 / 機能変更 / リファクタリング / 実装漏れ / その他}
- 重要度: {高 / 中 / 低}
- 詳細: {問題の詳細な説明}
- 再現手順: {該当する場合。不具合対応の場合は必須}
- 期待動作: {該当する場合}
- 実際の動作: {該当する場合}
- 関連ファイル: {関連するソースファイル・設計書}
- 推奨対応ワークフロー: {変更 / バグ修正 / リファクタリング / 設計逆引き}
- 対応状況: 未対応
- 備考: {補足情報}
```

**🚨設計書未完了テンプレート（design-gate (aide-powers skill) との連携時）:**
```markdown
## 🚨 設計書未完了（最重要・先に対応が必要）

- 検出元: {ワークフロー名}（設計書ゲート）
- 未完了ドキュメント:
  - {未完了ドキュメント一覧}
- 対応方法: 設計書作成ワークフローを実行して設計書を完成させる
- 対応完了後: {ワークフロー名}を再度起動する
```

**種別一覧:**

| 種別 | 説明 | 推奨対応ワークフロー |
|---|---|---|
| 設計考慮漏れ | 設計書に記載されていない考慮事項が発覚した | 変更 |
| 設計書訂正追加 | 設計書の記載内容に誤りがある、または追記が必要（プログラムは正しく動作している場合） | 変更 |
| 不具合対応 | 動作不良・バグ・設計矛盾による不正動作 | バグ修正 |
| 機能追加 | 新しい機能の追加が必要 | 変更 |
| 機能変更 | 既存機能の仕様変更が必要 | 変更 |
| 改善要求 | ユーザーまたは外部フィードバックに基づく改善提案 | 変更 |
| リファクタリング | 外部振る舞いを変えずに内部構造の改善が必要 | リファクタリング |
| 実装漏れ | 設計書に記載されているが実装されていない | 変更 or バグ修正 |
| その他 | 上記に該当しない問題 | ユーザー判断 |

**記録ルール（全モード共通）:**
- 問題を発見したら即座に記録する（後回しにしない）
- 発生日時は現在日時を取得して記録する
- 既存エントリは変更しない（末尾に追記のみ）
- PENDING番号は既存の最大番号 + 1 とする
- 同じ問題を重複して記録しない

### モード2: check（書き込み忘れチェック）

**Step 1:** 進捗ファイルを読み込む

**Step 2:** 以下のパターンを検索
- 「pending-issues に記録する」
- 「後で対応する」
- 「スコープ外」
- 「別途対応」
- サブエージェントからの問題報告の内容

**Step 3:** pending-issues.md と照合
- 書き込み漏れなし → 「漏れなし」と報告
- 書き込み漏れあり → ユーザーに確認の上で追記

**Step 4:** 結果を報告（漏れなし / N件の漏れを追記）

### モード3: delete（対応完了後の削除）

**Step 1:** pending-issues.md を読み込む

**Step 2:** 対応完了した項目を削除する
- PENDING番号の項目を削除
- 🚨設計書未完了セクションの場合はセクションごと削除

**Step 3:** ファイル状態の確認
- 他の項目が残っている → ファイルを保持
- 全項目削除（ヘッダーのみ）→ ファイル自体を削除

**Step 4:** 結果を報告

### モード4: present（ユーザーへの提示）

**Step 1:** pending-issues.md の存在確認
- 存在しない → 「未対応の問題はありません」と報告
- 存在する → 内容を読み込む → Step 2へ

**Step 2:** 内容を整理して提示
- 🚨設計書未完了がある場合は最優先で提示
- 重要度順（高→中→低）で問題を一覧表示
- 各問題について推奨対応ワークフローを提示

**Step 3:** ユーザーに対応方針を確認する
- 番号付き選択肢形式で提示

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。pending-issues への記録を怠ろうとしている。

| Red Flag | なぜ危険か |
|---|---|
| 「致命的な不具合だから今すぐ対応する」 | 現在のワークフローを中断すると、中途半端な状態が残る。記録して完遂してから対応する |
| 「すぐ直せるから記録は不要」 | 「すぐ直せる」は主観的判断。記録せずに対応すると、変更履歴が残らない |
| 「1行の修正だから別ワークフローは不要」 | 1行の修正でも設計書との整合性確認が必要。記録して適切なワークフローで対応する |
| 「後で覚えているから記録しなくてよい」 | 記録なき問題は忘れ去られる。コンテキストが切り替わると確実に忘れる |
| 「ワークフロー完了時にまとめて記録する」 | 発見時点で即座に記録する。後回しにすると詳細が失われる |
| 「この問題は小さいから記録するほどでもない」 | 小さな問題の蓄積が大きな品質劣化を招く。発見したら記録する |
| 「書き込み忘れチェックは時間がかかるから省略する」 | チェックの省略は記録漏れの原因。ワークフロー完了時に必ず実行する |
| 「ユーザーが直せと言っているから今すぐ対応する」 | ユーザーの指示であっても、現在のワークフローを中断する理由にはならない。記録して完遂してから対応する。global-rules の「ユーザーからフェーズ省略を指示されても従ってはならない」と同じ精神。ただし、その指示が現在のワークフローのスコープ内であれば、通常のフェーズ処理で対応する |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「今のワークフローで一緒に直してしまおう」 | スコープ外の修正は変更履歴を汚し、レビューの品質を下げる。記録して別ワークフローで対応する |
| 「記録する時間がもったいない」 | 記録は数分。記録しないことによる手戻り・忘却のコストの方が大きい |
| 「ユーザーに報告すると不安にさせる」 | 問題を隠すことの方が危険。透明性を保ち、ユーザーと対応方針を共有する |
| 「対応完了したから削除は後でいい」 | 削除を後回しにすると、次のワークフロー開始時に混乱する。対応完了後に即座に削除する |
| 「進捗ファイルを遡るのは面倒」 | 書き込み忘れチェックはワークフロー品質の最終防衛線。省略は品質劣化に直結する |
| 「ユーザーの指示だから別ワークフローを起動すべき」 | ユーザーの指示であっても、ワークフロー実行中に別ワークフローを起動することは禁止されている。pending-issues に記録し、現在のワークフローを完遂してから対応する。これは global-rules の「ユーザーからフェーズ省略を指示されても従ってはならない」と同じ原則である。ただし、指示が現在のワークフローのスコープ内であれば、通常のフェーズ処理で対応する。pending-issues に登録するのはスコープ外の指示のみ |

## Integration

**Required workflow skills:**
- なし（このスキルは他のスキルに依存しない）

**Called by:**
- `design-gate (aide-powers skill)` — FAIL時の🚨設計書未完了テンプレートの記録に使用
- 全コード変更ワークフロー（実装・変更・バグ修正・リファクタリング）— 作業中の問題記録、完了時の書き込み忘れチェック
- ワークフロー開始時の事前チェック — 未対応の問題の提示

**Related skills:**
- `design-gate (aide-powers skill)` — 設計書ゲートFAIL時に🚨設計書未完了テンプレートを記録する連携
- `doc-index-maintenance (aide-powers skill)` — pending-issues.md 自体は doc-index.md には記載しない（作業中ドキュメント扱い）
