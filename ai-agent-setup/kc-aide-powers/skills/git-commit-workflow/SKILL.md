# git-commit-workflow

## Overview

ワークフローのフェーズ完了時に変更内容をgitにコミットするための定型プロセス。コミットメッセージの自動生成、コミット対象ファイルの選別、ユーザー承認の取得、安全なgit操作を一貫して行う。

**Core principle:** コミット前に必ずユーザーの承認を得よ。承認なしのコミットを禁止する。

## The Iron Law

```
NO COMMIT WITHOUT USER APPROVAL.
ユーザーの承認なしに、git commit を実行してはならない。
```

```
NO BULK ADD. FILES MUST BE SPECIFIED INDIVIDUALLY.
git add -A や git add . を禁止する。対象ファイルは必ず個別に指定すること。
```

## Process

**Skip conditions:**
- 変更がない場合（`git status` で変更ファイルが0件）→ コミットをスキップする

**Step 1:** git管理状態の確認
- .git ディレクトリの存在を確認する
- 存在しない場合:
  - ユーザーに git init を勧める
  - ユーザーが承認 → git init を実行し、Step 2へ
  - ユーザーが拒否 → 処理を終了する
- 存在する場合 → Step 2へ

**Step 2:** コミットメッセージ言語の確認（初回のみ）
- dev-environment.md にコミットメッセージ言語の記載があるか確認する
- 記載がない場合はユーザーに確認し、dev-environment.md に記載する
- デフォルトは日本語

**Step 3:** 変更ファイルの確認
- git status で変更ファイルを一覧取得する
- 変更なし → コミットをスキップする（処理終了）
- **【必須】進捗ファイル確認:**
  - ワークフロー完了コミットの場合、*-progress.md（change-progress.md 等）が M（modified）に含まれているか確認する
  - 含まれていない場合 → 進捗ファイルの最終更新が漏れている可能性がある。ユーザーに「進捗ファイルが更新されていませんが、コミットに含めなくてよいですか？」と確認する
- 変更あり → ファイルを分類する:
  - M（modified）/ A（added）→ 基本対象
  - ??（untracked）→ **【必須】untracked ファイル確認プロセスを実行する**
    1. 各 untracked ファイル/ディレクトリが何かを調査する
    2. 本ワークフローで作成された成果物か判定する（changes/ ディレクトリ、設計書、新規スキルファイル等）
    3. 判定結果をユーザーに提示し、以下を確認する:
       - ワークフロー成果物 → コミット対象に含める
       - 一時ファイル/キャッシュ/IDE設定等 → .gitignore に追記
       - 判断がつかない → ユーザーに確認する
    - ※ 「M のファイルだけが今回の変更」と短絡的に判断することを禁止する
    - ※ untracked を無条件に除外することを禁止する
  - その他（json, ini, bin等）→ ユーザーに確認
    - 対象とする → コミット対象に含める
    - 対象としない → .gitignore に追記（.gitignore自体はコミット対象）
- **【必須】.gitignore 整備チェック:**
  - 以下の AI エージェント・IDE 生成ファイルが .gitignore に含まれているか確認する。含まれていない場合は .gitignore に追記してからコミット対象に含める。
  - .gitignore 必須パターン:
    - `.kiro/` ← Kiro IDE の設定・specs・agents 等
    - `.aide/references/` ← aide-powers が生成するツールマップ等の参照ファイル
    - `.aide/violation-history.md` ← aide-powers 違反履歴（ローカル運用ファイル）
    - `.aide/violation-clear-counter.txt` ← aide-powers 不正なしカウンター（ローカル運用ファイル）
    - `.claude/` ← Claude Code の設定ファイル
    - `.copilot/` ← GitHub Copilot の設定ファイル
    - `.gemini/` ← Gemini CLI の設定ファイル
    - `.codex/` ← Codex CLI の設定ファイル
    - `brainstorm-selection*.json` ← visual-companion の選択ファイル
  - ※ `.github/` はプロジェクトの CI/CD（workflows/ 等）として管理対象になりうるため、ユーザーに確認してから判断すること
  - ※ すでに .gitignore に記載済みの場合はスキップしてよい

**Step 4:** コミットメッセージの生成
- 以下のフォーマットに従って自動生成する:
  - 1行目: `<プレフィックス>: <要約>`（72文字以下）
  - 2行目: 空行
  - 3行目〜: ボディ（自明な場合は省略可）— ■変更理由 / ■対応内容 / ■影響範囲
  - フッター:
    - `Refs: #チケット番号`（任意）
    - `Docs: <ドキュメントフォルダパス>`（変更・バグ修正・リファクタリングの場合はMUST）
- プレフィックス選択:
  - 企画・設計・設計逆引き → `docs:`
  - 実装 → `feat:` / `test:`
  - 変更 → `feat:` / `fix:`（変更内容に応じて）
  - バグ修正 → `fix:`
  - リファクタリング → `refactor:`

**Step 5:** ユーザー承認（HARD-GATE: 承認なしのコミット絶対禁止）
- 以下をユーザーに提示する:
  1. コミット対象ファイルの一覧
  2. 生成したコミットメッセージ
  3. 確認メッセージ:
     - origin設定あり: 「これらをcommitしてpushします。いいですか？」
     - origin設定なし: 「commitのみ（pushなし）でいいですか？」
- **待機ルール（絶対）:** ユーザーの明示的な肯定応答（ok/はい/進めて/いいよ等）を受け取るまで git commit を実行してはならない。提示後は必ずユーザーの応答を待つこと。「前回承認済みだから今回も不要」という判断を禁止する。毎回、毎コミットで承認を取ること。
- ユーザーが承認 → Step 6へ
- ユーザーが修正を要求 → 修正してStep 5を再実行

**Step 6:** コミット・プッシュの実行
1. git add で対象ファイルをステージング
   - ※ ファイル単位で指定（git add -A / git add . 禁止）
   - 例: `git add src/domain/xxx.py src/application/yyy.py`
2. git commit でコミット
3. origin設定あり → git push / origin設定なし → pushスキップ

### プレフィックス一覧

| プレフィックス | 用途 |
|---|---|
| `feat:` | 新機能の実装 |
| `fix:` | バグの修正 |
| `docs:` | ドキュメントの作成・修正 |
| `style:` | コードの意味に影響しない修正（整形、スペース等） |
| `refactor:` | リファクタリング（機能を変えずコードを整理） |
| `perf:` | パフォーマンス改善 |
| `test:` | テストコードの追加・修正 |
| `chore:` | ビルド設定やライブラリ更新などの雑務 |
| `ci:` | CI/CD設定の変更 |
| `revert:` | 以前のコミットの打ち消し |

### ワークフロー別プレフィックス選択ガイド

| ワークフロー | フェーズ | 推奨プレフィックス |
|---|---|---|
| 企画 | 各フェーズ | `docs:` |
| 設計 | 各フェーズ | `docs:` |
| 実装 | 実装タスク | `feat:` / `test:` |
| 設計逆引き | 各フェーズ | `docs:` |
| 変更 | 全フェーズ完了 | `feat:` / `fix:`（変更内容に応じて） |
| バグ修正 | 全フェーズ完了 | `fix:` |
| リファクタリング | 全フェーズ完了 | `refactor:` |

### Docs: フッター必須ルール

変更・バグ修正・リファクタリングの3つのワークフローの場合のみ **必須**。

`Docs:` フッターは、コードとドキュメントのトレーサビリティを確保するために必須とする。

- `git blame` → コミットメッセージ → `Docs:` パスの流れで、コード変更の根拠となるドキュメントを特定できる
- 同じコードにさらなる修正が入った場合、`Docs:` パスが示すドキュメントも合わせて更新すべきことを明示する

パス形式（プロジェクトルートからの相対パス）:

```
Docs: .aide/specs/{feature_name}/changes/{YYYY-MM-DD}/
Docs: .aide/specs/{feature_name}/bugfix/{YYYY-MM-DD}/
Docs: .aide/specs/{feature_name}/refactoring/{YYYY-MM-DD}/
```

## revertプロセス（ユーザー要求時）

**Step 1:** ユーザーに確認
- 「コードを元に戻し、関連ドキュメントも削除します。いいですか？」
- 承認 → Step 2へ
- 拒否 → 処理終了

**Step 2:** コードを元に戻す
- git revert または手動で対象コミットの変更を取り消す

**Step 3:** ドキュメントフォルダを削除する
- 対象の changes/ bugfix/ refactoring/ 配下のフォルダを丸ごと削除
- ※ フォルダ統合済みの場合は追記部分のみ削除

**Step 4:** doc-index.md を更新する
- 削除したドキュメントのエントリを除去する

**Step 5:** revertコミット
- プレフィックス: `revert:`
- ボディ: 削除したドキュメントフォルダパスと削除理由
- ※ ユーザー承認を得てからコミット（通常のコミットフローと同じ）

### revertコミットメッセージ例

```
revert: {何を取り消したかの要約}

■変更理由
・{取り消しの理由}

■対応内容
・対象コミットをrevert
・ドキュメントフォルダを削除

■削除ドキュメントフォルダ
・{削除したフォルダパス}

■削除理由
・{削除の理由}
```

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。git-commit-workflow のルールを逸脱しようとしている。

| Red Flag | なぜ危険か |
|---|---|
| 「ユーザーに確認するまでもない変更だ」 | 全てのコミットにユーザー承認が必要。承認なしのコミットは Iron Law 違反 |
| 「git add . で全部まとめて追加しよう」 | 意図しないファイルがコミットされるリスクがある。ファイル単位で指定すること |
| 「Docs: フッターは今回は不要だろう」 | 変更・バグ修正・リファクタリングでは必須。トレーサビリティの確保に不可欠 |
| 「コミットメッセージは後で直せばいい」 | コミットメッセージはコード変更の記録。最初から正しいフォーマットで書くこと |
| 「変更が少ないからコミットは後でまとめよう」 | 都度コミット型ワークフローではフェーズ完了ごとにコミットする。まとめることを禁止 |
| 「コミットを忘れたが次のフェーズに進もう」 | コミット忘れは禁止。必ずコミットしてから次のフェーズに進むこと |
| 「前回のワークフローで承認済みだから今回も不要」 | 毎回、毎コミットで承認を取る。前回の承認は今回に引き継がれない |
| 「ユーザーが急いでいるから承認を省略する」 | 時間的制約は承認省略の理由にならない |
| 「変更内容が自明だから承認は形式的」 | 自明かどうかはユーザーが判断する。AIが判断してはならない |
| 「amend だから再承認は不要」 | amend も新規コミットと同様に承認が必要 |
| 「untracked ファイルは今回の変更と関係ない」 | untracked がワークフロー成果物（changes/ 等）である可能性がある。必ず調査してから判断すること |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「ドキュメントだけの変更だからボディは不要」 | ドキュメントのみの変更で内容が自明な場合はボディ省略可。ただし1行目のフォーマットは必須 |
| 「origin がないからコミットしなくてよい」 | originがなくてもローカルコミットだけでも価値がある。変更履歴の記録は重要 |
| 「.gitignore に追加するのは面倒だ」 | コミット対象外のファイルは .gitignore に追記する。次回以降の確認を省略できる |
| 「revert は git revert だけでよい」 | コードの取り消しに加えて、関連ドキュメントフォルダの削除と doc-index.md の更新が必要 |
| 「プレフィックスは何でもよい」 | ワークフロー種別に応じた推奨プレフィックスがある。一貫性のあるコミット履歴を維持すること |

## Integration

**Called by:**
- 企画ワークフロー（フェーズ完了ごと）
- 設計ワークフロー（フェーズ完了ごと + QAゲート通過後）
- 実装ワークフロー（フェーズ完了ごと + GUIモックアップ確認後 + README生成完了時）
- 設計逆引きワークフロー（フェーズ完了ごと）
- 変更ワークフロー（全フェーズ完了後に1回）
- バグ修正ワークフロー（全フェーズ完了後に1回）
- リファクタリングワークフロー（全フェーズ完了後に1回）

**Related skills:**
- `pending-issues-management` (aide-powers skill) — revert時のドキュメント削除に伴う pending-issues の更新
- `doc-index-maintenance` (aide-powers skill) — コミット後の doc-index.md 更新、revert時のエントリ除去

**Input from caller:**
- ワークフロー種別（プレフィックス選択に使用）
- feature_name（Docs: フッターのパス構築に使用）
- 完了フェーズ情報（コミットメッセージの要約に使用）
- ドキュメントフォルダパス（変更・バグ修正・リファクタリングの場合、Docs: フッターに使用）
