# phase-report-check（進捗管理）

## Overview

フェーズスキルの前処理・後処理で呼び出される進捗管理スキル。

write モードでは、進捗ファイルに対して以下を行う:

1. 進捗表（ステータステーブル）の該当フェーズ行を `✅ 完了` + 完了日時に更新する
2. フェーズ詳細セクションを追記する（状態・完了日時・skill_name・成果物一覧）

実体の進捗ファイル更新は `progress-updater (aide-powers agent)` サブエージェントに委譲する。
オーケストレータは進捗ファイルを直接編集してはならない。必ず本スキル経由でサブエージェントに委譲する。

---

## モード

| モード | 用途 | 呼び出しタイミング |
|---|---|---|
| **verify** | 直前フェーズの完了状態を確認する + ルール遵守宣言（進捗ファイルは書かない） | 前処理 |
| **write** | 成果物の存在を確認し、進捗ファイルを更新する + ルール違反自己申告 | 後処理 |
| **inform** | ユーザーからの不正指摘を違反履歴に追記する | ユーザーから不正指摘があった時 |
| **fix_open** | 進捗表に修正を起票する（対象フェーズを 🔧 修正中 にし、修正履歴に1行追記） | 修正のため前フェーズへ戻る時 |
| **fix_close** | 修正履歴エントリを ✅ 修正完了 にする | 修正作業の完了後 |

---

## verify モード（前処理 — 進捗確認 + ルール遵守宣言）

直前フェーズ（N-1）が完了状態であることを確認し、違反履歴の有無に応じてルール遵守を宣言する。

### 入力（オーケストレータ → 本スキル）

| 項目 | 説明 |
|---|---|
| mode | `verify` |
| progress_file_path | 進捗ファイルのプロジェクトルートからの相対パス |
| skill_name | これから実行するフェーズのスキル名（例: `fs-change-phase1-analysis`） |

### プロセス

**⚠️ verify モードは必ず progress-updater サブエージェントに委譲すること。オーケストレータが自己判断で PASS を返すことを禁止する。**

1. progress-updater (aide-powers agent) サブエージェントを invoke_sub_agent で起動する
   - 引数: mode `verify` / progress_file_path / skill_name
2. サブエージェントの結果（PASS / FAIL + reason）をそのまま採用する
3. オーケストレータがサブエージェントの結果を上書きすることを禁止する

#### Step 追加: ルール遵守宣言（verify PASS 後に必ず実施）

4. 違反履歴ファイル（`.aide/violation-history.md`）の存在を確認する
5. **違反履歴ファイルが存在しない場合** → 以下を宣言してから作業を継続する:

```
わたしは aide-powers のルールを忠実に守り、速度よりも精度を重視し、ひとつづつ作業を着実にこなします。
```

6. **違反履歴ファイルが存在する場合** → ファイルの内容を読み取り、以下を宣言してから作業を継続する:

```
私はこれまで以下の不正を行ってしまいました。

-----------------------------------------------------------
{違反履歴ファイルの内容を最新の5件表示}
-----------------------------------------------------------

二度と同様の不正を発生させないように、細心の注意を払って、aide-powers のルールを忠実に守り、速度よりも精度を重視し、ひとつづつ作業を着実にこなします。
```

### 出力

| 項目 | 説明 |
|---|---|
| result | PASS / FAIL |
| reason | FAIL の場合の理由 |

### FAIL 時の動作

- ユーザーに即通知する（前フェーズの完了処理が正常に行われていない疑い）
- 現フェーズの実行を阻止する
- 対応方針はユーザーが決定する

## write モード（後処理 — 進捗更新 + ルール違反自己申告）

### 入力（オーケストレータ → 本スキル）

| 項目 | 説明 |
|---|---|
| mode | `write` |
| progress_file_path | 進捗ファイルのプロジェクトルートからの相対パス |
| skill_name | 完了したフェーズのスキル名（例: `fs-change-phase1-analysis`） |
| changes_dir | 成果物格納先ディレクトリパス |
| expected_artifacts | このフェーズで作成されるべき成果物ファイル名リスト |

### プロセス

**⚠️ write モードは必ず progress-updater サブエージェントに委譲すること。オーケストレータが進捗ファイルを直接編集することを禁止する。**

#### Step 0: ルール違反自己申告（進捗更新の前に必ず実施）

オーケストレータ（FSスキル実行者）に対し、以下の「違反しがちなルール一覧」を提示し、このフェーズの実行中に違反がなかったかを**正直に**自己申告させる。

**━━━ 違反しがちなルール一覧（自己チェックリスト） ━━━**

| # | ルール | 違反の典型例 |
|---|---|---|
| R-1 | SKILL activate 必須・独自解釈禁止 | スキルを activate せずに内容を記憶で実行した / スキルの手順を自己流にアレンジした |
| R-2 | 手順の改変禁止・省略禁止 | プロンプト文やサブエージェント引数を独自に変更した / 「簡単だから」と手順を省略した / 自己流の代替手段で代用した |
| R-3 | フェーズスキル実作業禁止 | オーケストレータが直接ファイルを編集した / サブエージェントに委譲せず自分で実装した（※サブSKILLの手順に従った操作は違反ではない。禁止されるのはSKILL定義外の独自作業） |
| R-4 | 出力の即時記載 | サブエージェント結果をフェーズ末尾にまとめて記載した / 記載を忘れた |
| R-5 | 設計書なしの実装禁止 | design-gate PASS なしに実装コードを書いた |
| R-6 | git-commit-workflow 経由必須 | git commit を直接実行した |
| R-7 | 大きいファイルの全行読み出し | read_code 要約モードに頼って読み落とした / ファイル末尾まで読まなかった |
| R-8 | コンテキスト制約時の対応 | session-handover/task-orchestration を使わず自己判断で「次回に」と提案した |
| R-9 | 作業中の他ワークフロー起動禁止 | フェーズ進行中に別ワークフローを起動した |
| R-10 | サブエージェント結果の上書き禁止 | progress-updater 等の結果を独自判断で PASS/FAIL に変更した |
| R-11 | プロンプトテンプレートの独自改変禁止 | サブエージェントに渡すプロンプト文を独自に書き換えた / テンプレートの文言を変更・省略・追記した |
| R-12 | タスク分解ルール遵守 | task-orchestration を使わず大量タスクを一括実行した / 分解粒度がスキル定義と異なる / Wave 構成を無視した |
| R-13 | session-handover スキル経由必須 | session-handover スキルを activate せずに session-handover.md を直接作成した / スキルのフォーマットに従わず自己流で引継ぎファイルを書いた |

**━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━**

**⚠️ R-11（プロンプトテンプレート独自改変）の自己チェック方法:**
オーケストレータは申告時に必ずセッション履歴を遡り、サブエージェント呼び出し時のプロンプト文がスキル定義のテンプレートと一字一句同一であるかを再確認すること。「たぶん変えていない」という記憶に頼った申告を禁止する。差分がある場合は正直に違反として報告すること。

**申告手順:**

1. 上記リストの各項目について、このフェーズで違反があったかを正直に振り返る
2. **違反なし** → 「本フェーズでルール違反はありませんでした」と申告する
   - 不正なしカウンターファイル（`.aide/violation-clear-counter.txt`）のカウントを +1 する（ファイルがなければ `1` で新規作成）
   - カウントが **5 に達した場合** → 違反履歴ファイル（`.aide/violation-history.md`）を削除し、カウンターを `0` にリセットする。ユーザーに「不正なし5回連続達成により、違反履歴をクリアしました」と報告する
   - Step 1 へ進む
3. **違反あり** → 以下の情報を申告する:
   - 違反項目（R-1〜R-13 のいずれか）
   - 違反内容（具体的に何をしたか）
   - 違反日時（フェーズ実行中のいつ頃か）
   - 違反理由（なぜそうしたか）
4. 違反履歴ファイル（`.aide/violation-history.md`）に追記する（ファイルがなければ新規作成）
5. 不正なしカウンターファイル（`.aide/violation-clear-counter.txt`）を `0` にリセットする
6. ユーザーに違反履歴を申告し、以下の判断を仰ぐ:
   - **継続**: 違反を記録した上でこのまま進捗更新を行う
   - **やり直し**: 該当フェーズをやり直す

**⚠️ 虚偽申告（違反があるのに「なし」と申告すること）は不正の隠蔽であり、最も重大なルール違反である。**

#### 違反履歴ファイルのフォーマット

`.aide/violation-history.md` は以下の形式で記録する:

```markdown
# 違反履歴

| # | 違反日 | 違反項目 | 違反内容 | 違反理由 | フェーズ | 報告種別 |
|---|---|---|---|---|---|---|
| 1 | 2026-06-23 | R-3 | オーケストレータが直接ファイルを編集した | シンプルな変更だと判断した | fs-change-phase2-impl | 自己申告 |
```

#### 不正なしカウンターファイルのフォーマット

`.aide/violation-clear-counter.txt` は数値のみを格納するプレーンテキストファイル:

```
12
```

- 違反なし申告のたびに +1 する
- 違反あり（自己申告）または inform モード（ユーザー指摘）で `0` にリセットする
- 5 に達したら違反履歴ファイルを削除し、カウンターを `0` にリセットする

#### Step 1: progress-updater サブエージェントの起動

invoke_sub_agent で progress-updater (aide-powers agent) を起動する。
- 引数: mode `write` / progress_file_path / skill_name / changes_dir / expected_artifacts

サブエージェントは内部で以下を行い、全て PASS の場合のみ進捗ファイルを更新する:
- 成果物の存在確認（expected_artifacts が changes_dir に存在し1byte以上）
- 前フェーズ完了状態の整合性チェック（直前フェーズが ✅ 完了 または 🔧 修正中 であること）
- ステータステーブルの該当フェーズ行を `✅ 完了` + 完了日時に更新
- フェーズ詳細セクションを追記

#### Step 2: 結果の取り扱い

- PASS → 次フェーズ遷移を許可
- FAIL → ユーザーに即通知。次フェーズ遷移を阻止。理由を報告

### 出力

| 項目 | 説明 |
|---|---|
| result | PASS / FAIL |
| reason | FAIL の場合の理由 |

## inform モード（ユーザーからの不正指摘による追記）

ユーザーからルール違反の指摘があった場合に、違反履歴ファイルに追記する。

### 入力（オーケストレータ → 本スキル）

| 項目 | 説明 |
|---|---|
| mode | `inform` |
| violation_rule | 違反項目（R-1〜R-13、またはルール名の自由記述） |
| violation_content | 違反内容（具体的に何が起きたか） |
| violation_reason | 違反理由（なぜそうなったか） |
| violation_phase | 違反が発生したフェーズのスキル名 |

### プロセス

1. 違反履歴ファイル（`.aide/violation-history.md`）を確認する
   - 存在しない場合 → ヘッダー付きで新規作成する
   - 存在する場合 → 既存の最大連番 + 1 で追記する
2. 以下の形式で1行追記する:
   - `#`: 連番
   - `違反日`: 現在日付（YYYY-MM-DD）
   - `違反項目`: violation_rule
   - `違反内容`: violation_content
   - `違反理由`: violation_reason
   - `フェーズ`: violation_phase
   - `報告種別`: `ユーザー指摘`
3. 不正なしカウンターファイル（`.aide/violation-clear-counter.txt`）を `0` にリセットする
4. ユーザーに記録完了を報告する

### 出力

| 項目 | 説明 |
|---|---|
| result | RECORDED |
| message | 違反履歴に記録しました |

## fix_open モード（修正起票）

完了済みフェーズを修正のため差し戻すときに呼び出す。進捗表の該当フェーズを `🔧 修正中` にし、修正履歴に1行追記する。
**ステータステーブルの該当行を `⬜ 未着手` に戻してはならない（完了実績は保持する）。**

### 入力（オーケストレータ → 本スキル）

| 項目 | 説明 |
|---|---|
| mode | `fix_open` |
| progress_file_path | 進捗ファイルのプロジェクトルートからの相対パス |
| fix_phase | 修正対象フェーズ番号 |
| fix_reason | 修正理由 |
| fix_content | 修正内容 |
| requester_skill_name | 起票元フェーズのスキル名（修正を起票するフェーズのスキル名） |

### プロセス

**⚠️ fix_open モードは必ず progress-updater サブエージェントに委譲すること。オーケストレータが進捗ファイルを直接編集することを禁止する。**

invoke_sub_agent で progress-updater (aide-powers agent) を起動する。
- 引数: mode `fix_open` / progress_file_path / fix_phase / fix_reason / fix_content / requester_skill_name

サブエージェントは内部で以下を行う:
- 「## 修正履歴」テーブルが無ければ新規作成し、最大連番 + 1 で新しい修正ID（`FIX-{連番}`）を採番する
- 修正履歴に1行追記する（状態 `🔧 修正中`、起票日時=現在日時、完了日時=`—`）
- ステータステーブルの fix_phase 行を `✅ 完了` → `🔧 修正中` に更新する（完了日時は保持）

### 出力

| 項目 | 説明 |
|---|---|
| result | PASS / FAIL |
| fix_id | 採番された修正ID（例: `FIX-1`） |

---

## fix_close モード（修正完了）

修正作業が完了したときに呼び出す。修正履歴エントリを `🔧 修正中` → `✅ 修正完了` にする。

### 入力（オーケストレータ → 本スキル）

| 項目 | 説明 |
|---|---|
| mode | `fix_close` |
| progress_file_path | 進捗ファイルのプロジェクトルートからの相対パス |
| fix_id | 完了させる修正ID（例: `FIX-1`） |

### プロセス

**⚠️ fix_close モードは必ず progress-updater サブエージェントに委譲すること。オーケストレータが進捗ファイルを直接編集することを禁止する。**

invoke_sub_agent で progress-updater (aide-powers agent) を起動する。
- 引数: mode `fix_close` / progress_file_path / fix_id

サブエージェントは内部で以下を行う:
- 修正履歴から fix_id のエントリを探す（無ければ FAIL）
- 当該エントリの状態を `🔧 修正中` → `✅ 修正完了`、完了日時=現在日時 に更新する

### 出力

| 項目 | 説明 |
|---|---|
| result | PASS / FAIL |
| reason | FAIL の場合の理由 |
