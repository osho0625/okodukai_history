# コード品質レビュー

## Overview

実装コードの「中を見る」レビューの詳細ルール集。命名・型ヒント・docstring・コメント・SOLID・ダミー実装検出・過去不具合再発チェック・デッドコード排除を ERROR/WARNING/INFO の 3 段階で判定する。

**Core principle:** 実装したコードの品質は、設計との整合性ではなくコード自体の内部品質で判定せよ。ダミー実装と過去不具合の再発は、テストが通っても ERROR とせよ。

## The Iron Law

```
NO IMPLEMENTATION CODE ACCEPTED WITHOUT FULL QUALITY VERIFICATION.
全ての品質検証項目をパスしない限り、実装コードを受け入れてはならない。
```

```
NO DUMMY IMPLEMENTATION. NO LOST BUGFIX.
ダミー実装を通してはならない。過去の不具合修正を失ってはならない。
```

このルールに例外は存在しない。変更の規模・複雑さ・緊急度に関わらず、全セクション（1〜11）の検証を必ず実施すること。

## Process

**呼び出し元:** `agents/code-review-agent`（mode: implementation）がレビュー開始

**前提: 入力の受領**
- 対象ファイルパス（実装ファイル）
- 設計書ファイルパス（過去不具合履歴・テスト観点・Raises 等の参照用）
- プロジェクトのコーディング規約（例: program-structure.md に記載の命名規則）
- 過去不具合履歴フォルダの所在（例: `.kiro/specs/{feature_name}/bugfix/` または `.aide/specs/{feature_name}/bugfix/`）

**Step 1:** 対象ファイルの走査
- 対象レベル以下の全実装ファイルをリストアップ

**Step 2:** 各ファイルに対してセクション1〜11 の検証を順次実行

**Step 3:** 違反一覧の集計
- ファイル × 行番号 × 項目 × 内容 × 重要度 のテーブルを作成

**Step 4:** サマリの作成
- 検査ファイル数、ERROR 数、WARNING 数、INFO 数

**Step 5:** PASS/FAIL 判定
- ERROR 0 件 かつ WARNING 0 件 → PASS
- ERROR 1 件以上 または WARNING 1 件以上 → FAIL

**Step 6:** 出力フォーマットに従って結果を返す
- 呼び出し元（code-review-agent (aide-powers agent)）が「コード品質レビュー結果」として出力に組み込む

### セクション1: 命名規約

**優先順位ルール（上位が優先）:**

1. **ベースコード準拠**: 既存コードに命名パターンがある場合、それに従って統一性を保つ
2. **PEP 8**: 新規実装、またはベースコードに統一性が見られない場合は PEP 8 に従う
3. **Google Python Style Guide**: PEP 8 に記載がないパターンは Google Python Style Guide に従う

**基本ルール表（PEP 8 例）:**

| 対象 | 規則 | 違反例 |
|---|---|---|
| ファイル名 | スネークケース（`chunk_splitter.py`） | `ChunkSplitter.py`, `chunksplitter.py` |
| クラス名 | パスカルケース（`ChunkSplitter`） | `chunk_splitter`, `chunkSplitter` |
| メソッド名 | スネークケース（`calculate_cer`） | `calculateCer`, `CalculateCer` |
| 定数 | アッパースネークケース（`VALID_VAD_MODES`） | `validVadModes`, `valid_vad_modes` |
| プライベート | `_` プレフィックス（`_cancelled`） | プレフィックスなしの内部変数 |

**検証手順:**

1. 対象ファイルの周辺コード（同一パッケージ・同一レイヤー）の命名パターンを確認する
2. ベースコードに一貫したパターンがあれば、それとの一致を検証する
3. ベースコードにパターンがない、または新規ファイルの場合は PEP 8 との一致を検証する
4. PEP 8 でカバーされないケース（型変数、プロトコルクラス等）は Google Python Style Guide を参照する

**重要度:** 違反 → **ERROR**

### セクション2: ファイルサイズ

- 1ファイル200行以下（プロジェクトの規約に準拠。設計書 program-structure.md 相当の規約に従う）
- 超過している場合は報告する（即 FAIL ではなく **WARNING**）

**例外ルール（WARNING 不要）:**

- バリデーション分岐が同一パターンでシンプルに繰り返されるケース
- アーキテクチャ別の設定構築など同一パターンが並ぶケース
- ファクトリのルーティングなど同一パターンが並ぶケース
- 分割するとかえって可読性が下がるケース

**重要度:** 超過（例外に該当しない場合）→ **WARNING**

---

### セクション3: 1ファイル1クラス原則

- 基本的に1ファイルに1クラス
- **例外**: `exceptions.py`, `value_objects.py`, `interfaces.py`, `enums.py` など、設計書で複数クラスをまとめると定義されているファイル

**重要度:** 違反（例外に該当しない場合）→ **ERROR**

### セクション4: 型ヒント（必須対象の列挙）

- 全パブリックメソッドの**引数**に型ヒントがあるか
- 全パブリックメソッドの**戻り値**に型ヒントがあるか
- `__init__` の引数に型ヒントがあるか
- プライベートメソッドの型ヒントは**推奨だが必須ではない**

**重要度:** 必須対象の欠落 → **ERROR**

---

### セクション5: docstring

- 全パブリックメソッドに docstring があるか
- 全クラスにクラスレベルの docstring があるか
- 内容の品質は検証対象外（存在チェックのみ）

**重要度:** 欠落 → **ERROR**

### セクション5.5: コメント（PEP 8 準拠）

**基本原則:**
- コードと矛盾するコメントは、コメントがないよりも悪い。コードを変更したら、コメントも必ず更新する
- コメントは完全な文にする。最初の単語は大文字で始める（識別子の場合を除く）
- コメントは簡潔で必要最小限にする。コードを読めば分かることを繰り返さない

**ブロックコメント:**
- コメント対象のコードと同じレベルにインデントする
- `# ` で始める（`#` の後にスペース1つ）
- 段落の区切りは `#` のみの行で表す

**インラインコメント:**
- コードと同じ行に書くコメントは控えめに使う
- コードから少なくともスペース2つ以上離し、`# ` で始める
- 自明なことを説明するインラインコメントは書かない

```python
# 悪い例（自明）:
x = x + 1  # x をインクリメントする

# 良い例（意図の説明）:
x = x + 1  # 境界値を補正するため
```

**禁止事項（AI 生成コメントに特に注意、6 パターン）:**

1. コードの動作をそのまま日本語に翻訳しただけのコメントは書かない
2. 実装の経緯や言い訳をコメントに書かない（例: `# ライブラリの仕様上こうする必要がある` → 必要なら設計書に記載）
3. プログラム変更の経緯説明を書かない（例: `# 以前は○○だったが△△に変更した`）。変更履歴はバージョン管理の責務であり、コメントに書くものではない
4. 過剰なコメントは書かない。コード自体が明確であればコメントは不要
5. コメントアウトしたコードを残さない（バージョン管理で対応する）
6. （上記1〜5に包含される汎用原則として）AI が実装の成果をアピールする目的で書くコメントは禁止

**重要度:** 禁止事項該当 → **ERROR**

### セクション6: SOLID 原則チェック

#### 単一責任の原則（SRP）

- 1クラスの「変更理由」が1つに限定されているか
- SRP の本質は「意味の分離」であり、実装やロジックの共通性は関係ない
- たとえ1つのシンプルなメソッドしかなくても、そのメソッドを使う人の目的が異なれば分けなければならない。使う目的が異なる = 将来の変更で独立に変化する可能性がある = 変更理由が複数ある
- 機能定義が明確であいまいさがなく、定義と異なる用途で利用されることがないこと
- **判定方法**: そのクラスの各メソッド/属性について「誰が、何の目的で使うか」を問い、異なる目的を持つ利用者がいる場合は WARNING
- メソッド数やコード量、ロジックの同一性では判定しない

**SRP 検証の 2 観点（★重要）:**

1. **使用箇所の目的一貫性チェック**
   - 各パブリック関数・メソッドについて、呼び出し箇所を全て洗い出し、すべてが同じ目的で利用されていることを確認する
   - 呼び出し箇所ごとに利用目的が異なる場合、その関数・メソッドは複数の責任を担っている兆候 → WARNING

2. **bool 引数による責任混在チェック**
   - `bool` 型の引数を持つ関数・メソッドについて、その引数の `True` / `False` によって他の引数の役割や意味が変わっていないかを確認する
   - `bool` 引数の値に応じて内部で実質的に異なる処理パスに分岐し、他の引数が片方のパスでしか使われない、または異なる意味で解釈される場合は、実質的に2つの関数が1つに押し込められている状態 → WARNING
   - 例: `def process(data, is_batch: bool, chunk_size: int)` で `is_batch=True` のときだけ `chunk_size` が使われる場合 → `process_batch(data, chunk_size)` と `process_single(data)` に分離すべき

#### オープン・クローズドの原則（OCP）

- 条件分岐（if/elif チェーン）で拡張ポイントを処理していないか
- 特にファクトリやリポジトリ選択など、将来の拡張が想定される箇所を重点的に検査する

#### リスコフの置換原則（LSP）

- インターフェース（ABC）の実装クラスが、基底クラスの契約（事前条件・事後条件）を守っているか

#### インターフェース分離の原則（ISP）

- クライアントが使わないメソッドへの依存を強制していないか
- あるインターフェースを実装するクラスが、自分には関係のないメソッドの実装を強いられている場合は違反
- **判定方法**: インターフェースの各メソッドについて「全ての実装クラスがこのメソッドを意味のある形で実装しているか」を問い、空実装や `raise NotImplementedError` で済ませているメソッドがあれば WARNING
- メソッド数の多寡では判定しない（全メソッドが全実装クラスで使われていれば問題なし）

#### 依存性逆転の原則（DIP）

- アプリケーション層がインフラ層の具象クラスを直接参照していないか
- ドメイン層が外部ライブラリを直接 import していないか
- importルール検証（design-review-agent (aide-powers agent) 担当）と重複するが、こちらは **SOLID 観点**での指摘

#### SOLID の重要度（★場合分け★）

| 区分 | 重要度 | 該当例 |
|---|---|---|
| **明確な違反** | **WARNING** | ・SRP の「使用箇所の目的一貫性」が明確に破綻している（呼び出し箇所ごとに利用目的が異なる）<br>・DIP 違反により依存性逆転が欠落している（アプリケーション層がインフラ層の具象クラスを直接参照する等）<br>・ISP 違反により実装必須メソッドが空実装または `raise NotImplementedError` になっている<br>・OCP 違反により条件分岐で拡張ポイントを処理しており、将来の拡張で必ず既存コード改修が必要になる<br>・LSP 違反により基底クラスの契約（事前条件・事後条件）を明らかに破っている |
| **観察的指摘（懸念レベル）** | **INFO** | ・SRP の懸念（メソッドの使われ方が若干分かれつつあるが、現時点では目的の一貫性が保たれている等）<br>・bool 引数による責任混在の可能性（分岐はあるが、実質的に異なる処理パスになるほどではない等）<br>・OCP 的に将来の拡張で問題になりそうな懸念（現時点では拡張ポイントではないが、今後拡張されうる箇所等）<br>・その他、「まだ違反とまでは言えないが、将来的に注意すべき」レベルの観察 |

判定に迷う場合は、呼び出し元・利用者から見て「今すぐ修正を推奨すべきか（WARNING）」「現状は許容しつつ注意喚起するだけで十分か（INFO）」で切り分ける。

### セクション8: if/elif/else の網羅性

- `if/elif` チェーンで想定される全条件を列挙している場合、最後の条件を `else` で暗黙に処理せず、明示的に `elif` で書くこと
- `else` は「上記のいずれにも該当しない想定外のケース」として扱い、`raise` で例外を送出すること（想定外の状態を黙って通過させない）

```python
# 正しい:
if logic_type == LogicType.BATCH:
    return self._run_batch(audio)
elif logic_type == LogicType.PSEUDO_STREAMING:
    return self._run_pseudo_streaming(audio)
else:
    raise UnsupportedLogicError(f"未対応のロジック: {logic_type}")

# 間違い（想定外の値が黙って通過する）:
if logic_type == LogicType.BATCH:
    return self._run_batch(audio)
else:
    return self._run_pseudo_streaming(audio)
```

**重要度:** 違反 → **ERROR**

### セクション9: 過去不具合再発チェック（★最重要★）

> ★★★ AI Agent がリファクタリング等で過去のバグ修正を元に戻すことを防ぐための最重要チェック ★★★

**適用タイミング**: リファクタリング・変更・バグ修正のコードレビュー時に、過去の不具合修正が再発していないかを全件チェックする。

**対象:**
- `.kiro/specs/{feature_name}/bugfix/`（プロジェクトによっては `.aide/specs/{feature_name}/bugfix/`）配下の全サブディレクトリに含まれる `fix-design.md`（または `fix-plan.md`）
- bugfix/ 配下が存在しない場合はこのチェックをスキップする

**チェック手順:**

1. bugfix/ 配下の全バグ修正履歴を読み込む
2. 各バグ修正について、以下を1件ずつ確認する:
   a. 修正対象のファイル・クラス・メソッドを特定する
   b. 今回の変更対象と重なるかを確認する
   c. 重なる場合、修正内容（条件分岐、バリデーション、例外処理、ガード節等）が現在のコードに保持されているかを**コードの目視**で確認する
   d. 修正内容が失われている、または等価な対処がない場合は **ERROR** とする
3. 確認結果を出力に含める

**判定基準（★重要★）:**
- **テストコードの実行結果のみで「再発なし」と判断してはならない**。テストはプログラム変更と同時に変更されるものであり、テストが通っていても修正が保持されている保証にはならない
- 判断は設計内容とプログラムコードの**目視確認**で行う
- 修正内容がリファクタリングにより別の場所に移動した場合は、移動先で等価な対処が存在するかを確認する

**重要度:** 過去の不具合修正が失われている → **ERROR**

### セクション10: ダミー実装の検出（★最重要★、必須・ERROR）

> ★★★ AI エージェントが「とりあえず動く」ダミーコードを書いて先に進むことを防ぐための最重要チェック ★★★

以下のパターンを検出した場合は **ERROR** とする。例外なし。

**検出パターン表:**

| パターン | 具体例 | 判定 |
|---|---|---|
| `pass` のみのメソッド | `def process(self): pass` | ERROR |
| `NotImplementedError` を送出 | `raise NotImplementedError` | ERROR |
| ハードコードされた固定値を返す（ロジックなし） | `return 0`, `return ""`, `return []`, `return {}`, `return None` | ERROR |
| `# TODO` 付きの仮実装 | `# TODO: 後で実装する` + 空またはダミーのロジック | ERROR |
| `print` だけのメソッド | `def save(self): print("saving...")` | ERROR |
| `logging` だけのメソッド | `def process(self): logger.info("processing")` | ERROR |
| 「仮」「暫定」「ダミー」「stub」「mock」「placeholder」「temporary」というコメント | — | ERROR |
| 設計書に定義されたロジックが実装されていない | メソッドは存在するが中身が空同然 | ERROR |

**検証手順（★2 段階検証★）:**

1. 対象ファイルの全パブリックメソッド・全プライベートメソッドを走査する
2. 各メソッドについて以下の2段階で検証する:

   **第1段階: パターンマッチ検出**
   - 上記の検出パターン表に該当するかを確認する

   **第2段階: 実装内容の実質性チェック（★最重要★）**
   - パターンマッチに該当しなくても、以下の観点でメソッドの実装内容を精査する:
     - 設計書に記載されたロジック（条件分岐、バリデーション、計算、変換等）が実際にコードとして実装されているか
     - メソッドの行数が設計書の複雑さに対して不自然に少なくないか（例: 設計書に5つのバリデーション条件があるのに、メソッドが3行しかない）
     - 入力値のバリデーションが設計書通りに実装されているか（省略されていないか）
     - エラーハンドリングが設計書通りに実装されているか（省略されていないか）
     - 戻り値が設計書の仕様通りに構築されているか（固定値や簡略化された値を返していないか）
     - ループや条件分岐の中身が実質的な処理を行っているか（空ループ、常に true の条件分岐等がないか）

3. 第1段階・第2段階のいずれかで問題を検出した場合は **ERROR** として報告する
4. 「ライブラリが未インストール」「データが未配置」「外部サービスに接続できない」等は**理由にならない**。可能な限り実環境に近い実装を求める

**重要度:** いずれかに該当 → **ERROR**

### セクション11: デッドコードの排除

再利用可能でなかったり、独立性がないコードは積極的に削除する。検出した場合は **ERROR** とする。

- 仕様変更やリファクタリングの結果、どこからも参照されなくなったメソッド、属性、変数が残っていないか
- 未使用の import は `autoflake` 等のツールに頼るだけでなく、意味論的に不要なロジックを積極的に削除しているか
- 呼び出し元がなくなったパブリックメソッド、到達不能なコードパス、使われなくなったヘルパー関数も対象
- **AI はリファクタリング時に既存コードを「正」として残しがち**なので、特に注意して検出する
- 不要なコードはバージョン管理で復元できるため、躊躇なく削除する

**重要度:** 検出 → **ERROR**

## 重要度定義と判定ロジック

**重要度の定義（本スキルにおける単一の正）:**

| 重要度 | 意味 | 該当項目 |
|---|---|---|
| **ERROR** | 必ず修正が必要 | 命名規約違反、型ヒント欠落、docstring 欠落、1ファイル1クラス違反、コメント禁止事項違反、if/elif/else 網羅性違反、過去不具合再発、ダミー実装、デッドコード |
| **WARNING** | 修正を推奨 | ファイルサイズ超過、マジックナンバー、3段以上のネスト、未使用 import、リネーム漏れ、TODO/FIXME/HACK コメント、SOLID 原則の **明確な違反**（SRP 使用箇所の目的一貫性の明確な破綻、DIP 違反による依存性逆転の欠落、ISP 違反による実装必須メソッドの空実装、OCP 違反による条件分岐での拡張ポイント処理、LSP 違反による基底クラス契約の明らかな破綻 等） |
| **INFO** | 参考情報 | SOLID 原則の **観察的指摘（懸念レベル）**（SRP の懸念、bool 引数による責任混在の可能性、OCP 的に将来の拡張で問題になりそうな懸念 等） |

**PASS/FAIL 判定ロジック:**

- **ERROR 0件 かつ WARNING 0件 → PASS**
- **ERROR 1件以上 または WARNING 1件以上 → FAIL**
- INFO は PASS/FAIL に**影響しない**

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。このスキルの原則から逸脱している。

| Red Flag | なぜ危険か |
|---|---|
| 「テストが通っているから過去不具合は再発していないはずだ」 | テストはコード変更と同時に変更される。テスト通過は修正保持の証拠にならない。必ず目視確認で判定する |
| 「`pass` だけどテスト用の一時的な実装だからスルーしよう」 | ダミー実装は例外なく ERROR。「一時的」は来ない。設計書通りの実装を求める |
| 「`return None` でもメソッドは存在するからダミー実装ではない」 | ロジックなしの固定値返却はダミー実装。第 2 段階（実質性チェック）で必ず検出する |
| 「ファイルサイズが 201 行だから少しだけ超過。許容しよう」 | 例外 3 パターン（バリデーション分岐・アーキテクチャ別設定・ファクトリルーティング）に該当するか必ず確認する。該当しなければ WARNING は必ず出す |
| 「SOLID の SRP は『クラスが小さいから大丈夫』」 | コード量ではなく「変更理由が複数あるか」「使う目的が異なるか」で判定する。bool 引数による責任混在も必ず検査する |
| 「else を省略しても動くからいい」 | 想定外の値が黙って通過する。if/elif/else の網羅性違反は ERROR |
| 「TODO コメントは WARNING だから FAIL にしなくてよい」 | TODO 自体は WARNING（FAIL に影響しない）だが、TODO 付きの「仮実装」はダミー実装として ERROR。仕組みを混同してはならない |
| 「設計書の複雑さに対して実装が短いけど、シンプルに書けただけ」 | 第 2 段階のフラグ。実装がロジック・バリデーション・エラーハンドリングを全て含んでいるか 1 項目ずつ確認する |
| 「リファクタリングで元のコードは残しておこう」 | AI はリファクタリング時に既存コードを「正」として残しがち。参照のないコードは躊躇なく削除。残せば ERROR |
| 「Python 以外の言語だからこのスキルは当てはまらない」 | セクション1 の PEP 8 は例示。命名規約・型・docstring・SOLID・ダミー実装等の骨格は全言語共通 |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「private メソッドだから型ヒントは不要」 | public メソッドの引数・戻り値・`__init__` は必須。private は推奨。必須を満たしていないなら ERROR |
| 「同じパターンが繰り返されてるだけだから 230 行でも可読性高い」 | 例外 3 パターンに該当するか確認してから WARNING 判断する。該当しなければ WARNING を報告する |
| 「bugfix/ が存在しないから過去不具合再発チェックは不要」 | 正しい。存在しない場合のみスキップ可。存在するのに読み飛ばしたら原則違反 |
| 「`NotImplementedError` は抽象メソッドだから OK」 | ABC の抽象メソッドは OK。具象クラスでの `raise NotImplementedError` はダミー実装 ERROR |
| 「ライブラリがまだインストールされてないから `pass` で置いておく」 | 免罪符にならない。可能な限り実環境に近い実装を求める。環境問題は別途解決する |
| 「設計書の 5 条件のうち 3 条件を実装した。後で残りを追加する」 | 「後で」は来ない。設計書ロジック未実装はダミー実装として ERROR |
| 「コメントで『以前は○○だったが△△に変更した』と残しておくと親切」 | 変更履歴はバージョン管理の責務。コメントに書くな。書いたら ERROR |
| 「`# TODO` を付けておけば先送りマーカーとして許される」 | `# TODO` 付きの仮実装はダミー実装として ERROR。TODO は許容の印ではない |
| 「unused import は `autoflake` で後で消すからいいや」 | 意味論的に不要なロジックを積極的に削除する姿勢を求める。意識的削除なら WARNING、放置なら本スキルで検出して WARNING/ERROR |
| 「リファクタリングで古い実装を残した方が安全」 | 不要コードはバージョン管理で復元できる。残すな。残せば ERROR |
