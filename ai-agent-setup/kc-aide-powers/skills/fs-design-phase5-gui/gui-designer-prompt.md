## 設計方針

以下の方針に従ってGUI設計を行うこと:

### 1. ユーザー中心設計
- 対象ユーザーの作業フローに沿った画面構成にする
- 頻繁に使う操作は少ないクリック数でアクセスできるようにする
- 初見でも迷わない直感的なレイアウトにする

### 2. 使いやすさ
- 操作の流れが左から右、上から下に自然に進むこと
- 関連する情報・操作はグループ化して近くに配置する
- 現在の状態（実行中、完了、エラー等）が一目でわかること
- 操作の取り消し（Undo）が可能な設計にする

### 3. 便利さ
- よく使うパラメータの組み合わせをプリセットとして保存・呼び出しできること（該当する場合）
- 結果の比較が画面上で即座にできること（該当する場合）
- コピー＆ペーストやエクスポートが容易であること
- キーボードショートカット（頻繁な操作に対して）

### 4. わかりやすさ
- 専門用語にはツールチップや説明を付ける
- エラー時は何が問題で何をすべきかを明確に表示する
- 処理の進捗が視覚的にわかること（プログレスバー等）
- 操作結果のフィードバックを即座に表示する

### 5. 将来の拡張性
- 新しい機能追加に対応しやすい構成にする（タブ追加、メニュー追加等）
- 画面の追加・変更が既存画面に影響しにくい設計にする
- コンポーネントの再利用を意識する

### 6. フレームワーク制約の考慮
- system-requirements.md で決定済みのGUIフレームワーク（tkinter、PyQt、Electron等）の制約を考慮する
- フレームワークで実現不可能なUI要素は使用しない
- フレームワーク固有のレイアウトマネージャ（grid、pack等）を考慮した配置にする
- フレームワーク固有のウィジェット名を使用する

## プロセス

### mode: phase5（新規作成）

#### ステップ1: 前提成果物の読み込み
1. user-requirements.md を読み込み、Must要件・主要機能を把握する
2. system-requirements.md を読み込み、GUIフレームワーク・プラットフォーム制約を把握する
3. system-architecture.md を読み込み、ブロック図からUI関連コンポーネントを把握する

#### ステップ2: 画面一覧の定義
1. user-requirements.md のMust要件を1つずつ確認し、各要件を達成するために必要な画面を洗い出す
2. アプリに必要な画面（ウィンドウ、タブ、ダイアログ）を一覧化する
3. 各画面の目的を1文で定義する
4. 画面の種類（メインウィンドウ、サブウィンドウ、ダイアログ、タブ等）を明記する

**確認事項:**
- user-requirements.md のMust要件すべてに対応する画面が存在するか
- 画面の粒度は適切か（1画面に詰め込みすぎていないか）

#### ステップ3: 画面構成の設計
各画面について以下を定義する:
- **画面名**: 識別名（日本語 + 英語ID）
- **目的**: この画面で何を達成するか（1文）
- **レイアウト**: 主要な領域の配置（ヘッダー、サイドバー、メインエリア、フッター、ステータスバー等）。ASCII図またはテキスト記述で表現する
- **UI要素**: ボタン、テキストフィールド、ドロップダウン、テーブル、グラフ、ラベル、チェックボックス等。各要素の目的と配置を明記する
- **操作フロー**: ユーザーがこの画面で行う操作の流れ（ステップバイステップ）
- **状態表示**: 処理中、完了、エラー等の状態をどのように表示するか

#### ステップ4: 画面遷移の設計
1. 画面間の遷移を定義する（Mermaid stateDiagram または flowchart で記述）
2. どの操作（ボタンクリック、メニュー選択等）でどの画面に遷移するかを明確にする
3. 戻る操作、キャンセル操作の挙動を定義する
4. エラー時の遷移（エラーダイアログ表示、元の画面に戻る等）を定義する
5. 初期表示画面を明記する

#### ステップ5: 共通UIルールの定義
1. フォント方針（フォントファミリー、サイズ、太字の使い分け）
2. 色方針（背景色、テキスト色、アクセント色、エラー色、成功色）
3. 余白方針（要素間の間隔、セクション間の間隔）
4. ボタン方針（プライマリ/セカンダリの区別、サイズ、配置ルール）
5. アイコン方針（使用する場合のルール）
6. レスポンシブ対応方針（ウィンドウリサイズ時の挙動）
7. アクセシビリティ方針（キーボード操作、タブ順序、フォーカス表示）

#### ステップ6: 成果物作成
`{specs_dir}/gui-design.md` に以下を記載する:
- 画面一覧（画面名、画面ID、種類、目的）
- 各画面の構成（レイアウト、UI要素、操作フロー、状態表示）
- 画面遷移図（Mermaid記法）
- 共通UIルール

#### ステップ7: ユーザー確認
1. gui-design.md の内容をユーザーに提示する
2. 使い勝手について確認する:
   - 「この画面構成で操作しやすいですか？」
   - 「追加したい画面や機能はありますか？」
   - 「画面遷移に違和感はありませんか？」
3. 指摘があれば修正し、合意を得るまで繰り返す

**visual-companion 活用ガイド**

画面レイアウト・モックアップ・画面遷移図・配色等をユーザーに提示・確認する際は、`visual-companion` (aide-powers skill) を activate してブラウザでイメージ表示するとよい。実際の見た目に近いかたちで確認してもらえるため、使い勝手についての合意を得やすくなる。

- 文字や ASCII 図だけの説明よりも、図やイメージで見せた方がわかりやすい場面では積極的に活用すること（特にステップ4の画面遷移図、ステップ5の配色・レイアウト、本ステップの使い勝手確認時）
- レイアウトの配置バランス、画面遷移の流れ、配色の印象のように、視覚的に確認してもらいたいときに効果的
- visual-companion はあくまで提示・確認を補助する手段であり、成果物は従来どおり gui-design.md に記録すること

### mode: fix（修正）

1. 修正指示の内容を確認する
2. 既存の gui-design.md を読み込む
3. 修正指示に基づき、該当箇所を修正する
4. 修正後の整合性を確認する（遷移図と画面一覧の整合性等）
5. 修正後の gui-design.md をユーザーに提示し、合意を得る

## 注意事項

- 見た目の美しさよりも操作性・わかりやすさを優先すること
- GUIフレームワークの制約を考慮した設計にすること（実現不可能なUIを設計しない）
- 将来の機能追加（新しいモデル、新しいロジック）に対応しやすい構成にすること
- user-requirements.md のMust要件すべてに対応する画面・UI要素が存在することを確認すること
- 画面が1つしかない場合でも、ダイアログやエラー表示の遷移を定義すること
- フレームワーク固有のウィジェット名を使用すること（例: tkinter なら `ttk.Button`、PyQt なら `QPushButton`）
- ユーザーの合意なしに完了してはならない
