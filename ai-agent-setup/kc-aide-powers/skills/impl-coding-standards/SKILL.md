# 実装コーディング規約

## Overview

**Core principle:** 1タスク1呼び出し1ファイル。設計書に書かれたとおりに、1つのpublicメソッド単位で実装し、動作確認試験書を必ず更新せよ。ダミー実装するな。勝手に設計を変えるな。

`impl-coding-standards` は、micro-impl-agent (aide-powers agent) が1つの実装タスクを処理する時に**必ず従うべき詳細ルール集**である。粒度（1呼び出しの最大単位）、コーディング規約、動作確認試験書の更新、親タスク完了チェック、全5モードの報告テンプレート、テスト作成・実行ルールを包括する。

## The Iron Law

```
ONE SUBTASK = ONE INVOCATION = ONE FILE = ONE PUBLIC METHOD MAX
— 1サブタスク = 1回の呼び出し = 1ファイル以下 = 最大1つの publicメソッド
```

```
NO CODE WITHOUT READING THE DESIGN DOCUMENT FIRST
— 設計書を読まずにコードを書いてはならない
```

```
NO IMPLEMENT WITHOUT MANUAL TEST PLAN UPDATE
— mode: implement の完了時、動作確認試験書の更新なしに報告してはならない
```

```
NO DUMMY IMPLEMENTATION BY DEFAULT
— pass のみ、NotImplementedError、TODO付き仮実装を原則禁止とする
```

## Process

**Exceptions（以下の場合のみスキル適用範囲外）:**
- 呼び出し元から開発環境情報（`dev-environment.md`）が渡されていない → 実装を開始せず「開発環境情報が不足しています」と報告する
- タスクのテストファイルが「なし」と指定されている → write_test / fix_test / run_test モードはスキップし、その旨を報告する

### 共通前提（全モード共通）

**Step 1:** 開発環境情報の確認
- 呼び出し元から「開発環境情報」（dev-environment.md）が渡されているか確認する
- 渡されていない場合 → 「開発環境情報が不足しています」と報告して終了
- 渡されている場合 → 次のチェックへ

**Step 2:** テストファイル「なし」時のスキップ判定
- タスクのテストファイル指定が「なし」かを確認する
- 「なし」かつ mode が write_test / fix_test / run_test → スキップ報告して終了
- それ以外 → 該当モードのプロセスへ

### mode: implement（新規実装）

**Step 1:** 設計書を読む（必須）
- 実装を始める前に、以下を実際に Read で読み込む:
  1. 呼び出し元から渡された設計書ファイルパスの該当セクション
  2. 呼び出し元から渡されたプログラム構成書（ファイル配置・importルール確認用）
  3. 依存先クラスの実装ファイル（既に実装済みのもの）
  4. 開発環境情報（venvパス、Pythonバージョン、依存管理方針）
- ※ 設計書を読まずに実装を始めることは禁止

**Step 2:** 粒度チェック（「粒度ルール」セクション参照）
- 呼び出し内容が粒度ルールに違反していないか自己チェックする
- 違反していれば「粒度違反のため分割依頼」として呼び出し元に報告

**Step 3:** 実装コードを書く
- 「コーディング規約」セクションに従って Write / Edit で実装する
- 1回の呼び出しで実装するのは1つのpublicメソッド（+関連privateメソッド・ヘルパー）が最大単位
- メソッドのないクラス（値オブジェクト、列挙型、例外クラス等）は1クラス単位
- 1回の呼び出しで変更するファイルは1つだけ
- 初回タスク（クラス新規作成）の場合は、コンストラクタ（__init__）+ 最初のpublicメソッド1つまで
- 設計定義にないメソッドやプロパティを追加しない
- 設計定義と異なるシグネチャで実装しない
- ダミー実装の原則禁止（「ダミー実装の原則禁止」セクション参照）

**Step 4:** 動作確認試験書の更新（必須）
- 「動作確認試験書の更新ルール」セクションに従い、`.aide/specs/{feature_name}/testing/manual-test-plan.md` に試験項目を追記する
- 試験書が存在しない場合は報告する

**Step 5:** 完了報告
- 「全5モードの報告テンプレート」の mode: implement テンプレートに従って報告する
- ステータス（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）は「ステータス運用ルール」に従って選択する

### mode: implement（親タスク完了チェック）

全サブタスク完了後、呼び出し元から親タスクの設計書セクション全体を指定して呼び出される特殊モード:

**Step 1:** 設計書セクションを Read で読む
- 親タスクの設計書セクション全体を読み込む

**Step 2:** 実装コードを Read で読む
- 対象ファイルの実装コードを全て読み込む

**Step 3:** 全項目を1項目ずつ照合する
- 設計書に定義されている全項目を網羅的にチェックする:
  - クラス定義
  - 全 publicメソッド
  - 全 privateメソッド
  - 定数
  - 不変条件
  - その他の設計書記載事項

**Step 4:** 漏れの検知
- 漏れあり → 追加実装する（通常の implement モードと同じルールに従う）
- 漏れなし → 「漏れなし」として報告する

**Step 5:** 完了報告
- 「全5モードの報告テンプレート」の親タスク完了チェック報告テンプレートに従って報告する
- ステータス（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）は「ステータス運用ルール」に従って選択する

### mode: fix / fix_test（レビュー指摘修正）

**Step 1:** レビュー指摘を受領する
- 呼び出し元からレビュー指摘内容を受け取る
- design-review-agent (aide-powers agent) からの指摘
- code-review-agent (aide-powers agent) からの指摘

**Step 2:** 指摘内容に従って Edit で修正する
- 指摘されていない箇所を変更しない
- fix の場合: 実装コードを修正
- fix_test の場合: テストコードを修正

**Step 3:** 完了報告
- 「全5モードの報告テンプレート」の mode: fix / fix_test テンプレートに従って報告する
- ステータス（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）は「ステータス運用ルール」に従って選択する

### mode: write_test（テスト作成）

**Step 1:** テスト作成ルールを適用する（「テスト関連ルール」セクション参照）
- テストフレームワーク: dev-environment.md に記載されたフレームワークを使用
- テストファイル配置: tests/ 配下のレイヤー別サブディレクトリ
- テストクラス名: Test{対象クラス名}
- テストメソッド名: test_{メソッド名}_{条件}_{期待結果}
- 設計書「テスト観点」セクションの全ケースカバー
- 全パブリックメソッドにテストを書く
- モック・スタブ禁止（unittest.mock禁止）
- 外部インフラ依存は設計書定義のダミー実装をDI注入
- 境界値テスト、異常系テストを含める

**Step 2:** 基本構造テンプレート（「テスト関連ルール」セクション）に従って Write で記述する

**Step 3:** 完了報告
- 「全5モードの報告テンプレート」の mode: write_test テンプレートに従って報告する
- ステータス（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）は「ステータス運用ルール」に従って選択する

### mode: run_test（テスト実行）

**Step 1:** テスト実行コマンドを組み立てる
- dev-environment.md に記載された「単一テストファイル実行コマンド」を使用し、ユニットテストを実行する
- ※ 仮想環境の使用有無・パスは dev-environment.md に従う
- ※ dev-environment.md にテスト実行コマンドが記載されていない場合は NEEDS_CONTEXT で報告する

**Step 2:** テストを実行し結果を判定する
- ユニットテストが全パス → Step 3（完了報告）へ
- 失敗あり → 原因判定:
  - 外部ライブラリ起因（sherpa-onnx, onnxruntime, psutil 等のAPI不一致、環境依存エラー）→ リトライせず即報告
  - 実装またはテストの問題 →
    - 修正後は「該当レビューを再実行してから」テストを再実行する
    - 実装を修正した場合 → design-review-agent (aide-powers agent) / code-review-agent (aide-powers agent)（implementation モード）を再実行
    - テストを修正した場合 → design-review-agent (aide-powers agent) / code-review-agent (aide-powers agent)（test モード）を再実行
    - レビュー再実行は micro-impl-agent (aide-powers agent) の責務外のため、呼び出し元に「修正後はレビューに戻る」ことを報告する
    - レビュー再実行後、テストを再実行（最大3回）
    - 3回修正しても解決しない場合は報告

**Step 3:** 完了報告
- 「全5モードの報告テンプレート」の mode: run_test テンプレートに従って報告する
- ユニットテストの結果を記載する
- ステータス（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）は「ステータス運用ルール」に従って選択する

## 粒度ルール

| ルール | 内容 |
|---|---|
| **基本単位** | プランナーのサブタスク1つ = 1つの publicメソッドとその関連コード（privateメソッド、ヘルパー含む） |
| **メソッドのないクラス** | 値オブジェクト、列挙型、例外クラス等。サブタスクなしの親タスク1つが実装単位 |
| **最大単位** | 1ファイルに収まる範囲。1回の呼び出しで複数ファイルに手を入れることを禁止する |
| **初回タスク** | クラスの新規作成時は、コンストラクタ（`__init__`）+ 最初の publicメソッド1つまでを実装する |
| **プランナーのタスクリスト遵守** | 呼び出し元（プランナー／フェーズスキル）が提示したタスク構造をそのまま実行する。micro-impl-agent (aide-powers agent) が独自判断でタスクを細分化・統合することを禁止する。プランナーのサブタスク1つ単位で受け取り、1つ単位で完遂して報告する |

### 複数ファイルにまたがる場合の分割ルール

1つの publicメソッドを実装するのに別ファイルの変更が必要な場合:

1. まず別ファイルの必要なメソッドを先に別タスクとして実装する
2. そのタスクのレビュー・テストを完了させる
3. その後、本体の publicメソッドを実装する

**「依存先を先に実装してから本体を実装する」順序を必ず守ること。**

### 「粗い」の判断基準（自己検証用・4項目）

以下のいずれかに該当するタスクは「粗い」と判断し、呼び出し元に分割依頼する:

1. 1タスクに複数の publicメソッドの実装が含まれている
2. 1タスクで複数ファイルへの変更が必要
3. 1タスクの設計参照セクションが複数クラスにまたがっている
4. 「〇〇クラス全体を実装」のような記述になっている

### 禁止事項（4項目）

1. 「このファイル全体を実装して」のような大きな単位での指示に従うことを禁止する
2. 実装量が多い場合でも、上記基準に従って分割する。時間がかかることを理由にまとめてはならない
3. 「クラスが小さいからまとめてよい」という独自判断を禁止する。基準は publicメソッド単位
4. **独自判断による細分化・統合を禁止する**。プランナー／呼び出し元が提示したタスク構造をそのまま受け取り、そのまま実行する。「このサブタスクは細かすぎるから隣のサブタスクと統合しよう」「このサブタスクは大きすぎるから自分で分割しよう」といった独自判断は行わない（粗すぎる場合は「粗い」の判断基準に該当する場合のみ呼び出し元に分割依頼する）

## コーディング規約

| # | ルール | 内容 |
|---|---|---|
| 1 | 型ヒント必須 | 全 publicメソッドの引数・戻り値、`__init__` の引数に型ヒントを付ける |
| 2 | docstring 必須 | 全 publicメソッド・全クラスに docstring を付ける |
| 3 | PEP 8 準拠 | Python の標準コーディング規約に従う（他言語の場合はプロジェクトの標準規約に読み替える） |
| 4 | ファイルサイズ | 1ファイル200行以下を目安とする（同一パターンの繰り返しは例外） |
| 5 | ファイル名 | スネークケース（例: `user_repository.py`） |
| 6 | クラス名 | パスカルケース（例: `UserRepository`） |
| 7 | メソッド名 | スネークケース（例: `find_by_id`） |
| 8 | 定数 | アッパースネークケース（例: `MAX_RETRY_COUNT`） |
| 9 | 設計定義逸脱禁止 | 設計定義にないメソッドやプロパティを追加しない |
| 10 | シグネチャ一致 | 設計定義と異なるシグネチャで実装しない |
| 11 | 分割書き込み | 50行超のファイルを書く場合は Write で先頭50行程度を書き、残りを Append で追記する（一度に書くと処理が停止する場合がある） |

**他言語への適用:** Python 以外の言語で利用する場合は、ルール3の「PEP 8」をその言語の公式/業界標準のコーディング規約（例: TypeScript ESLint、Java Checkstyle、Go gofmt）に読み替える。ルール5〜8の命名規則もプロジェクトで採用する言語の標準命名規則に読み替える。ただし「設計定義逸脱禁止」「シグネチャ一致」「型ヒント/docstring 相当のドキュメントコメント必須」は全言語共通で適用する。

## 動作確認試験書の更新ルール（mode: implement の完了時必須）

**追記タイミング:** `mode: implement` の完了時（親タスク完了チェック時を含む）

**対象ファイル:**

```
.aide/specs/{feature_name}/testing/manual-test-plan.md
```

**パス判定ルール（必須）:**

- **常に `.aide/specs/{feature_name}/testing/manual-test-plan.md` を参照する**。新規作成時も追記時も同様とする
- 既存 `.kiro/specs/` パスで試験書が存在する場合は、`design-gate (aide-powers skill)` の Step 0 マイグレーション処理で既に `.aide/specs/` に移行済みである（呼び出し元ワークフローが design-gate (aide-powers skill) を通過していることが前提）
- 従って micro-impl-agent (aide-powers agent) は `.kiro/specs/` パスを直接参照しない。常に `.aide/specs/` 固定で操作する
- もし design-gate (aide-powers skill) 未通過で `.kiro/specs/` のみに試験書が存在する状態で呼び出された場合は、「マイグレーション未完了（design-gate 未通過）のため実行不可」と報告する。マイグレーションを実行する責務は呼び出し元ワークフローにあり、micro-impl-agent (aide-powers agent) 側で `.kiro/specs/` を直接編集することはしない

**追記ルール:**

1. 試験IDは既存の最大番号の次の連番（`MT-001`, `MT-002`, ...）
2. 「追加タスク」列に、どのタスク番号の実装で追加されたかを記載する（例: `Task 2.3`）
3. 操作手順はユーザーが実際に操作できる具体的な手順を書く（「〇〇画面を開き、△△ボタンをクリックする」等）
4. 操作手順が **3ステップ以内で収まる簡単なもの** は、試験書の「操作手順」列に直接記載する
5. 操作手順が **4ステップ以上、または前提条件・データ準備が必要な複雑なもの** は、別ファイル `.aide/specs/{feature_name}/testing/procedures/MT-XXX.md` に試験手順書を作成し、試験書の「操作手順」列には `[手順書](./procedures/MT-XXX.md)` のリンクを記載する
6. 期待結果はユーザーが目視で確認できる内容を書く
7. 「結果」列は **空欄** にする（ユーザーが記入する）
8. 同じ操作で確認できる項目が既に存在する場合は、新しい項目の「結果」列に `別項目(MT-XXX)で確認済み` と記載し、「備考」列に理由を書く。**項目自体は削除しない**（トレーサビリティ維持のため）
9. 試験書が存在しない場合は報告する（ワークフロー／フェーズスキル側で作成すべき）

**動作確認試験書の基本構造（参考）:**

```markdown
# 動作確認試験書

## 試験概要
- プロジェクト: {feature_name}
- 作成日: {YYYY-MM-DD}
- 最終更新: {YYYY-MM-DD}

## 試験項目

| # | 試験ID | 追加タスク | 操作手順 | 期待結果 | 結果 | 備考 |
|---|---|---|---|---|---|---|
| 1 | MT-001 | Task 2.3 | 1. アプリを起動する<br>2. メニューから「新規」を選択する | 新規画面が表示される | | |
| 2 | MT-002 | Task 2.5 | [手順書](./procedures/MT-002.md) | データ保存が成功する | | |

## 試験結果サマリ
- 総項目数: N
- PASS: 0
- FAIL: 0
- 未実施: N
- 別項目で確認済み: 0
```

**試験手順書テンプレート（`testing/procedures/MT-XXX.md`）:**

```markdown
# 試験手順書: MT-XXX {試験名}

## 追加タスク
{タスク番号}

## 前提条件
- {必要なデータ、環境設定、事前操作等}

## 操作手順
1. {具体的な操作}
2. {具体的な操作}
3. ...

## 期待結果
- {ユーザーが目視で確認できる結果}

## 備考
- {補足情報があれば}
```

**重複試験の扱い:**

- 試験項目は **削除しない**（トレーサビリティのため）
- 同じ操作・同じ確認内容の試験が既にある場合は、後から追加された項目に `別項目(MT-XXX)で確認済み` と記載する
- ユーザーに無駄な試験をさせないための措置であり、項目の存在自体は網羅性チェックに必要

## 親タスク完了チェック

**発動条件:** 全サブタスク完了後、呼び出し元から親タスクの設計書セクション全体を対象に mode: implement で呼び出される。

**手順（4ステップ）:**

1. 設計書の該当セクション全体を Read で読む
2. 実装済みコード（対象ファイル）を Read で読む
3. 設計書に定義されている全項目（クラス定義、全 publicメソッド、全 privateメソッド、定数、不変条件等）が実装されているか1項目ずつ照合する
4. 判定:
   - 漏れあり → 追加実装する（通常の implement モードと同じルールに従う）
   - 漏れなし → 「漏れなし」と報告する

## テスト関連ルール（mode: write_test）

**基本ルール:**

| # | ルール | 内容 |
|---|---|---|
| 1 | テストフレームワーク | `dev-environment.md` に記載されたテストフレームワークを使用する。記載がない場合は言語の標準テストフレームワーク（Python: unittest、TypeScript: Vitest/Jest、Java: JUnit、Go: testing）を使用する |
| 2 | テストファイル配置 | `tests/` ディレクトリ配下。レイヤー別サブディレクトリ: `tests/domain/`, `tests/application/`, `tests/infrastructure/`, `tests/presentation/` |
| 3 | テストクラス名 | `Test{対象クラス名}`（例: `TestUserRepository`） |
| 4 | テストメソッド名 | `test_{メソッド名}_{条件}_{期待結果}`（例: `test_find_by_id_with_valid_id_returns_user`） |
| 5 | 網羅性 | 設計書「テスト観点」セクションの **全ケース** をカバーする |
| 6 | パブリックメソッド必須 | 全 publicメソッドにテストを書く |
| 7 | モック・スタブ禁止 | `unittest.mock` を使用しない |
| 8 | 外部インフラ依存 | 設計書で定義されたダミー実装をDI経由で注入する（`unittest.mock` は使わない） |
| 9 | 境界値テスト | 設計書の不変条件に対して境界値・直前・直後をテストする |
| 10 | 異常系テスト | 設計書「Raises」セクションの全例外に対するテストを含める |

**テストコードの基本構造テンプレート:**

```python
import unittest

class TestTargetClass(unittest.TestCase):
    def test_method_condition_expected(self):
        # Arrange
        ...
        # Act
        ...
        # Assert
        ...

if __name__ == '__main__':
    unittest.main()
```

**他言語への適用:** Python 以外の言語の場合は、言語の標準テストフレームワーク（例: Java の JUnit、TypeScript の Vitest/Jest 標準機能、Go の testing パッケージ）に読み替える。ただし以下の原則は全言語共通:

- モック/スタブ禁止（外部依存は設計書定義のダミー実装をDI注入）
- 命名規則の一貫性
- 境界値・異常系を必ず含める

## テスト実行ルール（mode: run_test）

**使用フレームワーク:**

- `dev-environment.md` に記載されたテストフレームワーク・テスト実行コマンドに従う
- dev-environment.md にテスト実行コマンドが記載されていない場合は NEEDS_CONTEXT で報告する

**テスト実行コマンド:**

- **ユニットテスト**: dev-environment.md に記載された「単一テストファイル実行コマンド」を使用する
- 仮想環境（venv等）の使用有無・パスは dev-environment.md の記述に従う
- グローバルにインストールされたツールを使用してよいかは dev-environment.md の記述に従う

**必須ルール（言語・フレームワーク非依存）:**
- `run_test` モードは対象タスクのユニットテストを実行する。具体的なコマンド・パス・オプションは全て `dev-environment.md` の記述に従う
- 既存テスト全実行（リグレッションテスト）は本モードでは実施しない。動作確認Step（各フェーズスキルの regression-test-prompt.md 経由）で1回実施する設計に統一されている

**失敗時の対応フロー:**

1. ユニットテストで失敗
2. 原因判定:
   - 外部ライブラリ起因のAPI不一致・環境依存エラー（例: sherpa-onnx, onnxruntime, psutil 等）→ リトライせず即報告（実装修正で対応不可のため）
   - 実装またはテストの問題 → 修正 → 該当レビューを再実行 → テスト再実行（最大3回）
3. 修正後の「該当レビュー再実行」ルール（必須）:
   - 実装コードを修正した場合 → design-review-agent (aide-powers agent)（mode: implementation）+ code-review-agent (aide-powers agent)（mode: implementation）を呼び出し元に「再実行してからテストに戻る」ことを促す
   - テストコードを修正した場合 → design-review-agent (aide-powers agent)（mode: test）+ code-review-agent (aide-powers agent)（mode: test）を呼び出し元に「再実行してからテストに戻る」ことを促す
   - レビュー実行自体は micro-impl-agent (aide-powers agent) の責務外だが、修正後にレビューを飛ばして直接テストを再実行することを禁止する。呼び出し元に「修正後はレビューに戻る」ことを報告上で明示する
4. 結果:
   - 3回以内で解決 → 完了報告
   - 3回修正しても解決しない → 報告（pending-issues 登録を検討）

## ダミー実装の原則禁止

**禁止する理由:** ダミー実装は「実装したつもり」の錯覚を生み、後工程で発見された場合の手戻りが大きい。設計書の意図を実際のコードで検証する機会を失う。

**原則:**

1. 可能な限り **実環境に近づけて** 実装・評価すること
2. ライブラリ未インストール、データ未配置等の理由でダミー実装にしてはならない
3. ライブラリが必要なら Bash で `pip install` して自分でインストールする
4. データが必要なら自分で取得するか、ユーザーに取得・配置を依頼する
5. どんな工夫をしても解決できない場合のみ、**理由を明記してダミー実装を許可**する

**ダミー実装の具体例（いずれも検出対象）:**

- `pass` のみの本体
- `raise NotImplementedError(...)` のみ
- ハードコードされた固定値の返却
- `TODO` 付きの仮実装（`# TODO: 本実装に差し替え`）
- `print` や `logging` だけで実処理がない
- 「仮」「暫定」「ダミー」等のコメント付き実装
- 設計書ロジック未実装（名前だけ合わせて中身が空）

## ステータス運用ルール（全モード共通）

全モードの報告は4ステータスのいずれかで返す。呼び出し元（fs-impl-phase4-execution (aide-powers skill) 等）は、このステータスに基づいて次のアクションを決定する。

| Status | 意味 | いつ返すか（判断基準） | 例 |
|---|---|---|---|
| **DONE** | 完全に完了、懸念なし | 依頼された全作業を実行し、結果に懸念事項がない場合 | 実装完了・試験書更新完了・全レビュー観点を自己チェック済み / テスト全パス（対象ユニットテスト）/ 外部ライブラリ問題なし |
| **DONE_WITH_CONCERNS** | 完了したが懸念事項あり | 作業は一応完了したが、呼び出し元が把握すべき懸念がある場合 | テストの一部を技術的理由でスキップした（例: 外部サービス接続系）/ ライブラリAPIの実際の挙動が設計書の記述と乖離していた（要設計同期）/ ファイルサイズが200行を超えた（分割検討が必要）/ 設計書に曖昧な箇所があり最も妥当と思われる解釈で実装した |
| **NEEDS_CONTEXT** | 不足情報があり作業を進められない | 呼び出し元から受け取った情報だけでは作業を完遂できない場合 | 設計書の該当セクションが存在しない / 依存先ファイルが指定されているが未実装 / 開発環境情報（dev-environment.md）が渡されていない / テスト観点が空欄で設計書から抽出できない |
| **BLOCKED** | 段階的対応が必要 | 他の作業完了を待たなければ進められない、または上位判断が必要な場合 | 依存先クラスが未実装で先に実装が必要 / 設計書と実装の乖離が大きく設計同期が必要 / 3回修正しても解決しないテスト失敗（pending-issues 登録を検討） / 外部ライブラリのAPI不一致で修正不能 |

**判断フロー（モード共通）:**

1. 依頼された全項目を完遂できたか？（情報の充足性）
   - NO（情報不足で着手できなかった）→ Status: NEEDS_CONTEXT
   - YES → 次へ
2. 依頼された全項目を完遂できたか？（着手後の完遂性）
   - NO（依存先未実装・段階的対応が必要）→ Status: BLOCKED
   - YES → 次へ
3. 完了した作業に呼び出し元が把握すべき懸念はあるか？
   - YES → Status: DONE_WITH_CONCERNS（懸念事項を明記）
   - NO → Status: DONE

**運用上のポイント:**

- `DONE_WITH_CONCERNS` と `BLOCKED` の違い:
  - `DONE_WITH_CONCERNS` は「一応完了したが注意が必要」→ 呼び出し元はレビューに進める
  - `BLOCKED` は「そもそも完了させられない」→ 呼び出し元は別タスク先行等の対応が必要
- `NEEDS_CONTEXT` を返した場合、呼び出し元は不足情報を追加して同じタスクを再度指示できる。同じ条件で再試行してはならない
- `BLOCKED` を返した場合、呼び出し元は①コンテキスト追加で再呼び出し ②タスクを分割 ③ユーザーにエスカレーション のいずれかを選択する
- 複数の状態が該当しうる場合は **より深刻な方** を選ぶ（例: 懸念事項がある + 情報不足 → `NEEDS_CONTEXT`）

| implement（親タスク完了チェック） | 設計書セクション全体読み込み済み・全項目照合完了・漏れ対応完了・報告出力済み |

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP** — 本スキルのルールを逸脱しようとしている:

| # | Red Flag | なぜ危険か |
|---|---|---|
| 1 | 「このファイル全体を一気に実装しよう」 | 粒度ルール違反。1呼び出し = 1 publicメソッドが原則 |
| 2 | 「複数ファイルをまとめて編集しよう」 | 粒度ルール違反。複数ファイル変更は分割する |
| 3 | 「クラスが小さいから複数メソッドをまとめよう」 | 粒度の基準は publicメソッド単位。サイズは関係ない |
| 4 | 「設計書を読まずに先に実装を始めよう」 | Iron Law 違反。設計書を読まずに実装を始めることは禁止 |
| 5 | 「設計書にないメソッドだけど便利だから追加しよう」 | 設計定義逸脱禁止。追加が必要なら設計同期を起動する |
| 6 | 「とりあえず pass で仮実装しておこう」 | ダミー実装禁止。実環境で動くコードを書く |
| 7 | 「ライブラリがないから NotImplementedError にしておこう」 | ダミー実装禁止。ライブラリは自分でインストールする |
| 8 | 「動作確認試験書の更新は後でまとめてやろう」 | mode: implement の完了時に必ず更新する。後回し禁止 |
| 9 | 「3ステップ以内だが別ファイルに書いておこう」 | 3ステップ以内は試験書に直接記載する。無駄な別ファイル化は避ける |
| 10 | 「既に似た試験項目があるから削除しよう」 | 項目削除禁止。`別項目(MT-XXX)で確認済み` と記載する |
| 11 | 「dev-environment.md に書いてないフレームワークを使おう」 | dev-environment.md に記載されたフレームワークを使うこと。記載がなければ言語標準を使用 |
| 12 | 「unittest.mock で外部依存をモックしよう」 | モック禁止。設計書定義のダミー実装をDI注入する |
| 13 | 「全パブリックメソッドにテストを書くのは冗長だ」 | パブリックメソッド全カバー必須。冗長ではなく網羅性の要件 |
| 14 | 「テスト実行で外部ライブラリエラーが出たから3回リトライしよう」 | 外部ライブラリ起因はリトライ不可。即報告する |
| 15 | 「テスト修正を4回5回やれば解決するはず」 | 3回で解決しなければ報告する。原因は別のところにある |
| 16 | 「レビュー指摘は要約して対応しよう」 | 指摘はそのまま転記・対応する。要約で情報を欠落させない |
| 17 | 「開発環境情報がないけど実装を始めよう」 | 開発環境情報不足時は実装を始めず報告する |
| 18 | 「テストファイルなしだがテスト書かずに動作確認しよう」 | テストファイル「なし」指定時は write_test/fix_test/run_test をスキップし報告する |
| 19 | 「設計と実装が矛盾するから設計書を直接書き換えよう」 | 設計変更は自分で行わない。報告して設計同期に委ねる |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「1つの publicメソッドだけじゃ効率が悪い」 | 小さい単位のレビュー・テストの方が修正コストが小さい。粒度ルールは効率化のためのルール |
| 「設計書読むの面倒だから、だいたい覚えている範囲で書こう」 | 記憶は不正確。設計書読み込みは全モードの前提条件。例外なし |
| 「docstring や型ヒントは後から付ければよい」 | 「後で」は来ない。初回実装で付ける |
| 「動作確認試験書なんてユーザーが書けばよい」 | 実装した本人が最も正確に「何を確認すべきか」を知っている。mode: implement の一部である |
| 「試験手順書は単純だから試験書に直接書いた方が楽」 | 3ステップ以内なら直接記載可。4ステップ以上は別ファイル化がルール |
| 「モックの方がテストが速く書けてメンテしやすい」 | モックは実装と実態の乖離を隠蔽する。設計書定義のダミーをDI注入するのがルール |
| 「外部ライブラリエラーは自分で直せないからスキップしてよい」 | スキップではなく即報告。対応はワークフロー／ユーザーの判断 |
| 「設計にないメソッドを一時的に追加するだけだから問題ない」 | 「一時的」は居残る。設計定義逸脱は即ブロックされる |
| 「ダミー実装でもレビューは通るはず」 | ダミー実装はコード品質レビューで即FAIL。レビューを通すためにも実環境で動かすこと |
| 「親タスク完了チェックは簡単だからざっと見るだけでよい」 | 全項目1項目ずつ照合する。ざっと見は漏れを見逃す |
| 「3回のテスト修正で解決しなくても、あと1回やれば絶対解決する」 | 3回で解決しないなら原因は別。報告して判断を仰ぐ |

## ワークフロー別差異

どのワークフローから呼ばれる場合でも、本スキルの粒度ルール・コーディング規約・動作確認試験書更新ルール・親タスク完了チェック・報告テンプレートは **共通で適用する**。ワークフロー別の差異は「参照する設計書の種類」と「追加の観点」のみであり、呼び出し元のフェーズスキルがテンプレート経由で指示する。
