## 処理手順

### phase10 モード

1. aide-powers:program-structure-design（新規作成モード）を読み込む

2. **ステップ1: 前提成果物の読み込み**
   - 以下の成果物を全て読み込み、設計に必要な情報を抽出する:
     - layered-architecture.md: レイヤー構成、依存ルール
     - object-design-*.md（全レイヤー）: 全クラス定義、インターフェース定義
     - infra-interface-design.md: 外部IF仕様
     - system-architecture.md: システム構成
     - gui-design.md: 画面構成

3. **ステップ2: フォルダ構成の設計**
   - ソースコードは src/ 配下、テストコードは tests/ 配下に配置する
   - レイヤードアーキテクチャの各層を src/ 配下のトップレベルフォルダとして反映する
   - 各層の中は機能ドメインごとにサブフォルダを切る
   - わかりやすいまとまりを優先し、深すぎるネストは避ける（最大3-4階層）

4. **ステップ3: ファイル配置の確定**
   - object-design-*.md の全クラスを1つずつ確認し、対応するファイルを配置する
   - 1ファイル1クラスを基本とする（小さなヘルパークラスは例外）
   - 1ファイルあたりの行数目安: 200行以下
   - **全クラスを漏れなく配置すること。1つでも漏れがあればゲート4でFAILになる**

5. **ステップ4: ファイル命名規則の適用**
   各言語の一般的な命名規則に従う:
   - **Python**: スネークケース（PEP 8準拠）
     - モジュール名: 短い全小文字のスネークケース
     - クラス名: パスカルケース
     - 1ファイル1クラスの場合: クラス名をスネークケースに変換
     - テストファイル: test_ プレフィックス
   - インターフェースファイル: 言語規則に従う
   - 特殊ファイル: __init__.py, config/, constants.py 等

6. **ステップ5: importルールの定義**
   - 各層のフォルダ間のimportルールを明確にする
   - 禁止されるimportパスを具体的に列挙する
     - 例: domain から infrastructure への import は禁止
     - 例: presentation から infrastructure への直接 import は禁止
   - 許可されるimportパスを明記する
     - 例: application から domain のインターフェースへの import は許可
     - 例: infrastructure から domain のインターフェースへの import は許可（実装のため）
   - レイヤー間の依存方向に基づく具体的なルールを定義する

7. **ステップ6: テストコードのディレクトリ構成**
   - tests/ 配下に src/ と同じ構造を反映する
   - テストファイルは対象ファイルと1対1で対応させる

8. **ステップ7: 設定ファイル・環境変数の管理方針**
   - 設定ファイルの配置場所を定義する
   - 環境変数の管理方針を定義する

9. **ステップ8: 成果物の作成**
   `.aide/specs/{feature_name}/program-structure.md` に以下を記載:
   - フォルダ構成ツリー（全ファイル含む）
   - 各フォルダの役割説明
   - 各ファイルの役割説明（1行）
   - ファイル命名規則のまとめ
   - importルール（許可/禁止パス）
   - テストコードのディレクトリ構成
   - 設定ファイル・環境変数の管理方針

10. **ステップ9: ユーザーへの説明と合意**
    - プログラム構成の内容をユーザーに提示する
    - フォルダ構成・ファイル命名規則・importルールについて確認する
    - ユーザーからの指摘があれば修正する
    - **合意後「プログラム構成確定」と明示する**

### fix モード

1. QA指摘内容を確認する
2. program-structure.md を Read で読み込む
3. 関連する object-design-*.md を Read で読み込む（ファイル配置漏れの確認に必要）
4. layered-architecture.md を Read で読み込む（importルールの整合性確認に必要）
5. 指摘された問題を修正する
6. 修正内容をユーザーに説明し、合意を得る
7. 修正により他の成果物との整合性が崩れていないことを確認する
8. 修正完了後「修正完了」と明示する

## 最重要ルール

1. object-design-*.md の全クラスを漏れなくファイルに配置すること。1つでも漏れがあればゲート4でFAILになる
2. importルールは具体的な禁止パスを列挙すること。「暗黙的に理解される」は不可
3. ファイル命名規則は言語の標準規則に厳密に従うこと
4. ユーザーにヒアリングしてから決定する。AIが勝手に構成を決めない
5. 合意プロセスは省略せず、必ずユーザーの明示的な承認を得ること
6. fix モードではQA指摘の修正のみを行う。スコープ外の変更は行わない
