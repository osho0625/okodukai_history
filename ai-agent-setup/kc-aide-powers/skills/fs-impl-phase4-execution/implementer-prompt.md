# Implementer Prompt Template

micro-impl-agent（agents/ 配下の名前付きエージェント）を呼び出す際のプロンプト構築テンプレート。
5つのモード（implement, fix, write_test, fix_test, run_test）に対応する。

---

## mode: implement（新規実装）

### 使い方

micro-impl-agent を mode: implement で呼び出す際に、以下のテンプレートの `{変数}` を埋めて Task でディスパッチする。

### テンプレート

```
### タスク情報
- タスク番号: {impl-task-list.md のタスク番号}
- タスク内容: {タスクの説明文}

### 実行モード
implement

### 対象ファイル
- 実装ファイル: {src/レイヤー/ファイル名.py}
- テストファイル: {tests/レイヤー/test_ファイル名.py}（なし の場合もある）

### 設計書（読むべきファイルとセクション）
- {設計書ファイルパス} → セクション: {該当クラス名}
- {プログラム構成書ファイルパス} → セクション: ファイル配置

### テスト観点
{設計書から抽出したテストケース一覧をそのまま転記}

### 依存先（実装済みファイル）
- {依存先ファイルパス}（{説明}）
（依存がない場合は「なし」）

### 開発環境情報
- 環境定義ファイル: {dev-environment.md のパス}
- **このファイルを必ず Read で読み込み、実行環境・実行コマンド・開発ルールに従うこと**

## 実装ルール（micro-impl-agent が従うべきルール）
- 設計書を読んでから実装を始めること（設計書を読まずに実装を始めることは禁止）
- 1回の呼び出しで実装するのは1つのpublicメソッド（+ 関連するprivateメソッド・ヘルパー）が最大単位
- メソッドのないクラスは1クラス単位で実装する
- 1回の呼び出しで変更するファイルは1つだけ
- 設計定義にないメソッドやプロパティを追加しない
- 設計定義と異なるシグネチャで実装しない
- 動作確認試験書（testing/manual-test-plan.md）に試験項目を追記すること

## 報告フォーマット
- Status: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
- 実装内容
- 変更ファイル
- 動作確認試験書の更新内容
- 懸念事項（該当する場合）
```

## mode: implement（親タスク完了チェック）

### 使い方

全サブタスク完了後、親タスクの設計書セクション全体を指定して漏れチェックを行う際に使用する。

### テンプレート

```
### タスク情報
- 親タスク番号: {親タスク番号}
- チェック内容: 設計書の該当セクション全体を読み、実装済みコードと照合して、漏れがあれば追加実装する

### 実行モード
implement（親タスク完了チェック）

### 対象ファイル
- 実装ファイル: {src/レイヤー/ファイル名.py}

### 設計書（読むべきファイルとセクション）
- {設計書ファイルパス} → セクション: {該当クラス名}（セクション全体）

### 指示
設計書の該当セクション全体を読み、実装済みコードと照合してください。
- 漏れがあれば追加実装してください
- 漏れがなければ「漏れなし」と報告してください

### 開発環境情報
- 環境定義ファイル: {dev-environment.md のパス}
- **このファイルを必ず Read で読み込み、実行環境・実行コマンド・開発ルールに従うこと**

## 報告フォーマット
- Status: DONE（漏れなし）| DONE（追加実装あり）| NEEDS_CONTEXT | BLOCKED
- 漏れの有無
- 追加実装内容（該当する場合）
- 変更ファイル（該当する場合）
```

## mode: fix（レビュー指摘修正）

### 使い方

2段階レビューでFAILが出た場合に、レビュー指摘内容をそのまま転記して修正を依頼する。

### テンプレート

```
### タスク情報
- タスク番号: {タスク番号}

### 実行モード
fix

### 対象ファイル
- 実装ファイル: {src/レイヤー/ファイル名.py}

### レビュー指摘内容
#### design-review-agent からの指摘（{PASS/FAIL}）
{指摘内容をそのまま転記。PASSの場合は「指摘なし」}

#### code-review-agent からの指摘（{PASS/FAIL}）
{指摘内容をそのまま転記。PASSの場合は「指摘なし」}

### 開発環境情報
- 環境定義ファイル: {dev-environment.md のパス}

## 修正ルール
- レビュー指摘内容に従って修正すること
- 指摘されていない箇所を変更しないこと

## 報告フォーマット
- Status: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
- 修正内容
- 変更ファイル
- 懸念事項（該当する場合）
```

## mode: write_test（テスト作成）

### 使い方

実装コードのレビューがPASSした後、テストコードを作成する際に使用する。

### テンプレート

```
### タスク情報
- タスク番号: {タスク番号}

### 実行モード
write_test

### 対象ファイル
- 実装ファイル: {src/レイヤー/ファイル名.py}
- テストファイル: {tests/レイヤー/test_ファイル名.py}

### 設計書（テスト観点の参照元）
- {設計書ファイルパス} → セクション: {該当クラス名}

### テスト観点
{設計書から抽出したテストケース一覧をそのまま転記}

### 開発環境情報
- 環境定義ファイル: {dev-environment.md のパス}
- **このファイルを必ず Read で読み込み、実行環境・実行コマンド・開発ルールに従うこと**

## テスト作成ルール
- 設計書のテスト観点セクションの全ケースをカバーすること
- 全パブリックメソッドにテストを書くこと
- モック・スタブ禁止（unittest.mock は使わない）
- 外部インフラ依存のテストでは設計書で定義されたダミー実装をDI経由で注入すること
- 境界値テスト、異常系テストを含めること

## 報告フォーマット
- Status: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
- テスト内容
- 変更ファイル
- 懸念事項（該当する場合）
```

## mode: run_test（テスト実行）

### 使い方

テストコードのレビューがPASSした後、テストを実行する際に使用する。

### テンプレート

```
### タスク情報
- タスク番号: {タスク番号}

### 実行モード
run_test

### 対象ファイル
- テストファイル: {tests/レイヤー/test_ファイル名.py}

### テスト実行コマンド（必須）
- ユニットテスト: {dev-environment.md に記載のテスト実行コマンド} {テストファイルパス}

※ 必ず仮想環境内のPythonを使用すること。グローバルのpythonやpytestを直接使用してはならない。

### 開発環境情報
- 環境定義ファイル: {dev-environment.md のパス}
- **このファイルを必ず Read で読み込み、実行環境・実行コマンド・開発ルールに従うこと**

## テスト実行ルール
- ユニットテストを実行し、全パスを確認すること
- 失敗があれば原因を特定し、実装またはテストを修正すること
- 外部ライブラリ起因の場合はリトライせず即報告すること
- 3回修正しても解決しない場合は報告すること

## 報告フォーマット
- Status: DONE（全パス）| DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
- テスト実行結果（パス数/失敗数）
- 失敗テストの詳細（該当する場合）
- 修正内容（修正した場合）
```
