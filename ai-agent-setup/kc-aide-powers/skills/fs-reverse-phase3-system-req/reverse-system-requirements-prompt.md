## 解析プロセス

以下の7ステップを順番に実行し、最後に成果物を作成してユーザーの合意を得ること。

### ステップ1: アプリケーション形態の特定

コードの import 文と設定ファイルから以下を判定する:

| 形態 | 判定基準 |
|---|---|
| GUI | `tkinter`, `ttk`, `PyQt5`, `PyQt6`, `PySide2`, `PySide6`, `wxPython`, `kivy` 等の import |
| Web | `Flask`, `Django`, `FastAPI`, `Starlette`, `aiohttp`（サーバー側）等の import |
| CLI | `argparse`, `click`, `typer`, `fire` 等の import、または `if __name__ == "__main__"` のみ |
| API | REST/GraphQL エンドポイントの定義（`@app.route`, `@router.get` 等） |
| ライブラリ | `setup.py` / `pyproject.toml` でパッケージとして配布される構成（`[project]` セクション等） |
| バッチ/スクリプト | 定期実行・一括処理を目的としたスクリプト群 |
| 複合型 | 上記の複数に該当する場合（例: Web + CLI） |

### ステップ2: 技術スタックの抽出

`dev-environment.md` の依存パッケージ一覧と実際の import 文から技術スタックを整理する。

| 分類 | 抽出対象 | 記載内容 |
|---|---|---|
| 言語・ランタイム | Python バージョン | バージョン番号、`dev-environment.md` への参照 |
| フレームワーク | GUI / Web / CLI フレームワーク | フレームワーク名、バージョン、用途 |
| データ管理 | DB ライブラリ、ORM、ファイル形式 | ライブラリ名、用途、接続方式 |
| テスト | テストフレームワーク、モックライブラリ | フレームワーク名、設定、フィクスチャ |
| ユーティリティ | ログ、設定管理、日付処理等 | ライブラリ名、用途 |
| 外部サービス連携 | API クライアント、SDK等 | サービス名、クライアントライブラリ、認証方式 |

**注意:** 外部パッケージ（pip install するもの）と外部サービス（API呼び出し先）は明確に区別すること。

### ステップ3: データ管理方式の抽出

| データ管理方式 | 抽出項目 |
|---|---|
| データベース | 使用DB（SQLite, PostgreSQL, MySQL等）、接続文字列の管理方法、ORM設定（SQLAlchemy等）、マイグレーション方式、テーブル定義 |
| ファイルベース | 読み書きしているファイル形式（JSON, CSV, YAML, TOML等）、ファイルパスの決定方法、データのスキーマ（構造）、読み書きの排他制御、エラーハンドリング |
| メモリ | インメモリキャッシュの使用、辞書ベースのストレージ、永続化の有無 |
| データの保存場所 | ファイルパス、DB名、ディレクトリ構成 |

### ステップ4: エラーハンドリング方針の抽出

| 抽出カテゴリ | 抽出項目 |
|---|---|
| 例外クラスの定義 | カスタム例外クラスの一覧、例外の階層構造（基底クラス → 派生クラス）、各例外の用途・発生条件 |
| try/except パターン | どの層でどのような例外をキャッチしているか、例外の変換パターン（インフラ例外 → ドメイン例外等）、リトライ処理の有無と実装方式 |
| ユーザー向けエラー表示 | エラーダイアログ / エラーメッセージの表示方式、技術的詳細の隠蔽度合い、エラーコードの使用有無 |

### ステップ5: ログ出力方針の抽出

| 抽出項目 | 詳細 |
|---|---|
| ログライブラリ | `logging` モジュール / `print` / サードパーティ（loguru等） |
| ログ設定 | `logging.basicConfig`, `dictConfig`, カスタム設定、設定ファイルの有無 |
| ログレベルの使い分け | DEBUG, INFO, WARNING, ERROR, CRITICAL の実際の使用状況 |
| ログ出力先 | ファイル / 標準出力 / 標準エラー出力 / 両方 |
| ログフォーマット | 実際に使われているフォーマット文字列 |
| ログローテーション | RotatingFileHandler / TimedRotatingFileHandler 等の使用 |

### ステップ6: セキュリティ要件の抽出

| 抽出項目 | 詳細 |
|---|---|
| 認証・認可 | 認証方式（トークン、セッション、OAuth等）、認可の実装（ロールベース等）、該当なしの場合はその旨を記録 |
| 機密情報の管理 | 環境変数の使用、設定ファイルでの管理、ハードコードの有無、`.env` ファイルの使用 |
| 入力バリデーション | バリデーションの実装箇所、バリデーションライブラリの使用（pydantic等）、サニタイズ処理 |

**注意:** セキュリティ要件がない場合でも省略しないこと。「認証・認可の実装なし」「機密情報のハードコードあり」等、現実をそのまま記録する。

### ステップ7: 非機能要件の推定

| 抽出項目 | 推定方法 |
|---|---|
| パフォーマンス | スレッド（`threading`）/ プロセス（`multiprocessing`）/ 非同期処理（`asyncio`）の使用状況、キャッシュの使用、バッチ処理の有無 |
| スケーラビリティ | 設定の外部化の度合い、プラグイン機構の有無、モジュール分割の粒度 |
| 保守性 | テストカバレッジ（テストファイルの充実度）、型ヒントの使用率、ドキュメント文字列（docstring）の充実度、コード規約の遵守度 |

**注意:** 推定であることを明記して記載すること。コードから読み取れる範囲で推定する。

## 成果物の作成

### 出力先

`.aide/specs/{feature_name}/system-requirements.md`

### 記載セクション

以下のセクションを全て含めること:

1. **システム構成概要**: アプリケーション形態、全体構成の概要
2. **技術スタック**: 言語、フレームワーク、ライブラリ一覧（用途付き）
3. **データ管理**: データベース / ファイル / メモリの使用状況
4. **エラーハンドリング方針**: 例外クラス体系、エラー伝播ルール、ユーザー向け表示
5. **ログ出力方針**: ログライブラリ、レベル定義、出力先、フォーマット
6. **セキュリティ要件**: 認証、機密情報管理（該当する場合）
7. **非機能要件**: パフォーマンス、保守性等

## ユーザー確認の手順

成果物を作成したら、ユーザーに提示して以下を確認する:

1. 技術スタックの記載に漏れがないか
2. エラーハンドリング方針が実態と合っているか
3. 記載されていない制約や要件がないか

### visual-companion の活用

システム構成概要図（技術スタック関係図・データフロー図）や外部サービス連携図をユーザーに提示・確認する際は、`visual-companion (aide-powers skill)` を activate してブラウザで図示するとよい。文字だけの説明よりも図で見せた方がわかりやすい場面（コンポーネント間の依存関係、データの流れ、外部サービスとの連携構成等）では積極的に活用する。

なお、図示はあくまでユーザーとの確認を補助する手段であり、成果物は従来どおり `system-requirements.md` に記録すること。

確認の際は以下の形式で提示する:

```
`system-requirements.md` を作成しました。以下の点をご確認ください:

1. 技術スタックの記載に漏れはありませんか？
2. エラーハンドリング方針は実態と合っていますか？
3. 他に記載すべき制約や要件はありますか？

ご確認の結果を教えてください:
1. 問題なし（システム要件逆引き完了）
2. 修正が必要（具体的にお知らせください）
3. その他（自由記述）
```

合意を得たら「システム要件逆引き完了」と明示すること。

## 運用ルール

- 質問は1つずつ投げること
- コードの現実を記録すること（理想の設計ではない）
- 成果物作成後、ユーザーに提示して合意を得ること
- ユーザーに選択を求めるときは番号付き選択肢で提示すること（最後に「その他（自由記述）」を含める）
- ユーザーとの会話は日本語を使うこと
- `dev-environment.md` と内容が重複する部分（Python バージョン等）は、参照で済ませてよい
- 外部パッケージと外部サービスを混同しないこと
- コードに実装されていない要件（将来の計画等）は記載しない
- ログ出力が `print` のみの場合でも、そのまま記録する（改善提案は別途コメントとして記載可）
- **サブエージェントをさらに起動しないこと**（自身がサブエージェントとして呼び出されているため、さらなる委譲は禁止）
