# Design Sync（設計同期）

## Overview

設計書と実装が矛盾したら、どちらかを修正して同期を取れ。放置するな。

**Core principle:** 設計書は実装の正（Single Source of Truth）である。乖離が発生したら、実装を設計に合わせるか、設計を実装に合わせるか、必ずどちらかを選択して同期する。乖離を放置したまま次のステップに進むことは許されない。

## The Iron Law

```
NO DIVERGENCE WITHOUT SYNCHRONIZATION
— 設計書と実装の乖離を、同期なしに放置してはならない
```

種別: **Rigid**（厳密遵守）

## Design Sync Process

**Exceptions:**
- 設計書が存在しないプロジェクト（→ design-gate (aide-powers skill) の範囲）
- 乖離が設計同期で対応しきれない根本的な問題（→ `pending-issues.md` に記録）

### Phase 1: 乖離の検出と分類

乖離の報告を受け取り、問題の本質を特定する。

**入力**: レビュー結果、実装報告、テスト結果のいずれか

**分類基準**:

| 分類 | 影響範囲 | 判定基準 |
|---|---|---|
| 軽微 | 1クラス以内 | シグネチャの微修正、型の変更、引数の追加 |
| 中程度 | 複数クラス | クラスの責務変更、メソッド追加/削除、インターフェース変更 |
| 重大 | レイヤーをまたぐ | レイヤー構成の変更、アーキテクチャレベルの変更 |

**影響範囲の調査**:
- どのクラス・メソッド・レイヤーに波及するかを特定する
- 依存先を再帰的にたどり、影響範囲を過小評価しない
- 既に実装済み・テスト済みのコードへの影響を必ず確認する

### Phase 2: 乖離種別の判定

乖離が「設計漏れ」か「実装誤り」かを判定する。

```
乖離検出 → 乖離種別の判定
  ├─ 実装誤り（FAIL_IMPL）: 設計書が正しく、実装が設計に準拠していない
  │   → 実装を設計に合わせて修正（fix→再レビュー）
  └─ 設計漏れ（FAIL_PENDING→種別確定後）: 実装が正しく、設計書が実態を反映していない
      → Phase 3 へ（設計書更新フロー）
```

**判定基準**:
- 設計書の定義が技術的に正しく実装可能 → FAIL_IMPL（実装を修正）
- 実装上の制約・ライブラリAPIの実態・パフォーマンス要件により設計書の定義が不適切 → FAIL_DESIGN（設計書を修正）

**設計漏れ判定の対象外**（常に FAIL_IMPL = 実装修正が必要）:
- バリデーション条件と例外送出
- importルール違反

### Phase 3: 設計書修正案の作成と適用

1. **修正案の作成**:
   - 設計書のどの箇所をどう修正するかを明示する
   - 修正による影響範囲を列挙する
   - 既に実装済みのコードへの影響を報告する

2. **ユーザーへの提示**:
   - 問題の内容（何が乖離しているか）
   - 修正案（設計書をどう変えるか）
   - 影響範囲（どのタスク・コードに影響するか）

3. **承認判定**:
   - 承認 → Phase 4 へ
   - 却下 → 代替案を検討、または実装を設計に合わせて修正

### Phase 4: 設計書の更新

承認後、該当する設計書を更新する。

**更新対象の決定ルール**:
- **ワークフロー実装中**: 作業中の設計書（差分設計書）を修正する
  - 既存設計書はワークフロー最終フェーズの設計書反映プロセスで更新する
- **新規実装中**: 既存設計書を直接修正する

**更新内容の記録**:
- 進捗管理ドキュメントに設計同期の履歴を記録する
- 記録内容: 起因、分類、変更内容、影響タスク、ユーザー承認状況

### Phase 5: タスクリストの再構築

設計変更の影響を受けるタスクを特定し、タスクリストを更新する。

1. **影響タスクの特定**: 修正した設計書セクションに関連するタスクを検索
2. **再実装マーキング**: 完了済みタスクで再実装が必要なものを「要修正」としてマーク
3. **新規タスクの追加**: 設計変更により新たに必要になったタスクを追加
4. **依存関係の再計算**: タスク間の依存関係を再計算し、実行順序を更新

**並列実行時の特別ルール**:
- 並列実行中に設計同期が必要になった場合、他の並列タスクを一時停止する
- 設計同期完了後に並列タスクを再開する

## Red Flags — STOP

以下の思考パターンを検出したら **STOP** — 設計同期スキルを発動せよ:

| # | Red Flag | 正しい対応 |
|---|---|---|
| 1 | 「設計漏れだが軽微だから設計書更新は後でいい」 | 設計漏れ検出時の設計書更新は即座に実行する。乖離を放置しない |
| 2 | 「軽微な差分だから設計書はそのままでいい」 | 軽微でも乖離は乖離。設計書を更新する |
| 3 | 「設計書の修正は面倒だから、実装だけ直して先に進もう」 | 設計書 = 実装の正。設計書を更新しないと次の乖離を生む |
| 4 | 「テストが通っているから設計との差分は問題ない」 | テスト通過と設計準拠は別の品質軸。設計同期は必須 |
| 5 | 「コンテキストが大きくなってきたので設計同期は省略する」 | コンテキスト管理は省略の理由にならない |
| 6 | 「ユーザーが急いでいるので設計書更新はスキップする」 | 時間的制約で品質プロセスは省略できない |
| 7 | 「設計書にないpublicメソッドを追加したが、便利だから残す」 | 設計書に追記するか、メソッドを削除する。未定義の追加は放置しない |

## Common Rationalizations

| Excuse | Reality |
|--------|---------|
| 「設計漏れを検出すれば終わり」 | 検出は第一歩。設計書の同期更新まで完了して初めて終わり |
| 「設計書の更新は最後にまとめてやる」 | 乖離が蓄積すると追跡不能になる。発見時に即座に同期する |
| 「実装が正しいのだから設計書は古くてもいい」 | 設計書が古いと、次の実装者が間違った設計に基づいて実装する |
| 「影響範囲は小さいから再構築は不要」 | 影響範囲を過小評価すると、後続タスクで再び乖離が発生する |
| 「テストが全部通っているから大丈夫」 | テストは実装の正しさを保証するが、設計との整合性は保証しない |
| 「差分設計書を直せば既存設計書は自動的に反映される」 | 差分設計書の修正と既存設計書への反映は別プロセス。両方必要 |

## Integration

**Required workflow skills（設計同期が呼び出される元）:**
- **multi-stage-code-review (aide-powers skill)**: レビューで乖離が検出された場合に設計同期を起動
- 各ワークフローの実装フェーズスキル: 実装中に乖離が発覚した場合に設計同期を起動

**Related skills:**
- **design-gate (aide-powers skill)**: 設計書の存在確認（設計同期の前提条件）
- **doc-index-maintenance (aide-powers skill)**: 設計書更新後のインデックス更新

**Called by（設計同期を起動するタイミング）:**
- 実装ワークフロー: 各タスクのレビュー結果受領後
- 変更ワークフロー: フェーズ8（差分実装）のレビュー結果受領後
- バグ修正ワークフロー: フェーズ5（実装）のレビュー結果受領後
- リファクタリングワークフロー: フェーズ4（実装）のレビュー結果受領後
