# Usecase Analysis

## Overview

要件を実現するユースケースを網羅的に洗い出し、実現プロセスとユーザビリティを評価して改善せよ。

**Core principle:** ユースケース分析は、要件定義後・詳細設計前に実行する4段階プロセスである。利用者の目的をベースにUCを網羅的に洗い出し、各UCの実現プロセスを明確化し、ユーザビリティを定量的に評価し、低評価UCを改善する。改善は評価が収束するまでループする（最大3回）。

## Usecase Analysis Pipeline

**Adapt to context:**
- 評価基準の数値（ステップ数の閾値等）はプロジェクトの性質に応じて調整してよい
- 改善ループの継続/終了はユーザーとの対話で判断する
- UCの粒度はプロジェクトの規模に応じて調整する

**Skip conditions (ask your human partner):**
- 非常に小規模なプロジェクト（UC数が3件以下）で、ユーザーが省略を希望する場合
- プロトタイプ段階で、正式なUC分析が不要と判断される場合

### 工程①: UC網羅リストアップ

ユーザー要件・システム要件から、利用者がシステムを使って行うユースケースを網羅的に洗い出す。

汎用サブエージェントに委譲する。
プロンプトテンプレート: `usecase-lister-prompt.md`（要件ドキュメントのパスを渡す）

最重要原則: ユースケースは「利用者の目的（やりたいこと）」として記述する。機能定義やシステム操作手順ではない。

具体的な抽出方法・利用者の特定手順・最終チェック事項・成果物フォーマットはプロンプトテンプレートに定義。

**プロセス制御:**
- ユーザー合意が必須。合意なしに次工程に進まない
- 「他にやりたいことはないか」「これは不要か」を確認する
- 利用者の分類、UCの粒度、優先度を確認する

**出力:** ユースケース一覧ドキュメント

### 工程②: 実現プロセス明確化（UC単位、並列実行可能）

各UCの実現プロセス（操作手順・フロー）を明確化する。

汎用サブエージェントに委譲する（UC単位で並列実行可能）。
プロンプトテンプレート: `usecase-process-analyzer-prompt.md`（対象UC情報・参照ドキュメントのパスを渡す）

具体的な必須項目7つ・任意項目3つ・GUI設計との整合性確認手順・成果物フォーマットはプロンプトテンプレートに定義。

**プロセス制御:**
- UC単位で並列実行可能
- 各担当は指定されたUCのみを扱い、他のUCには触れない
- 全UCの実現プロセスが完了してから工程③に進む

**出力:** UC単位の詳細ドキュメント（実現プロセス部分）

### 工程③: ユーザビリティ評価（UC単位、並列実行可能）

各UCのユーザビリティを5観点×4段階で定量的に評価する。

汎用サブエージェントに委譲する（UC単位で並列実行可能）。
プロンプトテンプレート: `usecase-usability-evaluator-prompt.md`（対象UC情報・参照ドキュメントのパスを渡す）

5つの評価観点（操作ステップ数、認知負荷、エラー回復性、直感性、効率性）の具体的なA〜D基準テーブル・評価根拠の記述ルール・成果物フォーマットはプロンプトテンプレートに定義。

**総合評価の算出ルール:**
- D が1つでもあれば → 総合D
- C が2つ以上あれば → 総合C
- B が3つ以上あれば → 総合B
- それ以外 → 総合A

**プロセス制御:**
- UC単位で並列実行可能
- 各担当は指定されたUCのみを扱い、他のUCには触れない
- 評価に集中し、改善提案はしない（改善は工程④の範囲）
- 全UCの評価が完了してから工程④に進む

**出力:** UC単位の詳細ドキュメント（ユーザビリティ評価部分を追記）

### 工程④: 改善検討・最終まとめ

低評価UC（総合C以下）の改善案を検討し、全体の分析レポートを作成する。

汎用サブエージェントに委譲する。
プロンプトテンプレート: `usecase-improver-prompt.md`（全UC評価結果・参照ドキュメントのパスを渡す）

改善パターン6種の詳細・問題の本質分析手法・GUI設計への影響評価手順・成果物フォーマットはプロンプトテンプレートに定義。

**プロセス制御:**
- ユーザー承認が必須。承認なしに改善反映（工程⑤）に進まない
- 全UCがB以上でも、分析レポート（サマリー、次フェーズへの申し送り）は作成する
- 改善案の承認時に、GUI設計への影響も合わせて確認する

**出力:** ユースケース分析レポート

### 工程⑤: 改善反映（改善対象UCがある場合のみ）

改善対象UCの成果物修正と再評価ループを実行する。

**実行条件:** 分析レポートにC以下のUCが1件以上あり、ユーザーが改善案を承認した場合のみ。
**スキップ条件:** 全UCがB以上の場合、またはユーザーが「改善不要」と判断した場合。

**手順:**

1. 影響範囲を判定し、影響を受ける成果物を特定する
   - 「システム構成の変更が必要」→ システム構成設計書
   - 「GUI設計フィードバック」に項目あり → GUI設計書
   - 「UCの追加・削除・統合が必要」→ ユースケース一覧
2. 影響を受ける成果物を修正する（修正順序: システム構成設計 → GUI設計 → UCリスト）
3. 各修正後、ユーザー合意を得る
4. 改善対象UCについて再評価を実施する:
   - 工程②を再実行（プロンプトテンプレート `usecase-process-analyzer-prompt.md` を再利用）
   - 工程③を再実行（プロンプトテンプレート `usecase-usability-evaluator-prompt.md` を再利用）
5. 分析レポートに再評価結果を追記する（既存内容は保持、追記のみ）
6. ループ判定:
   - 全UCがB以上 → 完了
   - まだC以下のUCがある → ユーザーに報告し、再ループ（最大3回）
   - 3回で収束しない場合 → ユーザーに判断を仰ぐ

### Subagents and Prompt Templates

| 工程 | 役割 | プロンプトテンプレート | 並列実行 |
|---|---|---|---|
| ① UC網羅リストアップ | UCリスト作成 | `usecase-lister-prompt.md` | 不可 |
| ② 実現プロセス明確化 | UC詳細化 | `usecase-process-analyzer-prompt.md` | UC単位で可 |
| ③ ユーザビリティ評価 | UC評価 | `usecase-usability-evaluator-prompt.md` | UC単位で可 |
| ④ 改善検討・最終まとめ | 改善提案 | `usecase-improver-prompt.md` | 不可 |

プロンプトテンプレートは設計ワークフローのフェーズスキルディレクトリ直下に配置される。
各工程の具体的な手順・チェック項目・成果物フォーマットはプロンプトテンプレートに定義する。

**注記:** usecase-analysis は `agents/` 配下の名前付きエージェントを使用しない。全工程が汎用サブエージェント + プロンプトテンプレートで実行される。これは multi-stage-code-review (aide-powers skill)（`agents/design-review-agent` 等の名前付きエージェントを使用）とは異なる設計判断である。名前付きエージェントは複数ワークフローから共通利用される場合に定義するが、ユースケース分析の各工程は設計ワークフロー専用であり、プロンプトテンプレートによる委譲で十分である。

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。ユースケース分析の品質を損なおうとしている。

| Red Flag | なぜ危険か |
|---|---|
| 「機能一覧をそのままUCリストにすればよい」 | UCは利用者の目的であり、機能定義ではない。機能をUCに変換すると、利用者の視点が失われる |
| 「UCが少ないから評価は不要」 | UC数に関わらず、ユーザビリティ評価は必要。少数のUCでも低品質なら問題 |
| 「評価がC以下だが改善案が思いつかないのでスキップする」 | 改善案が思いつかない場合はユーザーに相談する。スキップは品質劣化の原因 |
| 「全UCがB以上だから工程④は不要」 | 全UCがB以上でも、分析レポート（サマリー、次フェーズへの申し送り）は作成する |
| 「改善ループが面倒だから1回で終わりにする」 | C以下のUCが残っている場合、ユーザーの判断なしにループを打ち切らない |
| 「GUI設計がまだないからUC分析を先にやる」 | GUI設計はUCの評価・改善で参照する。GUI設計完了後にUC分析を実行すること |
| 「要件定義の内容をそのままUCにコピーする」 | 要件定義の文言をそのままUCにするのではなく、利用者の目的に翻訳する |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「UCリストは要件定義で十分カバーされている」 | 要件定義はシステムの仕様を記述するもの。UCは利用者の目的を記述するもの。視点が異なる |
| 「ユーザビリティ評価は主観的で意味がない」 | 5観点×4段階の定量基準があり、根拠を明記することで客観性を担保する |
| 「改善ループは時間の無駄」 | 低品質なUCのまま詳細設計に進むと、後工程で大きな手戻りが発生する。改善は投資 |
| 「並列実行できるから全部一度にやればよい」 | 工程間の依存関係を守る必要がある。①→②→③→④の順序は固定 |
| 「小規模プロジェクトだからUC分析は不要」 | 小規模でも利用者の目的を明確にすることで、設計の方向性が定まる。省略はユーザーと相談 |

## Integration

**Required input documents:**
- ユーザー要件定義書（合意済み）
- システム要件定義書（合意済み）
- GUI設計書（合意済み）
- システム構成設計書（工程②の参照用）

**Called by:**
- 設計ワークフロー（GUI設計完了後、アーキテクチャ設計の前）

**Triggers (improvement feedback):**
- GUI設計の修正（改善反映でGUI設計への変更が必要な場合）
- システム構成設計の修正（改善反映でシステム構成の変更が必要な場合）

**Related skills:**
- `doc-index-maintenance` (aide-powers skill) — ユースケース関連ドキュメント作成時のインデックス更新
