## 処理手順

### phase9 モード

1. **前フェーズ成果物の読み込みと設計対象の特定**

   以下の観点で各成果物を分析する:
   - user-requirements.md: Must要件から外部IF要件を把握
   - system-requirements.md: 技術スタック、データ管理方式、外部サービス依存を把握
   - system-architecture.md: アーキテクチャ図から外部IF・データストア・外部サービスの接続先を把握
   - gui-design.md: UIイベントとアプリケーション層の連携ポイントを把握
   - layered-architecture.md: DDD採用/不採用の確認、レイヤー間依存ルールの把握
   - object-design-domain.md: ドメインオブジェクト（エンティティ、値オブジェクト、集約）の構造を把握。リポジトリインターフェースの定義を把握
   - object-design-infrastructure.md: インフラ層のクラス構成、リポジトリ具象実装の概要を把握

   設計対象の一覧を作成し、ユーザーに確認する。特に以下を確認:
   - 外部サービス連携の有無
   - データストアの種類
   - API/CLI/GUIのどれが該当するか

2. **DDD採用/不採用に応じた設計方針の決定**

   layered-architecture.md のDDD採用判断結果を確認し、以下の方針を適用する:

   **DDD採用時の設計方針:**
   - ドメインオブジェクトと永続化スキーマは明確に分離する
   - APIのリクエスト/レスポンスにはDTO（Data Transfer Object）を使用し、ドメインオブジェクトを直接公開しない
   - リポジトリの具象実装はドメイン層のインターフェースに忠実に従う
   - データマッピング（ドメインオブジェクト ↔ 永続化形式）の変換ルールを明確に定義する

   **DDD不採用時の設計方針:**
   - サービス層のデータ構造をそのままAPI/永続化に使用してよい
   - 過度な抽象化は避け、シンプルな変換で済ませる
   - 将来DDDが必要になった場合にサービス層からドメイン層を分離できる余地は残す

3. **API定義の設計（該当する場合）**

   **REST API の場合:**
   - エンドポイント一覧（メソッド、パス、概要）をテーブル形式で定義
   - リクエスト/レスポンスのスキーマ（JSON Schema形式）を定義
   - ステータスコードとエラーレスポンスの定義（正常系・異常系を網羅）
   - 認証・認可の方式（system-requirements.md のセキュリティ要件に基づく）
   - バージョニング方針（URLパス方式 / ヘッダー方式等）
   - CORS設定（該当する場合）

   **CLI の場合:**
   - コマンド一覧（サブコマンド、オプション、引数）をテーブル形式で定義
   - 入出力フォーマット（標準入力/出力、ファイル）を定義
   - 終了コードの定義（0: 正常、1: エラー等）
   - ヘルプテキストの構成（--help の出力内容）

   **GUI の場合（イベントインターフェース）:**
   - UIイベントとアプリケーション層の呼び出し対応表を定義
   - コールバック/イベントハンドラの定義（イベント名、引数、戻り値）
   - スレッド管理方針（UIスレッドとバックグラウンドスレッドの分離）

4. **データストアスキーマ定義の設計（該当する場合）**

   **RDB の場合:**
   - テーブル定義（カラム名、型、制約、インデックス）をテーブル形式で定義
   - ER図（Mermaid erDiagram 記法）
   - マイグレーション方針（初期スキーマ作成方法、スキーマ変更手順）
   - ドメインオブジェクトとテーブルの対応関係

   **ファイルベースの場合:**
   - ファイル形式（JSON、CSV、YAML等）とスキーマ（各フィールドの型・制約）
   - ディレクトリ構成とファイル命名規則
   - 読み書きの排他制御方針（ファイルロック、一時ファイル経由の書き込み等）
   - ファイルサイズの上限・分割方針（該当する場合）

   **KVS / NoSQL の場合:**
   - キー設計とアクセスパターン
   - データモデル（ドキュメント構造等）
   - インデックス設計（該当する場合）

5. **外部サービス連携定義の設計（該当する場合）**
   - 外部API呼び出し仕様（エンドポイント、認証方式、レート制限）
   - 外部ライブラリのラッパーインターフェース（ライブラリの型をドメイン層に漏洩させない）
   - モデル推論インターフェース（入力形式、出力形式、エラーハンドリング）— 該当する場合
   - リトライ方針（リトライ回数、バックオフ戦略、リトライ対象のエラー種別）
   - タイムアウト方針（接続タイムアウト、読み取りタイムアウト）
   - サーキットブレーカー方針（該当する場合）

6. **リポジトリインターフェース定義の設計**
   - object-design-domain.md で定義された各リポジトリインターフェースに対する具象クラスの実装方針
   - データマッピング（ドメインオブジェクト ↔ 永続化形式）の変換ルール
     - 各ドメインオブジェクトのフィールドと永続化形式のフィールドの対応表
     - 型変換ルール（例: 値オブジェクト → プリミティブ型）
     - ネストされたオブジェクトの扱い（フラット化 / JSON化 / 別テーブル等）
   - クエリ/フィルタリングの実装方針
     - 検索条件の組み立て方
     - ページネーション方針（該当する場合）
     - ソート方針（該当する場合）

7. **成果物作成**

   `.aide/specs/{feature_name}/infra-interface-design.md` に以下の構成で作成する:

   ```markdown
   # インフラ/インターフェース設計

   ## 0. 設計対象の一覧
   （どのインターフェースが該当するかの一覧）

   ## 1. API定義（該当する場合）
   ### 1.1 エンドポイント一覧 / コマンド一覧 / UIイベント対応表
   ### 1.2 リクエスト/レスポンス定義 / 入出力フォーマット
   ### 1.3 エラーハンドリング / 終了コード
   ### 1.4 認証・認可（該当する場合）

   ## 2. データストアスキーマ定義（該当する場合）
   ### 2.1 テーブル定義 / ファイルスキーマ / キー設計
   ### 2.2 ER図 / ディレクトリ構成
   ### 2.3 マイグレーション方針 / 排他制御方針

   ## 3. 外部サービス連携定義（該当する場合）
   ### 3.1 外部API仕様
   ### 3.2 ラッパーインターフェース
   ### 3.3 リトライ・タイムアウト方針

   ## 4. リポジトリ具象実装方針
   ### 4.1 各リポジトリの実装方針
   ### 4.2 データマッピングルール
   ### 4.3 クエリ/フィルタリング方針
   ```

8. **ユーザー確認**

   以下の観点でユーザーに確認し合意を得る:
   - API仕様が要件を満たしているか
   - データストアスキーマがドメインモデルを適切に永続化できるか
   - 外部サービス連携の方針が妥当か（リトライ、タイムアウト等）
   - リポジトリ具象実装方針がオブジェクト設計と整合しているか
   - データマッピングルールに漏れがないか

   合意後「インフラ/IF設計完了」と明示する。

### fix モード

1. QA指摘内容またはユーザー指摘内容を確認する
2. 指摘に基づき infra-interface-design.md を修正する
3. object-design-*.md との整合性を確認する
4. 修正範囲が他のフェーズの成果物に及ぶ場合は、その旨を報告する（修正自体は該当フェーズのエージェントが行う）
5. 修正内容をユーザーに提示し合意を得る
6. 修正完了後「修正完了」と明示する

## object-design-*.md との整合性ルール

- object-design-domain.md で定義されたリポジトリインターフェースの全メソッドに対する具象実装方針を定義する
- object-design-infrastructure.md で定義されたクラス構成と矛盾しない設計にする
- object-design-application.md で定義されたDTOとAPI定義のリクエスト/レスポンスの整合性を確認する
- 矛盾がある場合はユーザーに報告し、object-design-*.md の修正を提案する（修正自体はフェーズ8のエージェントが行う）

## system-requirements.md との整合性ルール

- system-requirements.md で決定されたデータ管理方式（RDB/ファイル/KVS等）に基づいてスキーマを設計する
- system-requirements.md で決定された外部サービス依存に基づいて連携定義を設計する
- system-requirements.md のセキュリティ要件に基づいて認証・認可方式を設計する
- この段階で新たなデータストアや外部サービスの追加を行わない

## テスト用ダミー実装の禁止ルール

- 「ライブラリが未インストール」「外部サービスに接続できない」「データが未配置」等の理由で、本来の処理をダミー・スタブ・固定値返却で代替する設計を含めてはならない
- テスト用ダミー実装（dry run用）は許可される。これは同一インターフェースを実装し、DIで本番実装と切り替え可能にするもの
- 本番コードパスにダミー実装が混入する設計は禁止
