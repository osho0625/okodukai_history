# プログラム構成設計

## Overview

**Core principle:** レイヤードアーキテクチャの依存方向を、具体的なフォルダ配置とimportルールで実装レベルに落とし込め。全クラスを漏れなくファイルに配置し、禁止importパスを明示せよ。

プログラム構成（フォルダ構成・ファイル配置・importルール・命名規則）の設計・更新を担当する共通スキルである。4つのモード（create / delta / reverse / fix）を持ち、設計ワークフロー・変更ワークフロー・設計逆引きワークフロー・バグ修正ワークフロー・リファクタリングワークフローから呼び出される。

## モード概要

| モード | トリガー | 入力 | 出力 |
|---|---|---|---|
| **create** | 設計WFフェーズ10 | 前フェーズ成果物群 | program-structure.md（新規） |
| **delta** | 変更/バグ修正/リファクタリングWFの差分設計 | 変更要求 + 既存設計書 + 影響分析 | 差分設計書に before→after 形式で記載 |
| **reverse** | 設計逆引きWFのフェーズ1 | 既存コード（ディレクトリ構成、ソースファイル群） | program-structure.md（逆生成） |
| **fix** | QA指摘/ユーザー指摘 | 指摘内容 + 既存 program-structure.md | program-structure.md（修正版） |

## Process

**Exceptions:**
- 単一ファイルのスクリプト等、フォルダ構成が不要なプロジェクト → 最小限の構成で対応可能

### モード判定

呼び出し元から渡された `mode` パラメータに基づき、以下のいずれかのモードで実行する。

### create モード（新規作成）

**Step 1:** program-structure-designer-prompt.md に基づきサブエージェントを起動
- Task でサブエージェントをディスパッチする
- サブエージェントが以下を実行:
  1. 前フェーズ成果物の読み込み
     - layered-architecture.md: レイヤー構成、依存ルール
     - object-design-*.md（全レイヤー）: 全クラス定義
     - infra-interface-design.md: 外部IF仕様
     - system-architecture.md: システム構成
     - gui-design.md: 画面構成
     - user-requirements.md, system-requirements.md: 要件
  2. フォルダ構成の設計
     - src/ 配下にレイヤー別トップレベルフォルダ
     - 各層の中は機能ドメインごとにサブフォルダ
     - 最大3-4階層、深すぎるネストは避ける
  3. ファイル配置の確定
     - object-design-*.md の全クラスを1つずつ確認し配置
     - 1ファイル1クラスを基本（小さなヘルパーは例外）
     - 1ファイルあたり200行以下を目安
  4. ファイル命名規則の適用
     - 各言語の標準命名規則に従う
  5. importルールの定義
     - 禁止されるimportパスを具体的に列挙
     - 許可されるimportパスを明記
  6. テストコードのディレクトリ構成の定義
     - tests/ 配下に src/ と同じ構造を反映
  7. 設定ファイル・環境変数の管理方針の定義
  8. program-structure.md の作成
  9. ユーザーへの提示と合意取得
     - 合意後「プログラム構成確定」と明示

**Step 2:** ユーザー合意の確認
- 合意あり → 完了
- 合意なし → サブエージェントに修正を指示し、Step 1に戻る

### delta モード（差分更新）

**Step 1:** 既存の program-structure.md を Read で読み込む

**Step 2:** 変更要求と影響分析結果を Read で読み込む

**Step 3:** 影響範囲の特定
- 影響分析結果から、プログラム構成に影響する変更を特定
- 既存 program-structure.md の該当セクションを確認

**Step 4:** 変更内容の設計
- 新規ファイルの追加（クラス追加の場合）
- 既存ファイルの移動・リネーム（構造変更の場合）
- importルールの更新（依存関係変更の場合）
- before → after 形式で差分を明確化
- ※ 影響範囲外のファイル配置・importルールは変更しない

**Step 5:** 整合性確認
- object-design-*.md との整合性（新規クラスのファイル配置漏れがないか）
- layered-architecture.md の依存ルールとimportルールの整合性

**Step 6:** 差分設計結果を返す（差分設計書に統合される）

### reverse モード（逆引き）

**Step 1:** program-structure-designer-prompt.md に基づきサブエージェントを起動
- Task でサブエージェントをディスパッチする
- サブエージェントが以下を実行:
  - **パス1: スケルトン解析**
    - ディレクトリ構成のツリーを取得（全ファイル名）
    - プロジェクト規模を判定（小規模〜50、中規模51〜150、大規模151〜）
    - エントリポイントを特定
    - 設定ファイルの概要を把握
  - **パス2: importツリー解析**
    - エントリポイント起点でimport/requireを再帰的にたどる
    - 動的importも検出
    - 各ファイルの役割を推定
    - 依存方向（実態のimportルール）を記録
  - **パス3: フォルダ単位の網羅チェック**
    - パス2で到達しなかったファイルを含め、全ファイルを網羅
    - フォルダ単位で解析（大規模プロジェクトは分割実行）
    - 各ファイルの役割説明を補完
    - ※ パス3の制御フロー（調査計画作成、ディレクトリ単位のループ、分割判定）はフェーズスキル（fs-reverse-phase1-program (aide-powers skill)）側で管理する。本スキルは各ディレクトリの解析手順を提供する。
  - **整合性チェック**
    - importルールの整理（依存方向の整合性確認、違反の記録）
    - 未到達ファイルセクションの整理
    - ファイル命名規則の補完
  - **成果物作成:** program-structure.md の逆生成
    - フォルダ構成ツリー（全ファイル名）
    - エントリポイント情報
    - 各フォルダの役割説明
    - 各ファイルの役割説明
    - ファイル命名規則（実態）
    - importルール（実態の依存方向）
    - 設定ファイルの概要
  - **ユーザー合意:** 提示と合意取得

**Step 2:** ユーザー合意の確認
- 合意あり → 完了
- 合意なし → サブエージェントに修正を指示し、Step 1に戻る

### fix モード（修正）

**Step 1:** 指摘内容を受け取る

**Step 2:** program-structure-designer-prompt.md に基づきサブエージェントを起動（fix モード）
- サブエージェントが以下を実行:
  1. 指摘内容の分析（修正が必要な箇所を特定）
  2. 修正の実行
     - ファイル配置漏れの修正時は object-design-*.md の全クラスを再確認
     - importルールの修正時はレイヤー間依存方向との整合性を確認
  3. 整合性確認
     - object-design-*.md との整合性
     - layered-architecture.md との整合性
  4. ユーザーへの提示と合意取得

**Step 3:** ユーザー合意の確認
- 合意あり → 完了
- 合意なし → 修正を再実行

### 完了条件

**create モード:**
1. `program-structure.md` が作成されている
2. フォルダ構成ツリー（全ファイル含む）が記載されている
3. object-design-*.md の全クラスが漏れなくファイルに配置されている
4. importルール（許可/禁止パス）が明記されている
5. ファイル命名規則が定義されている
6. テストコードのディレクトリ構成が定義されている
7. 設定ファイル・環境変数の管理方針が定義されている
8. ユーザーが合意している（「プログラム構成確定」が明示されている）

**delta モード:**
1. 差分設計書に program-structure.md の変更内容が before→after 形式で記載されている
2. 新規クラスのファイル配置が漏れなく含まれている
3. importルールの変更が layered-architecture.md の依存ルールと整合している
4. 影響範囲外のファイル配置・importルールが変更されていない
5. ユーザーが合意している

**reverse モード:**
1. `program-structure.md` が逆生成されている
2. 全ファイルが網羅されている（パス3完了）
3. importルール（実態の依存方向）が記録されている
4. ファイル命名規則（実態）が記録されている
5. コードの現実が正確に記録されている（理想化されていない）
6. ユーザーが合意している

**fix モード:**
1. 指摘内容に基づく修正が完了している
2. 修正後の内容が object-design-*.md と整合している
3. 修正後のimportルールが layered-architecture.md と整合している
4. ユーザーが合意している

### ステータス返却方針

本スキルは明示的なステータス（DONE/SKIPPED）を返さない。完了条件の達成をもって呼び出し元フェーズスキルが完了を判断する。

## 設計ルール

### フォルダ構成ルール

- ソースコードは `src/` 配下、テストコードは `tests/` 配下に配置
- レイヤードアーキテクチャの各層を `src/` 配下のトップレベルフォルダとして反映
- 各層の中は機能ドメインごとにサブフォルダを切る
- わかりやすいまとまりを優先し、深すぎるネストは避ける（最大3-4階層）

### ファイル配置ルール

- object-design-*.md の全クラスを1つずつ確認し、対応するファイルを配置
- 1ファイル1クラスを基本とする（小さなヘルパークラスは例外）
- 1ファイルあたりの行数目安: 200行以下

### ファイル命名規則

各言語の標準命名規則に従う:
- **Python**: スネークケース（PEP 8準拠）。モジュール名は短い全小文字
- **TypeScript/JavaScript**: キャメルケース or ケバブケース
- **Java/Kotlin/C#**: パスカルケース
- **インターフェースファイル**: 言語規則に従う
- **テストファイル**: `test_` プレフィックスまたは `_test` サフィックス

### importルール定義の原則

- layered-architecture.md の依存ルールを具体的なimportパスに変換する
- 禁止されるimportパスを具体的に列挙する
- 許可されるimportパスを明記する
- 「暗黙的に理解される」は不可。明示的に定義すること

### reverse モード固有の原則

- **コードの現実を記録する。** 理想の設計ではなく、実際のファイル配置・命名・依存関係をそのまま記録する
- 改善は別のワークフロー（変更・リファクタリング）で行う
- importルール違反を発見した場合は「違反」として記録する（修正はしない）

### delta モード固有の原則

- **影響範囲外のファイル配置・importルールを変更してはならない**
- 変更要求の影響範囲内のみを変更する
- 理想化・改善提案は不可（変更要求の範囲内のみ）

## Red Flags - STOP

以下の思考パターンが浮かんだら **STOP**。スキルのルールを逸脱しようとしている。

| Red Flag | なぜ危険か |
|---|---|
| 「オブジェクト設計のクラスは大体カバーしているから十分」（create モード） | 「大体」ではなく全クラスを1つずつ確認する。漏れがあればゲート4でFAILになる |
| 「importルールは暗黙的に理解されるから明記不要」 | importルールは明示的に定義しなければ実装時に依存方向が崩れる。禁止パスを具体的に列挙する |
| 「フォルダ構成は実装時に調整すればよい」 | フォルダ構成は設計の一部。実装時の変更はレイヤー間依存の崩壊リスクがある |
| 「コードの理想的な構成を書こう」（reverse モード） | 現実のコードをそのまま記録する。改善は別のワークフローで行う |
| 「影響範囲外のファイル配置も改善しよう」（delta モード） | 変更要求の影響範囲内のみを変更する |
| 「テストディレクトリ構成は後で決めればよい」 | テスト構成も設計段階で確定する。実装時に決めると一貫性が崩れる |
| 「system-requirements.md にない言語の命名規則を適用しよう」 | 言語の選定はシステム要件定義の範囲。選定された言語の標準規則に従う |

## Common Rationalizations

| Excuse | Reality |
|---|---|
| 「フォルダ構成は実装時に調整すればよい」 | フォルダ構成は設計の一部。実装時の変更はレイヤー間依存の崩壊リスクがある |
| 「importルールはリンターで強制すればよい」 | リンター設定の前提として、設計書にルールが明記されている必要がある。設計書がルールの正 |
| 「全クラスのファイル配置確認は手間がかかりすぎる」 | 手間がかかるからこそ設計段階で確認する。実装後の配置漏れ発見は修正コストが桁違いに高い |
| 「1ファイル1クラスは厳しすぎる」 | 基本原則であり、小さなヘルパークラスは例外として許容する。判断基準は200行以下 |
| 「逆引きだから理想的な構成に直してよい」 | 逆引きは現実の記録。改善は別のワークフロー（変更・リファクタリング）で行う |
| 「テスト構成はテストフレームワークに依存するから設計できない」 | テストフレームワークの選定はシステム要件で決定済み。その上でディレクトリ構成を設計する |
