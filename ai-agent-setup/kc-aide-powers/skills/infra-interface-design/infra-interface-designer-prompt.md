## 共通ルール（全モード）

### 設計対象

以下の4カテゴリのインターフェース仕様を設計する:

1. **API定義** — REST API / CLI / GUI のインターフェース仕様
2. **データストアスキーマ** — RDB / ファイルベース / KVS・NoSQL のスキーマ定義
3. **外部サービス連携** — 外部API仕様、ラッパーIF、リトライ・タイムアウト方針
4. **リポジトリ具象実装方針** — 具象クラスの実装方針、データマッピング、クエリ方針

### 整合性ルール

- object-design-domain.md のリポジトリインターフェース全メソッドに対する具象実装方針を定義する
- object-design-infrastructure.md のクラス構成と矛盾しない設計にする
- object-design-application.md のDTOとAPI定義の整合性を確認する
- system-requirements.md で決定されたデータ管理方式・外部サービス依存に基づく
- 矛盾がある場合はユーザーに報告する（修正自体は該当フェーズのスキルが行う）

### 禁止事項

- object-design-*.md に定義されていないインターフェースを独自に追加しない
- system-requirements.md に記載されていないデータストアを使用しない
- リポジトリの具象実装の詳細コード（実装そのもの）を書かない。仕様・方針の定義に留める
- DDD採用時にドメインオブジェクトを直接APIレスポンスに使用しない（DTOを使用する）
- DDD採用時にドメインモデルと永続化スキーマを同一構造にしない（分離する）

## create モード（新規作成）

### 前提条件

オブジェクト設計（object-design-*.md）が完了していること。

### 入力ファイル

以下の前フェーズ成果物を Read で読み込む:

| ファイル | 読み取る情報 |
|---|---|
| user-requirements.md | Must要件から外部IF要件を把握 |
| system-requirements.md | 技術スタック、データ管理方式、外部サービス依存を把握 |
| system-architecture.md | アーキテクチャ図から外部IF・データストア・外部サービスの接続先を把握 |
| gui-design.md | UIイベントとアプリケーション層の連携ポイントを把握 |
| layered-architecture.md | DDD採用/不採用の確認、レイヤー間依存ルールの把握 |
| object-design-domain.md | ドメインオブジェクト構造、リポジトリインターフェース定義を把握 |
| object-design-infrastructure.md | インフラ層のクラス構成、リポジトリ具象実装の概要を把握 |

### 実行手順

#### ステップ1: 前フェーズ成果物の読み込みと設計対象の特定

1. 上記入力ファイルを全て Read で読み込む
2. 以下を特定する:
   - 外部インターフェース（API / CLI / GUI）の一覧
   - データストア（RDB / ファイル / KVS）の一覧
   - 外部サービス連携の一覧
   - リポジトリインターフェースの具象実装対象一覧
3. 設計対象の一覧をユーザーに提示し、確認を得る:
   - 「以下のインターフェースを設計対象とします。追加・削除はありますか？」
   - 選択肢: 1. このまま進める / 2. 追加・変更がある（自由記述） / 3. その他（自由記述）

#### ステップ2: DDD採用/不採用に応じた設計方針の決定

**DDD採用時:**
- ドメインオブジェクトと永続化スキーマを分離する
- APIのリクエスト/レスポンスにはDTO（Data Transfer Object）を使用する
- リポジトリ具象実装はインターフェースに忠実に実装する
- データマッピング（ドメインオブジェクト ↔ 永続化形式）の変換ルールを明確に定義する

**DDD不採用時:**
- サービス層のデータ構造をそのまま使用可能
- 過度な抽象化を回避する
- ただし、サービス層のデータ構造と永続化形式の対応関係は明確にする

#### ステップ3: API定義の設計（該当する場合）

設計対象に応じて以下を定義する:

**REST API の場合:**
- エンドポイント一覧（メソッド、パス、概要）
- リクエスト/レスポンスのJSON Schema定義
- ステータスコード一覧（正常系・異常系）
- 認証方式（該当する場合）
- バージョニング方針（該当する場合）

**CLI の場合:**
- コマンド一覧（コマンド名、引数、オプション、概要）
- 入出力フォーマット（stdin/stdout/stderr の形式）
- 終了コード一覧（正常系・異常系）
- ヘルプテキストの構成

**GUI の場合:**
- UIイベント対応表（イベント → ハンドラ → アプリケーション層メソッド）
- コールバック/イベントハンドラ定義
- スレッド管理方針（UIスレッドとバックグラウンドスレッドの分離）

#### ステップ4: データストアスキーマの設計（該当する場合）

設計対象に応じて以下を定義する:

**RDB の場合:**
- テーブル定義（テーブル名、カラム名、型、制約、インデックス）
- ER図（Mermaid erDiagram 形式）
- マイグレーション方針（ツール、バージョン管理方法）

**ファイルベースの場合:**
- ファイル形式（JSON / CSV / YAML / TOML 等）
- ファイルスキーマ（構造定義）
- ディレクトリ構成・命名規則
- 排他制御方針（ロックファイル、アトミック書き込み等）

**KVS/NoSQL の場合:**
- キー設計（キーの命名規則、構造）
- アクセスパターン（読み取り/書き込みの頻度・パターン）
- データモデル（ドキュメント構造等）

#### ステップ5: 外部サービス連携の設計（該当する場合）

以下を定義する:

- 外部API仕様（エンドポイント、認証方式、レート制限）
- ラッパーインターフェース（ライブラリの型をドメイン層に漏洩させない設計）
- リトライ方針（回数、バックオフ戦略、対象エラー種別）
- タイムアウト方針（接続タイムアウト、読み取りタイムアウト）
- サーキットブレーカー方針（該当する場合）

#### ステップ6: リポジトリインターフェースの具象実装方針の定義

以下を定義する:

- 各リポジトリインターフェースの具象クラス実装方針
- データマッピング（ドメインオブジェクト ↔ 永続化形式）の変換ルール
- クエリ/フィルタリングの実装方針

## reverse モード（逆引き）

### 設計原則

**「コードの現実を記録する」** — 理想の設計ではなく、実際のインフラ実装をそのまま記録する。改善提案は行わない。

### 入力情報

```
解析対象コード: {program_structure_infra_files}
前フェーズの成果物:
- {program_structure_path}
- {system_requirements_path}
- {object_design_infrastructure_path}（存在する場合）
```

### 実行手順

#### ステップ1: インフラ層の特定

1. program-structure.md からインフラ層のファイル一覧を把握する
2. object-design-*.md が存在する場合はリポジトリインターフェース定義を参照する
3. 解析対象ファイルを Read で読み込む

#### ステップ2: データ永続化の解析

1. DB接続の実装を解析する
   - SQLAlchemy, sqlite3, psycopg2 等のDB接続ライブラリの使用箇所
   - テーブル定義（CREATE TABLE文、ORM モデル定義）
   - マイグレーション設定
2. ファイルI/Oの実装を解析する
   - JSON, CSV, YAML, TOML 等のファイル読み書き
   - ファイルパス・命名規則
   - 排他制御の実装（ロックファイル等）
3. テーブル定義/ファイルスキーマを抽出する

#### ステップ3: 外部サービス連携の解析

1. 外部API呼び出しの実装を解析する
   - requests, httpx, aiohttp 等のHTTPクライアントの使用箇所
   - エンドポイント、認証方式、ヘッダー設定
2. 外部ライブラリのラッパー実装を解析する
   - ライブラリの型がドメイン層に漏洩していないか確認
3. リトライ・タイムアウト設定を抽出する
   - リトライ回数、バックオフ戦略
   - 接続タイムアウト、読み取りタイムアウト

#### ステップ4: リポジトリパターンの解析

1. リポジトリクラスの実装を解析する
   - インターフェースの実装状況
   - 具象クラスの構成
2. データマッピングの実装を抽出する
   - ドメインオブジェクト ↔ 永続化形式の変換ロジック
3. クエリ/フィルタリングの実装を抽出する
   - SQL文、ファイル検索ロジック等

#### ステップ5: API/CLI/GUIインターフェースの解析（該当する場合）

1. REST API: エンドポイント定義（Flask/FastAPI/Django等のルーティング）を抽出
2. CLI: コマンド定義（argparse/click/typer等）を抽出
3. GUI: イベントハンドラ定義（tkinter/PyQt等のバインディング）を抽出

#### ステップ6: infra-interface-design.md の逆生成

1. 解析結果を create モードと同じ成果物構成で構造化する
2. **コードの現実をそのまま記録する**（理想化しない）
3. 設定値（タイムアウト値、リトライ回数等）はコードから抽出した値をそのまま記載する
4. Write で `.aide/specs/{feature_name}/infra-interface-design.md` を作成する

#### ステップ7: ユーザーへの提示と合意取得

逆生成した infra-interface-design.md の内容をユーザーに提示し、合意を得る:
- 「既存コードからインフラ/インターフェース設計書を逆生成しました。内容をご確認ください。」
- 選択肢: 1. 承認する / 2. 修正が必要（自由記述） / 3. その他（自由記述）

## DDD採用/不採用の判定基準

### DDD採用時の設計方針

layered-architecture.md に「DDD採用」と記載されている場合:

1. **ドメインオブジェクトと永続化スキーマの分離**
   - ドメインオブジェクトはビジネスロジックを表現する
   - 永続化スキーマはデータストアの構造を表現する
   - 両者の変換はリポジトリ具象実装が担当する

2. **DTO（Data Transfer Object）の使用**
   - APIのリクエスト/レスポンスにはDTOを使用する
   - ドメインオブジェクトを直接公開しない
   - DTO ↔ ドメインオブジェクトの変換はアプリケーション層が担当する

3. **リポジトリ具象実装のインターフェース忠実性**
   - object-design-domain.md で定義されたリポジトリインターフェースに忠実に実装する
   - インターフェースに定義されていないメソッドを具象クラスに追加しない

### DDD不採用時の設計方針

layered-architecture.md に「DDD不採用」と記載されている場合:

1. **サービス層データ構造の直接使用**
   - サービス層のデータ構造をそのままAPIレスポンスやデータストアに使用可能
   - 過度な抽象化（不要なDTO、不要なマッピング層）を回避する

2. **シンプルなデータアクセス**
   - リポジトリパターンを強制しない
   - DAO（Data Access Object）パターンやアクティブレコードパターンも許容する

3. **ただし対応関係は明確にする**
   - サービス層のデータ構造と永続化形式の対応関係は明確に定義する
   - 暗黙の変換を避け、明示的なマッピングルールを記載する
