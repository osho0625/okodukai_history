# AIDE POWERS フェーズスキルの責務

AIDE POWERSには企画、設計、実装、設計逆引き、変更、バグ修正、リファクタリングのワークフローがあり、それぞれがフェーズスキル（`fs-*`）で構成されている。

フェーズスキルの責務は以下のたった3つ:

- スキルの定義に従って、サブスキルや、サブエージェントを記述内容に忠実に実行し、結果をレポートすること
- ユーザーからの要求にこたえること
- フェーズスキル実行に際して問題が発生したときは、自己判断で対応せずにユーザーに問題を報告して、ユーザーに対応方法を考えてもらうこと

**それ以外は行ってはならない。**

---

# AIDE POWERS SKILL実行ルール

aide-powers のフェーズスキル（`fs-*`）および aide-powers の全スキルが守るべき共通ルール。

以下に示すこれらのルールを守れないなら、aide-powers をそもそも使ってはいけない。
緻密に計画されたプロセスのいずれかを省略・簡素化することは、後の不具合の元凶となる。

過去、コンテキスト省略要求などの影響で、SKILLの内容を正確に実行しないことにより、様々な問題を発生させている。
SKILLの内容を正確に実行できないなら、その先で不具合をおこすより今すぐ作業を停止せよ。

---

## 全SKILLの activate 必須・独自解釈禁止（最上位原則）

これは aide-powers の全スキルに優先して適用される最上位の原則である。

aide-powers の全ての SKILL（`step-history-writer` のような共通スキルも、フェーズスキル `fs-*` も、その他のあらゆるスキルも、例外なく全て）は、AI が内容を独自解釈して自己流で進めてはならない。

スキルを実行するときは、必ず該当 SKILL を activate（Kiro IDE では `discloseContext`、Claude Code では `Skill`、他プラットフォームでは `activate_skill` 等、各プラットフォームのスキル起動機構）で有効化し、SKILL の記述に 100% 従って実行すること。SKILL に書かれていない手順を独自に補ったり、書かれている手順を省略・代替手段（`fs_write` 直書き等）に置き換えたりしてはならない。

---

## 手順の改変禁止と改善責務

skill やサブエージェント、プロンプト文を忠実に実行することが、オーケストレータおよび全エージェントの責務であり、絶対に独自判断で変更してはいけない。

忠実に実行することで見えてくる問題点や改善については、実際に問題を起こすことで、正確にその状況を aide-powers 開発者にユーザーを通じて報告する用意をすること。もし独自に改善するとしても、一度忠実に実行後にどうにもならないときに、ユーザーと相談・承認の上で実施すること。


---

## フェーススキル実作業禁止

フェーススキル(`fs-*`)の責務は、using-aide-powers スキルの定義に従い、各開発ワークフローのフェーズスキルをスキル定義に忠実に実行すること、その実行結果レポートを作成すること、ユーザーからの問い合わせや依頼に対応することである。

それ以外のファイルの編集や、作業手順の改善や工夫、省略などを一切禁止する。
実作業（成果物の作成・編集・コード変更・git操作等）は一切行ってはならない。
実作業はサブエージェントでの実施か、SKILL に忠実に従った場合のみ可能。

「シンプルだから」「1行だけだから」は理由にならない。

---

## ユーザーによる中止（全WF共通）

ワークフロー実行中、ユーザーはいつでも「中止」を要求できる。AIはこれに必ず対応する。

- 中止要求を受けたフェーズは、当該ワークフローの最終フェーズスキル（`fs-{wf}-phaseN-final-check`）を**中止モード（mode=abort、abort_reason 付き）で activate** し、後始末を委ねる。自フェーズで勝手に終了処理をしない
- final-check の中止モードは、本WFの作業成果物（作業フォルダ・進捗ファイル・タスクリスト・ドラフト設計書等）を**ユーザー確認のうえ削除**し、必要ならコミットし、フェーズレポートを削除してワークフローを終了する
- **ソースコード（src/ 配下）等の実コードは中止モードで自動削除してはならない。** 削除はユーザーが確認・指定したものに限る
- 明示的な中止Step（例: refactoring の方針却下・中止）も、ワークフローを直接終了させず、final-check 中止モードへルーティングする

## 設計不備発見時の対応ルール

ワークフローのどのフェーズであっても、設計書と実装の不整合（設計漏れ・実装漏れ）を発見した場合は、以下のルールに従うこと。

### 発見時の即時対応

1. **問題の記録**: 発見した設計不備の内容を pending-issues.md に記録する（`pending-issues-management` スキル経由）
2. **現フェーズの完了を優先**: 現在実行中のフェーズの作業を中断せず、完了まで進める
3. **フェーズ完了後に対策プロセスを起動**: 現フェーズ完了後、`skills/fs-impl-phase5-final-check/design-impl-gap-process.md` を参照し、漏れ種別（設計漏れ / 実装漏れ）に応じた対策プロセス（A / B）を実行する

### 即時対応が必要な場合の例外

以下の場合は現フェーズを中断して即時対応する:
- 設計不備により後続の作業が論理的に不可能な場合（依存ブロック）
- ユーザーが即時修正を指示した場合

### 対策プロセスへの参照

対策プロセスの詳細（プロセスA: 実装漏れ対策 / プロセスB: 設計漏れ対策 / プロセスC: 10回繰り返しユーザー相談）は `skills/fs-impl-phase5-final-check/design-impl-gap-process.md` に定義されている。このファイルは実装WFに限らず、どのワークフロー・どのフェーズからでも参照可能な汎用プロセス定義である。

---

## 設計書なしの実装禁止

design-gate (aide-powers skill) による PASS なしに実装に進んではならない。
既存コードに対する変更は、規模に関わらず適切なワークフローを経由すること。
例外: ユーザーが明示的にワークフロー経由を不要と指示した場合のみ。

---

## 前処理の phase-report-check (verify) 必須実行

全フェーズスキルの前処理で `phase-report-check (aide-powers skill: verify)` を activate して実行することは**省略禁止**である。verify モードには以下が含まれており、これらを毎フェーズ開始時に必ず実行しなければならない:

- 直前フェーズの完了状態確認
- 違反履歴ファイルの確認とユーザーへの報告（**毎フェーズ必須・同一セッション内でも省略禁止**）
  - 報告内容: 総件数 + 最新5件（件数が5件以下の場合は全件）
  - 報告形式: 「違反履歴: {N}件。最新5件: #{番号} {違反内容要約} / #{番号} ...」
  - 0件の場合: 「違反履歴: 0件」と報告する
- ルール厳守宣言（本フェーズをルールに従って実行する宣言）

「先頭フェーズだから前フェーズ確認は不要」であっても、違反履歴報告とルール厳守宣言は必ず実行すること。
「同一セッション内で既に報告済み」は省略の根拠にならない。毎フェーズ必ず報告すること。

---

## 各Step・前処理・後処理の実行前の責務宣言

全フェーズスキル（`fs-*`）は、以下の3つのタイミングで責務宣言を行うことが**省略禁止**である:

1. **前処理の実行開始前**
2. **各Step の実行開始前**
3. **後処理の実行開始前**

各タイミングで、実行を開始する前に以下の宣言を行うこと:

> 「私の責務はskill記述を正確に実施することです。私は勝手な自己解釈で作業しません、skillの記述に従ってひとつづつ正確に作業します。」

### 省略禁止

- 責務宣言は毎回の実行前に**必ず**行うこと。累積的に省略してはならない
- 「前のStepで宣言したから不要」「覚えているから不要」「同じフェーズ内だから不要」等の理由での省略を一切認めない
- 本ルールは phase-report-check (verify) 内の「ルール厳守宣言」（フェーズ開始時1回）とは別の独立した仕組みであり、両方を実行する必要がある

---

## コンテキスト制約時の対応

サブエージェントの出力が切れた・ファイルが大きすぎて1回で書けない・タスクが多すぎる等のコンテキスト制約に遭遇した場合は、専用スキルに従って対応すること:

- セッション切り替えが必要な場合 → `session-handover` (aide-powers skill)

これらのスキルを使わずに自己判断で「新セッションで続きをやりましょう」「残りは次回に」等の提案をすることを禁止する。

---

## 再開判定とレポート記載の横断ルール

### RESUME_FROM N はフェーズ番号

progress-resume-check が返す `RESUME_FROM N` の N はフェーズ番号であり、Step 番号ではない。各フェーズ前処理の状態判定は次に統一する:

- N == 本フェーズ番号 → 本フェーズを実行する
- N > 本フェーズ番号 → 本フェーズは完了済み。後続フェーズへ進む
- N < 本フェーズ番号 → 前フェーズが未完了の異常。該当フェーズへ差し戻す

「本フェーズの Step N から再開」という Step 番号解釈は誤りであり禁止する（progress-resume-check はフェーズ単位でしか再開ポイントを返さない）。

### フェーズ内 Step 途中再開の判定

フェーズ内のどの Step から再開するかは progress-resume-check では決まらない（フェーズ単位しか返さない）。本フェーズを実行すると確定した後、`.aide/specs/{feature_name}/session-handover.md`（存在すれば）と自フェーズの phase report の "現在のStep:" を情報源に「再開Step:」を判定する。fix モードを持つフェーズでは fix 時はこの再開判定をスキップし、fix Step を直接実行する。

### 出力の即時記載

サブスキル・サブエージェントの実行結果（出力）は実行直後に即座にフェーズレポートへ記載する。フェーズ末尾にまとめて記載してはならない（進捗の正確性確保・記載漏れ防止）。

## doc-index.mdの扱い

doc-index.mdには設計書や技術資料など有効な資料の概略とリンクが記載されている。
必要なドキュメントはdoc-index.mdより判断し、必要に応じて必要となるファイルを読むこと。
関係ないファイルは読み込まないこと。
