# ドキュメントと実装の整合性チェック プロンプトテンプレート

## 使用方法

`{program_structure_path}`, `{user_requirements_path}`, `{project_root}` を実パスに置換してサブエージェントに渡す。

## プロンプト

```
以下の設計書と実際のコードを比較し、整合性を判定せよ。

## 入力

- program-structure.md: {program_structure_path}
- user-requirements.md: {user_requirements_path}
- プロジェクトルート: {project_root}

## 実行手順

### 1. ファイル構成の整合性チェック

1. `program-structure.md` を Read で読み込む
2. 記載されたフォルダ構成・ファイル一覧を抽出する
3. プロジェクトルート配下の実際のファイル構成を Glob / ListDir で確認する
4. 以下を検出する:
   - 設計書に記載があるが実体がないファイル（欠落）
   - 実体があるが設計書に記載がないファイル（未記載）
   - ディレクトリ構成の不一致
5. 除外対象（乖離として報告しない）:
   - `.git/`, `node_modules/`, `__pycache__/`, `.venv/`, `venv/`, `.aide/`, `.kiro/` 等の自動生成ディレクトリ
   - `*.pyc`, `*.pyo`, `.DS_Store` 等の自動生成ファイル
   - `package-lock.json`, `yarn.lock`, `poetry.lock` 等のロックファイル

### 2. レイヤー依存方向の整合性チェック

1. `program-structure.md` に記載された import ルール（レイヤー間依存方向）を抽出する
   - 例: 「domain 層は infrastructure 層に依存してはならない」
   - 例: 「presentation → application → domain の方向のみ許可」
2. import ルールが記載されていない場合 → このチェックをスキップ（PASS扱い）
3. import ルールが記載されている場合:
   - 各レイヤーのソースファイルから import 文を抽出する（grep で十分）
   - 禁止方向の import が存在するか確認する
   - 違反があれば報告する

### 3. 主要クラス・関数の存在確認

1. `program-structure.md` に記載された主要クラス名・関数名を抽出する
   - 「主要」の判断基準: ファイルの役割説明に明示的に名前が記載されているもの
2. 該当ファイルを Read で開き、記載されたクラス・関数が実際に存在するか確認する
   - 全ファイルを読む必要はない。設計書に名前が明記されているもののみ確認する
   - ファイル数が多い場合は grep で存在確認する
3. 設計書に記載があるが実装に存在しないものを報告する

## 判定基準

### PASS
- 乖離なし
- または軽微な乖離のみ:
  - 新規追加ファイルが数件程度で、既存構成に影響なし
  - 設計書に記載のない補助ファイル（テスト用fixture、設定ファイル等）の追加のみ

### WARN
- 中程度の乖離あり:
  - ファイル追加・削除が複数あるが、レイヤー構成は維持されている
  - 設計書に記載のないモジュールが追加されているが、依存方向は正しい
  - クラス名・関数名のリネームが検出されたが、機能は同等と推測される

### FAIL
- 重大な乖離あり:
  - ディレクトリ構成の大幅変更（レイヤーフォルダの追加・削除・リネーム）
  - レイヤー依存方向の違反が検出された
  - 主要クラス・関数が欠落している（削除されたか、大幅にリファクタされた）
  - 設計書に記載されたファイルの過半数が存在しない
```
