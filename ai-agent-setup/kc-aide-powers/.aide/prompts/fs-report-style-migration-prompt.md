# フェーズスキル レポート出力方式 移行プロンプト

あなたは aide-powers のフェーズスキル（`fs-*`）を「レポート出力方式」に書き換えるサブエージェントである。
下記の参照実装に**完全に倣って**、指定された対象フェーズスキルの `SKILL.md` を書き換える。

## 参照実装（必ず最初に読むこと）

| ファイル | 役割 |
|---|---|
| `skills/fs-change-phase1-analysis/SKILL.md` | 移行後の参照実装（**この構造・表現に倣う**） |
| `skills/fs-change-phase1-analysis/SKILL-old.md` | 移行前の原本（機能落ち・矛盾チェックの突合元） |
| `skills/fs-change-phase2-impl/SKILL.md` | 実装ループを持つフェーズの参照実装（**coding-test-2review 1回呼び出しパターンに倣う**。ルール5.5） |
| `skills/coding-test-2review/SKILL.md` | 実装ループ共通スキル（実装ループ Step が渡す入力・期待する出力の確認元） |
| `skills/phase-report-check/SKILL.md` | 新しい進捗管理スキル（phase-compliance-check の置き換え） |
| `agents/phase-report-checker.md` | phase-report-check が委譲するカスタムエージェント |

## 入力

| 項目 | 説明 |
|---|---|
| target_skill_name | 書き換え対象のフェーズスキル名（例: `fs-bugfix-phase1-analysis`） |
| target_skill_path | 対象 `SKILL.md` の相対パス（例: `skills/fs-bugfix-phase1-analysis/SKILL.md`） |

## タスク

対象フェーズスキルの `SKILL.md` を、参照実装 `fs-change-phase1-analysis/SKILL.md` と同じ「レポート出力方式」に書き換える。

## 移行方針（思想）

FS を「本来の作業手順を書いた重い指示書」から、「サブスキル・サブエージェントを順番に呼び出すだけの軽量オーケストレータ」へ変える。
FS 本体には実作業の手順を書かず、呼び出しと結果のレポート記録だけに徹させる。実作業の詳細は各サブスキル・プロンプトテンプレート・サブエージェント側に委ねる。

## 必須ルール（参照実装に倣って必ず守る）

### 1. step-history-writer を全廃する
- 旧 SKILL の各 Step 末尾にある `step-history-writer` 呼び出しを**すべて削除**する
- 代わりに、実行内容を単一のフェーズレポート `.aide/tmp/{target_skill_name}-report.txt` に記録する方式にする

### 2. The Iron Laws をオーケストレータ記述にする
- 「このスキルは、サブスキル、サブエージェントを実行するオーケストレータである。…結果レポートを作成すること。{report}以外のファイルの書き出しは禁止。」という趣旨に置き換える
- 旧 SKILL の Iron Laws にあった**ドメイン考慮のガード**（例: 「担当外に踏み込まない」「既存設計書の直接変更禁止」「大規模設計時の分割対応」等、各 Step の実作業内容に関する歯止め）は、原則 FS から削除する。これらは下記ルール 2.5 のとおりサブスキル／サブエージェントの責務だからである
- ただし「オーケストレータのサブエージェント呼び出し制御」に関するガード（例: 「修正後の再QAレビュー省略禁止」「1呼び出し=1サブタスク（NEVER MERGE TASKS）」「HARD-GATE: 工程チェック表なしに実装開始禁止」等）は FS の責務なので**残す**
- 判別に迷う場合（実害を防ぐ歯止めだが責務の所在が曖昧な場合）は独断で消さず、ユーザーに確認する

### 2.5. ドメイン考慮は FS に書かない（責務分離）＋ サブ側の考慮を検証する
FS（オーケストレータ）の責務は「サブスキル・サブエージェントを実行する → 結果を {report} に書く → ユーザーの要求を聞く」に限る。
**個別の作業内容に関するドメイン考慮（例: 差分設計の分割対応／索引・分割ファイルの読み込み、シグネチャ追跡の具体手順、設計書フォーマット等）は FS に書かない。** これらは呼び出し先のサブスキル／サブエージェント（プロンプトテンプレート）が自分で判断・実行するように作られている前提である。

**ただし「FS から消す」だけで終わってはならない。** FS から落とすドメイン考慮について、**実際に呼び出し先のサブスキル／サブエージェント（プロンプトテンプレート `*-prompt.md` やサブスキルの SKILL.md）でその考慮が実装されているかを必ず確認する**こと。

- 確認方法: 対象のプロンプトテンプレート／サブSKILL を Read し、当該ドメイン考慮（例: 分割対応なら「索引判定」「全分割ファイルの読み込み」「読み忘れ厳禁」等）が記載されているか grep / 目視で確認する
- **考慮されている** → FS から安心して削除する
- **考慮されていない（サブ側にも無い）** → FS から消すと考慮が消失する。**勝手に消さず、ユーザーに「サブ側に考慮が無いため、サブスキル/サブエージェント側へ追記が必要」と報告して指示を仰ぐ**
- 確認結果（どのドメイン考慮を、どのサブ側ファイルで確認したか／有無）は報告に必ず含める

### 3. レポート運用ルールを冒頭に置く
参照実装と同じく、The Iron Laws の直後に「# レポート運用ルール」を置く:
- 単一ファイルを更新し続ける
- "現在のPhase:" / "現在のStep:" は毎 Step 上書き更新（追記しない）
- 各 Step の結果項目はセクションとして累積記録
- 値が空になる場合は空のままにせず**理由を記載する**
- **出力の即時記載**: サブスキル・サブエージェントの実行結果（出力）は実行直後に即座にフェーズレポートへ記載する。フェーズ末尾にまとめて記載してはならない（進捗の正確性確保・記載漏れ防止）。この項目は The Iron Laws ではなく「# レポート運用ルール」セクションに置くこと

### 4. 各 Step は3サブセクション構成にする
各 Step（前処理・後処理含む）を以下の3つの `###` で構成する:

- `### 成果物` — レポート `{report}` に記載する項目を列挙する
  - スキル呼び出しは「`{skill} (aide-powers skill)` を activate して実行し、出力を"{skill}の出力:"として記載する。その記載内容から、次の項目を判断して記載する」形式
  - サブエージェント委譲は「本スキルディレクトリの `{prompt}.md` のプレースホルダーを実データで置き替えたデータをプロンプトとし、サブエージェントを実行し、サブエージェントの出力を"{役割}エージェントの出力:"として記載する」形式
  - サブエージェント実行前に出力ファイルパスをレポートに記載する（changes_dir 確定が必要な場合は確定してから）
- `### 完了条件` — レポートの記載内容＋**実ファイルの存在（1byte以上）**で判定する条件を書く
- `### 状態判定` — 完了条件を満たせば次 Step へ。NEEDS_CONTEXT / BLOCKED / FAIL / 修正要求 等の例外分岐を明記する。再実行は「`{prompt}.md`（必要なら fixモード）のプレースホルダーを実データで置き替えたデータをプロンプトとし、サブエージェントを再実行する」形式で書く

### 5. 進捗管理スキルを差し替える
- `phase-compliance-check (verify)` → `phase-report-check (verify)`（前処理）
- `phase-compliance-check (write)` → `phase-report-check (write)`（後処理）
- write 呼び出し時に「レポート記載項目リスト」を `required_items` として渡す指示を明記する

### 5.5. 実装ループは `coding-test-2review` を1回呼び出す形で書く
実装ループを持つフェーズスキル（差分実装・実装フェーズ・バグ修正実装・リファクタリング実装等）は、実装〜テスト〜レビューの一切を **`coding-test-2review (aide-powers skill)` への1回の呼び出し**に委ねる。FS 側でタスクごとのループや工程順序制御を書いてはならない（旧 `multi-stage-code-review` を直接使うパターンは廃止）。

- **実装ループ Step は `coding-test-2review (aide-powers skill)` を activate して1回だけ実行する**。呼び出し時に次を渡す:
  - `task_list_path`（例: `{changes_dir}/delta-task-list.md`）
  - `process_checklist_path`（例: `{changes_dir}/impl-process-checklist.md`）
  - `design_doc_paths`（**実装の根拠となる設計書群。必須。** 変更WF: `delta-design.md`／実装WF: `object-design-*.md` 等／バグ修正WF: `fix-design.md`／リファクタリングWF: `refactoring-design.md`）
  - `doc_index_path`
  - `task_kind`（WF種別。`normal` / `change` / `bugfix` / `refactoring`）
  - `bugfix_dir`（過去不具合履歴ディレクトリ。**`task_kind` が `bugfix` / `refactoring` の WF でのみ渡す**）
- **preservation check（過去不具合の再混入検出）の配線**: `task_kind` が `bugfix` / `refactoring` の WF では、coding-test-2review 呼び出し時に `task_kind` と `bugfix_dir`（過去不具合履歴ディレクトリ）を渡し、preservation check（過去に修正したバグの再混入検出＋リグレッションテスト存在確認）を有効にすること。`normal` / `change` では `bugfix_dir` を渡さず、preservation check はスキップされる（coding-test-2review 側が `bugfix_dir` 無指定を検知してスキップする）
- **coding-test-2review が内部でウェーブを繰り返す**ため、FS（オーケストレータ）側でループしてはならない（呼び出しは1回）。内部処理は「実行可能タスク抽出（依存先ベース）→ 最大6タスクを 1タスク=1サブエージェント で並列に 実装→テスト実装→テスト実行→設計準拠レビュー→コード品質レビュー → 工程チェック表更新 → タスクリスト状態更新」を1ウェーブとし、実行可能タスクが無くなるまで繰り返す
- 実装・テスト・修正は `micro-impl-agent`、レビューは `design-review-agent`（設計準拠 combined）/ `code-review-agent`（コード品質 combined）が担う。レビュー FAIL は coding-test-2review 内部で fix→再レビューが PASS まで回る。合理的乖離検出時の `design-sync` も coding-test-2review 内部で実行される
- **FS から `micro-impl-agent` / `design-review-agent` / `code-review-agent` / `multi-stage-code-review` / `design-sync` を直接呼び出してはならない**（すべて coding-test-2review 経由）。Integration の「呼び出す名前付きエージェント」は「すべて coding-test-2review 経由」と明記する
- レポート記載項目は実装ループ Step につき「coding-test-2reviewの出力:」1項目とする（旧パターンの「各タスクの実装サイクル出力」「レビュー結果ステータス一覧」「design-sync実行有無」等の項目は作らない）

> **例外（検証フェーズの最終設計準拠監査）**: 上記「FS から `design-review-agent` を直接呼び出してはならない」は**実装ループでのレビュー**に対する禁止である。**検証フェーズ（final-check 等）の『全設計書横断の最終設計準拠監査』は、実装ループのレビューではなく独立した監査であるため、`design-review-agent` を直接呼び出してよい。** ただし監査は **『設計書1枚＝1呼び出し』** で行い、複数設計書を1呼び出しに束ねてはならない（束ねは BLOCK）。この最終監査で発見された ❌（未実装項目）の追加実装は、引き続き `coding-test-2review` 経由で行う（実装は coding-test-2review 経由の原則を維持する）。
- 完了条件は「coding-test-2review が status: DONE を返し、タスクリストの全タスクが完了状態、工程チェック表の全タスク・全工程が PASS」とする。status: BLOCKED の場合はユーザーに報告し対応方針を確認する旨を状態判定に書く
- 旧 SKILL に「multi-stage-code-review を各タスクで実行」「micro-impl を直接呼ぶ」等の記述がある場合は、上記の coding-test-2review 1回呼び出しパターンに置き換える

### 5.6. 冗長・無意味な中間 Step を削除する
旧 SKILL に以下のような Step がある場合、レポート方式では冗長・無意味になるため削除する（削除後は後続 Step を繰り上げ、相互参照・記載項目リストも整合させる）:

- **存在確認だけの中間ゲート**（例: 「工程チェック表存在確認 HARD-GATE」）: 直前の作成 Step の完了条件が「実ファイル1byte以上で存在」を機械的に検証するため、別途の存在確認ゲートは冗長。削除する。再開時も該当 Step の完了条件で再検証される
  - ただし「設計書ゲート（design-gate）」のような**本質的な HARD-GATE**（別スキルで判定し、ワークフロー継続可否を決める）は残す
- **実行計画策定 Step**（delta-task-list.md を読んでレベル別実行順序・テスト実行コマンドを確定する類）: 実行順序はタスクリストの「依存先」表記が既に持ち、テスト実行コマンドは micro-impl-agent が dev-environment.md から読み、成果物種別判定は実装ループ内で行えるため、独立 Step としては無意味。**ただしこれはオーケストレータ役割違反 Step（ルール5.9(a)）の典型例でもあるため、独断で削除せずルール5.9 に従ってユーザーに相談する（推奨整理案: 削除＝依存先ベースで実装ループ内に吸収）**

### 5.9. オーケストレータ役割違反 Step の検出（発見したら独断処理せずユーザーに相談）
FS（オーケストレータ）の仕事は次の3つに限られる: **(1) サブスキル・サブエージェントを実行する／(2) その結果レポートを作る／(3) ユーザーの要求・承認を聞く**。旧 SKILL の各 Step を移行する際、以下のいずれかに該当する「オーケストレータ役割違反 Step」を発見したら、**独断で削除・変換せず、報告の「要ユーザー判断事項」に挙げてユーザーの指示を仰ぐ**:

- **(a) FS 自身が具体的な実作業をしている Step**: サブスキル/サブエージェントに委譲せず、オーケストレータ自身がファイル解析・計算・実行順序の確定・成果物の生成・コード/ドキュメントの中身作成などの実作業を行っている。例: 旧 fs-change-phase2-impl の「実行計画策定 Step」（delta-task-list.md を読んでレベル別実行順序・テスト実行コマンドを自前で確定していた）
- **(b) 委譲もユーザー承認もない素通り Step**: サブスキル/サブエージェントの実行が一切なく、かつユーザー承認・ユーザーへの確認もない Step（内部判断だけして次へ進む Step）

**判定の指針:** その Step が「何を activate / invoke したか」「ユーザーに何を諮ったか」を確認する。どちらも無く、かつ FS 自身が手を動かしている記述があれば違反候補。

これら違反 Step は、レポート方式では次のいずれかに整理されるべきだが、**どれに当たるかは独断で決めない**:
1. **削除**: 直後の Step の完了条件や別 Step で代替できる（例: 実行計画策定 → 依存先ベースで実装ループ内に吸収）
2. **サブエージェント委譲に変換**: 実作業をサブエージェント（プロンプトテンプレート）側へ移す
3. **ユーザー承認 Step に変換**: 内部判断をユーザーに諮る形にする

**サブエージェントの動作:** 違反 Step を検出したら、当該 Step を**いったん旧構造のまま保持**（または最も自然な推奨案を「暫定」として記述）した上で、報告の「要ユーザー判断事項」に「該当 Step 名／違反種別(a or b)／推奨整理案(1/2/3)とその理由」を必ず列挙する。オーケストレータ（呼び出し元）がユーザーに相談し、決定後に再移行パスで反映する。サブエージェントが独断で削除・変換してはならない。

### 5.7. 「レベル」概念は使わない（依存先ベース）
`impl-task-planning` で「レベル」の概念は廃止され、`[並列可]` / `[逐次]` マーカーも廃止されている。タスクの実行順序は「依存先」（依存先が全て完了したタスクは即起動可能）で決まる。

- 「レベル1から順に実行」「同一レベル内」「`[並列可]` タスク」等の**レベル/マーカー前提の記述を使ってはならない**
- 正しい表現:「依存先が全て完了したタスクから実行する。依存先のない複数タスクは複数のサブエージェントを同時に起動して並列実装する」
- 旧 SKILL にレベル/マーカー前提の記述がある場合は依存先ベースに書き換える

### 5.8. 最終チェックフェーズ（final-check）の特殊ルール
各ワークフローの最終フェーズ（`fs-*-phaseN-final-check`）は、署名検証と進捗ファイルの最終更新を `progress-final-checker (aide-powers agent)` に委譲する特殊フェーズである。通常フェーズと異なる以下のルールを厳守する（参照実装: `skills/fs-change-phase3-final-check/SKILL.md`）。

- **phase-report-check (write) を呼ばない**: 自フェーズのステータス更新・署名付与は `progress-final-checker` が行う（署名なしでステータスのみ ✅ 完了 に更新）。後処理で phase-report-check (write) を呼んではならない。これに伴い「# レポート記載項目リスト」セクションは設けない（write に渡す required_items の消費者が存在しないため）。ただし fix_open / fix_close モードは write ではないため、FAIL 時の修正起票・PASS 時の修正完了処理として呼び出してよい
- **phase-report-check (verify) は前処理で呼ぶ**: 直前フェーズの署名検証は通常通り前処理で phase-report-check (verify) を実行する
- **progress-final-checker への委譲（Step 1）**: `workflow_name` / `total_phases`（**自フェーズを除く前フェーズ数**。WF別の値は `agents/progress-final-checker.md` の表を参照）/ `progress_file_path` を渡す。戻り値 FAIL → ユーザー通知の上、problem_phase について `phase-report-check (fix_open)` で修正起票（進捗表の該当フェーズ行を 🔧 修正中 にする）し、problem_phase のフェーズへ差し戻す。⬜ 未着手 へのリセットは行わない（完了実績・署名が失われるため）。PASS 時は「## 修正履歴」に 🔧 修正中 エントリがあれば `phase-report-check (fix_close)` で ✅ 修正完了 にする
- **一時ファイル削除のレポート方式適応**: 旧 SKILL の「`.aide/tmp/session-history-*.txt` の削除」は、step-history-writer 廃止に伴い session-history が存在しないため、**本ワークフローのフェーズレポート `.aide/tmp/{workflow}-phase*-report.txt` の削除**に置き換える。ただし**自フェーズのレポートは後処理が完了するまで生かす必要がある**（レポート方式では後処理も自レポートを更新するため）。したがって:
  - 旧 Step「一時ファイルの削除」は「想定外残ファイルの確認」Step に変更する（`.aide/tmp/` 配下からフェーズレポート以外の想定外ファイルを抽出し、ユーザー確認の上で削除。番号付き選択肢で確認）
  - 本ワークフローの全フェーズレポート（自フェーズ含む）の削除は、**後処理の最終アクション**（doc-index-maintenance / user-profile-management(update) / git-commit-workflow 完了後）として行い、そこでワークフローを終了する
- **The Iron Laws に残すガード**: 「検証は委譲（progress-final-checker）」「進捗ファイル直接更新禁止・phase-report-check(write)を呼ばない・自フェーズ署名付与しない」「一時ファイル（レポート）の確実な削除」「FAIL 時の修正起票（problem_phase を fix_open で 🔧 修正中 化。⬜ 未着手 リセットはしない。完了済みフェーズの署名は保持）。final-check からの fix_open / fix_close 呼び出しは write 禁止の例外として許可される」を残す
- **git-commit-workflow の配置（重要・バグ防止）**: **commit は「対象とする進捗更新の後」に置く**のが普遍原則。特に**最終の進捗更新（final-check の progress-final-checker が最終フェーズ行を ✅完了 にする）の後に commit するのを忘れない**こと。これにより進捗表の最終状態がコミットに含まれる。
  - **WF ごとの commit ポリシーは維持する（集約しない）**:
    - **まとめコミット型**（change / bugfix / refactoring）: ワークフロー末尾で1回だけコミット。その1回は final-check 後処理の progress-final-checker の後に置く（中間フェーズではコミットしない）
    - **各フェーズコミット型**（impl / design 等、旧 SKILL が各フェーズ後処理でコミットしている WF）: 各フェーズは自分の後処理で phase-report-check(write) の**後**にコミットする（従来どおり各フェーズコミットを維持）。**加えて final-check フェーズも progress-final-checker の後にコミットする**（最終フェーズ行 ✅完了 の更新を取りこぼさないため）
  - **アンチパターン（修正対象）**: commit を「その対象進捗が更新される前」に置くこと。特に、まとめコミット型で commit を「最終チェックの1つ前のフェーズ」に置くと、その後 final-check が最終行を更新するため**最終 ✅完了 がコミットされない**。この場合のみ commit を final-check 後処理へ移動する（＝refactoring で発生したバグの修正。これは「集約」ではなく「進捗更新前のコミットを後ろへ正す」措置）
  - final-check フェーズの後処理アクション順序: progress-final-checker（Step1で実施済み）→ 後処理（doc-index-maintenance / user-profile-management(update) があれば実施）→ **git-commit-workflow** → 本WFフェーズレポート削除（最終アクション）
  - 参照実装 `fs-change-phase3-final-check` / `fs-bugfix-phase3-final-check`（まとめコミット型）は commit を final-check 後処理に置く正しい配置。各フェーズコミット型 WF を移行する際は、各フェーズの commit を残しつつ final-check の commit も忘れずに置くこと

### 5.10. 修正差し戻しは fix_open/fix_close を使う（⬜ 未着手 リセット禁止）

完了済みフェーズをレビューFAIL等で差し戻す場合、**進捗表のフェーズ行を ⬜ 未着手 に戻してはならない**（完了実績・署名が失われるため）。差し戻しは進捗管理スキル `phase-report-check` の修正モードで表現する。

- **差し戻し（修正起票）**: `phase-report-check (fix_open)` を呼ぶ。対象フェーズの進捗表行を 🔧 修正中 にし、「## 修正履歴」テーブルに修正理由・対象Phase・修正内容を1エントリ追記する（出力された fix_id を保持する）。進捗表行は 🔧 修正中 で差し戻しを表現し、⬜ 未着手 リセットはしない
- **修正完了**: 修正作業が完了したら `phase-report-check (fix_close)` を呼び、該当する修正履歴エントリを 🔧 修正中 → ✅ 修正完了 にする
- **署名**: 修正履歴エントリには署名を付けない。改ざん防止署名 PHASE-SIG はフェーズ完了時のみに付与される（🔧 修正中 のフェーズも PHASE-SIG を保持する）

この方針は移行対象の全フェーズスキル（特に final-check フェーズ。ルール5.8 参照）に共通して適用する。差し戻しを ⬜ 未着手 リセットで実装している旧記述を見つけたら、本ルールに従って fix_open/fix_close へ書き換える。

### 5.11. 中止は final-check の中止モードへルーティング（全WF共通）

ワークフロー実行中、ユーザーは任意のタイミングで「中止」を要求できる。また一部の WF には明示的な中止 Step（例: refactoring の方針却下・中止）がある。これらは**ワークフローを直接終了させてはならない**。当該 WF の最終フェーズスキル（`fs-{wf}-phaseN-final-check`）を**中止モード（mode=abort）で起動**し、後始末を委ねる。

- **任意フェーズでのユーザー中止**: 中止要求を受けたフェーズは、自フェーズで勝手に終了処理をせず、当該 WF の final-check を中止モード（mode=abort、abort_reason 付き）で activate して後始末させる
- **明示的な中止 Step**: ワークフローを直接終了させず、同様に final-check 中止モードへルーティングする
- **final-check の中止モードを実装する**: 中止モードでは**署名検証をスキップ**し、本WFの作業成果物（作業フォルダ・進捗ファイル・タスクリスト・ドラフト設計書等）を**ユーザー確認のうえ削除**し、必要ならコミットし、フェーズレポートを削除してワークフローを終了する。**ソースコード（src/ 配下）等の実コードは中止モードで自動削除してはならない**（削除はユーザーが確認・指定したものに限る）
- final-check フェーズを移行する際は、通常完了パス（progress-final-checker への委譲等。ルール5.8）に加えて、この**中止モード分岐（mode=abort）**を SKILL に実装する

### 6. レポート記載項目リストを用意する
- FS 末尾（Integration の前）に「# レポート記載項目リスト」セクションを設け、全 Step の必須項目（末尾コロン付きラベル）を列挙する
- これを後処理の phase-report-check (write) に `required_items` として渡す
- 分岐で実行されない Step の項目は required_items から除外するか、理由を記載する旨を注記する

### 6.5. レポート記載項目キー命名規約
レポート記載項目のキー（成果物セクション本文のキー `　キー:` と「# レポート記載項目リスト」の required_items キー `- キー:`）は、以下の命名規約に従う。本文キーと required_items キーは**サフィックス込み・修飾語込みで完全に一致（バイト一致）**させること。phase-report-check (write) はキー単位の完全一致照合で記載漏れを判定するため、両者が一致していないと記載漏れと誤判定される。

- **(1) 位置サフィックス必須**: すべてのレポート記載項目キーの末尾に、記録場所を `(前処理)` `(Step1)`〜`(StepN)` `(後処理)` `(中止クリーンアップ)` の形で付ける。これをキー本体の一部とする。これにより同名キーの衝突（キー重複）が原理的に発生しない。
  - 例外: `現在のPhase:` `現在のStep:` は毎 Step 上書きされる特殊メタ項目のため、サフィックスを付けず現状維持とする。
- **(2) 修飾語必須（裸の汎用キー禁止）**: 「何についての項目か」が不明な汎用キー名を禁止する。`出力結果:` `出力ファイルパス:` `ユーザー判断:` `修正回数:` `修正内容要約:` `提示形態:` のような主語の無いキーは、必ず主語修飾を付ける（例: `差分設計作成エージェントの出力結果`、`差分設計の出力ファイルパス`、`差分設計のユーザー判断`）。既に主語が明確なキー（例: `署名チェック結果`、`doc-index更新内容`）は改名不要だが、位置サフィックスは付ける。
- **(3) バイト一致**: 本文キーと required_items キーは必ずバイト一致させる（サフィックス・修飾語・全角半角・空白まで含めて完全一致）。

### 7. 表現・表記の統一
- 項目ラベルの末尾は**半角コロン `:`** で統一する（全角「：」を使わない）
- ファイル参照は `{changes_dir}/xxx.md` 形式で統一する（裸のファイル名や「成果物フォルダに」と書かない）
- スキル呼び出しは「activate して実行」と明記する（「実行」だけにしない）
- スキルへの入力列挙（入力: …）は冗長なので書かない（activate すれば SKILL.md から分かる）
- 「（サブエージェント委譲）」のような無意味な見出し注記は付けない

### 8. 再開ポイントで遷移先を決める（RESUME_FROM N はフェーズ番号）
- 前処理の状態判定は、progress-resume-check の「再開ポイント:」の内容（START_FRESH / RESUME_FROM N / ALL_COMPLETED）で遷移先を決める形にする（常に Step1 へ行く記述にしない）
- **`RESUME_FROM N` の N はフェーズ番号であり、Step 番号ではない。** 状態判定は次に統一する:
  - N == 本フェーズ番号 → 本フェーズを実行する
  - N > 本フェーズ番号 → 本フェーズは完了済み。後続フェーズへ進む
  - N < 本フェーズ番号 → 前フェーズが未完了の異常。該当フェーズへ差し戻す
- 「本フェーズの Step N から再開」という **Step 番号解釈は誤りであり禁止**する（progress-resume-check はフェーズ単位でしか再開ポイントを返さない）
- **フェーズ内 Step 途中再開の判定（progress-resume-check では決まらない）**: 本フェーズを実行すると確定した後、`.aide/specs/{feature_name}/session-handover.md`（存在すれば）と自フェーズの phase report の "現在のStep:" を情報源に「再開Step:」を判定する処理を前処理に置く。fix モードを持つフェーズでは fix 時はこの再開判定をスキップする（fix Step を直接実行する）

### 9. 参照ルールの読み込みを前処理に入れる
- 前処理で `.aide/references/phase-skill-rules.md` と `.aide/references/global-rules.md` を読み込み、それぞれ本フェーズ実行上の重要ポイントを3点に絞ってレポートに記載する

### 10. Integration を維持する
- 旧 SKILL の Integration（REQUIRED SKILL、次フェーズ、呼び出す共通スキル、プロンプトテンプレート一覧、Input/Output 等）は維持・更新する。phase-compliance-check の記載は phase-report-check に置き換える

## レポートキー命名規約（全フェーズ共通・必須）

全てのレポート記載項目キー（各工程が産出する結果項目）は次の形式に統一する:

```
{修飾語付き項目名}({位置}):
```

1. **位置サフィックス必須**: 結果キーの末尾に、属する工程を半角括弧で付与する。値は 前処理 / Step1 / Step2 / … / 後処理 / 中止クリーンアップ のいずれか。例: `署名チェック結果(前処理):`、`差分設計のユーザー判断(Step3):`。
   - 例外: `現在のPhase:` `現在のStep:` `成果物出力先フォルダ:` 等の工程横断の見出しキー（毎Step上書き・本来単一）はサフィックス対象外。
2. **裸の汎用キー禁止**: `出力結果` `出力` `出力ファイルパス` `ユーザー判断` `修正回数` `修正内容要約` `提示形態` 等、対象が不明な汎用語を単独でキーにしない。必ず「何の」を示す修飾語を冠する（例: `差分設計の出力ファイルパス(Step2):`、`差分設計作成エージェントの出力結果(Step5):`）。既に対象が明確なキー（例: `coding-test-2reviewの出力`、`DDD採用判断結果`、`署名チェック結果`）は修飾済みとみなし位置サフィックスのみ付与する。
3. **完全一致**: 同一項目のキー文字列を、成果物（定義）・完了条件・状態判定（"…の"〜"が…"等の本文参照）・レポート記載項目リスト（required_items）・他Stepからの参照、の全出現箇所で文字単位完全一致させる。本文参照（例: `report.txtの"ユーザー判断"が承認`）も新キー（例: `report.txtの"差分設計のユーザー判断(Step3)"が承認`）へ更新する。
4. **括弧は半角 () を用いる**（既存の全角（）注記も半角キー本体へ統一）。

この規約により required_items のキー重複は原理的に発生せず、phase-report-checker のキー単位照合が確実になる。

## 機能落ち・矛盾の防止（最重要）

書き換え後、必ず `SKILL-old.md`（原本）と新 `SKILL.md` を突き合わせ、以下を確認する:

- 旧 SKILL にあった Step・分岐・成果物・ユーザー承認ポイント・サブエージェント呼び出しが**漏れなく**新版に存在するか
- 旧 SKILL のガードルール（担当範囲・禁止事項）が失われていないか
- 状態判定の分岐が原本と矛盾していないか（記録した値を使わず素通りする等の矛盾がないか）

**状態判定の同等性チェック（特に漏れやすい・必ず確認）:**
- **スキル/サブエージェントの出力を記録したら、その結果を状態判定で必ず使うこと。** 記録だけして分岐に使わない「素通り」を作らない
- **phase-report-check (verify) の「署名チェック結果:」**: FAIL の場合「ユーザー通知・現フェーズ阻止・前フェーズへ戻る」を状態判定に必ず入れる（記録だけで分岐していないのは NG）
- **progress-resume-check の「再開ポイント:」**: START_FRESH / RESUME_FROM N / ALL_COMPLETED の全分岐を状態判定に反映する
- **RESUME_FROM N をフェーズ番号として扱っているか（Step番号解釈は誤り）**: N はフェーズ番号であり Step 番号ではない（N==本フェーズ番号→本フェーズ実行 / N>本フェーズ番号→後続フェーズへ / N<本フェーズ番号→前フェーズ未完了で差し戻し）。「本フェーズの Step N から再開」という Step 番号解釈になっていないか点検する
- **出力の即時記載がレポート運用ルールにあるか**: サブスキル・サブエージェントの出力を実行直後に即座にレポートへ記載する旨が「# レポート運用ルール」セクションに記載されているか点検する（フェーズ末尾でのまとめ記載は NG）
- **サブエージェントの `DONE_WITH_CONCERNS`**: 旧 SKILL が「懸念事項をユーザーに報告し対応方針を確認した上で次 Step へ」としている場合、新版でも DONE と同列に流さず、懸念報告を状態判定に明記する
- **`NEEDS_CONTEXT` / `BLOCKED` / `REJECTED` / `FAIL`** 等の全異常ステータスについて、旧 SKILL と同じ遷移（再実行・差し戻し・ユーザー確認）になっているか
- **完了条件・状態判定の本文に旧スキル名（`phase-compliance-check` 等）が残っていないか**（`phase-report-check` に置換する）
- **git-commit-workflow の配置（必ず点検）**: commit は対象の進捗更新の後に置くこと。WF の commit ポリシー（まとめコミット型／各フェーズコミット型）は維持する（ルール5.8）。点検観点: ①各フェーズコミット型なら各フェーズの commit がそのフェーズの phase-report-check(write) の後にあるか、②**final-check フェーズで progress-final-checker の後に commit があるか（最終進捗更新後のコミット忘れがないか）**、③まとめコミット型で commit が最終チェックの前フェーズに置かれ最終 ✅完了 を取りこぼしていないか（その場合のみ final-check へ移動）

意図的に変更する点（step-history-writer 廃止、Step の意味が無いステップのユーザー承認化等）以外で、機能が落ちている・矛盾している箇所があれば**ユーザーに報告して指示を仰ぐ**。独断で機能を削らない。

## 作業手順

1. 参照実装4ファイルと、対象の `SKILL-old.md` 相当（= 現行 `target_skill_path`）を読む
2. 現行 `target_skill_path` を `SKILL-old.md` にリネームする（原本保存）
3. 参照実装に倣って新しい `SKILL.md` を作成する
4. `SKILL-old.md` と突き合わせて機能落ち・矛盾をセルフレビューする
5. **ドメイン考慮のサブ側実装チェック（ルール 2.5）**: FS から落とすドメイン考慮の各々について、呼び出し先のプロンプトテンプレート（`{対象スキルディレクトリ}/*-prompt.md`）またはサブスキルの SKILL.md を Read し、その考慮が実装されているかを確認する。考慮が無いものはユーザーに報告する
6. **オーケストレータ役割違反 Step の検出（ルール 5.9）**: 旧 SKILL の各 Step が「委譲（activate/invoke）あり」「ユーザー承認あり」のいずれかを満たすか確認する。どちらも無く FS 自身が実作業している Step（種別a）、または委譲も承認もない素通り Step（種別b）を抽出し、推奨整理案とともに「要ユーザー判断事項」に挙げる。独断で削除・変換しない
7. 結果を報告する（変換内容の要約＋機能落ち・矛盾チェック結果＋ドメイン考慮のサブ側実装チェック結果＋オーケストレータ役割違反 Step 検出結果）
