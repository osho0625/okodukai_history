# 変更要求定義

## 変更概要
- **変更の目的・背景**: 現在、実装ステップ（coding-test-2review等）内でリグレッションテスト（preservation check、既存テスト全実行によるセーフティネット確認）を毎回実施しているが、これは冗長である。全てのワークフローにおいて、実装完了後の動作確認Stepで1回実施すれば十分である。また、「対象テキスト」等の聞きなれない独自用語が使用されており、標準的な用語（「ユニットテスト」等）に統一する必要がある。
- **変更種別**: 複合（機能削減 + 用語修正）

## 要求事項

### REQ-C-001: 実装ステップでの全てのリグレッションテスト実施の廃止
- **種別**: 変更（機能削減）
- **説明**: 実装ステップ（coding-test-2review等の実装ループ内処理）において実施されている全てのリグレッションテストを廃止する。具体的には preservation check（既存テストの保全確認）、既存テスト全実行（セーフティネット）、リグレッション目的のパラメータ・ロジック等が対象。
- **受入基準**:
  - AC-001: 該当する全ての箇所において、実装ステップ内での preservation check の実施が廃止されていること
  - AC-002: 該当する全ての箇所において、実装ステップ内でのセーフティネット目的の既存テスト全実行が廃止されていること
  - AC-003: 該当する全ての箇所において、リグレッションテスト目的のパラメータおよびその利用ロジックが廃止されていること
  - AC-004: 該当する全ての箇所において、実装ステップ内でのリグレッションテスト実行に関する手順・ロジックが廃止されていること
- **優先度**: 必須

### REQ-C-002: 全WFの実装完了後の動作確認Stepでリグレッションテストを1回実施するように変更
- **種別**: 変更（機能追加/統一）
- **説明**: 全てのワークフローにおいて、実装完了後の動作確認Step（verification step）でリグレッションテスト（既存テスト全実行）を1回実施する設計に統一する。どのWFでも実装完了後に動作確認Stepがあるので、そこで1度だけ実施するように変更する。
- **受入基準**:
  - AC-005: 該当する全ての箇所において、各WFの実装完了後の動作確認Stepにてリグレッションテスト（既存テスト全実行）が1回実施される設計となっていること
  - AC-006: リグレッションテストの実施タイミングが「実装完了後の動作確認Step」に統一され、それ以外の箇所では実施されない設計となっていること
- **優先度**: 必須

### REQ-C-003: 不明瞭な用語の標準用語への統一
- **種別**: 変更（用語修正）
- **説明**: 「対象テキスト」等の聞きなれない独自用語を、「ユニットテスト」等の標準的・一般的な用語に置換する。該当する全ての箇所が対象。
- **受入基準**:
  - AC-007: 該当する全ての箇所において「対象テキスト」という用語が存在しないこと
  - AC-008: 該当する全ての箇所において、テストに関する記述が「ユニットテスト」「テスト実行」等の標準的な用語で統一されていること
- **優先度**: 必須

## 対象外（スコープ外）
- テスト実行の仕組み自体（テストランナー、テストフレームワーク等）の変更は対象外
- テスト内容の変更（テストケースの追加・削除・修正）は対象外

## 前提条件
- 実装ステップ内でリグレッションテスト関連の記述が現在存在すること
- 各WFの実装完了後に動作確認Step（verification step）が既に存在すること
- 変更対象ファイルが Git 管理下にあり、変更履歴が追跡可能であること

## 関連する既存要件
- **UR-005**: 多段コードレビュー（設計準拠＋コード品質の2段階）を提供すること — coding-test-2review はこの要件の実現手段の一部であり、リグレッションテスト廃止後もレビュー機能は維持される
- **UR-001**: 7つのワークフローを提供すること — 全WFのフェーズ構成に影響する変更
- **UR-010**: 共通スキル群による横断的ユーティリティを提供すること — coding-test-2review は共通スキルの一つ
