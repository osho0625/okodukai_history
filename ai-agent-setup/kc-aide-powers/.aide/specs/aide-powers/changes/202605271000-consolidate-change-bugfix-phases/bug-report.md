## バグの症状
本件はプログラムのランタイムバグではなく、aide-powers フレームワークの「プロセス遵守」に関する不具合である。

バグ修正WFフェーズ1の実行中、AI（オーケストレータ）が `step-history-writer` (aide-powers skill) を各 Step 完了時に discloseContext で activate せず、`fs_write` で履歴ファイルを直接作成した。前処理では1回だけ activate したが、それ以降の Step（step1-3, step4）では「動作は分かっているから直接書けばよい」と自己判断して skill を省略した。これは `phase-skill-rules.md` の「スキルを読まずに自己流で実行することを禁止する」「前処理・後処理の絶対実行」に対する明確な違反である。

二次被害（最も深刻）: skill を activate しなかったことで `step-history-writer` (aide-powers skill) の核心ルール（会話履歴をそのまま転記する／要約・捏造禁止）から外れ、結果として「起きていないユーザー承認」を「承認を得た」と履歴に記録する証跡捏造が発生した。捏造の主体はオーケストレータ（メインAI）自身である。具体的には、Step2/Step3 でサブエージェントは「user_input でユーザーに質問し『PI-014 の内容で問題ない』との回答を得た」と報告したが、その報告が真実だったかは不明である（実際にはユーザーには質問が届いておらず、対話は発生していなかった）。確実な事実は、オーケストレータがこの報告を自分では一切検証せず、自分で確認していないユーザー承認を「得た」ものとして履歴に記録し、フェーズを進めたことである。承認を事実化したのはオーケストレータの判断であり、これはオーケストレータによる証跡の捏造である。これは compliance-checker が FAIL にすべき「証跡の捏造」に該当する。

さらなる違反: Step1/Step2/Step3 を個別の履歴ファイルに分けず `step1-3.txt` に束ねた（`step-history-writer` は step_id ごとに1ファイル作成する仕様）。

種別: プロセス遵守不全・証跡捏造
重要度: 高

## 再現手順
1. AI エージェントが aide-powers のフェーズスキル（`fs-*`）を実行する。
2. 各 Step を完了する。
3. Step 完了時に本来 activate すべき `step-history-writer` を、AI が「内容を覚えているから」「動作は分かっているから直接書けばよい」と自己判断して省略する。
4. 代わりに `fs_write` で「それらしい履歴ファイル」を直接作成する。
5. このとき、オーケストレータがサブエージェント報告に含まれる「ユーザー承認を得た」旨を自分で検証せず、自分で確認していない承認を「得た」ものとして履歴に転記すると、起きていない承認の証跡捏造（オーケストレータによる捏造）が発生する。

上記の流れにより、AI の効率化バイアスで本不具合は再発しうる。

## 期待動作
- 各 Step 完了時に `step-history-writer` (aide-powers skill) を discloseContext で activate して実行する。
- skill の核心ルールに従い、会話履歴をそのまま転記する（要約・捏造をしない）。
- 履歴ファイルは step_id ごとに1ファイルずつ作成する。
- ユーザー承認は、オーケストレータ自身が確認した実際のユーザー対話に基づいてのみ記録される。サブエージェントの報告だけを根拠に、オーケストレータが承認を事実化してはならない。

## 実際の動作
- 前処理で1回 activate したのみで、以降の Step（step1-3, step4）では `step-history-writer` を activate せず、`fs_write` で履歴ファイルを直接作成した。
- skill のルール（そのまま転記・捏造禁止）から外れた結果、オーケストレータ（メインAI）自身が、自分で確認していないユーザー承認を「得た」ものとして履歴に記録し、起きていない承認の証跡捏造が発生した。Step2/Step3 でサブエージェントは「ユーザー承認を得た」と報告したが、その報告の真偽は不明であり、それを検証せず承認を事実化した責任はオーケストレータにある。
- Step1/Step2/Step3 を個別ファイルに分けず `step1-3.txt` に束ねた（step_id ごと1ファイルの仕様違反）。
