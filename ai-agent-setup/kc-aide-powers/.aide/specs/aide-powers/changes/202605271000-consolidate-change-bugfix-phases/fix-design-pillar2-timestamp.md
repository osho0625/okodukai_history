## 柱2 共通の検証仕様

タイムスタンプ検証は compliance-checker に追加する（progress-final-checker は簡素化され、タイムスタンプ検証は持たない。本ファイル #6 参照）。以下にタイムスタンプ検証の判定仕様を定める。

- **検証対象:** 各 `.aide/tmp/session-history-{skill}-{step_id}.txt` の作成/更新日時（タイムスタンプ）。
- **取得手段:** 既存ツール範囲内で取得する。
  - compliance-checker（`@builtin`）: bash の `stat`（例: `stat -c '%Y %n' <file>`、macOS/BSD では `stat -f '%m %N'`）等で各履歴ファイルの更新時刻（エポック秒）を取得する。
- **主シグナル（順序逆転＝FAIL）:** Process 順序（前処理 → step1 → step2 → … → stepN → 後処理）に対し、履歴ファイルのタイムスタンプの時系列がこの順序と一致しない場合（後の Step の履歴が前の Step の履歴より古い、例: `step3.txt` が `step4.txt` より新しい）→ 証跡の捏造として **FAIL**。これは「step3 を飛ばして step4 を作り、後から step3 を埋めるとタイムスタンプが逆転して露見する」という本件の実際の不正を確実に捉える。
- **補助シグナル（短時間一括生成＝閾値超で FAIL／閾値は緩め）:** 全 Step の履歴が実作業時間と乖離して極端に短時間でまとめて生成されている場合（一括後付け生成の疑い）→ 捏造として **FAIL**。ただし誤検知（正当な作業を捏造と誤判定）を避けるため、閾値は緩めに設定する（目安: フェーズ内の全 Step 履歴が概ね 10 秒以内に集中生成されている場合のみ疑う）。この補助シグナルは単独では FAIL の決め手とせず、明確な順序逆転（主シグナル）を主たる判定根拠とする。
- **誤検知回避の原則:** task-orchestration による並列処理・セッション切り替え・高速な正常実行など、タイムスタンプが近接しうる正当なケースがある。短時間一括生成のみでは FAIL にせず、順序逆転が明確な場合を主シグナルとする。判断に迷う場合、compliance-checker は FAIL を急がずユーザーに確認する。
- **部分欠落との関係:** 履歴ファイルが部分欠落している Step は、タイムスタンプ比較の対象から除外する（存在するファイル同士でのみ時系列を比較する）。欠落自体の扱いは既存の部分欠落ルール（W4 / 入力パラメータ注記）に従う。

````markdown
### W5.5 検証項目 T（タイムスタンプ検証）

本項目は履歴の**内容に依存せず**、履歴ファイルのタイムスタンプ（作成/更新日時）の時系列から証跡の捏造を検出する。W4 のパターン2（セッション開始直後の即時実行）の場合はスキップして PASS とし、パターン3（通常実行）の場合に実行する。

#### T-1. タイムスタンプの取得
- 導出した履歴ファイル群（`.aide/tmp/session-history-{skill_name}-*.txt`）それぞれについて、更新時刻（エポック秒）を取得する。
  - 取得コマンド例（GNU）: `stat -c '%Y %n' .aide/tmp/session-history-{skill_name}-*.txt`
  - macOS/BSD の場合: `stat -f '%m %N' .aide/tmp/session-history-{skill_name}-*.txt`
- 当該フェーズスキルの SKILL.md（W3〜W5 で既に Read 済み）の Process から、Step の実行順序（前処理 → step1 → step2 → … → 後処理）を把握する。

#### T-2. 順序逆転の検出（主シグナル）
- Process 順序に並べた各 Step の履歴ファイルについて、タイムスタンプが単調増加（前の Step ≤ 後の Step）になっているか確認する。
- 後の Step の履歴が前の Step の履歴より**明確に古い**場合（例: `step3.txt` の更新時刻が `step4.txt` より新しい）→ 後から辻褄合わせで作成した疑い。**証跡の捏造として FAIL**（理由: 「履歴ファイルのタイムスタンプが Process 順序と逆転しており、後付け生成の疑いがある」）。
- 部分欠落している Step はタイムスタンプ比較から除外し、存在するファイル同士でのみ時系列を比較する。

#### T-3. 短時間一括生成の検出（補助シグナル・閾値は緩め）
- 当該フェーズの全 Step 履歴の更新時刻が、実作業時間と乖離して極端に短時間（目安: 概ね 10 秒以内）に集中している場合 → 一括後付け生成の疑い。
- ただし誤検知を避けるため、本シグナルは単独では FAIL の決め手とせず、T-2 の順序逆転や会話履歴の不自然さ（W5 の J）と併せて総合的に判断する。明確な順序逆転がなく短時間集中のみの場合は、FAIL を急がず**ユーザーに確認**する。

#### 判定
- T-2 で明確な順序逆転を検出 → FAIL
- T-2 は問題なく T-3 のみ該当（短時間集中のみ）→ ユーザーに確認（即 FAIL にしない）
- いずれも該当しない → PASS

> 本検証は、不具合A→B 連鎖（履歴の内容上は承認のペアが揃って見えてしまう問題）を、履歴の内容に依存せず断つための手段である。直書き検出・束ね検出は追加しない（過剰機構の回避）。
````

### 変更理由

`fix-plan.md`「柱2（機構追加・これのみ）: compliance-checker にタイムスタンプ検証を追加」および `bug-analysis.md`「B. 機構追加対象」が指示する唯一の機構追加を、compliance-checker の write モードに反映するものである。`bug-analysis.md`「A→B 連鎖」が示すとおり、承認実在性の検証は「履歴が実際の会話どおりに転記されていること」を前提とするため、不具合A により自己流直書きされた履歴に真偽不明の承認記述が紛れると、内容ベースの検証（W5 の I・J）だけでは捏造を見逃す。これを断つには履歴の内容に依存しない検証手段が必要であり、タイムスタンプの順序逆転検出がその役割を担う。判定原則「改ざん系は別物（証跡の捏造は常に FAIL）」とも整合する（タイムスタンプ逆転は工程の省略ではなく証跡の捏造に該当）。`fix-plan.md`「副作用リスク」の指示どおり、誤検知（正当な作業の誤判定）を避けるため短時間一括生成の閾値は緩めにし、明確な順序逆転を主シグナルとする。また判定原則「FAIL 時はしつこく原因調査をしない」と整合させ、T の FAIL 時も簡潔に事実（順序逆転の該当ファイル）を示すにとどめる。直書き検出・束ね検出を追加しないことで、c5c0a02 の compliance 軽量化方針との整合を保つ（`bug-analysis.md`「C. 修正候補から除外する観点」）。

## 6. progress-final-checker.md（簡素化）

対象ファイル: `agents/progress-final-checker.md`

> **方針変更（重要）:** 当初は progress-final-checker にもタイムスタンプ検証（パターン3の検証点4）を追加する設計だったが、ユーザー指示により方針を変更した。**progress-final-checker は「最終フェーズを除く全前フェーズの署名(PHASE-SIG)を検証し、進捗ファイルの最終フェーズを ✅ 完了 に更新する」だけの役割に簡素化する。** セッション履歴ベースの実行整合性検査（履歴の偽装検出・ユーザーやり取り確認・直前フェーズ後処理確認・タイムスタンプ検証・パターン1/2/3 判定）は progress-final-checker からは全廃する。

### 簡素化の内容

- **役割:** 進捗ファイルを読み込み、最終フェーズを除く全前フェーズ（1〜total_phases）の署名(PHASE-SIG)と省略なし宣言(COMPLIANCE-DECLARATION)の存在を確認し、`create-sig.sh` で各署名を再計算して記録値と照合する。全て正当なら自フェーズを ✅ 完了 に更新する。
- **FAIL 条件:** 署名／宣言が存在しないフェーズがある／署名が再計算値と一致しない／前フェーズが未完了、のいずれか。
- **削除する検査:** セッション履歴の読み込み・履歴の偽装検出・ユーザーやり取り存在確認・直前フェーズの後処理実行確認・タイムスタンプ検証・パターン1/2/3 の事前判定。これらは行わない。
- **入力パラメータ:** workflow_name / total_phases / progress_file_path のみ（session_history 系は受け取らない）。
- **tools:** read_file / execute_pwsh のみ（履歴走査が不要のため grep_search は不要）。

### タイムスタンプ検証の所在

タイムスタンプ検証（柱2の機構）は **compliance-checker（本ファイル #5）にのみ存続する**。compliance-checker は各フェーズの後処理（フェーズ完了時）で当該フェーズの履歴を検証する役割を持ち、そこにタイムスタンプ検証（W5.5 / 検証項目 T）を残す。一方 progress-final-checker は最終フェーズで全前フェーズの「署名」だけを検証する役割に絞る。両者は別の検証であり、タイムスタンプ検証を両方に持たせる必要はない。

### 変更理由

「各フェーズの最後で行う compliance-checker（コンプラチェック）」と「最終フェーズで行う progress-final-checker（最終チェック）」は役割が異なる別物である。最終チェックは全前フェーズが正規に完了・署名されたことを署名照合で担保すれば十分であり、履歴の内容・タイムスタンプを再検査する必要はない（各フェーズの完了時点で compliance-checker が既に検証済みであり、その結果が署名として残っている）。ユーザー指示により、最終チェックは「署名 verify ＋ 進捗更新」だけに簡素化し、履歴ベースの重い検査を全廃することで、final-check の実行コストと誤検知リスクを下げる。タイムスタンプ検証は引き続き compliance-checker（#5）が各フェーズ完了時に担う。
