# 差分設計: compliance-checker

> 対象: `agents/compliance-checker.md`
> 関連 REQ: REQ-C-004（成果物フォルダパスで履歴絞り込み）／ REQ-C-005（スクショ偽装検出）／ REQ-C-008（W4-D 時刻検証をファイル作成日時基準へ変更）
> 親索引: [delta-design.md](./delta-design.md)
> スコープ厳守: 既存の署名検証（W3 / W4-A 等の存在検証）・テキスト履歴検証（W5-1 / W5-2 の既存ロジック）は変更しない。本変更は W4 への絞り込み追加、W4-D の参照元差し替え、W5 へのスクショ照合観点追加に限定する。なお W4-C 本体（ユーザーが別途精緻化済みの現行ロジック＝処理内容ベースの最低実行時間見積もり判定）は変更せず、その生成間隔の時刻ソース統一と、判定原則の要約行を現行 W4-C と整合させる点のみを扱う（変更2・変更3）。

## 確定事項

| 項目 | 確定値 |
|---|---|
| 照合キーの導出（WF 種別分岐・compliance-checker 側で完結） | compliance-checker が照合キーを WF 種別で導出する。**`changes_dir` 相当を持つ WF（変更／バグ修正／リファクタリング）** は write 入力の `changes_dir` をそのまま照合キーに使う。**`changes_dir` 相当を持たない WF（設計／実装／企画／逆引き）** は `progress_file_path`（`.aide/specs/{feature_name}/{wf}-progress.md`）の親ディレクトリ、または `skill_name` から feature フォルダパス `.aide/specs/{feature_name}` を機械的に導出して照合キーに使う。導出は compliance-checker 側のロジックで完結し、設計／実装／企画／逆引きの fs-* の phase-compliance-check 呼び出しへの改修は不要（AC-004-4〜7） |
| 絞り込みキーの文字列照合 | 各履歴メタ情報「成果物フォルダパス」を、上記で導出した照合キーと文字列照合して絞り込む |
| 絞り込み対象モード | write モードのみ（verify は履歴内容を読まないため対象外） |
| W4-D 時刻基準 | 履歴ファイルの作成日時（FSタイムスタンプ）。Windows は CreationTime 優先、取得不能時 LastWriteTime にフォールバック |
| W4-C 判定ロジック | 現行どおり維持（ユーザー精緻化済み）。1 分一律 FAIL ではなく、該当 Step の処理内容から最低実行時間を見積もり、生成間隔が明らかに短すぎる場合のみ FAIL（妥当なら PASS）。本変更では生成間隔計算の時刻ソースを FS 作成日時へ統一するのみ |
| スクショ導出 | 履歴ファイル `...-{step_id}.txt` と同名ベースの `...-{step_id}.png`（なければ `.err`） |
| 撮り直し | 行わない（検証時点動作。撮り直しは step-history-writer の専管） |

## 変更1: W4 冒頭に「照合キー導出と成果物フォルダパスによる履歴絞り込み」を追加（REQ-C-004）

W4 の履歴ファイル glob 導出の直後に、照合キーの決定と絞り込み工程を新設する。

### before

```markdown
### W4. 履歴ファイル存在・タイムスタンプ検証

skill_name から当該フェーズスキルの SKILL.md を Read し、Process の各 Step（前処理・Step群・後処理）を列挙する。各 Step に対応する履歴ファイル `.aide/tmp/session-history-{skill_name}-*.txt` を glob で導出する。

#### A. 履歴ファイルの存在確認
```

### after

```markdown
### W4. 履歴ファイル存在・タイムスタンプ検証

skill_name から当該フェーズスキルの SKILL.md を Read し、Process の各 Step（前処理・Step群・後処理）を列挙する。各 Step に対応する履歴ファイル `.aide/tmp/session-history-{skill_name}-*.txt` を glob で導出する。

#### 0. 照合キーの決定と成果物フォルダパスによる絞り込み

**(1) 照合キーを決定する（WF 種別で導出方法が分岐する。導出は compliance-checker 側で完結する）**

skill_name の接頭辞から WF 種別を判別し、以下のとおり「照合キー（照合対象の成果物フォルダパス）」を決定する。

擬似手順:

```
# 入力: skill_name（既存）, progress_file_path（既存）, changes_dir（write 既存入力。changes_dir 系 WF のみ渡る）
if skill_name が fs-change- / fs-bugfix- / fs-refactoring- のいずれかで始まる:
    # changes_dir 系（作業別サブフォルダを持つ WF）
    照合キー = changes_dir            # write 入力の既存値をそのまま使う（AC-004-4）
elif skill_name が fs-design- / fs-impl- / fs-planning- / fs-reverse- のいずれかで始まる:
    # feature フォルダ導出系（作業別サブフォルダを持たない WF）
    照合キー = feature フォルダパスを導出する（下記）   # progress_file_path / skill_name から（AC-004-5）
```

- **`changes_dir` 相当を持つ WF（接頭辞 `fs-change-` / `fs-bugfix-` / `fs-refactoring-`）:** write モードの既存入力パラメータ `changes_dir` をそのまま照合キーとして使う（呼び出し元から渡された値。入力シグネチャ変更なし。AC-004-4）。
- **`changes_dir` 相当を持たない WF（接頭辞 `fs-design-` / `fs-impl-` / `fs-planning-` / `fs-reverse-`）:** これらの WF のフェーズスキルは作業別サブフォルダを持たず、成果物は feature フォルダ `.aide/specs/{feature_name}` 配下に置かれる。compliance-checker は次のいずれかで feature フォルダパスを**機械的に導出**して照合キーとする（AC-004-5）:
  - **progress_file_path の親ディレクトリ:** `progress_file_path` は `.aide/specs/{feature_name}/{wf}-progress.md` 形式である。その親ディレクトリ `.aide/specs/{feature_name}` を取り出して照合キーとする（例: `.aide/specs/aide-powers/design-progress.md` → 親 `.aide/specs/aide-powers`）。
  - **skill_name からの組み立て（フォールバック）:** `progress_file_path` から導出できない場合は、`skill_name`（`fs-{workflow}-phase{N}-{name}`）等から特定した `{feature_name}` で `.aide/specs/{feature_name}` を組み立てて照合キーとする。
- いずれの導出も compliance-checker 側のロジックで完結する。設計／実装／企画／逆引きの各 WF のフェーズスキル（phase-compliance-check 呼び出し）に `changes_dir` を新たに渡す改修は不要（AC-004-7）。

**(2) 各履歴メタの成果物フォルダパスを照合キーと文字列照合して絞り込む**

glob で導出した各履歴ファイルについて、ファイル内のメタ情報行 `- 成果物フォルダパス: {値}` を読み取り、(1) で決定した照合キーと文字列照合する。

- メタ情報の成果物フォルダパスが照合キーと一致する履歴ファイルのみを、以降の検証対象（A〜D および W5）に含める。
- 一致しない履歴ファイル（別の成果物フォルダに属する作業の履歴）は検証対象から除外し、その存在・内容を PASS/FAIL 判定に一切影響させない。
- メタ情報の成果物フォルダパスが `(未指定)` の履歴ファイルは、照合キーと一致しないため検証対象から除外する（誤って今回の作業の履歴とみなさない）。
- **照合は文字列一致で行う。** 双方ともプロジェクトルートからの相対パス形式である前提（step-history-writer がそう記録し、compliance-checker が同形式で照合キーを導出する）。末尾スラッシュの有無のみが異なる場合は一致とみなしてよい。
- 絞り込みの結果、照合キーに一致する履歴ファイルが **1 つも残らない** 場合 → FAIL（理由: 「セッション履歴ファイルが存在しない」）。これは下記 A の FAIL ルールと同一の扱い。

> final-check フェーズのように複数の前フェーズを検証する場合も、各フェーズの skill_name から導出した履歴に対して、同一の照合キー（当該フェーズ／WF に応じて (1) で決定したもの）による絞り込みを適用する。

#### A. 履歴ファイルの存在確認
```

### 変更理由

- REQ-C-004 AC-004-1/AC-004-2。複数の成果物フォルダ（changes_dir 等）の履歴が `.aide/tmp/` に混在した場合に、今回の作業と無関係な履歴を誤って検証対象に含めないため、メタ情報の成果物フォルダパスを照合キーと照合して絞り込む。
- **照合キーの導出方式の確定（AC-004-4〜7）:** REQ-C-004 で確定したとおり、照合キーは WF 種別で導出する。`changes_dir` 相当を持つ WF（変更／バグ修正／リファクタリング）は write 入力 `changes_dir` をそのまま照合キーに使う（AC-004-4）。`changes_dir` 相当を持たない WF（設計／実装／企画／逆引き）は `progress_file_path` の親ディレクトリまたは `skill_name` から feature フォルダパス `.aide/specs/{feature_name}` を機械的に導出して照合キーに使う（AC-004-5）。この導出した照合キーは、step-history-writer がこれらの WF で記録する `artifact_dir`（feature フォルダパス）と一致するため絞り込みが機能する（AC-004-6）。
- **fs-* への改修は不要（AC-004-7）:** 照合キーの導出は compliance-checker 側で完結するため、設計／実装／企画／逆引きの各 WF のフェーズスキルの phase-compliance-check 呼び出しに `changes_dir` を新たに渡す改修は不要であり、これらの fs-* の phase-compliance-check 呼び出しは変更しない。これにより、前回 QA レビューで指摘された「artifact_dir と changes_dir の一致根拠が未担保」「fs-* スコープを差分設計が自己宣言で拡張」という FAIL 要因は、要件スコープ（fs-* 本体改修はスコープ外）と整合する形で解消される。
- AC-004-3。絞り込み後に 0 件なら既存の「セッション履歴ファイルが存在しない」FAIL ルール（W4-A）をそのまま適用する。既存 FAIL ルールを変えず、glob 後にフィルタ工程を挟む拡張に留める（OCP遵守）。
- `(未指定)` フォールバック履歴の扱い: approach.md「フォールバックと REQ-C-004 絞り込みの相互作用」の論点に対し、本設計では **`(未指定)` は除外** とする。経路A 採用により呼び出し元が確実に値を渡すため、`(未指定)` は引数追加漏れ・新規 WF 等の例外時のみ発生する想定であり、それを今回作業の履歴として救済すると別作業の履歴を誤検証する恐れがある。除外側に倒し、結果 0 件なら既存どおり FAIL（AC-004-3）とする。
- `changes_dir` 相当を持つ WF では `changes_dir` が write モードの既存入力のため、入力シグネチャ変更なし。`changes_dir` 相当を持たない WF でも compliance-checker が `progress_file_path`・`skill_name` から照合キーを自己導出するため入力シグネチャ変更なし。verify モードは履歴内容を読まないため絞り込み対象外。

## 変更2: W4-D 時刻検証をファイル作成日時（FSタイムスタンプ）基準へ変更（REQ-C-008）

W4-D は現行「メタ情報の完了日時とファイル更新時刻の乖離検出」だが、step-history-writer のメタから完了日時が削除される（REQ-C-008）ため、参照元をファイルシステムのタイムスタンプ基準に差し替える。

### before

```markdown
#### D. メタ情報の完了日時とファイルタイムスタンプの整合性チェック
- 各履歴ファイル内の `完了日時:` の記載値と、ファイルの実際の更新時刻を比較する
- 両者が大幅に乖離（2時間以上）している場合 → FAIL（理由: 「履歴ファイル {ファイル名} のメタ情報完了日時（{記載値}）とファイル更新時刻（{実タイムスタンプ}）が大幅に乖離している」）
```

### after

```markdown
#### D. 履歴ファイル作成日時（ファイルシステムのタイムスタンプ）による時刻検証
- 各履歴ファイルの実際の作成日時（ファイルシステムのタイムスタンプ）を取得し、これを時刻検証の基準とする。**履歴メタ情報の完了日時には依存しない**（メタ完了日時は REQ-C-008 により廃止済み。本チェックはメタ完了日時を参照しない）。
- 作成日時の取得手段はプラットフォーム依存である。Kiro IDE / Kiro CLI（Windows 主環境）では PowerShell の `Get-Item` を用いる:
  - 作成日時: `(Get-Item ".aide/tmp/session-history-{skill_name}-{step_id}.txt").CreationTime`
  - 更新日時（作成日時が取得不能な環境のフォールバック）: `(Get-Item ...).LastWriteTime`
  - bash 環境では作成日時が取得できない場合があるため、GNU: `stat -c '%W %Y %n'`（%W=作成, %Y=更新。%W が 0/未対応なら %Y を用いる）、macOS/BSD: `stat -f '%B %m %N'`（%B=作成, %m=更新）を用いる。
- **基準の用い方:**
  - 作成日時（CreationTime / %W / %B）が取得できる場合はそれを時刻検証の基準とする。
  - 作成日時が取得不能（0・未対応）の場合は更新日時（LastWriteTime / %Y / %m）を基準とする。
  - 取得した作成日時を、W4-B（タイムスタンプ順序検証）・W4-C（短時間一括生成検出）の時刻ソースとしても用いる。**W4-C は現行どおり「該当 Step の処理内容（サブエージェント呼び出し・ユーザー承認取得・Read/Write 回数・条件分岐等）から実行に合理的に必要な最低時間を見積もり、実際の生成間隔がそれに対して明らかに短すぎる場合のみ FAIL（妥当なら PASS）」という判定ロジックを維持し、その「実際の生成間隔」を計算する際の時刻ソースを FS タイムスタンプ（作成日時）に統一する。** 本変更は W4-C の判定ロジック自体は変えず、時刻ソースの一本化のみを行う。
- 本 D 単独では、メタ完了日時とファイル時刻の「乖離比較」は行わない（比較対象のメタ完了日時が存在しないため）。乖離比較に起因する FAIL・ユーザー確認は廃止する。
- 時刻の異常（W4-B の順序逆転・W4-C で「Step の処理内容に対し生成間隔が短すぎる」と判定されたケース）は引き続き FAIL とする。
```

### 変更理由

- REQ-C-008 AC-008-3/AC-008-4。step-history-writer のメタから完了日時が削除されるため、メタ完了日時参照を廃し、客観的なファイルシステムのタイムスタンプ（作成日時）を時刻検証の基準に切り替える。完了日時メタへの依存を compliance-checker 内に一切残さない。
- AC-008-5。AI が手書きする完了日時とファイル実時刻が約 11 時間規模で乖離し W4-D で毎回ユーザー確認が発生していた検証ノイズを解消する。メタ完了日時を参照しないため、この乖離自体が発生しなくなる。
- Windows での扱い（approach.md 申し送り）: 作成日時（CreationTime）を優先し、取得不能時は更新日時（LastWriteTime）にフォールバックする方針を明記。Windows の `Get-Item` で両者を取得できる。
- W4-B/W4-C は既存ロジックを維持しつつ時刻ソースのみ FS タイムスタンプに統一し、本変更（メタ完了日時廃止）と整合させる。特に W4-C は、ユーザーが別途精緻化済みの現行ロジック（1 分一律 FAIL ではなく、該当 Step の処理内容から最低実行時間を見積もり、生成間隔が短すぎる場合のみ FAIL／妥当なら PASS）をそのまま維持し、その生成間隔計算の時刻ソースのみを FS 作成日時へ統一する。この時刻ソース統一は REQ-C-008（メタ完了日時削除）とは独立だが、時刻の客観基準を FS タイムスタンプに一本化する点で W4-D 改修と一体であるため、本変更2 の中で明記する。これらの FAIL ルール自体は変更しない（スコープ厳守）。

## 変更3: 判定原則「軸1: W3〜W4」のリストを現行 W4-C / W4-D に整合（REQ-C-008・軽微）

判定原則セクションの「軸1: W3〜W4 — 証跡の物理的検証」の箇条書きに、(1) メタ完了日時乖離を前提とした行（廃止する W4-D の旧仕様）と、(2) 「1分以内一括生成 → FAIL」という旧 W4-C を前提とした要約行が残っている。前者は削除し、後者は現行 W4-C（1 分一律ではなく処理内容ベースで生成間隔の短さを判定）の趣旨に合う文言へ更新する。

### before

```markdown
- 署名不一致 → FAIL
- タイムスタンプ逆転 → FAIL
- 1分以内一括生成 → FAIL
- メタ情報と実タイムスタンプの乖離（2時間以上）→ FAIL
- 成果物欠落・10行未満 → FAIL
```

### after

```markdown
- 署名不一致 → FAIL
- タイムスタンプ逆転 → FAIL
- 処理内容に対し生成間隔が短すぎる → FAIL
- 成果物欠落・10行未満 → FAIL
```

### 変更理由

- REQ-C-008。「メタ情報と実タイムスタンプの乖離（2時間以上）→ FAIL」は廃止する W4-D の旧仕様に対応する行であり、メタ完了日時の削除に伴い削除する。
- 「1分以内一括生成 → FAIL」は、現物 W4-C がユーザーによって「1 分以内なら一律 FAIL」から「該当 Step の処理内容から見積もった最低実行時間に対し、実際の生成間隔が明らかに短すぎる場合のみ FAIL（妥当なら PASS）」へ精緻化されたことにより、要約行として不整合になっている。判定原則の要約行を現行 W4-C の趣旨に合う「処理内容に対し生成間隔が短すぎる → FAIL」へ更新し、本体ロジックと矛盾しないようにする。本更新は要約行の文言整合であり、W4-C 本体の判定ロジックは変更しない（スコープ厳守）。
- タイムスタンプ逆転（W4-B）の機械的判定行は維持する。

## 変更4: W5 にスクリーンショット照合観点を追加（REQ-C-005）

W5（履歴内容検証）の偽装検出に、履歴テキストと対になるスクリーンショットを物証として活用する観点を追加する。既存の W5-1（プロセス実行チェック）・W5-2（偽装検出チェック）の各サブ項目は変更せず、新たに **W5-3（スクリーンショット照合チェック）** を追加する。

### before

W5 には W5-1（プロセス実行チェック）と W5-2（偽装検出チェック）のみが存在し、スクリーンショットに関する観点はない。W5 前準備は以下。

```markdown
#### 前準備（各 Step/前処理/後処理ごとに繰り返す）

**1. 対象 Step の記述を SKILL.md から抜き出す**
...
**2. 対応する履歴ファイルを Read で読み込む**
- `.aide/tmp/session-history-{skill_name}-*.txt` のうち、当該 Step に対応するファイルを読み込む

**3. → W5-1 を実行する**

**4. → W5-2 を実行する（W5-1 が PASS でも FAIL でも必ず実行する）**
```

### after

前準備に「対応スクショの読み込み」と「W5-3 の実行」を追加する。

```markdown
#### 前準備（各 Step/前処理/後処理ごとに繰り返す）

**1. 対象 Step の記述を SKILL.md から抜き出す**
...
**2. 対応する履歴ファイルを Read で読み込む**
- `.aide/tmp/session-history-{skill_name}-*.txt` のうち、当該 Step に対応するファイルを読み込む

**2'. 対応するスクリーンショット（または `.err`）を特定する**
- 当該履歴ファイル `...-{step_id}.txt` と同名ベースで拡張子を変えた `...-{step_id}.png`（画像）または `...-{step_id}.err`（撮影失敗代替）を特定する。
- 画像が存在する場合は内容（写っている文言）を読み取れる手段で読み込む。`.err` が存在する場合はその内容（失敗理由）を読み込む。

**3. → W5-1 を実行する**

**4. → W5-2 を実行する（W5-1 が PASS でも FAIL でも必ず実行する）**

**5. → W5-3 を実行する（W5-1 / W5-2 の結果に関わらず必ず実行する）**
```

さらに、W5-2 の直後に W5-3 セクションを新設する。

```markdown
---

#### W5-3. スクリーンショット照合チェック

W5-1 / W5-2 の完了後、**必ず** W5-3 を実行する。本チェックは、履歴テキストと対になるスクリーンショット（step-history-writer が screenshot-capture 経由で保存した物証）を独立して検証する。

**番人としての独立検証（最重要）:**
compliance-checker は step-history-writer の一次保証（撮影時の写り込み確認）を **信頼しない**。step-history-writer は検証される側であり、撮影時チェックをサボる・すり抜ける可能性があるため、compliance-checker は番人として検証時に独立して照合する。

**検証時点動作・撮り直ししない（最重要）:**
compliance-checker は検証時点（フェーズ完了時）に動作し、過去 Step の画面は再現できない。**撮り直し依頼は行わない**（撮り直しは step-history-writer の専管）。検証時点で文言が写っていない／一致しない場合は、撮影時チェックをすり抜けた異常＝偽装または不備として扱う。

##### W5-3-A. スクショ文言と履歴テキストの一致（改ざん検出）
- 当該 Step のスクショ内に表示されている文言（読み取れる範囲）が、当該履歴テキストに存在するかを確認する。
- スクショ全体が写っている必要はない。表示されている一部分でも履歴テキストとの一致が取れれば、その点については一致とみなす（**部分一致許容**）。
- スクショに写っている文言が履歴テキストにまったく存在しない（履歴テキストがスクショと無関係に書き換えられた疑い）→ FAIL（理由: 「Step X: スクショに表示された文言が履歴テキストに存在しない。履歴改ざんの疑い」）。

##### W5-3-B. 該当 Step 文言の写り込み独立検証
- 当該 Step の実行に関わる文言（Step タイトル・主要な処理・ユーザーとのやり取り等）が、スクショに写っているかを独立して確認する（step-history-writer の一次保証を信頼せず自前で確認する）。
- 写っていない場合 → 撮影時チェックをすり抜けた異常として扱う（理由: 「Step X: 該当 Step の文言がスクショに写っていない。偽装または撮影不備の疑い」）。

##### W5-3-C. 偽装パターンの判定
次のいずれかに該当する場合は偽装と判定する。
- (a) 複数 Step のスクショが**同一画面ばかり**である（理由: 「複数 Step のスクショが同一画面で、各 Step を実際に実行した物証になっていない」）。
- (b) スクショの内容がその Step の実行に**関わるものでない**（理由: 「Step X のスクショ内容が当該 Step の実行と無関係」）。
- (c) **chat（会話）画面が写っていない**（理由: 「Step X のスクショに chat 画面が写っておらず、実行の物証にならない」）。

##### W5-3-D. `.err`（撮影失敗代替）が存在する場合
- スクショ画像の代わりに `.err` が存在する場合、compliance-checker は **撮影できない環境（ディスプレイなし等）であるかをユーザーに直接確認する**（compliance-checker のユーザー確認の直接実施方針に従う）。
- 環境起因（撮影不可環境）であることが確認できた場合 → スクショ不在を偽装として FAIL にしない（当該 Step の W5-3-A/B/C はスクショ不在を理由に FAIL としない）。
- 環境起因であることが確認できない（撮影可能なはずなのに `.err`）→ 偽装または不備の疑いとして扱う。
- システム的にサブエージェントからユーザーへ直接確認できない場合は、compliance-checker の既存方針（確認不要でそのまま進めてよい）に従う。

##### W5-3 の判定と撮り直し非実施
- 検証時点で該当 Step の文言が写っていない／一致が取れない場合は、撮影時チェックをすり抜けた異常＝偽装または不備として扱う。**即 FAIL とするか、ユーザー確認を挟むかは、既存 compliance-checker のユーザー確認方針（FAIL 時のユーザー通知）に従う。**
- compliance-checker は撮り直し依頼を行わない（検証時点動作のため）。
```

## W7 完了日時について（変更なし・確認）

W6/W7 が進捗ファイルへ記録する「完了日時」は **進捗ファイル側の記録** であり、step-history-writer の履歴メタの「完了日時」とは別物である。REQ-C-008 が削除するのは履歴メタの完了日時のみであり、進捗ファイルの完了日時（W6/W7）は変更しない。

- W6「ステータステーブルを `✅ 完了` + 完了日時に更新」→ **変更なし**。
- W7「フェーズ詳細セクションに完了日時を追記」→ **変更なし**。

> この区別を delta-design に明記するのは、REQ-C-008 の「完了日時削除」が compliance-checker の進捗ファイル更新（W6/W7）に波及すると誤解されないようにするため。本変更は履歴メタの完了日時（step-history-writer 出力）と、それを参照していた W4-D のみを対象とする。
