# 対応方針書: スクリーンショット証跡による履歴偽装検出の強化

## 方針概要

- **対応方針: 両方（追加 + 既存変更）**
  - 追加: スクリーンショット撮影の単一責任共通スキルを新規作成（REQ-C-001）。
  - 既存変更: step-history-writer（REQ-C-002 / REQ-C-003 / REQ-C-008 / REQ-C-009）、compliance-checker（REQ-C-004 / REQ-C-005 / REQ-C-008）、dev-environment.md（REQ-C-006）に加え、全 7 ワークフローの全フェーズスキル fs-*（約 37〜41 スキル）の step-history-writer 呼び出し箇所（REQ-C-007）を変更。さらに、step-history-writer のメタ情報からの完了日時削除（REQ-C-008）と、compliance-checker の時刻検証の W4-D ファイル作成日時基準化（REQ-C-008）を行う。あわせて、step-history-writer に現 Step 履歴の書き込み前の前処理・前 Step 履歴の欠落検出と欠落先頭 Process からのやり直し促し工程を追加する（REQ-C-009）。さらに、本変更で screenshot-capture が新規生成する `.aide/tmp/session-history-*.png`/`.err` を確実に清掃するため、final-check 系7スキル（fs-bugfix-phase3 / fs-change-phase3 / fs-design-phase11 / fs-impl-phase7 / fs-planning-phase4 / fs-refactoring-phase7 / fs-reverse-phase6）の一時ファイルクリーンアップ範囲を拡張し、想定外の残ファイルをユーザー確認の上で削除する処理を追加する（REQ-C-010）。なお REQ-C-004 の履歴絞り込みは、`changes_dir` 相当を持つ WF（変更/バグ修正/リファクタリング）は `changes_dir` をそのまま照合キーに、持たない WF（設計/実装/企画/逆引き）は compliance-checker 側で `progress_file_path`・`skill_name` から feature フォルダパスを導出して照合キーとする方式とする（導出は compliance-checker 側で完結し、これらの WF の fs-* 呼び出しには波及しない）。

- **OCP検討結果（サマリ）:**
  - スクショ撮影能力は step-history-writer 内へ pyautogui ロジックを埋め込むのではなく、**新規の単一責任スキルとして「追加」し、step-history-writer は activate して呼ぶだけ**にする。これにより撮影手段（ライブラリ・`.err` 代替・`.venv` 導入）の変更が step-history-writer 本体へ波及しない（拡張による対処＝OCP遵守）。
  - 最大の論点 REQ-C-003 は、**経路A採用（ユーザー決定）。step-history-writer の入力に成果物フォルダパス（汎用名）を追加し、全フェーズスキルがその値を渡す**方式とする。当初の対応方針では経路A を OCP 違反（fs-* 群への引数追加波及）として不採用とし経路B（自己導出）を推奨していたが、ユーザーが「step-history-writer の入力を変える」ことを明示決定したため、経路A を採用する。
  - これにより fs-* 群への引数追加波及が生じるが、**これはユーザー決定によりスコープに含めたものである**（change-requirements.md の対象外節も、fs-* の step-history-writer 呼び出し改修（REQ-C-007）を**正式にスコープ内**として明記している）。波及は「step-history-writer 呼び出し箇所への成果物フォルダパス引数追加のみ」に限定され、**フェーズ構成・Process 手順・各フェーズの責務変更等の改修は一切伴わない**（機械的な引数追加に留まる）。なお REQ-C-009（step-history-writer SKILL.md 自体の改修）・REQ-C-004（compliance-checker 側ロジックでの照合キー導出）は fs-* 呼び出し側の改修ではなく、設計/実装/企画/逆引きの各 WF の phase-compliance-check 呼び出しには手を入れない。これらの範囲を超える fs-* 本体改修（フェーズ構成・Process 手順・責務変更）のみがスコープ外である。
  - REQ-C-004 の絞り込みに使う照合キーは WF 種別で導出方法が分かれる。`changes_dir` 相当を持つ WF（変更/バグ修正/リファクタリング）では compliance-checker の write モード入力に**既存**する `changes_dir` をそのまま照合キーに使うため、入力シグネチャの追加波及はない。`changes_dir` 相当を持たない WF（設計/実装/企画/逆引き）では compliance-checker が `progress_file_path`・`skill_name` から feature フォルダパス（`.aide/specs/{feature_name}`）を**自身で導出**して照合キーとするため、これらの WF の fs-* 呼び出しへの波及はない。いずれも内部ロジック（W4/W5）の拡張に限定できる。
  - REQ-C-004 / REQ-C-005 は既存の署名検証（W3）・テキスト履歴検証（W5 既存ロジック）を**変更せず、検証観点を追加**する形（拡張）で実現できる。
  - 結論: 本変更は「新規スキル 1 つの追加」＋「中核 3 ファイルへの非破壊な観点・工程の追加」＋「fs-* 群への機械的な引数追加（ユーザー決定でスコープ化、責務・構造は不変）」で構成される。経路A 採用に伴う fs-* への波及はユーザー決定済みであり、波及内容が引数追加に限定され破壊的でないため、OCP 上の懸念は許容範囲とする。
  - REQ-C-008（メタ完了日時削除 + 時刻検証の基準差し替え）は、既存メタ項目の削除と既存検証（W4-D 相当）の参照元差し替えに留まる非破壊な観点変更であり、署名検証・テキスト履歴検証等の他ロジックや入力シグネチャには影響しない。OCP 検討サマリ全体の判断を変えるものではない。
  - REQ-C-009（step-history-writer の履歴欠落検出・やり直し促し）は、step-history-writer の Process に「現 Step 書き込み前の前処理・前 Step 履歴の存在確認 → 欠落時のユーザー通知・やり直し促し」工程を追加する拡張であり、中核責務（会話履歴のそのまま転記・step_id ごと 1 ファイル）や入力シグネチャは不変。書き込み前チェック工程の追加に留まるため、OCP 検討サマリ全体の判断を変えるものではない。

## 変更方針の詳細

### REQ-C-001 スクリーンショット撮影スキル新規作成

- **方針: 追加（新規共通スキル）。** 撮影機能を step-history-writer へ直接埋め込まず、独立した単一責任スキルとして切り出す。
- **OCP評価:** 撮影手段（pyautogui 採用・`.venv` 導入手順・`.err` 代替・将来の OS 別撮影方法の差し替え等）が変化しても、呼び出し側（step-history-writer）は「保存先パスを渡して activate する」インターフェースのみに依存するため、呼び出し側を変更せずに撮影実装を拡張・差し替えできる。撮影という関心事を 1 箇所に閉じ込めることで、他スキルからの再利用（拡張）も容易。
- **責務境界:** 本スキルは「画面を撮る / `.err` 代替 / `.venv` 導入」のみを担い、履歴ドメインの判断（何が写っているべきか）は持たない。写り込み妥当性の確認は呼び出し側（REQ-C-002）の責務とする（AC-001-6）。
- **実現可能性:** 既存資産への影響なし（純粋な追加）。配布は setup 系のディレクトリ一括コピーで自動対象となるため、setup.bat 等への追記波及もない（影響分析どおり）。

### REQ-C-002 step-history-writer スクリーンショット保存

- **方針: 既存変更（工程追加）。** 履歴ファイル書き出し Process に「REQ-C-001 スキルを activate 呼び出しして同名・拡張子違いの画像を保存する」工程を追加する。あわせて撮影時の写り込み確認・撮り直し依頼（一次保証）を追加する。
- **OCP評価:** step-history-writer の既存の中核責務（会話履歴をそのまま転記・step_id ごと 1 ファイル）は変更せず、撮影呼び出し工程を追記する拡張に留まる。撮影の具体手段は REQ-C-001 側へ委譲しているため、撮影手段の変更が step-history-writer に波及しない。
- **既存原則との整合:** 撮影スキルの呼び出しも step-history-writer の「毎 Step activate 必須・自己流直書き禁止」原則に従って activate 経由で行う（AC-002-1）。撮影失敗は履歴書き出しの成否を妨げない（AC-002-4）ため、既存のエラー時動作（フェーズ中断しない）と整合する。

### REQ-C-003 成果物フォルダパス（★経路A採用＝ユーザー決定）

REQ-C-003 は本変更最大の論点であり、step-history-writer が「成果物フォルダパス（汎用名）」をどこから入手するかを決める。**結論として、ユーザー決定により経路A（step-history-writer の入力パラメータに成果物フォルダパスを追加）を採用する。**

- **方針: 既存変更（入力パラメータ追加）。** step-history-writer の入力に成果物フォルダパス（汎用名）を追加し、呼び出し元のフェーズスキルから受け取った値をメタ情報セクションに 1 行記録する。step-history-writer 自身は導出せず、渡された値をそのまま記録する。
- **入力パラメータは汎用名とする。** `changes_dir` は変更/バグ修正/リファクタリングの 3 WF にしか存在しないため、設計/企画/実装/逆引きの各 WF でも自分の成果物フォルダパスを渡せる汎用名（例: artifact_dir 等）が妥当。**最終的な引数名・各 WF のパス導出方法の詳細は設計工程で確定する。**
- **OCP評価:** 経路A は fs-* 群の呼び出し箇所すべてに引数追加が波及する。これは本来 OCP 上の懸念点だが、ユーザーが「step-history-writer の入力を変える」ことを明示決定したため採用する。波及内容は呼び出し箇所への機械的な引数追加に限定され、各スキルの責務・構造は不変であるため、破壊的変更ではない（fs-* 群の改修詳細は REQ-C-007 を参照）。
- **フォールバック（旧経路C 相当）:** 呼び出し元から成果物フォルダパスが渡されなかった場合の代替表記（空欄可否・代替文字列）を AC-003-3 の位置づけで定義し、その場合でも履歴ファイルの書き出し自体は成功させる。具体表記は差分設計工程で決定する。
- **AC との整合:** AC-003-2（changes_dir と文字列照合可能な相対パス形式）を満たすよう、記録値はプロジェクトルートからの相対パス形式とする（具体的正規化手順は差分設計工程）。AC-003-4（入力パラメータ方式・自己導出に依存しない）、AC-003-5/AC-003-6（全 fs-* が渡す・WF 種別ごとのパス定義）は REQ-C-007 と一体で満たす。

#### 検討の記録（経路A/B/C の比較評価）

当初の対応方針検討では以下の 3 経路を比較していた。ユーザー決定により**経路A を採用**したため、以下は意思決定の記録として残す。

**経路A: step-history-writer の入力パラメータに成果物フォルダパスを追加（採用）**
- **影響度:** 全 7 WF・約 37〜41 フェーズスキルの全 step-history-writer 呼び出し箇所（各 Step）に引数追加が波及する。
- **評価:** 当初は「既存の多数の安定モジュール（fs-* 群）を一斉に変更する」点を OCP 違反と評価し不採用としていた。しかしユーザーが入力パラメータ変更を明示決定したため採用。波及は機械的な引数追加に限定され破壊的でない点、および呼び出し元が成果物フォルダパスを確実に保持している（コンテキスト依存の不確実性がない）点が採用根拠。
- **判定: 採用（ユーザー決定）。**

**経路B: step-history-writer が成果物フォルダパスを自己導出（不採用）**
- **考え方:** step-history-writer がワークフロー実行コンテキスト（進捗ファイルパス・作業中の changes_dir 等）から成果物フォルダパスを自己導出し、fs-* 群を変更せずに済ませる。
- **評価:** fs-* への波及はゼロだが、「コンテキストから確実に導出できるか」が技術的に不確実（現行入力は skill_name / step_id / step_title の 3 つのみで changes_dir を渡していない）。自己導出が安定しないと代替表記の発動頻度が上がり REQ-C-004 の絞り込みが効きにくくなる懸念があった。
- **判定: 不採用。** 不確実性を排除するためユーザーは経路A を選択した。

**経路C: 取得不可時の代替表記（フォールバックとして存続）**
- **考え方:** 成果物フォルダパスを入手できない場合でも代替表記を記録し、履歴ファイルの書き出し自体は成功させる。
- **評価:** 経路A 採用後は「呼び出し元から渡されなかった場合」のフォールバックとして AC-003-3 の位置づけで存続する。
- **判定: フォールバックとして残す（上記「フォールバック」項参照）。**

### REQ-C-004 compliance-checker 履歴絞り込み

- **方針: 既存変更（内部ロジック追加）。** W4 の履歴ファイル glob 導出後に「各履歴メタ情報の成果物フォルダパスが、compliance-checker が決定する照合キーと一致するもののみを検証対象に含める」絞り込みを追加する。
- **照合キーの導出（WF 種別で分岐・compliance-checker 側で完結）:**
  - **`changes_dir` 相当を持つ WF（変更/バグ修正/リファクタリング）:** write モードの**既存入力**である `changes_dir` をそのまま照合キーとして使う。
  - **`changes_dir` 相当を持たない WF（設計/実装/企画/逆引き）:** これらの WF のフェーズスキルは作業別サブフォルダを持たず成果物は feature フォルダ `.aide/specs/{feature_name}` 配下に置かれるため、compliance-checker が write 入力の `progress_file_path`（`.aide/specs/{feature_name}/{wf}-progress.md` 形式）の親ディレクトリ、または `skill_name` から feature フォルダパス `.aide/specs/{feature_name}` を機械的に導出し、それを照合キーとして使う。
  - この導出は **compliance-checker 側のロジックで完結**する。設計/実装/企画/逆引きの各 WF のフェーズスキル（phase-compliance-check 呼び出し）に `changes_dir` を新たに渡す改修は不要であり、これらの fs-* の phase-compliance-check 呼び出しは変更しない。

  - 影響分析で「既存の署名検証（W3/W4）・テキスト履歴検証（W5-1/W5-2）ロジックそのものの変更はスコープ外」と明記されており、内部構造改善の対象も存在しない。
- **結論:** 別途リファクタリングワークフローへ委譲すべき事項はない。本変更内で対応方針どおり進められる。

## 対応方針上の前提・リスク（ユーザー確認が必要な点）

以下は対応方針上の前提・留意点である。経路A 採用（ユーザー決定）により、当初の最重要リスク（経路B の成立性）は解消した。残る留意点と申し送りを整理する。

1. **経路A 採用に伴う留意点（旧リスク1「経路B の成立性」は解消）**
   - 当初の最重要リスクは「経路B（step-history-writer の自己導出）が同一セッションのコンテキストから成果物フォルダパスを確実に導出できるか」であった。ユーザー決定で**経路A（入力パラメータ方式）を採用**したため、自己導出の不確実性に起因するこのリスクは**解消**した（呼び出し元が確実に保持する値を渡すため）。
   - 一方、経路A 採用に伴う新たな留意点が生じる:
     - **fs-* 全スキルへの引数追加は件数が多い（約 37〜41 スキル）。** 漏れなく全件へ同一の汎用名引数を適用する必要がある（task-orchestration を活用、実装工程）。適用漏れがあるとそのスキルから書き出した履歴に成果物フォルダパスが記録されず、REQ-C-004 の絞り込みが効かなくなる。
     - **設計/企画/実装/逆引きの各 WF が渡す「成果物フォルダパス」が、各 WF で具体的に何を指すか**（changes_dir 相当のフォルダがない WF での定義）を**設計工程で確定する必要がある**。汎用入力パラメータ名の最終決定も設計工程の担当。なお、step-history-writer が記録する artifact_dir と compliance-checker の照合キーの一致根拠は、REQ-C-004 の精緻化により **compliance-checker 側が `progress_file_path`・`skill_name` から feature フォルダパスを導出して照合キーとする方式で担保される**ため、旧来懸念していた「artifact_dir と changes_dir の一致根拠未担保」リスクは**解消**した。設計工程では、各 WF が渡す artifact_dir がこの導出される feature フォルダパス（設計等の WF では `.aide/specs/{feature_name}`）と整合するよう定義すればよい。

2. **フォールバック（旧経路C 相当）の履歴と REQ-C-004 絞り込みの相互作用（軽減）**
   - 呼び出し元から成果物フォルダパスが渡されずフォールバック表記となった履歴は照合キー（changes_dir 相当を持つ WF では `changes_dir`、持たない WF では compliance-checker が導出する feature フォルダパス）と文字列一致しないため、REQ-C-004 の絞り込みで検証対象から外れうる。AC-004-3（履歴 0 件なら FAIL）と組み合わさると、フォールバックが頻発する場合に「全履歴がフォールバック表記 → 絞り込みで 0 件 → FAIL」となる懸念が残る。
   - ただし経路A では呼び出し元が確実に値を渡すため、フォールバック発動は例外的（引数追加漏れ・新規 WF 等）に限定され、旧経路C 中心運用に比べリスクは大きく軽減される。フォールバック表記の履歴を絞り込みでどう扱うか（除外／救済）の確定は、差分設計工程で REQ-C-003 と REQ-C-004 を突き合わせて決める。

3. **スクショ文言読み取り（OCR/ビジョン）能力の前提**
   - REQ-C-005 は compliance-checker がスクショ内文言を読み取り履歴テキストと照合できることを前提とする。具体手段の選定は本変更の対象外だが、「画像文言を読める能力が実行環境で利用可能か」が成立しない場合、スクショ偽装検出が機能しない。
   - → 実行プラットフォーム（Kiro IDE / Kiro CLI）で画像文言読み取りが可能かの前提確認が望ましい。

4. **メタ開発の反映遅延（既知の特殊事情）**
   - skills/・agents/ の編集は setup.bat 再実行＋セッション再起動まで AI Agent 挙動に反映されない（dev-environment.md §0/§11）。実機での撮影・偽装検出の検証は人間の手動検証に委ねる前提となる。

5. **W4-D 時刻検証のファイル作成日時取得の前提（REQ-C-008）**
   - REQ-C-008 後の W4-D は履歴ファイルの実際の作成日時（ファイルシステムのタイムスタンプ）を時刻検証の基準とする。これは実行プラットフォーム（Kiro IDE / Kiro CLI）で `.aide/tmp/` 配下の履歴ファイルの作成/更新日時を取得できることを前提とする。
   - Windows では作成日時（ctime）と更新日時（mtime）の扱いが異なるため、どちらをどう基準に用いるか・取得不能時の代替を差分設計工程で確定する必要がある（下記申し送り参照）。なお完了日時メタの削除自体は履歴書き出しの成否に影響しないため、本前提が満たせない場合でも履歴記録そのものは継続できる。

### 設計工程への申し送り（レビュー指摘の非ブロッキング事項）

- **`.aide/tmp/` のスクショ／`.err` 増加に伴う phase-compliance-check のクリーンアップ範囲の整合:** 本変更で `.aide/tmp/` に画像（`.png` 等）・`.err` ファイルが新たに増えるため、phase-compliance-check 等が `.aide/tmp/` をクリーンアップする際の対象範囲（履歴テキストと対になる画像/`.err` を巻き込まないか・残置すべきか）との整合を、差分設計工程で確認すること。本書ではブロッキングしない申し送りとして記録する。
- **W4-D の時刻検証をファイル作成日時基準に変えるにあたっての具体手段の確定（REQ-C-008）:** `.aide/tmp/` の履歴ファイルの作成日時を取得する具体手段はプラットフォーム依存（Kiro IDE / Kiro CLI 等）であるため、その取得手段と、Windows における作成日時（ctime）／更新日時（mtime）の扱い（どちらを時刻検証の基準に用いるか・取得不能時の代替）を差分設計工程で確定すること。本書ではブロッキングしない申し送りとして記録する。
