> 関連 REQ: REQ-C-002（スクショ呼び出し追加）／ REQ-C-003（入力パラメータ・メタ情報に成果物フォルダパス追加）／ REQ-C-008（メタ情報から完了日時削除）／ REQ-C-009（履歴欠落検出と欠落先頭Processからのやり直し）

## 変更1: 入力パラメータ表に artifact_dir を追加（REQ-C-003）

### before

```markdown
## 入力パラメータ

| パラメータ | 型 | 説明 |
|---|---|---|
| skill_name | string | 呼び出し元フェーズスキル名（例: `fs-change-phase1-analysis`） |
| step_id | string | Step 識別子（例: `"前処理"`, `"step1"`, `"step2"` ...） |
| step_title | string | Step のタイトル文字列（例: `"設計書ゲート"`, `"変更要件ヒアリング"` ...） |
```

### after

```markdown
## 入力パラメータ

| パラメータ | 型 | 説明 |
|---|---|---|
| skill_name | string | 呼び出し元フェーズスキル名（例: `fs-change-phase1-analysis`） |
| step_id | string | Step 識別子（例: `"前処理"`, `"step1"`, `"step2"` ...） |
| step_title | string | Step のタイトル文字列（例: `"設計書ゲート"`, `"変更要件ヒアリング"` ...） |
| artifact_dir | string | 当該作業の成果物フォルダパス（汎用名）。呼び出し元フェーズスキルが渡す（変更/バグ修正/リファクタリングは `changes_dir` 相当、設計/企画/実装/逆引きは各自の成果物フォルダパス）。プロジェクトルートからの相対パス（例: `.aide/specs/aide-powers/changes/{timestamp}-{name}`）。**渡されなかった場合は `(未指定)` を記録する**（自己導出はしない） |
```

### 変更理由

- REQ-C-003 AC-003-1/AC-003-4/AC-003-6。成果物フォルダパスを step-history-writer 自身が導出すると不確実性が残るため、呼び出し元から確実に保持している値を受け取る経路A（ユーザー決定）を採る。
- 汎用名 `artifact_dir` とする理由は、`changes_dir` が変更/バグ修正/リファクタリングの 3 WF にしか存在せず、全 7 WF が同一パラメータ名で各自の成果物フォルダパスを渡せるようにするため（AC-003-6）。
- 自己導出に依存しない旨（AC-003-4）を「自己導出はしない」と明記する。

## 変更2: メタ情報セクションの改訂（成果物フォルダパス追加＋完了日時削除）（REQ-C-003 / REQ-C-008）

Process Step 1 の書き出しテンプレート内「## メタ情報」ブロックを改訂する。

### before

```
# Session History: {skill_name} / {step_id}

## メタ情報
- スキル名: {skill_name}
- Step ID: {step_id}
- Step タイトル: {step_title}
- 完了日時: {YYYY-MM-DD HH:MM}（現在時刻）

## 会話履歴（そのまま転記）
```

### after

```
# Session History: {skill_name} / {step_id}

## メタ情報
- スキル名: {skill_name}
- Step ID: {step_id}
- Step タイトル: {step_title}
- 成果物フォルダパス: {artifact_dir}

## 会話履歴（そのまま転記）
```

> 補足（フォールバック）: `artifact_dir` が呼び出し元から渡されなかった場合、`- 成果物フォルダパス: (未指定)` と記録する。空欄にはしない（compliance-checker の照合・可読性のため）。完了日時行は出力しない。

### 変更理由

- **成果物フォルダパス追加（REQ-C-003 AC-003-1/AC-003-2）:** どの成果物フォルダ（changes_dir 等）に属する作業の履歴かを示し、compliance-checker が `changes_dir` と文字列照合して絞り込めるようにする。記録値はプロジェクトルートからの相対パス形式とし、compliance-checker が受け取る `changes_dir` と照合可能にする（AC-003-2）。
- **フォールバック `(未指定)`（REQ-C-003 AC-003-3）:** 渡されなかった場合でも履歴書き出し自体は成功させる。空欄ではなく明示文字列とすることで、`changes_dir` と誤って文字列一致しないことを保証する。
- **完了日時削除（REQ-C-008 AC-008-1/AC-008-2）:** AI が手書きする完了日時は時刻基準が不安定で、ファイル実時刻と乖離し compliance-checker W4-D の検証ノイズ（毎回のユーザー確認）を生んでいた。手書き完了日時を廃止し、時刻検証はファイルシステムのタイムスタンプ（compliance-checker 側 W4-D 改修）に一本化する。他メタ項目（スキル名・Step ID・Step タイトル・成果物フォルダパス）は維持する。

## 変更3: Process に screenshot-capture 呼び出し工程を追加（REQ-C-002）

Process Step 1 の後段（履歴ファイル書き出し完了後）に、スクリーンショット保存の工程を追加する。

### before

```markdown
4. 書き出し完了を確認する（ファイルが存在すること）

### 記述ルール
```

### after

```markdown
4. 書き出し完了を確認する（ファイルが存在すること）

### Step 2: スクリーンショットの保存（screenshot-capture 呼び出し）

履歴ファイルを書き出した各 Step で、履歴の物証として同名・拡張子違いのスクリーンショットを保存する。

**処理:**

1. スクショ保存先パスを構築する: 履歴ファイル `.aide/tmp/session-history-{skill_name}-{step_id}.txt` と同じベース名で、拡張子を画像用に変えた `.aide/tmp/session-history-{skill_name}-{step_id}.png` とする。
2. **撮影前の写り込み準備（一次保証）:** その Step の chat（会話）画面が表示されている**撮影時点**で撮影することを前提とする。撮影後、撮影したスクショに「該当 Step の関連文言」と「chat（会話）画面」が写っているかを確認する。
3. `screenshot-capture (aide-powers skill)` を **activate して実行する**（自己流の直書き・直接の pyautogui 実行で代替しない）。パラメータ — output_path: `.aide/tmp/session-history-{skill_name}-{step_id}.png`。
4. **撮影結果の確認と撮り直し（一次保証）:**
   - 撮影成功（`.png` が生成され `.err` がない）した場合、スクショに「該当 Step の関連文言」と「chat 画面」が写っているか確認する。写っていなければ、ユーザーにスクロール等で当該 Step の文言・chat 画面が画面に映るよう操作を依頼したうえで、再度 3 を実行して撮り直す。これにより撮影時点で有効な（該当 Step の文言・chat 画面が写った）スクショを保証する。
   - 撮影が成功している（`.err` でない）にもかかわらず、複数回の撮り直しでも写り込みが得られない場合の扱いは、本スキルの既存のユーザー確認・進行方針に従う。
   - 撮影失敗（`.err` が生成された）の場合は、screenshot-capture の仕様どおり同名ベースの `.err` が代替として残る。撮影不可環境（ディスプレイなし等）とみなし、撮り直しは行わない。
5. **撮影の成否は履歴書き出しの成否を妨げない。** スクショ撮影に失敗してもフェーズスキルの実行を中断しない（履歴ファイルの書き出しが成功していれば本スキルの責務は果たされている）。

### 記述ルール
```

> 既存の「### Step 1: 履歴ファイルの書き出し」見出しは維持し、その配下の処理（1〜4）の後に上記「### Step 2: スクリーンショットの保存」を新設する。以降の「### 記述ルール」「### エラー時の動作」見出しは順序・内容を維持する。

### 変更理由

- **activate 経由での呼び出し（REQ-C-002 AC-002-1）:** step-history-writer の「毎 Step activate 必須・自己流直書き禁止」原則（および phase-skill-rules.md 最上位原則）に従い、撮影も screenshot-capture を activate して行う。自己流の pyautogui 直書きを禁止する。
- **同名・拡張子違いの保存先（AC-002-2）:** 履歴テキストとスクショを 1 対 1 で対応づけ、compliance-checker が履歴ファイルから対応スクショを機械的に導出できるようにする。
- **撮影失敗時の `.err` 代替（AC-002-3）:** screenshot-capture の仕様に委譲。step-history-writer 側は `.err` が残ることを前提に進行する。
- **撮影失敗が履歴書き出しを妨げない（AC-002-4）:** 既存のエラー時動作（履歴書き出し失敗はフェーズ中断の理由にならない）と整合させ、スクショ撮影失敗も同様にフェーズを中断しない。
- **撮影時の写り込み確認・撮り直し（一次保証）（AC-002-5）:** 撮影時点でのみ可能な「該当 Step の文言・chat 画面の写り込み確認」を step-history-writer の責務（一次保証）とする。compliance-checker は検証時点で動作し過去画面を再現できないため撮り直しできない。一次保証を step-history-writer が担うことで、撮影時点で有効なスクショを確保する。

## 変更5: 履歴欠落検出と欠落先頭Processからのやり直し（REQ-C-009）

現 Step の履歴ファイルを書き込む**前**に、同一 `skill_name` の「前処理」および現 Step より前に実行されるべき各 Step の履歴ファイルが揃っているかを確認し、欠落（歯抜け）があればユーザーへ通知して欠落の先頭 Process からやり直すよう促す工程を、Process Step 1（履歴ファイルの書き出し）の冒頭に追加する。

> **挿入位置の整理:** REQ-C-009 の欠落チェックは「現 Step 履歴を書き込む前」に行う必要があるため、`### Step 1: 履歴ファイルの書き出し` の **「**処理:**」の 1（出力ファイルパス構築）より前**に挿入する。変更3 で追加した `### Step 2: スクリーンショットの保存` は Step 1 の履歴書き出し完了後の工程であり、本変更5（Step 1 冒頭の書き込み前チェック）とは順序が前後で分離するため矛盾しない。実行順は「Step 1 書き込み前チェック（本変更5）→ Step 1 履歴書き出し（既存・変更2）→ Step 2 スクショ保存（変更3）」となる。

### before

```markdown
### Step 1: 履歴ファイルの書き出し

**処理:**

1. 出力ファイルパスを構築: `.aide/tmp/session-history-{skill_name}-{step_id}.txt`
2. `.aide/tmp/` ディレクトリが存在しない場合は作成する
```

### after

```markdown
### Step 1: 履歴ファイルの書き出し

> **書き込み前チェック（履歴欠落検出・REQ-C-009）:** 下記「**処理:**」の 1 以降（現 Step 履歴の書き込み）へ進む前に、まず本 Step より前に実行されるべき履歴ファイルの欠落を確認する。欠落があればユーザーへ通知し、欠けている先頭の Process からやり直すよう促す。欠落がなければ通常どおり下記の処理へ進む。

**書き込み前チェック手順（履歴欠落検出）:**

A. `skill_name` から当該フェーズスキルの SKILL.md を参照し、その Process 順序（前処理 → Step 1 → Step 2 → …）を取得する。**自己流で順序を推定してはならない**（判定根拠は当該フェーズスキル SKILL.md の Process 順序）。
B. 取得した Process 順序に基づき、「前処理」および現 Step（`step_id`）より前に実行されるべき各 Step について、期待される履歴ファイル `.aide/tmp/session-history-{skill_name}-{当該 step_id}.txt` の一覧を構築する。
C. 一覧の各履歴ファイルが実際に存在するかを確認する。
D. **欠落（歯抜け）がある場合:** ユーザーへ「どの Step／前処理の履歴が欠落しているか」を具体的に通知し、欠けている先頭の Process（前処理、または最初に欠落している Step）からやり直すよう促す。やり直し要否の最終判断や、セッション跨ぎで欠落が説明可能な場合の扱いは、通知を受けたユーザー／オーケストレータが判断する。
E. **欠落がない場合:** 通常どおり下記「**処理:**」へ進み、現 Step の履歴を書き込む（既存の履歴書き込み動作を妨げない）。

**処理:**

1. 出力ファイルパスを構築: `.aide/tmp/session-history-{skill_name}-{step_id}.txt`
2. `.aide/tmp/` ディレクトリが存在しない場合は作成する
```

> 既存の「**処理:** 1〜4」（出力パス構築 → `.aide/tmp` 作成 → Write → 存在確認）および変更2 のメタ情報改訂、変更3 で追加した「### Step 2: スクリーンショットの保存」は順序・内容を維持する。本変更5 は Step 1 冒頭に「書き込み前チェック」ブロックを新設するのみで、既存の処理番号（1〜4）の振り直しは行わない。

### 変更理由

- **書き込み前の欠落確認（AC-009-1）:** 現 Step 履歴の Write より前に、同一 `skill_name` の前処理履歴および現 Step より前の各 Step 履歴の存在を確認する工程を Step 1 冒頭に追加する。これにより履歴の歯抜けを書き込み時点で検知できる。
- **欠落箇所の通知（AC-009-2）:** 手順 D で「どの Step／前処理の履歴が欠落しているか」を具体的にユーザーへ通知する。
- **欠落先頭 Process からのやり直し促し（AC-009-3）:** 手順 D で、欠けている先頭の Process（前処理、または最初に欠落している Step）からやり直すよう促す。最初の欠落起点から実行し直させることで、歯抜けの連鎖を断つ。
- **判定根拠は SKILL.md の Process 順序（AC-009-4）:** 手順 A・B で、欠落判定対象（前処理・現 Step より前の Step）を `skill_name` から当該フェーズスキル SKILL.md の Process 順序を参照して決定する。step-history-writer が自己流で順序を推定することを禁止する。
- **欠落なし時は既存動作を維持（AC-009-5）:** 手順 E で、欠落がなければ通常どおり下記「**処理:**」（既存の履歴書き出し）へ進む。書き込み前チェックは欠落時のみ通知・やり直し促しを発火させ、正常時は素通しするため、既存の履歴書き込み動作を妨げない。
- **位置づけ（final-check の早期前倒し）:** 本工程は、履歴の歯抜け（工程の飛ばし・履歴書き出し漏れ）を final-check（progress-final-checker による全件検証）まで待たず、各 Step の書き込み時点で早期検出するものである。既存 compliance-checker W4-A（履歴ファイルの存在確認＝「記録が存在しない＝FAIL」）の原則を、書き込み時点での早期検出として補完し、欠落の起点から正しく実行し直させることで final-check における履歴欠落起因の FAIL を前倒しで防ぐ。
