## 変更方針の詳細

### 1. 新Step「再現性確認・原因特定」の挿入
- **方針**: 現Step 3（設計書ゲート）と現Step 4（原因分析）の間に新Stepを挿入する。新Stepは以下のサブフローで構成する:
  - 再現性確認（開発環境→本番環境）
  - 再現性なし時: 環境情報収集→状態変化による再現試行
  - 再現性あり時: 原因明白→仮実装検証 / 原因不明→段階的デバッグログ手法→仮実装検証
- **理由**: 原因分析の前に実環境での再現性を確認し、仮実装で「こうしたら直る」を検証することで、後続の原因分析・修正方針策定の精度と安全性を向上させる

### 2. 仮実装ブランチ運用
- **方針**: 仮実装は fix_xxxx ブランチで実施し、ブランチ作成・切り替え・削除の具体的な委譲先は差分設計時に決定する（下記「6. git-commit-workflow のブランチ操作対応」参照）。ブランチ削除は Phase2（実装）の動作確認完了後とする。ただし、fix ブランチが残っている間も後続Step（差分設計・実装）では仮実装コードを参照してそのまま実装に流用することを禁止する旨を、差分設計および実装Stepのプロンプト・ルールに明示的に警告として記載する
- **理由**: git操作の一元管理（global-rulesのgitコミットルール準拠）。仮実装はあくまで調査目的であり、デバッグコード・ルール違反コードが含まれる前提。正式実装の動作確認が取れるまでは参考情報として保持するが、直接流用は禁止する

### 3. 後続Stepへの知見引き継ぎ
- **方針**: 新Stepの成果物（レポート記載）として「特定された原因箇所」「仮実装で改善が確認されたポイント」を記録し、後続の原因分析Step（bugfix-analyzer-prompt.md）にこの情報を入力として渡す。仮実装のコード差分は引き継がない
- **理由**: 調査結果の知見は活用するが、品質保証されていない仮実装コードは使わない

### 4. 既存Step番号の繰り下げ
- **方針**: 現Step 4〜9を Step 5〜10に繰り下げ。遷移ロジック（状態判定の遷移先Step番号）も全て更新する。後処理の遷移先には影響なし（「後処理へ」記述のため）
- **理由**: 挿入に伴う機械的な番号整理

### 5. bugfix-analyzer-prompt.md への入力追加
- **方針**: 原因分析サブエージェントプロンプトに「再現性確認・原因特定Stepの結果」を渡すプレースホルダーを追加する
- **理由**: 調査Stepで得た知見を原因分析に活用し、分析精度を向上させる

### 6. git-commit-workflow のブランチ操作対応
- **現状確認結果**: git-commit-workflow/SKILL.md を精査した結果、同スキルはコミット操作（git add / git commit / git push）専用であり、ブランチ作成（`git checkout -b`）・ブランチ削除（`git branch -D`）の操作パターンは一切定義されていない。revert プロセスもコミット取り消しであり、ブランチ操作ではない
- **方針**: 差分設計時に以下の選択肢を精査し、最適なアプローチを決定する:
  - (a) git-commit-workflow に「ブランチ操作」セクションを追加拡張する（スキルの責務拡大）
  - (b) 新Step内のサブエージェントプロンプト（bugfix-investigator-prompt.md）にブランチ操作手順を直接記述し、git-commit-workflow には委譲しない（スキルの責務を変えない）
  - (c) ブランチ操作専用の共通スキルを新設する
- **理由**: 仮実装ブランチは「調査目的の一時的なブランチ作成→検証→削除」であり、既存の git-commit-workflow の「フェーズ完了時のコミット」とは性質が異なる。責務の分離とスキル設計の一貫性を考慮して差分設計時に判断する
