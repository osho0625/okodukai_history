# 差分設計書

## 設計方針

### 全体方針
- 現 Step 3（設計書ゲート）と現 Step 4（原因分析）の間に「新Step 4: 再現性確認・原因特定」を挿入する
- 新Stepは専用サブエージェントプロンプト `bugfix-investigator-prompt.md` で実行される
- 既存 Step 4〜9 は Step 5〜10 に繰り下げる
- 仮実装ブランチ操作は新Stepのサブエージェントプロンプト内に直接記述し、git-commit-workflow には委譲しない

### approach.md 項目6の判断: git-commit-workflow へのブランチ操作委譲

**採用する選択肢: (b) 新Step内のサブエージェントプロンプト（bugfix-investigator-prompt.md）にブランチ操作手順を直接記述し、git-commit-workflow には委譲しない**

**判断根拠:**
1. git-commit-workflow/SKILL.md を精査した結果、同スキルは **コミット操作（git add / git commit / git push）専用** であり、ブランチ作成（`git checkout -b`）・ブランチ削除（`git branch -D`）の操作パターンは一切定義されていない
2. 仮実装ブランチは「調査目的の一時的なブランチ作成→検証→削除」であり、git-commit-workflow の「フェーズ完了時のコミット」とは責務が根本的に異なる
3. git-commit-workflow に「ブランチ操作」セクションを追加すると、同スキルの責務が肥大化し、「コミット操作専用」という明確な設計意図が崩れる
4. ブランチ操作専用の共通スキル新設(c)は、現時点では本Stepのみが利用者であり、過剰設計となる
5. fix ブランチの作成・削除は git コマンドを直接実行する。グローバルルール §4-2「gitコミットは必ず git-commit-workflow 経由」はコミット操作に関するルールであり、ブランチ操作は対象外である

## 実行手順

### パート1: 再現性確認

#### ステップ1: 前提情報の読み込み

1. bug-report.md を Read で読み込み、再現手順・期待動作・実際の動作を把握する
2. doc-index.md を Read で読み込み、dev-environment.md / program-structure.md の
   内容を Read で確認する

#### ステップ2: 開発環境での再現確認

1. bug-report.md の再現手順に従い、開発環境で不具合を再現する
2. dev-environment.md に記載のテストコマンドで関連テストを実行する
3. 再現結果を記録する:
   - 再現できた → パート2A（再現性あり）へ
   - 再現できなかった → ステップ3（本番環境確認）へ

#### ステップ3: 本番環境での再現確認（開発環境で再現不可の場合）

1. ユーザーに本番環境での再現状況を確認する（質問は1つずつ）
2. 本番環境でのみ再現する場合はその条件を記録する
3. 判定:
   - 本番環境で再現確認 → パート2A（再現性あり）へ
   - どの環境でも再現不可 → パート1B（環境要因収集）へ

### パート1B: 環境要因収集・再現試行（再現性なしの場合）

#### ステップ4: 環境情報の収集

以下のカテゴリの情報を可能な限り収集する:
1. **ログ**: アプリケーションログ、エラーログ、システムログ
2. **実行時パラメータ**: 設定値、入力データ、引数
3. **実行タイミング**: 発生時刻、頻度、前後のイベント
4. **実行手順**: ユーザーの操作手順の詳細差分
5. **環境状態**: メモリ容量、ディスク容量、CPU負荷、他プロセスの影響、
   ネットワーク状態、同時実行プロセス

#### ステップ5: 状態変化による再現試行

1. 収集した環境情報をもとに、不具合発生時の状態に近づける
2. 1つずつ状態要素を変化させて再現を試みる
3. 再現に成功した場合:
   - 変化させた状態要素を「原因候補」として記録する
   - パート2A（再現性あり）へ遷移する
4. 再現に成功しなかった場合:
   - 収集した環境情報と試行結果を記録する
   - ユーザーに状況を報告し、追加情報を求めるか判断する
   - ステータスを DONE_WITH_CONCERNS として完了する

### パート2A: 原因特定（再現性ありの場合）

#### ステップ6: 原因の明白さ判定

再現結果から原因が明白かどうかを判定する:
- **原因が明白**: エラーメッセージ、スタックトレース等から原因箇所が特定できる
  → ステップ8（仮実装検証）へ
- **原因が不明**: 再現はするが原因箇所が不明
  → ステップ7（段階的デバッグログ手法）へ

#### ステップ7: 段階的デバッグログ手法（原因不明の場合）

以下の6段階で原因を絞り込む:

**(1) 正しい処理フローの明確化**
- program-structure.md を参照し、期待される処理フロー（入口→出口）を整理する

**(2) 上流の確実動作箇所へのログ埋め込み**
- 処理フローの入口付近（確実に動作する箇所）にログを追加する

**(3) 下流分岐点・Exception箇所前後へのログ埋め込み**
- 条件分岐、try/except、例外処理の前後にログを追加する
- 判定に使われるパラメータの値もログに含める

**(4) 各実行ポイントへの識別可能なログ埋め込み**
- 処理フローの各ステップに一意に識別できるラベル付きログを追加する

**(5) ログ実行・確認**
- ログを埋め込んだ状態で再現手順を実行する
- ログ出力を確認する:
  - 途切れ箇所を特定する（どこまで到達しているか）
  - 想定外のパラメータ値を特定する

**(6) 原因特定 → 仮実装検証**
- ログ分析の結果から原因箇所を特定する
- ステップ8（仮実装検証）へ進む

#### ステップ8: 仮実装による改善検証

**仮実装ブランチの作成:**
1. 現在のブランチを確認する: `git branch --show-current`
2. fix ブランチを作成・切り替える: `git checkout -b fix_{識別文字列}`
   - 命名規則: `fix_` + 不具合を示す識別可能な文字列
   - 既存ブランチと重複しないこと（`git branch` で確認）

**仮実装の実施:**
1. 原因箇所に対する最小限の修正を行う
2. 開発環境で再現手順を実行し、改善を確認する
3. 改善確認できた場合: 原因候補を確定する
4. 改善確認できなかった場合: 別の仮説を立て再試行する

**開発環境で再現不可・実環境のみの場合:**
1. ユーザーに実環境での仮実装試験の可否を確認する
2. 運用影響がないことの確認を得たうえで実環境で検証する

**仮実装完了後のブランチ操作:**
1. 元のブランチに戻る: `git checkout {元のブランチ名}`
2. ⚠️ **fix ブランチはこの時点では削除しない**
   - 削除タイミング: Phase2（実装）の動作確認完了後
   - 理由: 正式実装の参考情報として保持する（ただし直接流用は禁止）

## Red Flags（自己検知して回避すること）

| Red Flag | なぜ危険か |
|---|---|
| 仮実装コードを正式実装としてコミットしようとしている | 仮実装は調査目的。品質保証されていない |
| fix ブランチを Step 完了時に削除しようとしている | 削除は Phase2 動作確認完了後 |
| 修正方針を提案している | 修正方針策定は別工程 |
| 原因分析レポートを作成している | bug-analysis.md は後続Step の担当 |
| git-commit-workflow を呼び出してブランチ操作しようとしている | ブランチ操作は直接 git コマンドで実行 |
| デバッグログを残したまま完了しようとしている | デバッグログは仮実装ブランチ内に留め、元ブランチに影響させない |
