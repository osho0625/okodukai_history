# 変更要求定義

## 変更概要
- **変更の目的・背景**: バグ修正ワークフロー（`fs-bugfix-phase1-analysis`）において、現在の Step 4「原因分析」はコードベースの静的解析に基づく原因推定を行うが、実際のバグ修正では「再現性の確認」と「実行環境での原因特定」が不可欠である。再現性の有無によって調査アプローチが大きく異なるにもかかわらず、現行プロセスにはこの判断分岐がない。本変更により、原因分析の前に体系的な再現性確認と環境要因の切り分けを行い、原因特定の精度と効率を向上させる。
- **変更種別**: 追加

## 要求事項

### REQ-C-001: 再現性確認フェーズの追加
- **種別**: 追加
- **説明**: `fs-bugfix-phase1-analysis` の現在の Step 4（原因分析）の前に「再現性確認・原因特定Step」を新規挿入する。このStepでは、開発環境および本番環境での不具合再現を試み、再現性あり／なしの判定を行う。
- **受入基準**:
  - AC-001: 設計書ゲート（現Step 3）通過後、原因分析（現Step 4）の前に新Stepが配置されている
  - AC-002: 開発環境での再現確認の手順が定義されている
  - AC-003: 本番環境での再現確認の手順が定義されている
  - AC-004: 再現性あり／なしの判定結果が成果物として記録される
- **優先度**: 必須

### REQ-C-002: 再現性なし時の環境要因収集・再現試行プロセス
- **種別**: 追加
- **説明**: 再現性なしと判定された場合、ログ・実行時パラメータ・実行タイミング・実行手順・実行時の環境状態（メモリ容量、ディスク容量、CPU負荷、他プロセスの影響等）を可能な限り収集し、実行状態を不具合発生時に近づけることで再現を試みるプロセスを定義する。変化した状態要素から原因の手がかりを得る。
- **受入基準**:
  - AC-005: 収集すべき環境情報のカテゴリ（ログ、実行時パラメータ、実行タイミング、実行手順、環境状態）が定義されている
  - AC-006: 環境状態の変化による再現試行の手順が定義されている
  - AC-007: 再現に成功した場合、変化させた状態要素を原因候補として記録する手順が定義されている
  - AC-008: 再現に成功した場合、REQ-C-003（再現性ありのプロセス）に遷移する
- **優先度**: 必須

### REQ-C-003: 再現性あり時の原因特定・仮実装検証プロセス
- **種別**: 追加
- **説明**: 再現性ありと判定された場合の原因特定プロセスを定義する。原因が一目瞭然であれば仮実装で改善確認を行う。原因が不明な場合はデバッグログ埋め込みによる段階的原因特定手法（処理フロー明確化→上流ログ→分岐点ログ→実行確認→問題箇所絞り込み）を用いる。
- **受入基準**:
  - AC-009: 原因が明白な場合に仮実装で改善確認を行う手順が定義されている
  - AC-010: 原因不明時のデバッグログ埋め込みによる段階的原因特定手法が以下の6段階で定義されている: (1)正しい処理フローの明確化、(2)上流の確実動作箇所へのログ埋め込み、(3)下流分岐点・Exception箇所前後へのログ埋め込み（要因パラメータ含む）、(4)各実行ポイントへの識別可能なログ埋め込み、(5)ログ実行・確認（途切れ箇所分析、想定外パラメータ分析）、(6)原因特定後の仮実装検証
  - AC-011: 仮実装は開発環境で実施することが原則として定義されている
  - AC-012: 開発環境で再現できず実環境でのみ再現する場合、ユーザーに運用影響がないことを確認のうえ実環境で仮実装試験を実施する手順が定義されている
- **優先度**: 必須

### REQ-C-004: 仮実装ブランチ運用ルール
- **種別**: 追加
- **説明**: 再現性確認・原因特定Stepで使用する仮実装のブランチ操作（作成・切り替え・削除）は `bugfix-investigator-prompt.md` 内で直接 git コマンドにより実行する（git-commit-workflow のコミット操作とは責務が異なるため委譲しない）。本Stepは fix ブランチの命名規則とライフサイクルを定義する。仮実装はあくまで調査目的であり、デバッグコードやルール違反の変更が含まれる前提とする。新Step完了時に fix ブランチを削除せず Phase2 の動作確認完了後に削除し、後続Stepには「原因箇所」と「こうしたら直った」という知見（情報）のみを引き継ぐ。仮実装のコード差分・変更内容自体を後続Stepで流用することを禁止する。
- **受入基準**:
  - AC-013: 仮実装ブランチの命名規則が `fix_xxxx`（xxxは不具合を示す識別可能な文字列で、既存ブランチと重複しない）として定義されている
  - AC-014: ブランチ作成・切り替え・削除の操作が `bugfix-investigator-prompt.md` 内で直接 git コマンドにより実行されることが定義されている（git-commit-workflow のコミット操作とは責務が異なるため委譲しない）
  - AC-015: 仮実装ブランチの削除タイミングが「Phase2（実装）の動作確認完了後」と定義されている
  - AC-016: ブランチ削除前に元の作業ブランチへの切り戻し手順が定義されている
  - AC-017: 後続Step（原因分析・修正方針等）に引き継ぐのは「特定された原因箇所」と「仮実装で改善が確認されたポイント（知見）」のみであり、仮実装のコード差分・変更内容自体の流用を禁止するルールが明記されている
  - AC-018: 差分設計Step及び実装Stepのプロンプト・ルールに「fix ブランチの仮実装コードを参照してそのまま実装に流用してはならない」旨の警告が明示的に記載されている
- **優先度**: 必須

### REQ-C-005: 既存Step番号の再採番
- **種別**: 変更
- **説明**: 新Stepの挿入に伴い、現在のStep 4以降のStep番号を繰り下げる。挿入位置は現Step 3（設計書ゲート）と現Step 4（原因分析）の間とする。
- **受入基準**:
  - AC-019: 新Stepが現Step 3の直後に配置されている（新Step 4）
  - AC-020: 現Step 4（原因分析）以降の全Stepが1つずつ繰り下がっている
  - AC-021: Step間の遷移ロジック（状態判定セクションの遷移先Step番号）が整合している
  - AC-022: レポート項目名のStep番号表記が新番号に更新されている
- **優先度**: 必須

### REQ-C-006: 再現性確認・原因特定Stepの成果物定義
- **種別**: 追加
- **説明**: 新Stepの実行結果を記録する成果物（レポート記載項目）を定義する。再現性判定結果、環境情報収集結果、原因特定手法の実行ログ、仮実装の結果等が含まれる。
- **受入基準**:
  - AC-023: 再現性判定結果（あり／なし）がレポートに記録される
  - AC-024: 再現環境（開発環境／本番環境）がレポートに記録される
  - AC-025: 再現性なしの場合に収集した環境情報がレポートに記録される
  - AC-026: 仮実装を実施した場合、ブランチ名・検証結果・原因候補がレポートに記録される
  - AC-027: 新Stepの完了条件が「再現性判定が完了し、原因候補が特定されている」として定義されている
- **優先度**: 必須

## 対象外（スコープ外）
- `fs-bugfix-phase2-impl`（設計・実装・ドキュメント反映フェーズ）の変更
- `fs-bugfix-phase3-final-check`（完全性チェックフェーズ）の変更
- バグ修正ワークフロー以外のワークフローへの影響
- サブエージェントプロンプト（bugfix-analyzer-prompt.md 等）の具体的な修正内容の設計
- 新Stepで使用するサブエージェントプロンプトの具体的な内容設計
- 仮実装コードの品質基準・レビュー基準の定義

## 前提条件
- `fs-bugfix-phase1-analysis` スキル定義（SKILL.md）が既存の10Step構成（前処理＋Step1〜9＋後処理）で運用されていること
- バグ修正ワークフローの進捗管理（bugfix-progress.md）が3フェーズ構成であること
- git ブランチ操作が可能な開発環境であること（仮実装ブランチの作成・削除のため）
- ユーザーが不具合の再現環境（開発環境・本番環境）へのアクセス権を持っていること

## 関連する既存要件
- **UR-001**: 7つのワークフロー（バグ修正を含む）の提供 — バグ修正WFの内部Step構成変更として本変更が位置づけられる
- **UR-007**: 進捗管理機構 — 新Step追加に伴うレポート記載項目の拡張が必要
- **UR-012**: エラーハンドリング体系 — 新Stepでの BLOCKED/NEEDS_CONTEXT 等の状態遷移に既存体系を適用する
- **UR-014**: ワークフロー中止メカニズム — 新Stepにおいても中止可能であること
