# 変更要件定義書 — 設計漏れ・実装漏れ発見時の対策プロセス定義

## 1. 変更概要

### 1.1 変更の目的・背景

設計漏れ・実装漏れが発見された場合の対策プロセスが明文化されておらず、対応が場当たり的になりがちである。特に `fs-impl-phase5-final-check`（設計準拠監査）が漏れを検出した場合のフローとして、明確なプロセスを正式に組み込む必要がある。

現状の問題:
- 設計準拠監査（final-design-audit-agent）が漏れを検出しても、その後のフローが未定義
- 実装漏れの場合にタスクリスト再作成→実装ループの回数制限が未定義
- 設計漏れの場合に該当フェーズスキルの再実行範囲・手順が未定義
- 無限ループ防止策が未定義

### 1.2 変更種別

機能追加（新しいプロセス定義を追加）

### 1.3 起因元

PI-050（pending-issues）

---

## 2. 要求事項

### REQ-C-001: 実装漏れ検出時の対策プロセス定義

| 項目 | 内容 |
|---|---|
| **種別** | 機能追加 |
| **説明** | `fs-impl-phase5-final-check`（または同等の設計準拠チェック）が実装漏れを検出した場合に、タスクリスト再作成→`coding-test-2review` スキルでの実装→全タスク完了確認を繰り返すプロセスを定義する |
| **優先度** | Must |

**受入基準:**
- AC-001-1: 実装漏れ検出時に、漏れている箇所のタスクリスト（impl-task-list.md 形式）を再作成する手順が定義されていること
- AC-001-2: `coding-test-2review` スキルによる実装ループの手順が定義されていること
- AC-001-3: ループ終了条件が「全タスク完了（未実装0件）」として明記されていること

---

### REQ-C-002: 設計漏れ検出時の対策プロセス定義

| 項目 | 内容 |
|---|---|
| **種別** | 機能追加 |
| **説明** | `fs-impl-phase5-final-check`（または同等の設計準拠チェック）が設計漏れを検出した場合に、設計WFの該当フェーズスキル（FS）を再実行し、影響する後続FSも継続実行し、差分についてタスクリスト追加→実装のプロセスを定義する |
| **優先度** | Must |

**受入基準:**
- AC-002-1: 設計漏れ検出時に、該当FSを前処理・後処理なしで正確に再実行する手順が定義されていること
- AC-002-2: プログラム構成が変わるような場合に後続FSの成果物にも影響があるため、そのFSも継続実行する手順が定義されていること
- AC-002-3: 差分ができた箇所についてタスクリストを追加する手順が定義されていること
- AC-002-4: `coding-test-2review` スキルで追加タスクを実装し、全量完了まで繰り返すプロセスが定義されていること

---

### REQ-C-003: 大量漏れ検出時のユーザー相談

| 項目 | 内容 |
|---|---|
| **種別** | 機能追加 |
| **説明** | 治るまでやるのが基本原則。上限で停止はしない。ただし10回繰り返しても解消しない場合は前工程に問題がある可能性があるため、ユーザーに相談する。ユーザーが「続けろ」と言えば再度10回続ける。 |
| **優先度** | Must |

**受入基準:**
- AC-003-1: 設計修正・実装リトライは完了するまで繰り返すことが基本原則として明記されていること
- AC-003-2: 10回繰り返しても解消しない場合にユーザーに相談する手順が定義されていること（前工程の問題の可能性を報告）
- AC-003-3: ユーザーが続行を指示した場合、再度10回繰り返すフローが定義されていること

---

### REQ-C-005: 設計不備修正の全体ルール定義

| 項目 | 内容 |
|---|---|
| **種別** | 機能追加 |
| **説明** | 設計不備（設計漏れ・実装漏れ）はワークフローのどの段階でも発覚する可能性がある（例: phase3 GUIモックアップでのユーザー指摘、phase4 実装中の発見等）。個別パスの限定列挙ではなく「設計不備修正が必要になったらどこからでも起動できる」汎用ルールとして、phase-skill-rules.md 等の全体ルールに定義する |
| **優先度** | Must |

**受入基準:**
- AC-005-1: phase-skill-rules.md（全フェーズスキル共通ルール）に「設計不備発見時の対応ルール」が追加されていること
- AC-005-2: 設計不備修正プロセス（design-impl-gap-process.md）への参照が、特定パスに限定されず汎用的に定義されていること
- AC-005-3: GUIモックアップフィードバック（phase3）やコーディング中（phase4）等、任意のフェーズで設計不備を発見した場合の起動手順が明確であること

## 3. 対象外（スコープ外）

| # | 対象外事項 | 理由 |
|---|---|---|
| EX-001 | 設計漏れ・実装漏れの「検出」方法自体の改善 | 検出は既存の `fs-impl-phase5-final-check`（final-design-audit-agent）が担当。検出精度の改善は別課題 |
| EX-002 | 既存のQAレビューエージェント（object-design-qa-agent, architecture-qa-agent等）の変更 | 本要求はプロセス定義の追加であり、QAエージェントの内部ロジック変更は含まない |
| EX-003 | 各WF固有の検出ロジック改善 | 本要求は汎用的な対策プロセスの定義と全体ルールの追加であり、各WF固有の設計不備検出ロジックの改善は含まない |

## 6. 用語定義

| 用語 | 定義 |
|---|---|
| 設計漏れ | 設計書に定義されるべきクラス・メソッド・不変条件・テスト観点が設計書に存在しない状態 |
| 実装漏れ | 設計書に定義されているクラス・メソッド・不変条件・テスト観点が実装コードに反映されていない状態 |
| 対策プロセス | 漏れ検出後に自動的に実行される修正→検証のループフロー |
| FS | フェーズスキル（`fs-*` 形式のスキル）の略称 |
