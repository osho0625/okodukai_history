# 差分設計書（詳細） - object-design-qa-agent 3プラットフォーム版

対象ファイル:
- `agents/object-design-qa-agent.md`（Claude Code版）
- `agents/kiro/object-design-qa-agent.md`（Kiro IDE版）
- `agents/kiro/prompts/object-design-qa-agent-prompt.md`（Kiro CLI版）

3ファイルは既存の役割分担ルールにより内容が同一構造のため、同一の追加内容を機械的に反映する（approach.md 変更方針の詳細 REQ-C-003 参照）。

## 新設する検証項目L（3ファイル共通の追加内容）

3ファイルとも、検証項目K「技術情報記載有無検証」の直後に以下を新設する:

```markdown
#### L. 外部連携部分の技術調査結果・公式ドキュメントリンク検証

- 外部ツール・外部サービスと連携するクラスについて、「技術的実装情報」セクションに「技術調査結果」カテゴリが記載されているか。未記載であればFAIL
- 同セクションに「参考ドキュメント（URLリンク付き）」カテゴリが記載され、最低1件のURL形式のリンクが含まれているか。未記載または0件であればFAIL
- 記載された調査結果・リンクの内容が、当該クラスの他の設計記述（API呼び出し手順、外部ライブラリ使用方法等）と整合しているか。不整合があればFAIL
- 外部連携が存在しないクラスは本検証項目の対象外とする（DDD採用/不採用に関わらず、外部連携の有無で判定する）
- 本検証項目は全レイヤー（ドメイン・アプリケーション・インフラ・プレゼンテーション）に適用する
```

チェック内容はAC-005（検証項目の追加）・AC-006（既存の判定基準への統合、FAIL/WARNING判定）を満たす。既存の判定基準（`FAIL が 0件 かつ WARNING が 0件 → APPROVED`）の文言は検証項目数に依存しない汎用的な表現のため変更不要（approach.md確認済み）。DDD不採用時のスキップ対象リスト（C・E・G）には追加しない（外部連携部分の検証はDDD採用/不採用に関わらず常に実施する）。

## 追加対応: 見出し番号の不整合解消（ユーザー指摘）

ユーザーから、検証項目リスト直後の見出し番号について3ファイル間で不整合がある（Claude Code版は「ステップ3」、Kiro IDE版・Kiro CLI版は「ステップ4」）との指摘があり、今回の変更に統合して解消する。

3ファイルとも、レビュープロセスは以下の4ステップで構成される:
- ステップ1: レビュー対象の読み込み
- ステップ2: 考慮漏れ検証
- ステップ3: 検証項目の実行
- ステップ4: 判定と結果の出力（＝検証項目リスト直後の見出し）

各ファイルの実際の記述を確認した結果:
- `agents/object-design-qa-agent.md`（Claude Code版）: 検証項目リスト直後の見出しが「ステップ3: 判定と結果の出力」となっており、直前の「ステップ3: 検証項目の実行」と番号が重複している
- `agents/kiro/object-design-qa-agent.md`（Kiro IDE版）: 検証項目リスト直後の見出しが「ステップ4: 判定と結果の出力」と正しく連番になっている
- `agents/kiro/prompts/object-design-qa-agent-prompt.md`（Kiro CLI版）: 検証項目リスト直後の見出しが「ステップ4: 判定と結果の出力」と正しく連番になっている

前段のステップ1〜3の見出し個数（レビュー対象の読み込み／考慮漏れ検証／検証項目の実行の3つ）は3ファイルとも同一であり、その直後に続く4番目のステップは論理的に「ステップ4」であるべきである。したがって、Kiro IDE版・Kiro CLI版の「ステップ4」表記が正しく、Claude Code版の「ステップ3」表記が誤りと判定した。

対応方針: Claude Code版（変更対象4-2）の見出し番号のみを「ステップ4」に修正する。Kiro IDE版・Kiro CLI版（変更対象5-2・6-2）は元から正しいため、見出し番号の変更は不要（検証項目Lの追加のみ）。この修正はユーザー指摘による既存不整合の解消であり、対応方針（approach.md）・実装コード・影響範囲の変更を伴わないため、pending-issues.md への登録は不要とする（本差分設計内で解消済みのため）。

**承認経緯:** 本追加対応は、2026-07-06のオーケストレータとユーザーの対話において、Step2完了後にユーザーへ懸念事項として報告し、ユーザーが選択肢2「今回の変更に含めて修正する」を明示的に選択したことにより承認されている。approach.mdへの追記は行わず、本delta-design内での承認記録として明記する。
