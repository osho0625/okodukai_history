# 対応方針書

## 方針概要
- **対応方針**: 追加で対応（一部、既存の箇条書き・テーブルへの行追加、既存手順への新規ステップ挿入を伴う）
- **OCP検討結果**: 追加のみで対処可能。既存構造（プロセスの順序・既存テンプレートの骨格・既存QA判定ロジック）を破壊的に変更する必要はない

本変更要求（REQ-C-001〜003）は、いずれも既存の仕組み（object-designスキルの各モード処理手順、object-designer-prompt.md のテンプレート、object-design-qa-agent の検証項目リスト）に対して、要素を「追加」することで実現できる。既存の記述・判定基準を削除・変更する必要はない。

**既存「技術的実装情報」セクションとの統合方針（impact-analysis.md の検討事項への回答）**:
PI-049 で新設された「技術的実装情報」セクション（API呼び出し手順／データ変換ルール／エラーハンドリング方針／外部ライブラリ使用方法／設定値・定数の5カテゴリのテーブル）は、そもそも「技術調査結果（tech-investigation）で判明した情報が該当クラスに反映されているか」を検証対象に含んでいた（quality_check チェック項目8、QA検証項目K）。したがって今回の「技術調査結果」「参考ドキュメント（URLリンク付き）」は、**既存の「技術的実装情報」テーブルに新しいカテゴリ行として追加する**（別セクションとして新設しない）。これにより、1クラスにつき技術情報を記載する場所が1つに保たれ、既存の「該当するカテゴリのみ記載する」という運用ルールもそのまま適用できる。

## 変更方針の詳細

### REQ-C-001: オブジェクト設計ドキュメントへの技術調査結果・公式ドキュメントリンク記載欄の追加
- **方針**: 既存の「技術的実装情報」テーブル（カテゴリ: 内容 の2列テーブル）に、新規カテゴリ行を2行追加する。
  - `技術調査結果` — 外部ツール・外部サービス連携部分に関する tech-investigation の調査結果要約
  - `参考ドキュメント（URLリンク付き）` — 参照した公式ドキュメントへのURLリンク（最低1件、複数可）
  - 追加先は `skills/object-design/object-designer-prompt.md`（reverse モードの出力テンプレート）と、`skills/fs-design-phase8-object/object-designer-prompt.md`（新設する技術的実装情報テンプレート）の両方。他モード（quality_check/delta、phase8_summary/fix）はこのテーブルを直接生成しないため、テンプレート自体の追加は不要（チェック観点の追加のみで対応）。
  - 既存の「該当するカテゴリのみ記載する。該当なしの場合はセクション自体を省略してよい」という運用ルールを継承し、外部連携が存在しないクラスにはこの2カテゴリを記載不要とする。
- **理由**: 既存テーブルへの行追加はOCP原則に完全に合致する（既存カテゴリの意味・書式を変更せず、拡張ポイントとして機能する行を追加するだけ）。別セクションを新設すると、1クラスに技術情報が2箇所に分散し、記載場所の一貫性が失われる。AC-001（記載欄の存在）・AC-002（最低1件のURLを記載できる構造）は、テーブルの1セル内にMarkdownリンクを複数列挙できるため、この構造で満たされる。

### REQ-C-002: 設計書作成プロセス（object-designスキル）への技術調査ステップの追加
- **方針**: 実際に新規クラス設計が行われる `skills/fs-design-phase8-object/object-designer-prompt.md`（mode: phase8_{layer-name}）の処理手順に、「対象クラスが外部ツール・外部サービスと連携する場合、tech-investigation (aide-powers skill) を実施し、調査結果と参考ドキュメントリンクを技術的実装情報セクションに反映する」という新規ステップを挿入する。加えて、共通スキル側 `skills/object-design/SKILL.md` の各モード（create/delta/reverse）の処理説明にも、対応するステップ・チェック観点を追加し、スキル定義レベルでプロセスが明記されている状態にする（AC-003）。
  - delta モードでは既存レイヤーへの変更が外部連携部分に及ぶ場合のみ tech-investigation を実施する（impact-analysis.md の影響範囲に基づき判断）。
  - reverse モードでは、既存コードのコメントやREADME等から参考ドキュメントURLを抽出できる場合は記録し、抽出できない場合は tech-investigation で補足調査してもよいという任意規定とする（既存ドキュメントへの遡及適用はスコープ外のため、新規に逆引きを実行する場合のみ対象）。
  - ステップ完了後は必ずREQ-C-001の記載欄（技術的実装情報テーブルの新設2カテゴリ）に調査結果とリンクを反映することをプロセス上に明記する（AC-004）。
- **理由**: 実装への影響が最も大きいのは実際に新規設計を行う `fs-design-phase8-object` 側のプロンプトであるため、ここに具体的な実施ステップを置く。共通スキル本体（`skills/object-design/SKILL.md`）にも同内容を明記することで、スキルの振る舞いを読む側（オーケストレータやレビューア）が処理内容を一貫して把握できる。既存の処理手順は数字リストのため、新規ステップの挿入によって後続ステップの番号がずれるが、これは処理内容の追加であり、既存ステップの意味・順序関係を破壊するものではないためOCP原則の範囲内と判断する。

### REQ-C-003: レビュー観点（object-design-qa-agent）への公式ドキュメント整合性検証の追加
- **方針**: 3プラットフォーム版（`agents/object-design-qa-agent.md` / `agents/kiro/object-design-qa-agent.md` / `agents/kiro/prompts/object-design-qa-agent-prompt.md`）の検証項目リストに、既存の検証項目K（技術情報記載有無検証）の直後に新規検証項目L「外部連携部分の技術調査結果・公式ドキュメントリンク検証」を追加する。
  - チェック内容: (1) 外部連携部分に技術調査結果の要約が記載されているか、未記載ならFAIL。(2) 参考ドキュメント（URL）が最低1件記載されているか、未記載ならFAIL。(3) 記載されたリンク・調査結果の内容と、該当クラスの設計内容（API呼び出し手順等）が整合しているか、不整合があればFAIL。(4) 外部連携が存在しないクラスは本検証の対象外とする。
  - 既存の判定基準（FAIL=0 かつ WARNING=0 → APPROVED）の枠組みはテキストを変更せずにそのまま適用される（判定基準の文言は検証項目数に依存しない汎用的な表現のため、変更不要）。
  - DDD不採用時のスキップ対象リスト（C・E・G）には追加しない。外部連携部分の検証はDDD採用/不採用に関わらず常に実施する。
- **理由**: 既存の検証項目A〜Kのリストに項目を1つ追加するだけであり、既存項目の判定ロジック・出力フォーマット・総合判定の計算方法に一切手を加えない。3ファイルは内容が同一構造であるため、同一の追加内容を機械的に反映する（プラットフォーム間の一貫性維持）。

## リファクタリング検討結果
- **検討結果**: 不要
- **理由**: 全ての変更が「既存テーブルへの行追加」「既存箇条書きへの項目追加」「既存の番号付き手順への新規ステップ挿入」で実現可能であり、既存のプロセス構造・判定ロジック・ファイル分割方針を変更する必要がない。唯一の例外として `skills/fs-design-phase8-object/object-designer-prompt.md` には「技術的実装情報」テンプレート自体がこれまで存在していなかったため、本変更のスコープ内で新設する（既存5カテゴリ＋新規2カテゴリをまとめて追加）。これは既存構造の変更ではなく新規セクションの追加であるため、リファクタリングには該当しない。
