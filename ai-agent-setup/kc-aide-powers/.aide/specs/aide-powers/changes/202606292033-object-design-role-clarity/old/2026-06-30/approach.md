# 対応方針書

## 方針概要
- **対応方針**: 追加で対応
- **OCP検討結果**: 追加のみで対処可能

全5要求（REQ-C-001〜005）は、既存のスキル定義・エージェント定義・プロンプトテンプレートの構造を変更することなく、セクション追加・ルール追加・検証項目追加のみで実現できる。既存の create/delta/reverse 3モード構造、QAエージェントの判定フレームワーク（FAIL/WARNING/APPROVED/REJECTED）はそのまま維持される。

## 変更方針の詳細

### 1. クラス役割定義の具体化テンプレート追加（REQ-C-001）

- **方針**: `object-designer-prompt.md` の reverse モード出力形式（クラス一覧テンプレート）および quality_check モードのチェック項目に「役割定義（具体）」セクションを追加する。テンプレートには「入力（何を受け取るか）」「出力（何を返すか）」「責務外（何を担当しないか）」の3項目を明記する形式を定義する。
- **理由**: 既存の「役割」フィールド（1行の曖昧な記述）を置き換えるのではなく、「役割定義（具体）」として詳細な3項目セクションを**追加**することで、既存構造との互換性を維持しつつ具体性を確保する。create/delta/reverse 全モードでテンプレートが参照されるため、テンプレート1箇所の追加で全モードに波及する。

### 2. 役割定義からのpublicメソッド網羅的導出ルール追加（REQ-C-002）

- **方針**: `skills/object-design/SKILL.md` の品質基準セクションに「役割定義→publicメソッド導出ルール」を追加する。`object-designer-prompt.md` の各モード処理手順に、役割定義で宣言した全責務に対応するpublicメソッドの存在をセルフチェックするステップを追加する。各publicメソッドがどの責務に対応するかのトレーサビリティ列をテンプレートに追加する。
- **理由**: 既存のメソッドテーブル（メソッド名/引数/戻り値/責務）に「対応する役割定義項目」列を追加するだけで、テーブル構造の既存列は変更しない。導出ルールは品質基準の新規カテゴリとして追加されるため、既存の6カテゴリ（SOLID/テスタビリティ/貧血症/依存違反/ユビキタス言語/ダミー実装）を変更しない。

### 3. 技術的実装情報セクションの追加（REQ-C-003）

- **方針**: `object-designer-prompt.md` のクラス定義テンプレート（各モード共通）に「技術的実装情報」セクションを追加する。記載すべき情報カテゴリ（API呼び出し手順、データ変換ルール、エラーハンドリング方針、外部ライブラリ使用方法、設定値・定数）をテンプレートに定義する。tech-investigation 結果や system-requirements.md の技術情報を該当クラスに反映する手順をプロンプトに追加する。
- **理由**: クラス定義テンプレートにセクションを追加するだけで、既存の「メソッド」「プロパティ」「依存関係」「テスト観点」の各セクション構造は変更しない。技術情報の反映手順は処理手順の既存ステップの後に新ステップとして追加する形で対応する。

### 4. QAレビューへの役割↔publicメソッド網羅性検証項目追加（REQ-C-004）

- **方針**: `agents/object-design-qa-agent.md` のステップ3検証項目に「J. 役割↔publicメソッド網羅性検証」を追加する。検証内容は「各クラスの役割定義（具体）で宣言された入力・出力・責務に対応するpublicメソッドが全て定義されているか」をチェックし、欠落があればFAIL判定とする。全レイヤーに適用する。同等の検証項目を `agents/kiro/` 配下のKiro版にも追加する。
- **理由**: 既存の検証項目A〜Iの構造・判定ロジックを一切変更せず、新規検証項目Jとして追加するだけ。判定基準（FAIL=0かつWARNING=0→APPROVED）も変更不要。

### 5. QAレビューへの技術情報記載有無検証項目追加（REQ-C-005）

- **方針**: `agents/object-design-qa-agent.md` のステップ3検証項目に「K. 技術情報記載有無検証」を追加する。検証内容は「前提成果物（system-requirements.md、layered-architecture.md、技術調査結果）に記載された技術情報のうち、該当クラスに関連するものが『技術的実装情報』セクションに反映されているか」をチェックし、未反映があればFAIL判定とする。同等の検証項目を `agents/kiro/` 配下のKiro版にも追加する。
- **理由**: REQ-C-004と同様、既存の検証項目構造を変更せず新規項目Kとして追加する。前提成果物の参照先も既にQAエージェントの入力定義に含まれている（system-requirements.md、layered-architecture.md）ため、入力インターフェースの変更は不要。

## リファクタリング検討結果
- **検討結果**: 不要
- **理由**: 本変更はスキル定義・テンプレートの拡張であり、既存構造を壊さずにセクション追加・ルール追加・検証項目追加で対応可能。既存の3モード構造（create/delta/reverse）、品質基準カテゴリ構造（6カテゴリ）、QA検証項目構造（A〜I）、判定フレームワーク（FAIL/WARNING/APPROVED/REJECTED）はいずれも拡張に対して開かれており、変更する必要がない。リファクタリングを行うべき構造的課題は存在しない。
