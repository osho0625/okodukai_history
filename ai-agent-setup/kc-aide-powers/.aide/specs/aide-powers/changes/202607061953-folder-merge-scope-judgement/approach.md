- **対応方針**: 両方（新Stepの追加 + 既存Step3のわずかな拡張）
- **OCP検討結果**: 追加中心で対処可能。既存変更は `folder-merge-check/SKILL.md` 1ファイル内の Step3（提示情報の拡張）に限定され、**3つの呼び出し元スキル（fs-change-phase1-analysis / fs-bugfix-phase1-analysis / fs-refactoring-phase2-candidates）への変更は不要**と判断した。

## 変更方針の詳細

### 1. 起因元要件と今回の作業要件の読み込み方式（current_dir自動探索 vs 新規パラメータ渡し）
- **方針**: `current_dir` 配下からの自動探索を採用する。新規パラメータは追加しない。folder-merge-check は既に `workflow_type`（変更/バグ修正/リファクタリング）と `current_dir` を受け取っているため、`workflow_type` の値に応じて読み込み対象ファイル名を決定的に判定できる。
  - `workflow_type`=変更 → `{current_dir}/change-requirements.md`
  - `workflow_type`=バグ修正 → `{current_dir}/bug-report.md`（bug-analysis.mdの扱いは差分設計で確定）
  - `workflow_type`=リファクタリング → `{current_dir}/refactoring-candidates.md`
- **理由**: 各WF種別の要件文書ファイル名は既に固定（change-requirements.md自身の「前提条件」セクションで「今回の作業のドキュメント（change-requirements.md / bug-report.md等）が既に作成されていること」と明記されている実態と整合する）。新規パラメータを追加する場合、3つの呼び出し元スキルのInput/Output定義変更が必要になり、影響範囲が広がる。既存パラメータのみで決定的に実現できるため、新規パラメータは不要と判断した。これにより影響範囲分析で「高（呼び出し元3スキルへの影響の可能性）」とされていた依存箇所は、実質的に「影響なし」に縮小する。

### 2. 新設Step（起因元要件まとめ＋関連性判断）の追加位置と内部フロー
- **方針**: `folder-merge-check/SKILL.md` の既存 Step 2（起因元フォルダの経緯確認）と 既存 Step 3（ユーザーへの確認）の間に、新設Stepを1つ挿入する。挿入に伴い、既存Step3以降のStep番号は1つずつ後ろにリナンバリングされる（Step3→Step4、Step4→Step5、Step5→Step6、Step6→Step7）。既存Step1・Step2・旧Step4（ファイル移動）以降の内部ロジックは変更しない。
- **新設Stepの内部フロー（方針レベル）**:
  1. **(a) 起因元要件のまとめ**: 既存Step2で読み込んだ起因元フォルダの `history.md`（またはhistory.md不在時は主要ドキュメント）に加え、起因元フォルダ内の要件文書（`change-requirements.md` 等、恒久的設計資産に該当するものがあればそれも参照可）を基に、AIが起因元フォルダの要件内容を要約する。
  2. **(b) 統合先要件の読み込み**: `current_dir` と `workflow_type` から、今回の作業の要件文書を機械的に特定して読み込む（読込方式は「変更方針の詳細1」参照）。
  3. **(c) 関連性の強弱判断**: (a)と(b)の内容を比較し、追加・変更・不具合修正等を問わず関連性が「強い」か「弱い（なし）」かを二値で判断する。判断理由（根拠）を明文化する。
  4. **(d) 判断困難時の処理**: 強弱の判断が難しい場合、AIは独自判断で確定せず、判断に迷っている旨と両方の可能性の根拠をユーザーに提示し、確認を得る。ユーザーの回答をもって強弱を確定する。
  5. **(e) 分岐**:
     - 関連性「強い」と確定 → 判断結果と根拠を保持したまま既存Step3（ユーザーへの確認）に進む
     - 関連性「弱い（なし）」と確定 → 起因元なし扱いとし、Step3以降（ユーザーへの統合可否確認・ファイル移動等）をスキップし、`current_dir` をそのまま返す（`merged=false, result_dir=current_dir`）。既存Step1の「起因元フォルダが存在しない」場合の早期returnと同様の扱いとする
- **理由**: REQ-C-001 AC-001〜AC-003を素直に手順化したもの。既存Step1（存在確認）→Step2（経緯確認）→新設Step（要件まとめ+関連性判断）→Step3（ユーザー確認）という段階的な絞り込みの流れは、既存のIron Law（`NO MERGE DECISION WITHOUT ORIGIN VERIFICATION`）が要求する「起因元フォルダの存在確認とhistory.mdの経緯確認なしに統合可否をユーザーに問うてはならない」という構造をそのまま拡張するものであり、既存ロジックの意味を変えずに追加できる。

### 3. Step3（ユーザーへの確認）のユーザー提示情報の拡張
- **方針**: 既存Step3のユーザー提示情報リスト（起因元フォルダ／過去の経緯／現在のフォルダ）に、新設Stepで関連性「強い」と判断された場合に限り、「関連性の判断結果（強いこと）」と「その判断理由（根拠）」の2項目を追加する。既存の提示情報・選択肢（1.はい/2.いいえ/3.その他）・分岐ロジックは変更しない。
- **理由**: REQ-C-002 AC-001・AC-002を満たすための最小限の拡張。既存Step3は「関連なし」のケースには到達しない（新設Stepで早期returnするため）ため、Step3側に「関連なし」の分岐を追加する必要がない。

### 4. 3ワークフロー共通の適用（呼び出し元スキルの変更不要）
- **方針**: `fs-change-phase1-analysis` / `fs-bugfix-phase1-analysis` / `fs-refactoring-phase2-candidates` の3スキルは変更しない。3スキルは既に `origin_folder_path` / `current_dir` / `workflow_type` を渡して `folder-merge-check` を activate する呼び出し構造になっており、新設Stepと拡張されたStep3はいずれも `folder-merge-check` の内部処理としてこの既存インターフェースの範囲内で実現できる。リファクタリングWFの引き継ぎ経路（`refactoring-candidates.md` 不在）では `folder-merge-check` 自体が呼ばれない既存分岐がそのまま活きるため、新設Stepもこのケースでは実行されない（影響なし）。
- **理由**: REQ-C-003（3WF一貫適用）は、folder-merge-check側のみの変更で自動的に満たされる。3スキルへの変更が不要になったことで、影響範囲分析で「高」とされていたシグネチャ変更の波及リスクは解消される。

## リファクタリング検討結果
- **検討結果**: 不要
- **理由**: 変更対象は `folder-merge-check/SKILL.md` という単一ドキュメント内への新設Step挿入とStep3の提示情報拡張のみであり、既存のIron Law・Red Flags・Common Rationalizations・完了条件・Integration（呼び出し元/被呼び出し関係）といった構造は一切変更しない。既存の3つの呼び出し元スキルへの変更も不要と判断できたため、影響範囲は当初懸念（impact-analysis.md記載の「高」評価3件）より大幅に縮小した。将来的に同様の「関連性判断」ロジックが他のスキルでも必要になる可能性はあるが、現時点でそれを見越した共通化（例: 関連性判断を汎用スキルとして切り出す等）を行うことは、まだ存在しない将来要求に対する過剰な抽象化（YAGNI違反）となるため見送る。
