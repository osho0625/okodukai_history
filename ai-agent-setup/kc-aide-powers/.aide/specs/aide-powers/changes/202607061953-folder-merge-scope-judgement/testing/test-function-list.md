# 動作確認対象機能リスト

## 前提

本変更の対象は `skills/folder-merge-check/SKILL.md` 1ファイル（スキル定義書）であり、GUIやAPIを持つアプリケーションではない。folder-merge-check は変更WF・バグ修正WF・リファクタリングWFの各フェーズスキルから呼び出されるAI Agent実行プロセスであり、「機能」とはこのスキルが実行時に辿る処理フロー・分岐を指す。

ここでの「ユーザー」とは、変更WF・バグ修正WF・リファクタリングWFを実行する開発者（aide-powers利用者）を指す。「操作」とは、いずれかのワークフローを実際に起動し、起因元フォルダが特定される状況（git blame で過去のコミットのDocs:フッターが検出される状況）を経て、フォルダ統合判定（folder-merge-check）に到達するまで進めること、およびその際にAIエージェントが提示する確認情報・選択肢を確認することを指す。

本リポジトリは自動テストフレームワークを導入していない（dev-environment.md §7.4）ため、動作確認試験の実施段階（execution_mode=execute）では、実際にワークフローを動作させる実動作確認に加えて、AIエージェントによるSKILL.md記載内容のコードレビューによる代替確認も想定する。

変更内容の要点（delta-design.md）: 既存Step2（起因元フォルダの経緯確認）とStep3（ユーザーへの確認）の間に、新設Step3「起因元要件との関連性判断」を挿入する。これに伴い既存Step3〜6はStep4〜7にリナンバリングされる。新設Step3は (a)起因元要件のまとめ（優先順位付き3段階）、(b)統合先要件の読み込み、(c)関連性の強弱判断、(d)判断困難時のユーザー確認、(e)分岐 の5段階で構成される。新Step4（旧Step3）のユーザー提示情報には「関連性の判断結果」「判断理由（根拠）」が追加される。

## 機能1: 起因元要件のまとめと統合先要件の読み込み（新設Step3(a)(b)）

- **機能名**: 起因元要件のまとめと統合先要件の読み込み（folder-merge-check 新設Step3(a)(b)）
- **機能概説**: 起因元フォルダの要件内容を優先順位付き3段階で読み込み要約し、`workflow_type` に応じて統合先（今回の作業）の要件文書を `current_dir` から機械的に特定・読み込む処理。
- **機能詳細**:
  - (a) 起因元要件のまとめ：以下の優先順位で情報源をRead で読み込み要約する。
    - 優先1: 起因元フォルダのトップレベルに現存する (b)分類ファイル（`change-requirements.md` / `bug-report.md` / `bug-analysis.md` / `refactoring-candidates.md` 等、存在するもの）
    - 優先2: 起因元フォルダ内の `old/{日付}/` 配下に退避されている過去の要求文書（`old/{日付}/` が複数存在する場合は最新日付を優先）
    - 優先3: `history.md`（不在時は主要ドキュメントの概要）
    - 既存の除外ルール（移動ルール b の「`old/{日付}/` 退避ファイルは以降のフェーズの入力対象から除外する」）は、本Step（統合可否を判断するために過去の経緯を確認する目的）には適用されない
  - (b) 統合先要件の読み込み：`current_dir` と `workflow_type` から機械的に特定しRead で読み込む。
    - `workflow_type`=「変更」→ `{current_dir}/change-requirements.md`
    - `workflow_type`=「バグ修正」→ `{current_dir}/bug-report.md` と `{current_dir}/bug-analysis.md` の両方
    - `workflow_type`=「リファクタリング」→ `{current_dir}/refactoring-candidates.md`
- **アクション・イベント制御**:
  - 条件: Step2（起因元フォルダの経緯確認）が完了し、起因元フォルダが存在すると確認された直後
  - 処理: (a) 優先順位に従い起因元要件を読み込み要約する → (b) `workflow_type` に応じた統合先要件文書を読み込む
  - 遷移先: 機能2（新設Step3(c)(d)(e) 関連性の強弱判断と分岐）へ
- **関連タスク**: タスク0.1（skills/folder-merge-check/SKILL.md の更新。新設Step3(a)(b)の追加）

## 機能2: 関連性の強弱判断と分岐（新設Step3(c)(d)(e)）

- **機能名**: 関連性の強弱判断と分岐（folder-merge-check 新設Step3(c)(d)(e)）
- **機能概説**: 機能1で読み込んだ起因元要件と統合先要件の内容を比較し、関連性の強弱を二値で判断する。判断が困難な場合はAIが独自判断せずユーザーに確認する。確定結果に応じて後続処理を分岐する。
- **機能詳細**:
  - (c) 関連性の強弱判断：起因元要件と統合先要件の内容比較に基づき、追加・変更・不具合修正等を問わず「強い」か「弱い（なし）」かを二値判断し、判断理由（根拠）を明文化する
  - (d) 判断困難時の処理：強弱の判断が難しい場合、AIが独自判断で確定せず、判断に迷っている旨と両方の可能性の根拠をユーザーに提示し確認を得る。提示する選択肢は「1. 関連性は強い（統合検討へ進む）」「2. 関連性は弱い・なし（起因元なし扱いとする）」「3. その他（自由記述）」の3択
  - (e) 分岐：関連性「強い」と確定した場合は判断結果と判断理由（根拠）を保持したまま新Step4（ユーザーへの確認）へ進む。関連性「弱い（なし）」と確定した場合は起因元なし扱いとし、`current_dir` をそのまま返す（`merged=false, result_dir=current_dir`）
- **アクション・イベント制御**:
  - 条件: 機能1（新設Step3(a)(b)）完了後
  - 処理: 内容比較 → 二値判断（判断困難時はユーザー確認で確定） → 判断結果に応じた分岐
  - 遷移先: 「強い」確定 → 機能3（新Step4 ユーザーへの統合可否確認）へ／「弱い（なし）」確定 → フォルダ統合フロー終了（早期return、新Step4以降スキップ）
- **関連タスク**: タスク0.1（skills/folder-merge-check/SKILL.md の更新。新設Step3(c)(d)(e)の追加）

## 機能3: ユーザーへの統合可否確認（新Step4：提示情報拡張と遷移先変更）

- **機能名**: ユーザーへの統合可否確認（folder-merge-check 新Step4、旧Step3）
- **機能概説**: 機能2で関連性「強い」と確定した場合にのみ到達する。既存の提示情報（起因元フォルダ・過去の経緯・現在のフォルダ）に加えて「関連性の判断結果」「判断理由（根拠）」を追加提示し、統合可否をユーザーに問う。
- **機能詳細**:
  - 提示情報：起因元フォルダ、過去の経緯（history.md の内容要約／主要ドキュメントの概要）、関連性の判断結果（強い）、判断理由（根拠：機能2の(c)または(d)で確定した根拠）、現在のフォルダ、統合可否を問う文言
  - 選択肢：「1. はい（統合する）」「2. いいえ（新規フォルダで続行）」「3. その他（自由記述）」
  - 「1. はい」選択時 → 新Step5（ファイル移動の実行）へ遷移
  - 「2. いいえ」選択時 → `current_dir` をそのまま返す（`merged=false, result_dir=current_dir`）
- **アクション・イベント制御**:
  - 条件: 機能2で関連性「強い」と確定した場合のみ到達
  - 処理: 提示情報の構築（判断結果・根拠を含む） → ユーザーの選択待ち → 選択結果に応じた分岐
  - 遷移先: 「1. はい」→ Step5（ファイル移動の実行）／「2. いいえ」→ フォルダ統合フロー終了
- **関連タスク**: タスク0.1（skills/folder-merge-check/SKILL.md の更新。新Step4の提示情報拡張・遷移先変更）

## 機能4: 既存フロー（Step1・Step2・Step5〜7・完了条件）の非退行動作

- **機能名**: 既存フローの非退行動作（folder-merge-check Step1・Step2・新Step5〜7・完了条件・Red Flags・Common Rationalizations）
- **機能概説**: 新設Step3の挿入と既存Step3〜6のリナンバリングが行われた後も、変更対象外の既存処理内容（Step1・Step2・新Step5〜7）と、完了条件・Red Flags・Common Rationalizationsの記述整合性が損なわれていないことを確認する。
- **機能詳細**:
  - Step1（起因元フォルダの存在確認）：起因元フォルダが存在しない場合の早期return（`merged=false, result_dir=current_dir`）処理が変更されていないこと
  - Step2（起因元フォルダの経緯確認）：history.md 読み込みロジックが変更されておらず、機能1（新設Step3(a)）の入力として引き継がれること
  - 新Step5（旧Step4、ファイル移動の実行）：移動ルール（a/b/b-2/c）・Step5-事前（統合先の前WF成果物の一括退避処理）の内部ロジックが変更されておらず、自己参照「本Step4の判定基準」が「本Step5の判定基準」に正しく更新されていること
  - 新Step6（旧Step5、history.md の更新）：`workflow_type` による分岐処理（変更/リファクタリングは即時更新、バグ修正はdoc-sync委譲）が変更されていないこと
  - 新Step7（旧Step6、結果の返却）：`merged=true, result_dir=origin_folder_path` の返却処理が変更されていないこと
  - 完了条件セクション：「統合した場合」項目1（新設Step3の判断完了確認、新規追加）〜項目8（旧項目1〜7からリナンバリング）、「統合しなかった場合」項目1（関連性「弱い（なし）」確定時の分岐が追加されたこと）が正しく反映されていること
  - Red Flagsテーブル：末尾に「Step3を経ずに即座にユーザーへ統合可否を確認する」「関連性の強弱判断（Step3）は省略してよい」の2行が追加されていること
  - Common Rationalizationsテーブル：末尾に「history.mdの経緯だけで関連性は判断できる」「判断が難しいときは『強い』側に倒す」の2行が追加されていること
- **アクション・イベント制御**:
  - 条件: 各Stepの実行タイミング（Step1はフロー開始時、Step2はStep1完了直後、新Step5〜7は機能3で「1.はい」選択後の各段階）
  - 処理: 各Stepの既存ロジックをそのまま実行（内部処理内容は変更しない、見出し番号・自己参照のみ更新）
  - 遷移先: 既存と同一（Step1→Step2→機能1・機能2・機能3→新Step5→新Step6→新Step7）
- **関連タスク**: タスク0.1（skills/folder-merge-check/SKILL.md の更新。既存Step3〜6のリナンバリング、完了条件・Red Flags・Common Rationalizationsの更新）

## 機能5: 3ワークフロー共通適用（REQ-C-003）

- **機能名**: 3ワークフロー共通適用（変更WF・バグ修正WF・リファクタリングWFからの呼び出し）
- **機能概説**: folder-merge-check は変更WF・バグ修正WF・リファクタリングWFの3ワークフローで共通利用されるスキルであり、新設Step3（関連性判断プロセス）はどのワークフローから呼び出された場合でも同一に実行される。
- **機能詳細**:
  - 変更WF（`fs-change-phase1-analysis` Step6「フォルダ統合判定」）から呼び出された場合、`workflow_type`=「変更」として新設Step3が実行され、Step3(b)で `change-requirements.md` が読み込まれる
  - バグ修正WF（`fs-bugfix-phase1-analysis` Step7「フォルダ統合判定」）から呼び出された場合、`workflow_type`=「バグ修正」として新設Step3が実行され、Step3(b)で `bug-report.md` と `bug-analysis.md` の両方が読み込まれる（Step7はStep5・Step6完了後に実行されるため両ファイルは常に存在する）
  - リファクタリングWF（`fs-refactoring-phase2-candidates` Step2「フォルダ統合判定」）から呼び出された場合、`workflow_type`=「リファクタリング」として新設Step3が実行され、Step3(b)で `refactoring-candidates.md` が読み込まれる。ただし引き継ぎ経路（`refactoring-request.md` あり）ではStep2自体が実行されないため新設Step3も実行されない（対象外）
- **アクション・イベント制御**:
  - 条件: 各WFのフォルダ統合判定タイミングでfolder-merge-checkが `origin_folder_path` / `current_dir` / `workflow_type` を渡して呼び出されたとき
  - 処理: `workflow_type` の値に応じてStep3(b)の読込対象ファイルを分岐しつつ、機能1〜3と同一の判断プロセスを実行する
  - 遷移先: 機能1〜3のフローへ（呼び出し元WFによる分岐なし）
- **関連タスク**: タスク0.1（skills/folder-merge-check/SKILL.md の更新。呼び出し元3スキルへの変更は不要と確認済みだが、folder-merge-check内部の`workflow_type`分岐ロジックがタスク0.1に含まれる）
