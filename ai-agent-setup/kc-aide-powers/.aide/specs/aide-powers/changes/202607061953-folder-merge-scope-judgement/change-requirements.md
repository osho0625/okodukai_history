# 変更要求定義

## 変更概要
- **変更の目的・背景**: folder-merge-check スキル（`skills/folder-merge-check/SKILL.md`）は変更WF・バグ修正WF・リファクタリングWFの3ワークフローで共通利用され、フォルダ統合実行時のStep3「ユーザーへの確認」で統合可否をユーザーに問う。現行のStep3は、git blame と Docs: フッターの追跡によって特定された起因元フォルダの存在確認（Step1）・経緯確認（Step2、history.md や主要ドキュメントの概要）のみを判断材料としてユーザーに提示しており、「今回の作業（統合先）が起因元フォルダの元要件と関連性を持つのか」を判断するプロセスが組み込まれていない。この判断が行われないまま統合判断が行われると、本来関連のない経緯が同一フォルダに混在し、後からのドキュメント追跡・意味理解を誤らせるおそれがある。本変更では、Step3の統合可否確認に先立ち、AIが起因元フォルダの要件内容をまとめ、今回の作業がその起因元要件との関連性（追加・変更・不具合修正等を問わず、関連の強さ）を持つかどうかを判断するプロセスを追加する。関連が強いと判断した場合は、その判断理由（根拠）とともにユーザーに統合可否を確認し、関連がないと判断した場合は起因元なし扱いとする。これにより、より正確な統合判断を可能にする。
- **変更種別**: 仕様変更

## 要求事項

### REQ-C-001: 起因元フォルダとの関連性判断プロセスの追加
- **種別**: 変更
- **説明**: folder-merge-check の Step3（ユーザーへの確認）に先立ち、以下の2段階のプロセスを追加する。(a) AIが起因元フォルダの要件内容をまとめる。(b) 統合先（今回の作業）の要件が、その起因元要件との関連性（追加・変更・不具合修正等を問わず、関連の強さ）を持つかどうかを判断する。
- **受入基準**:
  - AC-001: 起因元フォルダが特定された場合、Step3のユーザー確認が実行される前に、AIが起因元フォルダの要件内容をまとめること
  - AC-002: 上記のまとめに基づき、今回の作業（統合先）の要件と起因元要件との関連性の強弱が判断されること。この判断は、git blame の情報および Docs: フッターの情報だけでなく、起因元フォルダ内の実際のドキュメント内容（history.md や主要設計書等）と今回の作業内容（change-requirements.md / bug-report.md 等）の内容比較に基づいて行われること
  - AC-003: 関連性が強いか弱いかの判断が難しい場合、AIが独自判断で決定せず、ユーザーに確認すること。関連がないと判断した場合は、起因元なし（統合フローに進まない）として扱うこと
- **優先度**: 必須

### REQ-C-002: 判断結果のユーザー提示
- **種別**: 変更
- **説明**: 関連性が強いと判断された場合、Step3でユーザーに統合可否を問う際、既存の提示情報（起因元フォルダ・過去の経緯・現在のフォルダ）に加えて、REQ-C-001で判断した関連性の判断結果（関連が強いこと）とその判断理由（根拠）を判断材料として提示する。
- **受入基準**:
  - AC-001: Step3でユーザーに提示される情報に、起因元要件との関連性の判断結果とその判断理由（根拠）が含まれること
  - AC-002: ユーザーは判断結果と根拠を確認した上で、統合可否（はい／いいえ／その他）を選択できること
- **優先度**: 必須

### REQ-C-003: 3ワークフロー共通の適用
- **種別**: 変更
- **説明**: folder-merge-check は変更WF・バグ修正WF・リファクタリングWFの3ワークフローで共通利用されるスキルであるため、REQ-C-001・REQ-C-002 で追加する関連性判断プロセスは3WF全てに一貫して適用される。
- **受入基準**:
  - AC-001: 変更WF（`fs-change-phase1-analysis` 経由）・バグ修正WF（`fs-bugfix-phase1-analysis` 経由）・リファクタリングWF（`fs-refactoring-phase2-candidates` 経由）のいずれから呼び出された場合でも、同一の関連性判断プロセスが実行されること
- **優先度**: 必須

## 対象外（スコープ外）
- git blame や Docs: フッターによる起因元フォルダの特定ロジック自体の変更（本変更は特定後の統合判断プロセスのみが対象）
- Step4（ファイル移動）以降の処理ロジック（移動ルール・(a)/(b)分類・old/退避処理等）の変更
- history.md の追記テンプレート形式の変更
- 統合判断そのものの自動化（AIが独自判断で統合可否を最終決定すること）。最終的な統合可否の判断はユーザーが行う原則（Iron Law）は維持する
- 関連性が「強い」「弱い（なし）」以外の分類（3分類判定等）の導入。本変更では関連の強弱による二値判断のみを対象とする

## 前提条件
- folder-merge-check の Step1（起因元フォルダの存在確認）・Step2（経緯確認）が正常に完了していること
- 起因元フォルダに history.md または主要ドキュメントが存在し、内容を確認できること
- 今回の作業のドキュメント（change-requirements.md / bug-report.md 等）が既に作成されていること
