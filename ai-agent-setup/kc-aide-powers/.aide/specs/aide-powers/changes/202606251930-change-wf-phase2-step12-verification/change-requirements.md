# 変更要求定義書 — 動作確認試験書レビューループの導入

- **feature_name:** aide-powers
- **変更ID:** 202607010000-manual-test-review-loop
- **変更種別:** 機能追加（新規レビューエージェント）＋ 仕様変更（4WFの動作確認Step改修）の複合
- **作成日:** 2026-07-01

---

## 1. 変更概要

### 1.1 背景・目的

実装WF・バグ修正WF・変更WF・リファクタリングWFには、実装後に「動作確認Step」があり、各WFの verification プロンプト（`impl-verification-prompt.md` / `bugfix-verification-prompt.md` / `change-verification-prompt.md` / `refactoring-verification-prompt.md`）で動作確認試験エージェントが試験書を作成・実行している。

しかし、例えばWebアプリを実装した際に、バックエンドAPIの評価試験書だけが作られ、ユーザー視点のアプリ動作（画面操作・E2E）を全く検証しない、という問題が発生した。各 verification プロンプト末尾には「開発者視点ではなくユーザー視点で作成」という注意書きが1行あるが、**プロンプト記述の強化だけでは品質が担保されない**ことが確認された。

本変更の目的は、プロンプト記述の強化ではなく、**動作確認試験書（成果物）をレビューする専用エージェントを新設し、「生成→レビュー→指摘→修正→再レビュー（PASSまでループ）」方式を4WFの動作確認Stepに組み込む**ことで、試験書がユーザー視点で全動作を検証していることを構造的に担保することである。

この方式は、aide-powers の他の品質保証機構（設計QAゲート、コード2段階レビュー、ユースケース網羅性レビュー）と同じ「生成→レビュー→修正ループ」の設計思想と一貫する。

### 1.2 変更のゴール

- 動作確認試験書がユーザー視点の仕様で全動作を検証しているかをレビューする仕組みを持つこと
- 4WF（実装・バグ修正・変更・リファクタリング）すべての動作確認Stepで、試験書がレビューされ、ユーザー視点でない試験書はPASSしないこと
- レビュー指摘があれば修正ループが回り、PASSするまで次に進まないこと
- 各WF固有のレビュー基準の差異に対応できること

## 2. 要求事項

### REQ-C-001: 動作確認試験書レビュー専用エージェントの新設

- **種別:** 機能追加
- **説明:**
  動作確認試験書を「ユーザー視点の仕様で全動作を検証しているか」の観点でレビューする専用エージェント（レビューアー）を新設する。このレビューアーは、少なくとも次の観点で試験書を評価できること。
  1. **ユーザー操作シナリオになっているか** — バックエンドAPI単体試験などの内部実装視点になっていないか
  2. **全ユースケース／要件／受入基準がユーザー視点でカバーされているか** — 検証対象の網羅性
  3. **期待結果がユーザーが目視確認できる形か** — 内部状態ではなく、画面・出力など利用者が確認できる形の期待結果になっているか
  4. **内部実装視点の試験項目が紛れていないか** — 開発者視点の項目の混入検出
- **受入基準:**
  - **AC-001-1:** レビューアーは、上記4観点それぞれについて試験書を評価し、観点ごとの合否（または指摘）を出力できる。
  - **AC-001-2:** レビューアーは、試験書がユーザー視点でない（内部実装視点に偏っている・網羅性が不足している）場合に PASS ではない判定（指摘あり）を返す。
  - **AC-001-3:** レビューアーは、指摘を出す際に「どの試験項目／どの要件が、どの観点で不足・不適切か」を修正可能な粒度で明示する。
- **優先度:** Must

### REQ-C-002: 4WFの動作確認Stepへのレビューループ組み込み

- **種別:** 仕様変更
- **説明:**
  実装WF・バグ修正WF・変更WF・リファクタリングWFの4つの動作確認Stepに、REQ-C-001 のレビューアーによる「試験書生成 → レビュー → 指摘 → 修正 → 再レビュー（PASSまでループ）」を組み込む。対象となる動作確認Stepは以下の前提のものである（前提条件 §4 参照）。
  - 実装WF: `fs-impl-phase4-execution` の動作確認Step
  - バグ修正WF: `fs-bugfix-phase2-impl` の動作確認Step
  - 変更WF: `fs-change-phase2-impl` の動作確認Step
  - リファクタリングWF: `fs-refactoring-phase5-impl` の動作確認Step
- **受入基準:**
  - **AC-002-1:** 4WFすべての動作確認Stepにおいて、生成された動作確認試験書がレビューアーによってレビューされる。
  - **AC-002-2:** レビューアーが PASS でない判定（指摘あり）を返した場合、試験書が修正され、再度レビューされる。この修正→再レビューは PASS 判定になるまで繰り返される。
  - **AC-002-3:** レビューアーが PASS 判定を返すまで、動作確認Stepは完了扱いにならず、後続のStep／フェーズへ進まない。
  - **AC-002-4:** ユーザー視点でない試験書（内部実装視点に偏った試験書）は、いずれのWFの動作確認StepでもPASSしない。
- **優先度:** Must

### REQ-C-003: WF固有のレビュー基準差異への対応

- **種別:** 機能追加
- **説明:**
  各WFの動作確認は検証すべき対象が異なるため、レビューアーはWF種別に応じたレビュー基準の差異に対応できること。少なくとも次の差異を扱えること。
  - **バグ修正WF:** 再現手順が再現しなくなったこと（バグ再現手順の検証）と、受入基準の検証がユーザー視点で行われているか
  - **変更WF:** 変更の受入基準がユーザー視点で検証されているか
  - **リファクタリングWF:** 外部から観測される振る舞いが保持されていること（外部振る舞い保持）がユーザー視点で検証されているか
  - **実装WF:** ユースケース／要件／受入基準がユーザー視点で網羅的に検証されているか
- **受入基準:**
  - **AC-003-1:** レビューアーは、対象WF種別に応じたレビュー基準（バグ修正＝再現手順／受入基準、変更＝受入基準、リファクタリング＝外部振る舞い保持、実装＝ユースケース／要件／受入基準の網羅）を適用してレビューできる。
  - **AC-003-2:** WF種別が識別可能な形でレビューアーに渡され、レビュー結果にどのWF基準を適用したかが判別できる。
- **優先度:** Must

### REQ-C-004: 試験書作成・レビュー・試験実行の3工程分離

- **種別:** 仕様変更
- **説明:**
  現状の各WFの動作確認Stepは、1つの動作確認試験エージェントが「機能リスト作成 → 試験書作成 → 試験実行 → 結果報告」を一気通貫で実施しており、**試験書の作成と試験の実行が分離されていない**。このため、REQ-C-001／REQ-C-002 のレビューループが試験書に対して正しく機能しない（レビュー前・レビュー未完了の試験書のまま試験実行まで進んでしまう）。
  これを解消するため、動作確認Stepを以下の順序に明確に分離する。
  1. **試験書作成** — 動作確認試験書を作成する（この時点では試験実行はしない）
  2. **試験書レビュー** — REQ-C-001 のレビューアーが試験書をレビューする。NEEDS_FIX（指摘あり）の場合は試験書を修正して再レビューし、PASS（APPROVED）になるまでループする
  3. **試験実行（動作確認）** — レビューが PASS（APPROVED）となった試験書に基づいて、実際の動作確認（試験実行）を行う

  すなわち「レビューでOKになった試験書に基づいて実際の動作確認を実行する」フローとし、試験書作成工程と試験実行工程を跨いでレビューゲートを設ける。
- **受入基準:**
  - **AC-004-1:** 動作確認Stepにおいて、試験書作成・試験書レビュー・試験実行が明確に分離された工程として順に実行される。
  - **AC-004-2:** 試験実行は、当該試験書のレビューが PASS（APPROVED）となった後にのみ行われる。
  - **AC-004-3:** レビュー前・レビュー未完了（NEEDS_FIX を含む）の試験書に基づいて試験実行を行わない。
  - **AC-004-4:** レビューが NEEDS_FIX の場合、試験書が修正・再レビューされ、PASS になるまで試験実行工程に進まない。
- **優先度:** Must

### REQ-C-005: 動作確認の実施方法（エビデンス）のユーザー報告

- **種別:** 機能追加
- **説明:**
  動作確認完了後にユーザーへ「動作確認OK」と報告する際、実際にはコードレビューだけで済ませて「OK」と報告してしまう事象が発生していた。これを防ぐため、動作確認結果をユーザーへ報告する際には、**各試験項目について「どうやって確認したか（実施方法・エビデンス）」を必ず明示する**。
  具体的には、各試験項目ごとに次を区別して報告する。
  - **実動作確認** — 実際にアプリを動作させて確認した（例: Playwright 等のブラウザ操作、実際のAPIコール、CLI実行 など、用いた手段を明示）
  - **コードレビュー代替** — 実際の動作確認を行わずコードレビューで代替した（その旨を明示し、実動作確認でない項目が判別できるようにする）

  「OK」だけの報告（実施方法・エビデンスの記載がない報告）は許容しない。
- **受入基準:**
  - **AC-005-1:** 動作確認結果のユーザー報告に、各試験項目の確認方法（実動作確認／コードレビュー代替の区別）が含まれる。
  - **AC-005-2:** 実動作確認の項目については、用いた手段（ブラウザ操作／APIコール／CLI実行等）が判別できる形で示される。
  - **AC-005-3:** コードレビューで代替した項目は、その旨が明示され、実動作確認でない項目として区別できる。
  - **AC-005-4:** 実施方法・エビデンスの記載を欠いた「OK」のみの報告は、動作確認報告として成立しない（許容しない）。
- **優先度:** Must

## 3. 対象外（スコープ外）

| # | 対象外事項 | 理由 |
|---|---|---|
| OUT-01 | 動作確認試験の「実行」方法自体の変更（Playwright MCP 等の実行手段の導入・変更） | 本変更は試験書の「品質レビュー」に集中する。実行手段は今回のスコープ外 |
| OUT-02 | ユースケース分析フェーズ（`fs-design-phase6-usecase`）の変更 | 前回の変更WFで対応済みのため対象外 |
| OUT-03 | 影響範囲の分析・対応方針の策定・具体的なコード（before→after）変更設計 | 本ドキュメントは変更要求定義に限定。後続フェーズで扱う |
| OUT-04 | 4つの動作確認Step以外のフェーズ・Stepの品質保証機構の変更 | 本変更は4WFの動作確認Stepに限定する |
