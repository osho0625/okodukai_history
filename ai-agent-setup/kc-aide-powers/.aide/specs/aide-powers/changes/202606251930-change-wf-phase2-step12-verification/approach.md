## 1. 方針概要

動作確認試験書の品質（ユーザー視点で全動作を検証しているか）を構造的に担保するため、**動作確認試験書レビュー専用の「名前付きエージェント」を1つ新設**し、4WF（実装・バグ修正・変更・リファクタリング）の各動作確認Stepに「試験書生成 → レビュー → 指摘 → 修正 → 再レビュー（PASSまでループ）」を組み込む。

本方針は既存の品質保証機構と同一の設計思想に一貫させる。すなわち、

- 生成側（`{wf}-verification-prompt.md` による試験書生成）と レビュー側（新エージェント）を分離する（`micro-impl-agent`＝生成 / `design-review-agent`・`code-review-agent`＝レビュー の分業構造と同型）。
- 「PASSするまで次に進まない」ゲート型（設計QAゲート UR-006、コード2段階レビュー UR-005 と同型）。
- レビュー結果に基づく修正→再レビューのループ（`fs-design-phase6-usecase` のUC網羅性レビューループ、`coding-test-2review` の内部ループと同型）。

### 1.1 REQ-C-004（試験書作成・レビュー・試験実行の3工程分離）の反映

REQ-C-004 により、動作確認Stepは **「①試験書作成 → ②試験書レビュー（NEEDS_FIXなら修正→再レビュー、PASSまでループ）→ ③試験実行（動作確認）」の3工程に明確分離**する。従来は1つの動作確認試験エージェントが「機能リスト作成→試験書作成→試験実行→結果報告」を一気通貫で実施しており、試験書作成と試験実行が未分離だったため、レビューループが試験書に対して正しく機能しなかった（レビュー未完了の試験書のまま試験実行まで進む）。3工程分離により、②のレビューは①の成果物（試験書）に対してのみ行い、③の試験実行は②が APPROVED になった後にのみ実行する（レビューゲートを②③間に置く）。

この3工程分離を実現するため、**verificationプロンプト4本の改修が「任意・設計判断」から「必須改修」へ格上げ**された（impact-analysis §1.1 / §3.4 と整合）。生成側プロンプトを「試験書作成まで（試験実行しない）」と「試験実行」に工程分離する改修が不可避となるためである。改修は §2.2 の変更対象（必須改修）に含める。実現方式の推奨は §3.7（論点5）に示す。

### 1.2 REQ-C-005（動作確認の実施方法・エビデンスのユーザー報告）の反映

REQ-C-005 により、動作確認完了後のユーザー報告では、**各試験項目について「どうやって確認したか（実施方法・エビデンス）」を必ず明示**する。実際にはコードレビューだけで済ませて「OK」と報告してしまう事象を防ぐため、各試験項目ごとに「実動作確認（用いた手段=ブラウザ操作／APIコール／CLI実行等を明示）」か「コードレビュー代替（実動作確認でない旨を明示）」かを区別して報告する。**「OK」だけの報告（実施方法・エビデンスの記載がない報告）は動作確認報告として成立しない**（完了条件として不許容）。

この反映は2箇所に及ぶ（impact-analysis §3.5 / 注意事項9 と整合）。①verificationプロンプトの「結果の出力」に試験項目ごとの実施方法（実動作確認／コードレビュー代替）を記録・報告させる、②各WF SKILL の動作確認Step のユーザー報告部分にエビデンス添付を義務化し、エビデンスなしの「OK」のみを完了条件として認めない。実現方式は §3.8（論点6）に示す。

### 1.3 OCP原則の観点

OCP原則の観点では、**新規追加（新エージェント1体）を主体とし、既存4スキルへの改修は「動作確認Step内の3工程分離＋レビューループ挿入＋エビデンス報告追加（拡張）」に限定**する。verificationプロンプトの改修も、既存の一気通貫構造を工程分離へ再編する拡張であり、他のStep・フェーズや他機構の破壊的変更は行わない。将来WFが増えた場合も、レビュー基準はエージェント内の分岐（`wf_type`）を拡張すればよく、4スキルを個別に書き換える必要がない構造とする。

## 3. 変更方針の詳細

### 3.1 論点1: レビューアーの実装方式 —【決定】名前付きエージェント新設

**決定:** 動作確認試験書レビューアーを **名前付きエージェント（`agents/` 4系統）** として新設する。暫定名 `manual-test-review-agent`（正式名は設計フェーズで確定）。「各WFスキル配下のレビュー用プロンプト（4スキル各1ファイル）」方式は採らない。

**判断根拠（OCP・DRY・既存機構との一貫性）:**

1. **単一の情報源（DRY / OCP）。** 本レビューアーは4WF共通の4観点（REQ-C-001）と、WF別基準（REQ-C-003）を持つ「1つの論理的なレビューアー」である。名前付きエージェントなら定義は1箇所に集約され、`wf_type` 引数で基準を切り替える。将来WFが増えても「エージェント内の基準分岐を拡張」するだけでよく、変更に対して閉じている（既存4スキルを書き換えない）。プロンプト方式では4スキルディレクトリに実質同一のレビュー本文を複製することになり（DRY違反・4箇所同時保守）、共通の4観点を修正するたび4ファイルを直す必要が生じる。

2. **既存の最も近い類似機構と同型。** レビュー・監査を担う既存機構はいずれも名前付きエージェント（`design-review-agent`, `code-review-agent`, 各QAエージェント, `test-coverage-audit-agent`）である。特に `test-coverage-audit-agent`（動作確認試験書の網羅性を監査する名前付きエージェント）は、本レビューアーと役割が最も近い（ともに動作確認試験書を対象とする監査／レビュー）。同じカテゴリの機構を同じ実装方式（名前付きエージェント）で揃えることが構造的に一貫する。

3. **生成側と評価側の分離という既存パターンに合致。** 既存の `{wf}-verification-prompt.md` は「試験書の生成側」であり、これは各スキルディレクトリのプロンプトのままとする（3工程分離後も生成側＝プロンプトの位置づけは変わらない）。本変更で追加するのは「評価側（レビュー）」であり、これは QA／レビューエージェント群と同じく名前付きエージェントに置く。`micro-impl-agent`（生成）と `design-review-agent`/`code-review-agent`（評価）が別立てである構造と一致する。

4. **レビューロジックの実質量。** 4観点（REQ-C-001）＋4WF別基準（REQ-C-003）＋PASS/指摘の出力フォーマット＋指摘の修正可能粒度（AC-001-3）を担うため、独立したエージェント定義に値する規模である。

**留意:** 既存の「動作確認試験エージェント（生成側）」がプロンプト方式である点は本決定と矛盾しない。生成側はプロンプト、評価側は名前付きエージェント、という役割による使い分けであり、上記2・3の一貫性判断を優先する。

### 3.2 論点2: test-coverage-audit-agent との責務境界

両者は「動作確認試験書を扱う」点で近いが、**軸（質 vs 量）・タイミング・対象WF・対象ファイル・アクション**で明確に切り分ける。設計フェーズでは、新エージェント定義の「担当外」に test-coverage-audit-agent の担当領域を明記し、逆も同様に相互参照させて重複を防ぐこと。

| 軸 | test-coverage-audit-agent（既存） | manual-test-review-agent（新設） |
|---|---|---|
| 主眼 | **量的網羅性**（要件と試験項目の1対1照合＝カバレッジの穴検出） | **質的視点**（試験書がユーザー視点で全動作を検証する質を持つか） |
| 実行タイミング | 実装WFの最終チェック（`fs-impl-phase5-final-check`） | 4WFの動作確認Step（3工程の②＝試験書作成直後の品質ゲート） |
| 対象WF | 実装WFのみ | 実装・バグ修正・変更・リファクタリングの4WF |
| 照合軸／対象 | `user-requirements.md` 全要件 × `manual-test-plan.md` 全試験項目 | 動作確認Stepで生成された試験書（`testing/` 配下）そのものの視点・期待結果・観点 |
| 検出する問題 | 「要件Aに対応する試験項目がない」（未カバー要件） | 「試験書がバックエンドAPI単体視点に偏る／期待結果が目視不能／内部視点が混入」 |
| 出力後アクション | 試験項目漏れ→`manual-test-plan.md` に追記／実装漏れの疑い→Step1差し戻し推奨 | PASS/指摘（指摘→試験書修正→再レビューのループ） |

**重複回避の切り分け（重要）:** REQ-C-001 の観点2「全ユースケース／要件／受入基準が**ユーザー視点で**カバーされているか」は網羅性に触れるが、新レビューアーの担当は **「ユーザー視点でカバーされているか（質的な視点の妥当性）」に限定**し、「要件IDと試験項目の1対1突合（量的カバレッジ監査）」は行わない。後者は `test-coverage-audit-agent` の専任とする。両者は「動作確認Stepの質的ゲート（前）」と「final-checkの量的網羅監査（後）」の二段構えで補完関係になり、観点が重ならない。

### 3.3 論点3: レビューループの組込構造（3工程分離前提）

REQ-C-004 により、各WFの動作確認Stepを **①試験書作成 → ②試験書レビュー → ③試験実行** の3工程に明確分離する。②のレビューは①の成果物（試験書）に対して行い、③の試験実行は②が APPROVED になった後にのみ実行する。②のレビュー→修正→再レビューのループ構造は、既存の `fs-design-phase6-usecase` Step3（UC網羅性レビュー）および `coding-test-2review`（レビューFAIL→未PASSへ戻し fix→再レビューがPASSまで）と同型である。

**動作確認Step内のフロー（4WF共通の骨格・3工程）:**

**【工程①】試験書作成（試験実行しない）**
1. `{wf}-verification-prompt.md` の「試験書作成」セクション/モード（§3.7）を用い、プレースホルダーを実データで置換してサブエージェントを起動し、動作確認試験書を**作成**させる（この時点では試験実行しない。試験書パスを受領）。

**【工程②】試験書レビュー（PASSまでループ）**
2. `manual-test-review-agent` を起動し、`wf_type` と試験書パス・WF固有の入力ファイル（§3.4）を渡してレビューさせる。出力をレポートへ即時記載する。
3. レビュー判定による分岐:
   - **APPROVED（PASS）** → 工程③へ進む。
   - **NEEDS_FIX（指摘あり）** → 指摘（どの試験項目／どの要件が、どの観点で不足・不適切か）に基づき試験書を修正する。修正は生成側サブエージェント（`{wf}-verification-prompt.md` の「試験書作成」セクション/モード）へ指摘内容を渡して該当試験書を修正・再生成させる形とする。修正後、手順2へ戻る（**APPROVED になるまで繰り返す**）。

**【工程③】試験実行（動作確認）**
4. ②が APPROVED となった試験書に基づき、`{wf}-verification-prompt.md` の「試験実行」セクション/モード（§3.7）を用いてサブエージェントを起動し、実際の動作確認（試験実行）を行う。試験結果を受領する。**②が APPROVED になる前に③を実行してはならない**（AC-004-2 / AC-004-3）。
5. 試験結果の確認 → ユーザー承認（このユーザー報告に REQ-C-005 のエビデンス明示を添える。§3.8）。

**Step完了条件**に「試験書レビュー結果 = APPROVED（PASS）」＋「試験実行が APPROVED 済み試験書に基づいて実施済み」＋「エビデンス付きユーザー報告済み」を追加する（AC-002-3 / AC-004-1〜4 / AC-005-4）。

**判定文字列の一貫性:** 新レビューアーの判定は QA／コードレビュー系に合わせ **`APPROVED` / `NEEDS_FIX`**（PASS/指摘）とする。SKILL側の状態判定条件は、レビューアー出力の判定行の文字列とレベルで一致させる（`fs-design-phase6-usecase` Step3 が「全操作カバー済み」という文字列一致で判定しているのと同じ設計）。判定基準は「観点ごとの指摘が0件 → APPROVED、1件以上 → NEEDS_FIX」を基本とし、既存QA（FAIL=0 かつ WARNING=0 で APPROVED）と整合させる（Q-04/Q-05との整合）。

**停滞時の扱い:** ②のループがPASSに収束しない場合は、既存のメタ開発の反復停滞対応（`design-impl-gap-process.md` のプロセスC「一定回数の繰り返しでユーザー相談」）に準じ、一定回数で停止しユーザーへ相談する旨を各SKILLのStepに明記することを推奨する（無限ループ防止）。具体的な回数・文言は設計フェーズで確定する。

### 3.4 論点4: WF固有基準の渡し方

**渡し方:** レビューアー起動時の入力に **`wf_type`（`impl` / `bugfix` / `change` / `refactoring`）を明示的な引数として渡す**（AC-003-2: WF種別が識別可能な形で渡され、結果にどの基準を適用したか判別できる）。レビューアーは出力に「適用したWF基準」を明記する。あわせて、WF別に必要な入力ファイルを渡す。

| wf_type | 適用するWF別基準（REQ-C-003） | レビューアーに渡す主な入力（例） |
|---|---|---|
| `impl` | ユースケース／要件／受入基準がユーザー視点で網羅的に検証されているか | 試験書パス、`usecase-analysis.md`、`user-requirements.md` |
| `bugfix` | 再現手順が再現しなくなったこと＋受入基準がユーザー視点で検証されているか | 試験書パス、バグ再現手順（bug報告／`fix-plan.md`）、受入基準 |
| `change` | 変更の受入基準がユーザー視点で検証されているか | 試験書パス、変更要求の受入基準（`change-requirements.md` 等） |
| `refactoring` | 外部から観測される振る舞いの保持がユーザー視点で検証されているか | 試験書パス、外部振る舞い基準（`refactoring-plan.md` 等） |

**基準の構造:** REQ-C-001 の共通4観点（ユーザー操作シナリオか／ユーザー視点の網羅性〔質的〕／目視可能な期待結果か／内部視点混入検出）は `wf_type` に依存せず常に適用する。REQ-C-003 のWF別基準は `wf_type` による分岐で適用する。この「共通観点＋WF別分岐」構造により、WF追加時はエージェント内の分岐追加のみで対応でき、OCPを満たす。

### 3.5 4WFそれぞれのレビューループ挿入位置（3工程構造）

impact-analysis §4-6 で特定済みの接続点に、§3.3 の3工程構造（①試験書作成→②レビューPASSまでループ→③試験実行）を構成する。いずれも現状は「試験書生成 →（結果OK）→ ユーザー承認」の構造であり、これを3工程に再構成する。

| WF | スキル | 挿入するStep | 3工程への再構成位置 |
|---|---|---|---|
| 実装 | `fs-impl-phase4-execution` | Step 2「動作検証・ユーザー確認」 | 現状の「試験書生成→結果OK→ユーザー承認」を「①試験書作成→②レビューPASSまでループ→③試験実行→ユーザー承認（エビデンス付）」に再構成 |
| バグ修正 | `fs-bugfix-phase2-impl` | Step 10「動作検証・ユーザー確認」 | 同上（Step9=リグレッション確認、Step11=設計書反映の間） |
| 変更 | `fs-change-phase2-impl` | Step 12「動作検証・ユーザー確認」 | 同上（Step11=リグレッション確認、Step13=設計書反映の間） |
| リファクタリング | `fs-refactoring-phase5-impl` | Step 3「動作確認試験」 | 同上（Step2=リグレッション確認の後） |

各SKILLの当該Step「完了条件」に「試験書レビュー結果 = APPROVED」「試験実行は APPROVED 済み試験書に基づく」「エビデンス付きユーザー報告済み」を追加し、「状態判定」に「②が NEEDS_FIX の場合は試験書修正→再レビューへループ／②が APPROVED になるまで③に進まない」を追加する。既存の「動作確認結果NG→Step1/実装差し戻し」フローはそのまま維持する（レビューは試験書の質、動作確認NGは実装の問題、という役割の違いを保つ）。

### 3.6 論点（旧・verificationプロンプトの改修要否）—【更新】必須改修へ格上げ

> **本論点は REQ-C-004 追加により結論が変わった。** 旧版では「必須改修ではない（任意・推奨）」としていたが、REQ-C-004 の3工程分離により生成側プロンプトの工程分離が不可避となり、REQ-C-005 でエビデンス報告追加も必要となったため、**verificationプロンプト4本は必須改修（§2.2 C5〜C8）**となった。具体的な実現方式は §3.7（論点5）・§3.8（論点6）に示す。

### 3.7 論点5: 3工程分離（REQ-C-004）の実現方式 —【推奨】方式(a) 1プロンプト2セクション化

verificationプロンプトを3工程分離に対応させる方式は2案ある。

- **方式(a)〔推奨〕:** 既存の1プロンプトを「試験書作成」モード/セクションと「試験実行」モード/セクションの**2セクション構成に再編**し、SKILL側で工程を区切って**同一プロンプトを2回呼び分け**る（①で「試験書作成」セクションのみ、レビューPASS後の③で「試験実行」セクションのみを起動）。ファイル数は4本のまま。
- **方式(b):** プロンプトファイル自体を「試験書作成用」と「試験実行用」の**2ファイルに分割**する（変更対象が4本→8本に増える）。

**推奨は方式(a)。** 理由:

1. **ファイル数を増やさない（保守負荷・DRY）。** 方式(b)は4本→8本にファイルが倍増し、配布・整合対象が増える。同一WFの「試験書作成」と「試験実行」は同じ機能リスト・同じ試験書を前提に連続する工程であり、1ファイル内に置く方が文脈の一貫性を保ちやすく、共通の前提（対象機能・入力プレースホルダー）を重複記述せずに済む。
2. **既存構造からの改修が最小・非破壊的（OCP）。** 現行プロンプトは「動作確認方法（機能リスト作成→試験書作成）」「試験実行方法について」「結果の出力」の3ブロックから成る。方式(a)は、これを「試験書作成」セクション（＝機能リスト作成→試験書作成まで）と「試験実行」セクション（＝試験実行方法について＋結果の出力）に区切り直すだけで実現でき、既存記述を活かせる。ファイル分割のような大きな再編を伴わない。
3. **SKILL側の工程制御と自然に対応。** §3.3 の3工程（①作成→②レビュー→③実行）に対し、SKILLは①で「試験書作成」セクションを、③で「試験実行」セクションを起動する形になり、工程とセクションが1対1で対応する。レビューゲート（②）を工程間に自然に挿入できる。
4. **既存の呼び分けパターンと同型。** aide-powers には既に「同一の対象に対しモード/セクションを切り替えて起動する」パターン（fix モードを持つ設計フェーズスキル等）があり、方式(a)はその設計思想と一貫する。

**留意:** 方式(a)採用時、各SKILLの当該Stepは同一 verificationプロンプトを「作成モード」「実行モード」で2回起動する記述となる。セクション/モードの指定方法（プロンプト冒頭に実行モード指示を差し込む等）と、①→②→③の工程境界の明示は設計フェーズで具体化する。「試験実行方法について」セクションは③（試験実行）工程に属するものとして「試験書作成」セクションから切り離す。

### 3.8 論点6: エビデンス報告（REQ-C-005）の実現方式

REQ-C-005 のエビデンス報告は、影響が **2箇所** に及ぶ（impact-analysis §3.5 / 注意事項9 と整合）。両者の報告フォーマットを整合させ、「試験実行時に実施方法を記録 → SKILLがそれをユーザー報告へ反映」という流れを一気通貫にする。

1. **verificationプロンプト4本の「結果の出力」（C5〜C8）:** 試験実行工程（§3.7 の「試験実行」セクション）の「結果の出力」に、**各試験項目ごとに実施方法を記録・報告**させる記述を追加する。
   - **実動作確認** — 用いた手段（ブラウザ操作／APIコール／CLI実行 等）を判別可能に明示（AC-005-2）。
   - **コードレビュー代替** — 実動作確認を行わずコードレビューで代替した旨を明示し、実動作確認でない項目として区別できるようにする（AC-005-3）。現行の「実装確認OK/NG」表記を、この区別が判別できる形へ強化する。
2. **各WF SKILL の動作確認Step のユーザー報告部分（C1〜C4）:** 実装WF Step2「動作確認結果が全てOKの場合、ユーザーに実装内容と確認結果を報告し承認を得る」（bugfix Step10 / change Step12 / refactoring Step3 も同構造）の報告部分に、**「各試験項目の実施方法・エビデンス（実動作確認／コードレビュー代替の区別、実動作確認は用いた手段）を添えて報告する」旨を追加**する。あわせて、当該Stepの**完了条件に「エビデンスを欠いた『OK』のみの報告は不可（成立しない）」を明記**する（AC-005-1 / AC-005-4）。

**報告フォーマットの整合方針:** 試験実行工程が出力する「試験項目ごとの実施方法・エビデンス」を、SKILLがそのままユーザー報告に転記・要約できる形（試験項目単位で実動作確認／コードレビュー代替が並ぶ一覧）に揃える。具体的なフォーマット（項目・列・記載粒度）は設計フェーズで確定する。

## 4. リファクタリング検討結果

**判定: リファクタリング不要（パターンA・通常続行）。`refactoring-request.md` は作成しない。**

> **REQ-C-004 / REQ-C-005 追加後も判定は不変。** 要件追加により verificationプロンプト改修が必須化され、動作確認Stepが3工程に再構成されるが、これらはいずれも「新規追加＋既存構造の非破壊的拡張」の性質を保つ（既存Stepの削除・意味変更や既存アーキテクチャの再編を伴わない）。したがってリファクタリング不要の判定は維持する。

**根拠:**

1. **新規追加が主体（OCP準拠）。** 中核は新エージェント1体の追加であり、既存構造の内部改変を伴わない。変更に対して「新規追加で拡張」する形になっている。

2. **既存4スキルの改修は非破壊的な拡張。** 各SKILLの動作確認Stepへの「3工程への再構成（①作成→②レビュー→③実行）」「レビューループ挿入」「完了条件へのPASS・エビデンス報告追加」であり、既存Stepの削除・再編・意味変更は行わない。既存の動作確認NG差し戻しフローも維持する。3工程分離は既存の「試験書生成→試験実行」の順序を工程として明示化・ゲート挿入するものであり、処理内容自体を作り替えるものではない。

3. **verificationプロンプト4本の必須改修も非破壊的拡張。** 推奨方式(a)（§3.7）は既存の1プロンプトを「試験書作成」「試験実行」の2セクションへ区切り直す再編であり、ファイル分割や記述の作り替えを伴わない。既存の3ブロック（動作確認方法／試験実行方法について／結果の出力）を工程境界で仕切り、REQ-C-005 のエビデンス報告を「結果の出力」に追記する拡張に留まる。

4. **4スキルで同型のループ・工程記述が増える点について。** 4つの動作確認Stepに同型の3工程＋ループ記述が加わるが、これは「各WFが独立した進捗管理・状態判定・完了条件を持つ同型Step」という**既存のアーキテクチャそのもの**（4WFの動作確認Stepは現状すでにほぼ同型で各スキルに独立存在）に従うものである。レビューロジックの本体は新エージェントに集約されるため、各SKILL側の増加分は「エージェント呼び出し＋工程区切り＋判定分岐＋完了条件＋エビデンス報告」の薄い記述に留まる。この重複は既存構造と一貫しており、共通化（＝リファクタリング）を要するほどの重複負債ではない。むしろ各SKILLの独立性・可読性を保つ現行方針に沿う。

5. **既存機構への波及が限定的。** `test-coverage-audit-agent` 等の既存エージェントは変更せず、責務境界の明記（新エージェント定義側の記述）で重複を回避する。program-structure.md の「12→13」整合およびStep構成記述（3工程分離）の更新は構成記述の更新であってリファクタリングではない。

以上より、本変更は新規追加＋非破壊的拡張で完結し、REQ-C-004 / REQ-C-005 追加後も事前・事後のリファクタリングは要しない。
