## 変更1: The Iron Law

### before

```markdown
# The Iron Law

​```
1 タスク = 1 サブエージェント。1 ウェーブ最大 6 タスクを並列実行する。
実装・テスト・2レビューの全工程を通さないタスクを完了にしてはならない。
親タスクの全サブタスクが全工程 PASS になったら、親タスク完了チェックを通すまで親タスクを完了にしてはならない。
​```

- **1呼び出し = 1サブタスク**: 1つのサブエージェントに複数タスクを束ねて渡してはならない
- **並列実行**: 同一ウェーブ内の複数タスク（最大6）は、それぞれ別のサブエージェントに同時にアサインして並列実行する
- **工程順序厳守**: 実装 → テスト実装 → テスト実行 → 設計準拠レビュー → コード品質レビュー。各工程は前工程が PASS のタスクのみ進める（設計準拠レビュー・コード品質レビューは実装＋テストをまとめて検証する）
- **FAIL は前工程を fix で再実行**: レビュー FAIL のタスクは、micro-impl-agent の fix / fix_test モードで修正し、該当工程を PASS まで再実行する
- **親タスク完了チェック必須**: ある親タスクの全サブタスクが全工程 PASS になったら、その親タスクの設計参照セクション全体と実装ファイル群を design-review-agent に holistic 照合させ、設計項目の実装漏れ（サブタスク化されていなかった定義・メソッド等）がないことを確認してから親タスクを完了にする。漏れが見つかったら新規サブタスクとして追加して再実行する
```

### after

```markdown
# The Iron Law

​```
1 タスクの 1 工程 = 1 サブエージェント。1 ウェーブ最大 6 タスクを並列実行する（上限はタスク本数で数える）。
同一タスク内では「実装」と「テスト実装」を並列起動し、「設計準拠レビュー」と「コード品質レビュー」を並列起動する。
実装・テスト・2レビューの全工程を通さないタスクを完了にしてはならない。
親タスクの全サブタスクが全工程 PASS になったら、親タスク完了チェックを通すまで親タスクを完了にしてはならない。
手順を逸脱（省略・一括実行・簡易手順・不正確な実行）する場合は、実行前にユーザー承認と品質低下リスク説明を必須とする。
​```

- **1呼び出し = 1タスクの1工程**: 1つのサブエージェントに複数タスク、または同一タスクの複数工程を束ねて渡してはならない。タスク内工程の並列化により 1 タスクが複数のサブエージェントを同時に起動しうるが、束ね禁止の本意（1 サブエージェント＝独立した 1 作業単位）は維持する
- **タスク間並列実行（上限不変）**: 同一ウェーブ内の複数タスク（最大6）は、それぞれ別のサブエージェントに同時にアサインして並列実行する。**ウェーブの上限カウントはタスク本数（最大6）で数える。** タスク内で同時起動される工程サブエージェント数（実装＋テスト実装＝2、または 2 レビュー＝2）はこの 6 タスク上限のカウント対象外（別レイヤー）
- **タスク内工程の並列起動（新規）**: 同一タスク内の「実装（implement）」と「テスト実装（write_test）」は単純並列で同時起動する（テスト実装は設計書のテスト観点を起点に書けるため実装非依存）。「設計準拠レビュー（spec_review）」と「コード品質レビュー（quality_review）」は、対象タスクの実装・テスト実装・テスト実行が PASS した後に単純並列で同時起動する
- **工程依存の維持**: テスト実行（run_test）は実装とテスト実装の両方が PASS した後に実施する（並列対象外）。2 レビューはテスト実行 PASS の後に並列起動する。この前後依存（実装・テストが揃っていることが前提）は維持する
- **FAIL は前工程を fix で再実行**: レビュー FAIL のタスクは、指摘起因に応じて当該工程行（実装／テスト実装）を未PASS（`❌ failed`／`⬜ todo`）に戻し、micro-impl-agent の fix / fix_test モードで修正して PASS まで再実行する（詳細は「レビュー FAIL 時の再実行ルール（共通）」）
- **手順逸脱時の実行前承認＋リスク説明必須**: 確実な手順の省略・一括実行・簡易手順・不正確な実行を行う場合は、**実行前に**ユーザー承認を取得し、その際に品質低下リスク（不具合の混入・コードの設計書からの乖離）を必ず説明する。事後報告は不可。詳細は「手順逸脱時のユーザー承認とリスク説明」節（承認なしの手順逸脱を禁止する）
- **親タスク完了チェック必須**: ある親タスクの全サブタスクが全工程 PASS になったら、その親タスクの設計参照セクション全体と実装ファイル群を design-review-agent に holistic 照合させ、設計項目の実装漏れ（サブタスク化されていなかった定義・メソッド等）がないことを確認してから親タスクを完了にする。漏れが見つかったら新規サブタスクとして追加して再実行する
```

### 変更理由

- REQ-C-001/002: 「工程順序厳守＝実装→テスト実装→…の逐次」前提を、実装∥テスト実装の並列・2レビューの並列へ改める。一方、run_test の前後依存（実装・テストが揃ってから）と「2レビューはテスト実行PASS後」は維持する必要があるため、逐次を解く範囲と維持する範囲を明示的に区別した。
- 「1 タスク = 1 サブエージェント」は、タスク内工程の並列化により 1 タスクが複数サブエージェントを同時起動しうるため、「1 タスクの 1 工程 = 1 サブエージェント」へ趣旨を読み替える（束ね禁止の本意は維持）。
- AC-001-2: 「1ウェーブ最大6タスク」のタスク間並列上限は本変更の対象外であることを明記し、タスク内工程並列を別レイヤーとして峻別。上限カウント単位がタスク本数であることを明示し、工程サブエージェント数を上限カウント対象外とすることで両立させる。
- REQ-C-003/004: 最上位統制レイヤーである Iron Law に手順逸脱時の実行前承認＋リスク説明の条項を追加し、詳細節へ参照させる。

## 変更2: Overview（工程順序の記述）

### before

```markdown
タスクリスト・工程チェック表・doc-index.md・実装に必要な設計資料 を受け取り、タスクリストの全てのタスクについて、設計書に従って「実装 → テスト実装 → テスト実行 → 設計準拠レビュー → コード品質レビュー」を実行する。設計準拠レビューとコード品質レビューは、実装コードとテストコードをまとめて検証する（工程効率化）。また、タスクリスト・工程チェック表の各工程、各タスク完了と同時に動的に更新する。
```

### after

```markdown
タスクリスト・工程チェック表・doc-index.md・実装に必要な設計資料 を受け取り、タスクリストの全てのタスクについて、設計書に従って各工程を実行する。同一タスク内では「実装」と「テスト実装」を並列起動し、両者の PASS 後に「テスト実行」を実施し、テスト実行 PASS 後に「設計準拠レビュー」と「コード品質レビュー」を並列起動する。設計準拠レビューとコード品質レビューは、実装コードとテストコードをまとめて検証する（工程効率化）。工程チェック表は「1 工程 = 1 行」構造で管理し、各工程の担当サブエージェント本人が自分の工程行を 3 段階（開始 🔄 / 完了 ✅ / 失敗 ❌）で更新する。タスクリストはタスク完了と同時に更新する。
```

### 変更理由

- 工程フローの記述を逐次（→ で連結）から、並列起動を含むフロー（実装∥テスト実装 → テスト実行 → 設計準拠レビュー∥コード品質レビュー）へ更新（REQ-C-001/002）。
- 工程チェック表の更新方式が「1工程1行・担当本人3段階更新」に変わったため、Overview の「動的に更新する」記述を新方式に合わせて具体化（案A）。

## 変更3: Process（実行タスク編成・工程実行順序）

### before

```markdown
# Process

タスクリストを確認し、次の条件を満たす **実行タスク** の一覧(.aide/tmp/do_task_list-(重複排除用のpostfix).txt)を作成する:
   - タスクの状態が未完了（タスクリスト上で未完了）
   - かつ「依存先: なし」または「依存先のタスクが全て完了済み」

**実行タスク** の一覧について、工程チェック表のPASSしていない工程で、次に実行する工程を特定
タスクと工程のペアを最大6つ形成し、それぞれ毎で以下のサブエージェントを使って工程を実行する
※同一タスク内での工程実行順序(実装 → テスト実装 → テスト実行 → 設計準拠レビュー → コード品質レビュー)
全てのサブエージェントの実行が完了すれば**実行タスク** の一覧を削除する

タスク内の全ての工程がPASSとなったら、タスクリスト内の該当タスク（サブタスク）の進捗チェック欄を更新する

ある親タスクに属する**全サブタスクが全工程 PASS** になったら、その親タスクについて「親タスク完了チェック」工程を実行する（後述）。漏れが検出されたら不足分を新規サブタスクとして追加し、次ウェーブで通常通り処理する。漏れなしなら親タスクを完了としてマークする。

全ての工程がPASSとなるまで繰り返す。
レビュー工程でFAILとなった場合、FAILを出したサブエージェントの指摘に従って、実装やテスト工程をFAILに設定し再実行対象とする。

実行可能タスクが無くなったら（未完了タスクが残っていない）、全タスクの処理結果とともに status: DONE を返して終了する。未完了タスクが残っているが依存先未完了で着手できず進行中もない場合は、デッドロックとして status: BLOCKED で理由とともに報告する。

## 各工程のサブエージェント実行

タスクと工程のペアごとに **1ペア = 1サブエージェント** をアサインする（最大6ペアを同時に起動して並列実行）。各サブエージェントには下記「エージェント呼び出しペイロード」の項目を渡し、**実行後に当該タスクの工程チェック表セルを当該エージェント自身に更新させる**（自タスク行のみ最小編集）。

工程の実行順序は工程チェック表の工程（列）の並び順に従う。各タスクについて「PASSしていない最初の工程」を次に実行する工程として選ぶ。
```

### after

```markdown
# Process

タスクリストを確認し、次の条件を満たす **実行可能タスク** の一覧(.aide/tmp/do_task_list-(重複排除用のpostfix).txt)を作成する:
   - タスクの状態が未完了（タスクリスト上で未完了）
   - かつ「依存先: なし」または「依存先のタスクが全て完了済み」（タスク間依存原則は不変）

**実行可能タスク** の各々について、工程チェック表（1 工程 = 1 行）から、状態が `⬜ todo` かつ前提工程が全て `✅ done` の工程行（＝今すぐ実行可能な工程）を特定する。工程の前提は次のとおり:
   - 実装（implement） / テスト実装（write_test）: 前提なし。**同一タスク内で同時に並列起動できる**
   - テスト実行（run_test）: 実装・テスト実装の両方が `✅ done`（並列対象外）
   - 設計準拠レビュー（spec_review） / コード品質レビュー（quality_review）: テスト実行が `✅ done`。**両者は同時に並列起動できる**

実行可能な「タスク × 工程」のペアを集め、**タスク本数で最大 6 タスク**になるよう選ぶ（タスク内で同時起動される工程サブエージェント数は 6 の上限カウントに含めない）。各ペアごとに 1 サブエージェントをアサインして同時に起動する。例として、依存先のない非依存タスク A／B の起動初期には、実装A・テスト実装A・実装B・テスト実装B の 4 サブエージェントを同時起動できる（タスク本数は 2 で上限内）。
全てのサブエージェントの実行が完了すれば**実行可能タスク** の一覧を削除し、再評価する。

タスク内の全ての工程行が `✅ done`（または `➖ skip`）となったら、タスクリスト内の該当タスク（サブタスク）の進捗チェック欄を更新する

ある親タスクに属する**全サブタスクが全工程 PASS** になったら、その親タスクについて「親タスク完了チェック」工程を実行する（後述）。漏れが検出されたら不足分を新規サブタスクとして追加し（工程チェック表にも該当タスクの工程行を追加し）、次ウェーブで通常通り処理する。漏れなしなら親タスクを完了としてマークする。

全ての工程行が PASS となるまで繰り返す。
レビュー工程で FAIL となった場合、FAIL を出したサブエージェントの指摘起因（実装／テスト実装）に従って、該当する工程行を未PASS（`⬜ todo`）に戻して再実行対象とする（「レビュー FAIL 時の再実行ルール（共通）」を参照）。

実行可能タスクが無くなったら（未完了タスクが残っていない）、全タスクの処理結果とともに status: DONE を返して終了する。未完了タスクが残っているが依存先未完了で着手できず進行中もない場合は、デッドロックとして status: BLOCKED で理由とともに報告する。

## 各工程のサブエージェント実行

「タスク × 工程」のペアごとに **1ペア = 1サブエージェント** をアサインする（タスク本数で最大 6 タスク。タスク内工程の同時起動は上限カウント対象外）。各サブエージェントには下記「エージェント呼び出しペイロード」の項目を渡し、**実行後（および開始直後）に当該工程の工程チェック表の行を当該エージェント自身に更新させる**（自分が担当した工程の行のみ最小編集。CF-5 の 3 段階更新）。

工程の実行順序は工程チェック表の**工程行の前提依存**に従う（上記の前提一覧）。各タスクについて「状態が `⬜ todo` かつ前提工程が全て `✅ done` の工程行」を実行可能な工程として全て選ぶ（同一タスク内に複数あれば並列起動する）。
```

### 変更理由

- 「工程の実行順序は工程チェック表の工程（列）の並び順に従う」「PASSしていない最初の工程を選ぶ」という**列前提・逐次前提**の記述を、1工程1行構造での「前提工程が全て done の工程行を全て選ぶ」へ読み替え（案A ＋ REQ-C-001/002）。
- 実装∥テスト実装、2レビュー並列という並列起動を Process フローに明記。run_test と 2レビューの前後依存（並列対象外／テスト実行PASS後）を保持。
- AC-001-2: 6 タスク上限がタスク本数で数えること、タスク内工程サブエージェント数を上限カウント対象外とすることを Process にも明記して両立を担保。
- 「自タスク行のみ最小編集」→「自分が担当した工程の行のみ最小編集（3段階更新）」へ。親タスク完了チェックの漏れ追加時に「工程チェック表にも工程行を追加」と行構造へ整合。

## 変更5: レビュー FAIL 時の再実行ルール（共通）

### before

```markdown
### レビュー FAIL 時の再実行ルール（共通）
- レビュー工程（設計準拠レビュー / コード品質レビュー）が FAIL になったら、FAIL を出したサブエージェントの指摘に従い、**実装またはテスト実装工程の工程チェック表セルを FAIL（未PASS）に戻す**。これにより当該タスクは次ウェーブで実装/テスト実装工程から再実行され、その後レビュー工程も再実行される
- 実装の修正自体は `micro-impl-agent`（mode: fix / fix_test）で行い、レビュー指摘内容をそのまま転記して渡す
```

### after

```markdown
### レビュー FAIL 時の再実行ルール（共通）

レビュー工程（設計準拠レビュー / コード品質レビュー）が FAIL になったら、FAIL を出したサブエージェントの指摘の**起因**に応じて、差し戻す工程行を一意に決め、未PASS（`⬜ todo`）に戻す。各工程が独立した行（1 工程 1 行）で状態管理されるため、差し戻し（状態変更）も工程行単位で衝突なく行える。

**単独レビュー FAIL の場合:**
- 実装起因の指摘 → `implement` 工程行を `⬜ todo` に戻す
- テスト（テスト実装）起因の指摘 → `write_test` 工程行を `⬜ todo` に戻す

**両レビューが同時に FAIL した場合（AC-002-3）:**
- 両レビューの指摘が**同一工程**を指す（例: 双方とも実装起因）→ 当該工程行を **1 回だけ** `⬜ todo` に戻し、両レビューの指摘を**統合して** fix（micro-impl-agent の fix / fix_test）で対応する
- 実装起因とテスト起因が**混在**する → `implement` 工程行と `write_test` 工程行の**両方**を `⬜ todo` に戻す

**再実行の連鎖:**
- 差し戻した `implement` / `write_test` を次ウェーブで再実行（micro-impl-agent の fix / fix_test。本人が工程行を 🔄 → ✅ に更新）したら、実装・テストが変わったため `run_test` 工程行も `⬜ todo` に戻して再実行し、その PASS 後に `spec_review` / `quality_review` 工程行を `⬜ todo` に戻して**両レビューを再度（並列で）実行**する
- これにより並列化後も「FAIL 工程を未PASSに戻して再実行する」原則が一貫して成立し、FAIL 時の扱いが曖昧化しない
- 実装の修正自体は `micro-impl-agent`（mode: fix / fix_test）で行い、レビュー指摘内容をそのまま転記して渡す

> 差し戻し（工程行を `⬜ todo` へ戻す）の操作は、再実行スケジューリングとして起動元が行ってよい（実施していない工程を `✅ done` にする代理チェック禁止には抵触しない — done を偽る行為ではなく未完了へ戻す行為のため）。再実行後の 🔄 / ✅ / ❌ は必ず担当本人が書く。
```

### 変更理由

- AC-002-3: 並列レビューでは 2 つの FAIL が同時に返りうるため、差し戻し先の決定規則（実装起因→実装行、テスト起因→テスト実装行、同一工程は統合 fix、混在は両行差し戻し）を明文化し、再実行対象が曖昧にならないようにする。
- 案A: 「セルを FAIL（未PASS）に戻す」を行状態遷移「工程行を `⬜ todo` に戻す」へ統一（CF-6）。1工程1行のため差し戻しが工程行単位で衝突なく行える点を明記。
- 再実行後に run_test → 2レビューの順で再評価する連鎖を明記し、実装・テスト変更後にテスト実行と両レビューが必ず再実行される前後依存を保証。
- 差し戻し操作の主体（起動元のスケジューリング行為）が代理チェック禁止に抵触しないことを補足し、approach.md の「本人が証跡を書く」原則と矛盾しないことを担保。

### after（新規追加する節の全文）

```markdown
## 手順逸脱時のユーザー承認とリスク説明

本スキルの定められた手順（工程順序・並列起動の前提・レビュー・工程チェック表更新・親タスク完了チェック等）を逸脱する場合は、**実行前に**ユーザー承認を取得し、その際に品質低下リスクを必ず説明しなければならない。

### 手順逸脱の定義

次のいずれかを「手順逸脱」とする:
- 確実な手順の**省略**（例: テスト実行・レビュー・親タスク完了チェックを飛ばす）
- 複数工程・複数タスクの**一括実行**（束ね）による簡略化
- 定義された手順と異なる**簡易手順**での実行
- その他、本スキルを**正確に実行しない**こと

### 実行前ユーザー承認の必須化（REQ-C-003 / AC-003-1・AC-003-2・AC-003-3）

- 手順逸脱を行う場合は、**逸脱した手順を実行する前に**ユーザーの承認を取得すること。承認は番号付き選択肢で諾否を問う形で求める
- **事後報告は不可。** 「逸脱して実行した後で報告する」ことは禁止する
- ユーザー承認なしの手順逸脱を禁止する

### 品質低下リスク説明の必須化（REQ-C-004 / AC-004-1・AC-004-2・AC-004-3）

- 上記の承認を求める際は、**品質低下リスクを必ず説明**したうえで承認を求めること
- 説明すべきリスクには、少なくとも次を具体的に含める:
  - **不具合の混入**（手順簡略化により欠陥が検出されないまま残るおそれ）
  - **コードの設計書からの乖離**（レビュー省略等により実装が設計書と食い違うおそれ）
- **リスク説明と承認取得は一体の必須手順である。** リスク説明を伴わない承認取得は無効とする
```

### 変更理由

- REQ-C-003 / REQ-C-004 を 1 箇所に集約して明文化することで、Iron Law・Red Flags からの参照先を一元化し、重複なく最上位統制として機能させる（approach.md の配置方針）。
- 手順逸脱の定義（省略・一括実行・簡易手順・不正確な実行）、実行前承認（事後報告不可）、リスク説明（不具合の混入・コードの設計書からの乖離）とのセット必須化を、各受入基準（AC-003-1〜3 / AC-004-1〜3）に対応する形で網羅的に記述。
