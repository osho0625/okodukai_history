# 変更要求定義

## 変更概要

### 変更の目的・背景
`coding-test-2review` スキルは、タスクリストの各タスクについて「実装 → テスト実装 → テスト実行 → 設計準拠レビュー → コード品質レビュー」を実行する実装ループスキルである。現状の SKILL.md では、同一タスク内の工程は上記順序で逐次実行することが厳守されており、特に以下2点に改善余地がある。

- **性能面**: 同一タスク内で「実装」と「テスト実装」、および「設計準拠レビュー」と「コード品質レビュー」が逐次実行されている。これらを並列で実行することで、所要時間を短縮できる。
- **品質ガード面**: 確実な手順を省略して一括実行したり、簡易手順・不正確な手順でスキルを実行した場合に、ユーザー承認やリスク説明を必須とする明文化されたルール（Iron Law / Red Flag）が存在しない。手順逸脱が無検出・無承認で行われると、不具合の混入やコードの設計書からの乖離といった品質低下を招く。

本変更は、上記2系統（(1) 並列実行化による性能改善、(2) 手順逸脱時のユーザー承認・リスク説明の必須化による品質ガード）を、同一スキル `coding-test-2review` への変更としてまとめて対応する。

### 変更種別
- 既存スキル仕様の変更（`skills/coding-test-2review/SKILL.md` および関連プロンプトの記述変更）
- 機能改善（性能改善）＋ 品質ガード（プロセス統制の強化）

## 要求事項

### REQ-C-001: 実装工程とテスト実装工程の並列実行化
- 種別: 性能改善 / プロセス変更
- 説明: 同一タスク内で逐次実行されている「実装」工程と「テスト実装」工程を、並列で実行できるようにする。現状は「実装 → テスト実装」と逐次化されているが、これを並列起動に変更し、所要時間を短縮する。テスト実装の実装への依存を理由に逐次化したり、並列化可否を設計工程に先送りしたりはしない。
- 受入基準:
  - AC-001-1: SKILL.md に、同一タスク内の「実装」工程と「テスト実装」工程を並列で起動する旨の記述が存在すること（検証: 該当記述の有無を SKILL.md 上で確認できる）。
  - AC-001-2: 実装とテスト実装の並列化に関する記述が、既存のタスク間並列原則（1 ウェーブ最大 6 タスク）と矛盾しないこと（両立して読めること）。
- 優先度: Must

### REQ-C-002: 2種類のレビュー工程（設計準拠レビュー / コード品質レビュー）の並列実行化
- 種別: 性能改善 / プロセス変更
- 説明: 現状逐次実行されている「設計準拠レビュー（design-review）」と「コード品質レビュー（code-review）」について、両者が実装＋テストの揃った後に互いに独立して実行可能であることを前提に、並列起動できるようにする。
- 受入基準:
  - AC-002-1: SKILL.md に、設計準拠レビューとコード品質レビューを並列起動できる旨の記述が存在すること。
  - AC-002-2: 並列レビューの前提条件（対象タスクの実装・テストが揃っていること）が明記されていること。
  - AC-002-3: いずれかのレビューが FAIL した場合の再実行ルール（該当工程を未PASSに戻し再実行する）が、並列化後も矛盾なく成立すること（並列化により FAIL 時の扱いが曖昧化していないこと）。
- 優先度: Must

### REQ-C-003: 手順逸脱時のユーザー承認の必須化
- 種別: 品質ガード / プロセス統制
- 説明: `coding-test-2review` の確実な手順を省略して一括実行する、別の簡易手順で実行する、その他スキルを正確に実行しないといった「手順逸脱」を行う場合は、実行前にユーザーの承認を取ることを必須とする。承認なしの手順逸脱を禁止する旨を、SKILL の Iron Law / Red Flag に明文化する。
- 受入基準:
  - AC-003-1: SKILL.md に、手順の省略・一括実行・簡易手順・不正確な実行を行う場合は「実行前」にユーザー承認を取得することを必須とする記述が存在すること。
  - AC-003-2: 承認なしに手順逸脱を行うことを禁止する旨が、Iron Law または Red Flags（STOP 項目）として明記されていること。
  - AC-003-3: 「実行前」承認であること（事後報告では不可であること）が読み取れること。
- 優先度: Must

### REQ-C-004: 手順逸脱時の品質低下リスク説明の必須化
- 種別: 品質ガード / プロセス統制
- 説明: REQ-C-003 のユーザー承認を求める際には、「手順変更により、不具合の混入・コードの設計書からの乖離などの品質低下リスクがある」旨を必ず説明したうえで承認を求めることを必須とする。リスク説明なしの承認取得を禁止する。
- 受入基準:
  - AC-004-1: SKILL.md に、手順逸脱の承認を求める際は品質低下リスクを必ず説明する旨の記述が存在すること。
  - AC-004-2: 説明すべきリスクとして「不具合の混入」「コードの設計書からの乖離」が具体的に明記されていること。
  - AC-004-3: リスク説明と承認取得が一体の必須手順（リスク説明を伴わない承認取得は不可）として記述されていること。
- 優先度: Must

## 対象外（スコープ外）

本変更要求では、以下は扱わない（別工程・別ワークフローで実施する）。

- 影響範囲の分析（変更が SKILL.md 以外のどのファイル・プロンプト・呼び出し元スキルに波及するかの特定）
- 対応方針の策定（どの記述をどこに追記・修正するかの具体的な設計）
- before→after 形式の具体的なコード／文面変更設計
- 並列化の実現方式（サブエージェントの同時起動方法、ウェーブ編成アルゴリズム等の技術的実現手段）の詳細検討
- 関連プロンプト（`implementer-prompt.md` / `spec-reviewer-prompt.md` / `code-quality-reviewer-prompt.md`）の具体的な改修内容
- 1ウェーブ最大6タスクという既存のタスク間並列上限の変更（本変更はタスク内工程の並列化が対象であり、タスク間並列の仕様変更は要求に含まない）

## 前提条件

- 本プロジェクトは aide-powers フレームワーク自体のメタ開発であり、通常アプリ型の設計書（doc-index.md / user-requirements.md / program-structure.md）は存在しない（dev-environment.md §14 確定判断）。変更対象の設計根拠は対象スキルの `skills/coding-test-2review/SKILL.md` が兼ねる。
- 現状の SKILL.md では、同一タスク内の工程順序は「実装 → テスト実装 → テスト実行 → 設計準拠レビュー → コード品質レビュー」と定義され、各工程は前工程が PASS のタスクのみ進める逐次実行である。
- 現状でもタスク間（同一ウェーブ最大6タスク）の並列実行は既に行われている。本変更が新たに対象とするのは「同一タスク内の工程」の並列化である。
- 設計準拠レビューとコード品質レビューは、いずれも実装＋テストが揃った後に独立して実行できるため、(1b) の並列化対象になりうる。
- 要求(2)（REQ-C-003 / REQ-C-004）は、スキル本体の Iron Law / Red Flag への明文化が主眼であり、検証は SKILL.md 上の記述の有無で行える。

## 関連する既存要件

- 既存 Iron Law「1 タスク = 1 サブエージェント。1 ウェーブ最大 6 タスクを並列実行する」: REQ-C-001 / REQ-C-002 の工程内並列化は、この既存のタスク間並列原則と矛盾しない形で追加する必要がある（AC-001-2 で担保）。
- 既存の「工程順序厳守」原則および「依存先が全完了したタスクのみ実行可能」原則: REQ-C-001 の実装・テスト実装の並列化は、タスク間の依存関係厳守（依存先が全完了したタスクのみ実行可能）とは別レイヤーの「同一タスク内工程の並列化」であり、タスク間の依存関係原則には影響しない。
- 既存の「レビュー FAIL 時の再実行ルール（共通）」: REQ-C-002 のレビュー並列化後も、FAIL 工程を未PASSに戻して再実行するルールが成立し続ける必要がある（AC-002-3 で担保）。
- 既存の Red Flags（STOP 項目）群: REQ-C-003 / REQ-C-004 は、この Red Flags / Iron Law に「手順逸脱時の実行前ユーザー承認＋品質低下リスク説明の必須化」を追加する形で整合させる。
- 既存の「作業中の他ワークフロー起動禁止」「設計書なしの実装禁止」等のフェーズスキル共通ルール: 本変更はこれらに抵触しない。
