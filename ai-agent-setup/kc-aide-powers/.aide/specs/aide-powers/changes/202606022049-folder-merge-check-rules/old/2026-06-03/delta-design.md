# 差分設計書

## 設計方針

本変更は `skills/folder-merge-check/SKILL.md` への追記・更新で完結する。Step 4 移動ルール b は既存の追記挙動を削除せず、(a) 恒久的設計資産の追記・更新ルートとして保持したまま、判定分岐構造へ拡張する（既存挙動は (a) ルートに包含して維持する）。

変更は以下の3箇所:
1. **Red Flags テーブル末尾に1行追加**（REQ-C-001）: WF種別差を理由とした統合拒否を STOP 対象に追加
2. **Step 4 移動ルール b を判定分岐構造に拡張**（REQ-C-002/003）: 同名衝突時に「まず判定基準で (a)/(b) を分類 → (a) 恒久的設計資産=追記・更新（既存ルール b の挙動を (a) ルートとして保持） / (b) その時用の設計資料・進捗ファイル=old/{日付}/退避」へ対等に分岐する構造に整理
3. **完了条件 #2 の文言を判定分岐構造に整合**（FAIL-1）: 「同名ファイルの衝突が追記ルールに従って解決されている」を、(a) 追記・更新 / (b) old/{日付}/ 退避 の2分類に従って解決されている、へ更新

既存フォーマット（テーブル構造、移動ルールのリスト形式、文体）をそのまま踏襲する。

## 変更箇所 2: Step 4 移動ルール（REQ-C-002 / REQ-C-003）

### before

```markdown
**Step 4:** ファイル移動の実行
- `current_dir` 内の全ファイルを `origin_folder_path` に移動する
- 移動ルール:
  - a. 移動先に同名ファイルが存在しない場合: そのまま移動する
  - b. 移動先に同名ファイルが存在する場合:
    - 既存ファイルの末尾に以下のヘッダを付けて追記する:
      ```
      ---
      ## 追記（{YYYY-MM-DD}）
      ```
    - 移動元ファイルの全内容を追記する
    - 移動元ファイルを削除する
  - c. 全ファイルの移動が完了したら: 空になった `current_dir` を削除する
```

### after

```markdown
**Step 4:** ファイル移動の実行
- `current_dir` 内の全ファイルを `origin_folder_path` に移動する
- 移動ルール:
  - a. 移動先に同名ファイルが存在しない場合: そのまま移動する
  - b. 移動先に同名ファイルが存在する場合: まず以下の判定基準でファイルを (a) / (b) に分類し、分岐する
    - **判定基準（分岐の前に必ず分類すること）:**
      同名ファイルの扱いは、ファイルの性質に対する以下の判定基準で「恒久的か / その時用か」を判断する。ファイル名が下記の対象例に載っていない未知のファイルに遭遇した場合も、この判定基準に従って分類すること。
      - **(a) 恒久的設計資産**: 元のユーザー要求に関する資料や、データ構造など、**プロジェクトの最新の設計情報を表すもの**。常に最新状態が正であり、WF完了後も参照され続ける。
        - 対象例: `user-requirements.md` / `system-requirements.md` / `object-design-*.md` / `history.md` 等
      - **(b) その時用の設計資料・進捗ファイル**: 差分設計や進捗ファイルなど、**そのWF（ワークフロー）が終わると履歴としてしか価値がないもの**。WF完了後はスナップショットとして固定され、最新の設計情報を表すものではない。
        - 対象例: `delta-design.md` / `change-requirements.md` / `impact-analysis.md` / `approach.md` / `delta-task-list.md` / `impl-process-checklist.md` / `change-progress.md` / `bugfix-progress.md` / `refactoring-progress.md` 等
    - **(a) 恒久的設計資産と判定した場合 → 追記・更新ルート:**
      - 既存ファイルの末尾に以下のヘッダを付けて追記する:
        ```
        ---
        ## 追記（{YYYY-MM-DD}）
        ```
      - 移動元ファイルの全内容を追記する
      - 移動元ファイルを削除する
    - **(b) その時用の設計資料・進捗ファイルと判定した場合 → `old/{日付}/` 退避ルート:**
      - 統合先フォルダ配下に `old/{日付}/` サブフォルダを作成する（既に存在する場合はそのまま使用する）
      - `{日付}` は、退避対象に関連する `history.md` に記載されている日付を用いる（例: `old/2025-05-27/`）
      - 統合先の既存ファイル（旧WFの成果物）を `old/{日付}/` へ退避する
      - 今回WFの成果物を正規名で配置する（移動元ファイルをそのまま移動する）
      - `old/{日付}/` に退避したファイルは履歴保全目的で保持し、以降のフェーズ（タスク計画・doc-sync・design-sync 等）の入力対象から除外する（読み込み対象は正規名ファイルのみ）
    - **(a) / (b) のどちらにも明確に該当しない同名ファイルの場合 → (a) 追記・更新ルートを従来通り適用する**
    - **注意事項:**
      - 本ルールは全WF種別（変更 / バグ修正 / リファクタリング）に共通して適用する
      - 旧方式（`~1` / `~2` 等のサフィックスを付けてリネームする方式）は採用しない
  - c. 全ファイルの移動が完了したら: 空になった `current_dir` を削除する
```

### 変更理由

PI-016（進捗ファイルの同名衝突）および PI-027（その時用の設計資料の同名上書き事故）を解消するため、同名衝突時の移動ルールを「判定分岐構造」に拡張する。

現行 SKILL.md の移動ルールは a / b / c の3つのみで、b は「同名ファイルが存在する場合は末尾に単純追記する」挙動だけを定義している（old/{日付}/ 退避のような分岐は存在しない）。この単純追記のみの挙動では、WF完了後はスナップショットとして固定されるべき「その時用の設計資料・進捗ファイル」まで、完全に異なるWFの成果物が追記で混合されてしまい、可読性の低下と上書き事故（PI-027）を招いていた。

これを解消するため、同名衝突時は **まず判定基準で (a) / (b) を分類し、両ルートへ対等に分岐する** 構造に拡張する。判定は対象ファイルの**性質に対する判定基準**で行う。ファイル名リストはあくまで判定基準を補足する「例」であり、リストに載っていない未知のファイルでも判定基準に従って分類できるようにしている。

- **(a) 恒久的設計資産 → 追記・更新ルート**: 元のユーザー要求に関する資料やデータ構造など、プロジェクトの最新の設計情報を表すもの。常に最新状態が正であり、WF完了後も参照され続ける（例: `user-requirements.md` / `object-design-*.md` 等）。末尾に `## 追記（YYYY-MM-DD）` ヘッダを付けて追記・更新する（現行ルール b の単純追記挙動をこのルートとして保持）。仕様は追記で内容が蓄積されても可読性を維持できる。
- **(b) その時用の設計資料・進捗ファイル → `old/{日付}/` 退避ルート**: 差分設計や進捗ファイルなど、そのWFが終わると履歴としてしか価値がないもの。WF完了後はスナップショットとして固定される（例: `delta-design.md` / `change-requirements.md` / `change-progress.md` 等）。完全に異なるWFの成果物を追記で混合すると可読性が著しく低下し上書き事故が発生するため、`old/{日付}/` 退避で世代管理する。
- **どちらにも明確に該当しない同名ファイル**: (a) 追記・更新ルートを従来通り適用する（安全側のデフォルト）。

現行ルール b の単純追記挙動は (a) 恒久的設計資産の追記・更新ルートとして保持される（削除・改変はせず、判定分岐構造へ拡張する）。判定を分岐の先頭に置くことで、`old/{日付}/` 退避ルートが追記ルートと対等に提示され、埋もれることがなくなる。

## 変更箇所 3: 完了条件 #2（FAIL-1）

### before

```markdown
**統合した場合:**
1. current_dir 内の全ファイルが origin_folder_path に移動されている
2. 同名ファイルの衝突が追記ルールに従って解決されている
3. 空になった current_dir が削除されている
4. origin_folder_path 内の history.md が更新されている（※バグ修正WFを除く。バグ修正WFではフェーズ6完了時に doc-sync (aide-powers skill) が追記する）
5. 呼び出し元に統合結果（merged=true, result_dir=origin_folder_path）が返却されている
```

### after

```markdown
**統合した場合:**
1. current_dir 内の全ファイルが origin_folder_path に移動されている
2. 同名ファイルの衝突が移動ルール b の判定分岐＝(a) 恒久的設計資産→追記・更新／(b) その時用の設計資料・進捗ファイル→`old/{日付}/` 退避 に従って解決されている
3. 空になった current_dir が削除されている
4. origin_folder_path 内の history.md が更新されている（※バグ修正WFを除く。バグ修正WFではフェーズ6完了時に doc-sync (aide-powers skill) が追記する）
5. 呼び出し元に統合結果（merged=true, result_dir=origin_folder_path）が返却されている
```

### 変更理由

現行 SKILL.md の完了条件 #2「同名ファイルの衝突が追記ルールに従って解決されている」は、移動ルール b が「単純追記のみ」だった前提の文言である。本変更で移動ルール b を判定分岐構造（(a) 追記・更新 / (b) `old/{日付}/` 退避）に拡張すると、(b) のファイルは追記ではなく退避で解決されるため、「追記ルールに従って」という文言ではこの解決ケースを包含できず、改修後 SKILL.md 内で矛盾する。完了条件 #2 を2分類の判定分岐に整合する文言へ更新し、(a)/(b) いずれのルートで解決されたケースも完了条件が正しく包含するようにする。
