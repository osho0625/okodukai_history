# 変更要求定義

## 変更概要

- **変更の目的・背景**: `folder-merge-check` スキルの運用中に、フォルダ統合判定に関する3つの問題が顕在化した。
  1. **WF種別の違いによる誤った統合拒否（PI-015）**: AI Agent が「起因元フォルダが `changes/` で今回は `bugfix/` だからWF種別が異なり統合できない」と誤判断した。`folder-merge-check` の目的は「同じコード変更に起因するドキュメントを1箇所に集約してトレーサビリティを確保する」ことであり、WF種別やディレクトリ階層の違いは統合を阻む条件ではない。
  2. **進捗ファイル名の衝突（PI-016）**: 異なるWF種別のフォルダへ統合する場合（例: bugfix→changes, refactoring→changes, change→bugfix 等）、進捗ファイル名が衝突する可能性があるが、衝突回避ルールが定義されていない。
  3. **進捗ファイル以外の成果物の同名上書き（PI-027）**: バグ修正WFを起因元フォルダへ統合した際、統合元に既存していた変更WFの完了済み成果物（`delta-task-list.md` / `impl-process-checklist.md` 等）が同名で上書きされた。その時用の設計資料・進捗ファイルともに、統合時の同名衝突を回避するための統一されたルールが定義されていないため発生した。

  上記3点を解消するため、`skills/folder-merge-check/SKILL.md` に必要な記述を追加する。これにより、フォルダ統合時のドキュメント散逸・成果物の意図しない上書きを防ぎ、トレーサビリティを確保する。

  なお、統合時のファイル扱いは以下の2分類で統一する（PI-016 / PI-027 を整合的に解消するための基本方針）。
  - **(a) 仕様・全体設計に関する恒久的設計資産**（`user-requirements.md` / `system-requirements.md` / `object-design-*.md` 等）: 統合先の既存ファイルへ**追記・更新**で対応する（既存の移動ルール b に準ずる）。
  - **(b) その時用の設計資料 + 進捗ファイル**（`delta-design.md` / `change-requirements.md` / `impact-analysis.md` / `approach.md` 等の差分設計資料、および `change-progress.md` / `bugfix-progress.md` / `refactoring-progress.md` 等の進捗ファイル）: 統合先フォルダ配下の `old/{日付}/` サブフォルダへ**退避**する。退避先の `{日付}` は、退避対象に関連する `history.md` に記載されている日付を用いる。

- **変更種別**: 変更（ルール追加）

## 要求事項

### REQ-C-001: WF種別の違いは統合拒否の理由にならないことを Red Flags に明記（PI-015）

- **種別**: 変更（ルール追加）
- **説明**: `skills/folder-merge-check/SKILL.md` の Red Flags テーブルに、「起因元フォルダのWF種別（`changes/` / `bugfix/` / `refactoring/`）が今回のWF種別と異なることを理由に統合を拒否する」という誤った思考パターンを STOP 対象として追加する。`folder-merge-check` の目的は同じコード変更に起因するドキュメントを1箇所に集約してトレーサビリティを確保することであり、WF種別やディレクトリ階層の違いは統合を阻む条件ではないことを、その根拠として明記する。
- **受入基準**:
  - AC-001-1: Red Flags テーブルに、「起因元フォルダが `changes/` で今回は `bugfix/` だからWF種別が異なり統合できない（→ STOP）」に相当する Red Flag 行が新たに1行以上追加されている。
  - AC-001-2: 追加された行の「なぜ危険か」列に、(a)`folder-merge-check` の目的は同じコード変更に起因するドキュメントを1箇所に集約してトレーサビリティを確保することである旨、(b)WF種別やディレクトリ階層の違いは統合を阻む条件ではない旨、の両方が記載されている。
  - AC-001-3: 既存の Red Flags 行（6行）が削除・改変されていない（追加のみ）。
- **優先度**: 必須

### REQ-C-002: 統合時の進捗ファイル衝突回避ルール（全WF共通）を統合手順に追加（PI-016）

- **種別**: 変更（ルール追加）
- **説明**: `skills/folder-merge-check/SKILL.md` の統合手順（ファイル移動を扱う箇所）に、全WF種別に共通するルールとして、進捗ファイルの衝突回避運用を追加する。進捗ファイル（`change-progress.md` / `bugfix-progress.md` / `refactoring-progress.md` 等）は「その時用のファイル」に分類され、統合先フォルダ配下の `old/{日付}/` サブフォルダへ退避することで衝突を回避する。`{日付}` は退避対象の進捗ファイルに関連する `history.md` に記載されている日付を用いる。これにより、進捗ファイルとその他のその時用設計資料を同一の退避ルールで統一的に扱う（REQ-C-003 と整合）。
- **受入基準**:
  - AC-002-1: 統合手順（Step 4 のファイル移動ルール、またはそれに準ずる箇所）に、進捗ファイルの衝突回避ルールが記載されている。
  - AC-002-2: 進捗ファイル（`bugfix-progress.md` / `change-progress.md` / `refactoring-progress.md` 等）が「その時用のファイル」として old/ 退避の対象に含まれる旨が明記されている。
  - AC-002-3: 進捗ファイルの退避先が、統合先フォルダ配下の `old/{日付}/` サブフォルダである旨が明記されている。
  - AC-002-4: 退避先サブフォルダ名に用いる `{日付}` は、退避対象の進捗ファイルに関連する `history.md` に記載されている日付を用いる旨が明記されている。
  - AC-002-5: 旧方式（`~1` / `~2` 等のサフィックスを付けてリネームする方式）を採用しないこと、当該ルールが全WF種別に共通して適用されることが明示されている。
- **優先度**: 必須

### REQ-C-003: その時用の設計資料の同名衝突時の old/{日付}/ 退避ルールを統合手順に追加（PI-027）

- **種別**: 変更（ルール追加）
- **説明**: `skills/folder-merge-check/SKILL.md` の統合手順に、全WF種別に共通するルールとして、その時用の設計資料の同名衝突を回避するための old/{日付}/ 退避ルールを追加する。統合時のファイル扱いを「(a) 仕様・全体設計に関する恒久的設計資産 → 追記・更新」「(b) その時用の設計資料 + 進捗ファイル → old/{日付}/ 退避」の2分類で整理し、その時用の設計資料（`delta-design.md` / `change-requirements.md` / `impact-analysis.md` / `approach.md` 等）と進捗ファイル（REQ-C-002）が同一の退避ルールに従うことを整合的に記載する。
- **受入基準**:
  - AC-003-1: 統合手順に、統合時のファイル扱いを「(a) 仕様・全体設計に関する恒久的設計資産（`user-requirements.md` / `object-design-*.md` 等）→ 追記・更新」「(b) その時用の設計資料 + 進捗ファイル → old/{日付}/ 退避」の2分類で整理したルールが記載されている。
  - AC-003-2: その時用の設計資料の退避先が、統合先フォルダ配下の `old/{日付}/` サブフォルダである旨が明記されている。退避後は今回WFの成果物を正規名で配置する。
  - AC-003-3: 退避先サブフォルダ名に用いる `{日付}` は、退避対象に関連する `history.md` に記載されている日付を用いる旨が明記されている。
  - AC-003-4: `old/{日付}/` に退避したファイルは履歴保全目的であり、以降のフェーズ（タスク計画・doc-sync・design-sync 等）の入力対象から除外する（読み込み対象は正規名ファイルのみ）旨が明記されている。
  - AC-003-5: (a) の恒久的設計資産は追記・更新で対応し、(b) のその時用の設計資料・進捗ファイルは old/{日付}/ 退避とする、という2分類の棲み分けが整合的に記載されている。
  - AC-003-6: old/{日付}/ 退避の対象となるその時用の設計資料の例として `delta-design.md` / `change-requirements.md` / `impact-analysis.md` / `approach.md` / `delta-task-list.md` / `impl-process-checklist.md` 等が挙げられている。
- **優先度**: 必須

## 対象外（スコープ外）

- `skills/folder-merge-check/SKILL.md` 以外のファイルへの変更（呼び出し元フェーズスキル `fs-change-phase1-analysis` / `fs-bugfix-phase1-analysis` / `fs-refactoring-phase2-candidates`、`doc-sync`、`git-commit-workflow` 等の関連スキルは本変更の対象外）。
- 影響範囲の分析（別工程で実施）。
- 対応方針の策定・before→after 形式の具体的なコード変更設計（別工程で実施）。
- 実装コードの作成・既存ルール記述の実際の編集（別工程で実施）。
- フォルダ統合の自動化や、ユーザー承認フロー（The Iron Law）の変更。本変更は統合手順・Red Flags への記述追加に限定し、統合可否のユーザー承認原則は変更しない。
- 既に実施済みの暫定対処（PI-027 で `202605271000-consolidate-change-bugfix-phases/old/` に退避した実例）の再処理。
- `old/{日付}/` サブフォルダの命名規約（`history.md` 記載の日付を用いる方針）以外の代替記法・命名規則の検討・標準化。

## 前提条件

- 本プロジェクトは aide-powers フレームワーク自体のメタ開発であり、変更対象は単一のスキル定義ファイル `skills/folder-merge-check/SKILL.md` である。
- 変更要求は pending-issues.md の PI-015 / PI-016 / PI-027 に詳細に記録されており、フレームワークオーナー（ユーザー）が要求内容を熟知している。
- 既存の `folder-merge-check` スキルの基本構造（Overview / The Iron Law / Process（Step 1〜6）/ Red Flags / Common Rationalizations / Integration）は維持される前提で、各要求は既存セクションへの追記として実現される。
- 進捗ファイルのワークフロー固有名（`bugfix-progress.md` / `change-progress.md` / `refactoring-progress.md` 等）は既存の各WFで使用されている命名規約に準拠する。
- 退避先サブフォルダ名に用いる日付の参照元となる `history.md` は、各WFフォルダ配下に存在し、退避対象に関連する日付が記載されている前提である。

- **PI-027**: folder-merge-check にその時用の設計資料の同名衝突時の old/{日付}/ 退避ルールを追記 → REQ-C-003 に対応。
