## 変更方針の詳細

### REQ-C-001: Red Flags テーブルへの1行追加

- **方針**: 既存 Red Flags テーブル（6行）の末尾に1行を追加する
- **追記箇所**: `## Red Flags - STOP` セクション内のテーブル最終行の後
- **追記内容の方向性**:
  - Red Flag 列: 「起因元フォルダのWF種別（`changes/` / `bugfix/` / `refactoring/`）が今回のWF種別と異なるから統合できない」に相当する思考パターン
  - なぜ危険か列: (a) folder-merge-check の目的は同じコード変更に起因するドキュメントを1箇所に集約しトレーサビリティを確保すること、(b) WF種別やディレクトリ階層の違いは統合を阻む条件ではないこと、の両方を記載
- **理由**: 既存テーブルの構造・フォーマットをそのまま踏襲し、追記のみで対処可能

### REQ-C-002: 進捗ファイルの old/{日付}/ 退避ルールの追加

- **方針**: Step 4 移動ルールに、進捗ファイルを「その時用のファイル」として `old/{日付}/` へ退避するルールを追記する（REQ-C-003 の (b) 分類に統合する）
- **追記箇所**: Step 4 の移動ルール c（空フォルダ削除）の前に、(b) その時用の設計資料+進捗ファイルの退避ルールの一部として挿入
- **追記内容の方向性**:
  - 進捗ファイル（`change-progress.md` / `bugfix-progress.md` / `refactoring-progress.md` 等）はWF固有名をそのまま使用する
  - 同名の進捗ファイルが統合先に既に存在する場合は、統合先フォルダ配下の `old/{日付}/` サブフォルダへ退避する
  - 退避先サブフォルダ名に用いる `{日付}` は、退避対象の進捗ファイルに関連する `history.md` に記載されている日付を用いる
  - 旧方式（`~1` / `~2` 等のサフィックスを付けてリネームする方式）は**採用しない**旨を明記する
  - 当該ルールが全WF種別に共通して適用される旨を明記する
- **理由**: 進捗ファイルは各WF固有の「その時用のファイル」であり、恒久的設計資産とは性質が異なる。REQ-C-003 の (b) 分類（その時用の設計資料）と同一の `old/{日付}/` 退避ルールに統一することで、退避運用を一本化し、ルールの重複・矛盾を避ける

### REQ-C-003: その時用の設計資料の old/{日付}/ 退避ルールの追加（判定分岐構造への拡張）

- **方針**: Step 4 移動ルール b を判定分岐構造へ拡張する。同名衝突時にまず判定基準で (a)/(b) を分類してから分岐する。(a) 恒久的設計資産は追記・更新（既存ルール b の単純追記挙動を (a) ルートとして保持）、(b) その時用の設計資料+進捗ファイルは `old/{日付}/` へ退避する
- **追記箇所**: Step 4 の移動ルール b の本体を判定分岐構造に書き換える形で挿入（移動ルール c（空フォルダ削除）の前。REQ-C-002 の進捗ファイル退避もこの (b) に包含する）
- **追記内容の方向性**:
  - 同名衝突時はまず判定基準で以下の2分類に分類してから分岐する旨を明記:
    - **(a) 仕様・全体設計に関する恒久的設計資産**（`user-requirements.md` / `system-requirements.md` / `object-design-*.md` 等）→ 統合先の既存ファイルへ**追記・更新**（既存ルール b の単純追記挙動を (a) ルートとして保持）
    - **(b) その時用の設計資料 + 進捗ファイル**（`delta-design.md` / `change-requirements.md` / `impact-analysis.md` / `approach.md` / `delta-task-list.md` / `impl-process-checklist.md` 等、および進捗ファイル）→ 統合先フォルダ配下の `old/{日付}/` サブフォルダへ**退避**し、今回WFの成果物を正規名で配置する
  - 退避先サブフォルダ名に用いる `{日付}` は、退避対象に関連する `history.md` に記載されている日付を用いる
  - `old/{日付}/` に退避したファイルは履歴保全目的であり、以降のフェーズ（タスク計画・doc-sync・design-sync 等）の入力対象から除外する（読み込み対象は正規名ファイルのみ）旨を明記
  - (a) と (b) の棲み分け（恒久的設計資産は追記・更新、その時用の設計資料・進捗ファイルは `old/{日付}/` 退避）を整合的に記載
  - (a)/(b) のどちらにも明確に該当しない同名ファイルは (a) 追記・更新ルートを従来通り適用する（安全側のデフォルト）旨を明記
  - 当該ルールが全WF種別に共通して適用される旨を明記
- **理由**: 現行ルール b（同名ファイルの単純追記）は (a) 恒久的設計資産の継続的な更新（`history.md` 等）に適しているが、完全に異なるWFのその時用成果物を追記で混合すると可読性が著しく低下し、上書き事故（PI-027）も発生する。そこで移動ルール b を判定分岐構造へ拡張し、既存の単純追記挙動を (a) 追記・更新ルートとして保持しつつ、(b) のその時用の設計資料・進捗ファイルは `old/{日付}/` 退避の別ルートで統一的に扱うことで、上書き事故を防ぎつつトレーサビリティを保全する

## 既存ルール b との棲み分け方針

Step 4 移動ルール b（同名ファイルが存在する場合の扱い）を判定分岐構造へ拡張する。既存の単純追記挙動は削除・破壊的改変をせず、(a) 恒久的設計資産の追記・更新ルートとして保持する。同名衝突時はまず判定基準で (a)/(b) を分類してから、以下の2ルートへ対等に分岐する。

| 分類 | 対象ファイル例 | 扱い | 該当ルート |
|---|---|---|---|
| **(a) 恒久的設計資産** | `user-requirements.md` / `system-requirements.md` / `object-design-*.md` 等（仕様・全体設計） | 統合先の既存ファイルへ**追記・更新** | 移動ルール b の (a) ルート（既存の単純追記挙動を保持） |
| **(b) その時用の設計資料 + 進捗ファイル** | `delta-design.md` / `change-requirements.md` / `impact-analysis.md` / `approach.md` / `delta-task-list.md` / `impl-process-checklist.md` / `change-progress.md` / `bugfix-progress.md` / `refactoring-progress.md` 等 | 統合先フォルダ配下の `old/{日付}/` へ**退避**（`{日付}` は history.md 記載日付）し、今回WFの成果物を正規名で配置 | 移動ルール b の (b) ルート（新規追加：REQ-C-002 / REQ-C-003） |

適用判定の順序（同名衝突時にまず分類してから分岐する）:
1. **対象が (a) 恒久的設計資産か？** → Yes: (a) 追記・更新ルート（既存の単純追記挙動）で解決
2. **対象が (b) その時用の設計資料・進捗ファイルか？** → Yes: (b) `old/{日付}/` 退避ルートで解決
3. 上記いずれにも明確に該当しない同名ファイル → (a) 追記・更新ルートを従来通り適用する（安全側のデフォルト）

この拡張により、既存ルール b の単純追記挙動は (a) 恒久的設計資産の追記・更新ルートとして引き続き機能する（挙動の削除・破壊的改変はしない。判定分岐構造へ拡張するのみ）。(b) のその時用の設計資料・進捗ファイルは、進捗ファイル（REQ-C-002）・その他のその時用設計資料（REQ-C-003）ともに `old/{日付}/` 退避という単一の退避ルートに統一され、上書き事故（PI-027）を防止する。

## リファクタリング検討結果

- **検討結果**: 不要
- **理由**:
  - 本変更は単一ファイル（`skills/folder-merge-check/SKILL.md`）への追記・更新であり、既存の構造（Red Flags テーブル、Step 4 移動ルールのリスト形式）をそのまま活用して拡張できる
  - 移動ルール b は既存の単純追記挙動を (a) ルートとして保持したまま判定分岐構造へ拡張するのみであり、挙動の削除・破壊的改変は伴わない（OCP原則に準拠）
  - 今後同様のルール追加が発生しても、同じテーブル/リスト形式への追記・分岐追加で対応可能であり、拡張ポイントの追加は不要
  - 対象がプログラムコードではなくスキル定義ドキュメント（Markdown）であり、パターン導入の対象にならない
