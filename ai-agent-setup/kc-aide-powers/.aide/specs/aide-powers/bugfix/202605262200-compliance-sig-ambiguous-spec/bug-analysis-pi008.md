# バグ原因分析（PI-008）

## 根本原因

compliance-sig.ps1 の verify-phase サブコマンド内の成果物ハッシュ抽出正規表現が、進捗ファイルの成果物テーブルの列数に対応していない。

## 詳細分析

### 問題の正規表現

```powershell
$hashMatches = [regex]::Matches($phaseSection, '\|\s*\S+\s*\|\s*([0-9a-fA-F]{64})\s*\|')
```

この正規表現の意図: `| ファイル名 | SHA256ハッシュ |` の2列テーブルからハッシュを抽出する。

### 実際のテーブル構造

進捗ファイルの成果物テーブルは3列:
```
| ファイル | 説明 | SHA256 |
|---|---|---|
| change-requirements.md | 変更要件定義書（REQ-C-001〜004） | 452FE45FA26173D7D17E8433102F23D6E081D412... |
```

### なぜマッチしないか

正規表現 `\|\s*\S+\s*\|\s*([0-9a-fA-F]{64})\s*\|` は:
1. `|` の後に非空白文字列（`\S+`）を期待
2. 次の `|` の後に64文字hexを期待

しかし実際は:
1. `|` の後に `change-requirements.md`（OK、`\S+` にマッチ）
2. 次の `|` の後に `変更要件定義書（REQ-C-001〜004）`（空白を含むため `\S+` ではない → ここで64文字hexを期待するが、説明文がある）

結果: マッチ0件 → hashValues が空 → E3B0C44... が使用される

### sign-phase が影響を受けない理由

sign-phase は成果物ファイルのパスを引数で受け取り、ファイルから直接 SHA256 を計算する。進捗ファイルのテーブルを解析しない。

## 修正方針

正規表現を「行内の任意の位置にある64文字hexを抽出する」方式に変更する。テーブルの列数に依存しない汎用的なパターンにする。

推奨パターン: `([0-9a-fA-F]{64})\s*\|?\s*$`（行末付近の64文字hex）
