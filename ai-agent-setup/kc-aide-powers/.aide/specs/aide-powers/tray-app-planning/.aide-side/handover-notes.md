# 設計オーケストレーターへの引き継ぎメモ（ことづけ）

## 特に注意すべき点

### タスクトレイアプリは既存aide-powersへの追加機能
- タスクトレイ管理アプリは新プロジェクトではなく、既存aide-powersへの追加機能として位置づけられている
- 既存の設計書（フェーズ1〜6のユースケース分析まで完了済み）はそのまま維持し、タスクトレイアプリ部分を追加設計する形で進める

### 2つのセットアップ方式の並立
- 方式A（タスクトレイアプリ方式）と方式B（git clone方式）は並立する設計
- git clone方式はsuperpowersと同じ手法で、aide-powersをセットアップするだけ。バージョン管理・desk-agents等は非対応
- 完全にタスクトレイ管理に一本化しないこと

### 更新の全自動禁止
- ユーザーが明確に「更新の全自動実行は禁止」と指示している
- バージョン監視・通知は自動だが、更新実行のトリガーは必ずユーザーが引く設計にすること

### kiro-desk-agentsの扱い
- 確実に後から追加する（「やるかも」ではなく「やる」）
- ただし今回のスコープでは深く考慮しない
- desk-agents追加時は、aide-powers機能なしでdesk-agents単体利用もあり得る
- タスクトレイアプリの設計では、将来のdesk-agents追加に対応できる拡張性を考慮する程度でよい

### ストレージ抽象化
- MinIO前提だが、S3や他クラウドに切り替え可能な抽象化設計が必須
- Repositoryパターンでの抽象化を推奨（技術調査で確認済み）

## ユーザーの意思決定の経緯

| 判断 | 理由 |
|---|---|
| タスクトレイアプリの追加 | 非エンジニアも含む社内メンバー全員がaide-powersを使えるようにするため。コマンドライン操作が難しいメンバーへの対応 |
| UIはブラウザベース | tkinterのGUIではなく、ブラウザでUIを表示する方式を選択 |
| MinIOストレージ | 当面のストレージとして選択。ただし将来の切り替えを見据えた抽象化を指示 |
| 更新の全自動禁止 | ユーザーの意思なしに更新が走ることを明確に禁止 |
| git clone方式の維持 | エンジニアが手軽にaide-powersだけを使いたい場合の選択肢として残す |
| desk-agentsは後から | 今考えると進まないので後回し。ただし確実にやる |
| リソース・コストは気にしない | レビューで指摘された工数見積もり・運用費用の具体化は不要と判断 |

## ユーザー技術レベルの所感

- ドメイン知識・プログラミングともにスコア5。AIDEフレームワーク全体の設計者本人であり、技術的な議論は専門用語をそのまま使って問題ない

- 番号選択での回答を好む（1文字で回答することが多い）
