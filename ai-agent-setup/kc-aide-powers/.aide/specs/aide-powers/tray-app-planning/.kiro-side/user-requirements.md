# ユーザー要件定義書: aide-powers

## 1. プロジェクト概要

kiro版AIDE（オーケストレーター＋サブエージェント構成のマルチエージェント開発フレームワーク）を、マルチプラットフォーム対応のスキルベース形式に最適化再構成し、全プラットフォーム共通のAIDE本体とする。

### 背景・動機

- 社内からKiro以外の環境でもAIDEの開発プロセスを使いたいという要望がある
- チームメンバーがClaude Code / Codex CLI等を日常的に使用している
- kiro専用AIDEは開発停止とし、本プロジェクトの成果物が全プラットフォーム共通のAIDEとなる

### 対象ユーザー

社内の幅広いメンバー（非エンジニアも含む）

### 利用シーン

- 日常の開発業務全般（新規開発・保守・バグ修正等すべて）
- ドキュメント駆動開発のプロセスを各プラットフォーム上で実行する場面
- チームメンバーが好みのエディタ/CLIでAIDEの開発プロセスを利用する場面

### プロジェクトの特性

本プロジェクトはプログラム作成が主体ではなく、スキル定義ファイル・エージェント定義ファイル・設定ファイルの再構成が中心である。

## 2. 要件一覧

### 2.1 Must（必須要件）

#### REQ-M01: 既存AIDEと同等以上の成果物生成

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、7つのオーケストレーター（企画・設計・実装・設計逆引き・変更・リファクタリング・バグ修正）の全てにおいて、既存kiro版AIDEと同等以上の成果物（設計書・コード・ドキュメント）を漏れなく生成しなければならない。
- **受入基準**: 各オーケストレーターが生成する全ドキュメント（orchestrator-index.mdの成果物一覧に記載されたもの）が正しく出力されること。

#### REQ-M02: マルチプラットフォーム対応

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、以下の8つのプラットフォームで動作しなければならない。
  1. Claude Code（メインターゲット）
  2. Codex CLI
  3. Kiro
  4. Cursor
  5. OpenCode
  6. Gemini CLI
  7. Copilot CLI（GitHub Copilot CLI）
  8. VSCode GitHub Copilot
- **受入基準**: 各プラットフォームでAIDEのオーケストレーターが起動し、成果物が生成されること。
- **補足**: 8プラットフォーム対応はaide-powersの存在意義そのものである。

#### REQ-M03: superpowers形式への最適化再構成（必須手段）

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、kiro版AIDEの構成ファイルをsuperpowers形式（スキルシステム、プラグイン配布、サブエージェント生成パターン等）に最適化再構成しなければならない。単なる機械的なファイル変換ではなく、superpowersの優れた仕組みを取り入れた設計判断を伴う再構成であること。
- **受入基準**: 出力（成果物）はkiro版AIDEと同等だが、内部のプロセスやロジックがsuperpowersの知見で強化・最適化されていること。
- **補足**: 技術調査により全構成ファイルの変換方針が整理済みであり、変換不可能なファイルはゼロであることが確認されている。本手段はユーザーにより必須と判断されている。

#### REQ-M04: superpowersの優れた仕組みの取り込み

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、superpowersの以下の5つの仕組みを内部プロセスに取り込まなければならない。
  1. **構造化された報告形式**: サブエージェントの報告を定型ステータスで管理する仕組み
  2. **規律パターン**: 「Xなしに、Yしてはならない」形式の核心ルールと多層防御による規律の強化
  3. **検証パターン**: 完了判定時に証拠に基づく検証を義務付ける仕組み
  4. **多段階レビュー**: 成果物の検証を複数の観点で段階的に実施する仕組み
  5. **構造化されたデバッグ手法**: 問題解決を体系的なフェーズで進め、一定回数の失敗でエスカレーションする仕組み
- **受入基準**: 各仕組みがaide-powersのプロセスに組み込まれ、サブエージェントの動作に反映されていること。

#### REQ-M05: サブエージェントのユーザー対話維持

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、既存AIDEのサブエージェントがユーザーと直接対話するシーケンスを維持しなければならない。サブエージェントがユーザーへの質問・確認を行う際、オーケストレーターを経由せず直接対話できること。
- **受入基準**: サブエージェントからのユーザー対話要求がパススルーされ、既存AIDEと同等の対話体験が提供されること。
- **補足**: フォアグラウンドサブエージェントでの実現が前提。リグレッションバグ（Issue #34592）の動向を監視し、発生時はバージョン固定で対応する。

#### REQ-M06: 社内限定配布

- **EARS分類**: Constraint（制約）
- **要件文**: aide-powersは、社内限定で配布しなければならない。パブリックへの展開は不可とする。
- **受入基準**: 社内メンバーのみがアクセス可能な配布手段が確立されていること。

#### REQ-M07: 容易なインストールと初回実行

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: 社内メンバーがaide-powersをインストールする際、簡易な手順で導入でき、短時間で初回実行（任意のオーケストレーターの起動）ができなければならない。
- **受入基準**: インストールから初回実行まで10分以内に完了すること。セットアップ用の実行ファイルを起動し、タスクトレイアプリの初期設定ウィザードを経て、10分以内に初回実行できること。

#### REQ-M08: オーケストレーター自動選択

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: ユーザーがリクエストを入力した際、aide-powersは7つのオーケストレーターから適切なものを自動選択し、対応するプロセスを開始しなければならない。ユーザーはオーケストレーターの存在を意識せず、自然言語でリクエストするだけでよいこと。
- **受入基準**: kiro版AIDEと同等のオーケストレーター選択体験が提供されること。

#### REQ-M09: 設計品質保証の維持・強化

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、kiro版AIDEの設計品質保証（DDD、SOLID、QAゲート等）を維持し、superpowersの仕組みで補強しなければならない。
- **受入基準**: 設計フェーズにおいてDDD・SOLID等の設計手法が明示的に適用され、QAゲートが機能すること。

#### REQ-M10: kiro専用AIDEの開発停止と移行

- **EARS分類**: Constraint（制約）
- **要件文**: kiro専用AIDEは開発停止とし、aide-powersが安定稼働した時点で完全に移行する。aide-powersが全プラットフォーム共通のAIDEとなること。
- **受入基準**: aide-powersがkiro版AIDEの全機能を代替できる状態になっていること。

#### REQ-M11: オーケストレーターの実作業禁止の維持

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersにおいても、オーケストレーターの役割はフェーズ管理・サブエージェント委譲に限定し、成果物の作成・編集等の実作業を行ってはならない。
- **受入基準**: オーケストレーターが直接ファイル書き込み・コード変更を行わず、全てサブエージェントに委譲していること。
- **補足**: handover-notes.mdの「コンテキスト汚染防止」に対応。superpowersでも同じ原則が採用されていることが確認済み。

#### REQ-M12: タスクトレイ管理アプリによるGUI管理

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、タスクトレイに常駐する管理アプリを提供し、ブラウザベースのUIでインストール・初期設定・プラグイン管理・更新管理を行えなければならない。非エンジニアでもコマンドライン操作不要で利用開始・管理できること。
- **受入基準**: タスクトレイアプリからブラウザUIを通じて、プラグインのインストール・初期設定（使用するプラットフォームの選択）・更新管理が完結すること。PC起動時にタスクトレイアプリが自動起動すること。
- **補足**: 初回セットアップウィザードと右クリックメニュー操作の2つのUIモードを提供する。

#### REQ-M13: S3互換ストレージからの配布

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、S3互換ストレージからプラグインをダウンロード配布しなければならない。ストレージ抽象化設計により、将来別のクラウドストレージに切り替え可能であること。
- **受入基準**: S3互換ストレージからプラグインのダウンロード・配置が正常に行われること。ストレージ実装の差し替えのみで別のストレージサービスに切り替え可能な設計であること。
- **補足**: 当面のストレージとしてMinIOを使用する。MinIOはS3互換APIを提供しており、将来AWS S3や他クラウドへの切り替えが設定変更レベルで可能。

#### REQ-M14: バージョン監視と更新通知

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: aide-powersのタスクトレイアプリは、ストレージ上のプラグインバージョンを定期的にチェックし、新バージョンが利用可能な場合に通知しなければならない。更新の実行はユーザーの明示的なトリガーのみとし、全自動更新は禁止する。
- **受入基準**: 新バージョンの検出時にユーザーへ通知が表示されること。更新実行はユーザーが明示的に操作した場合のみ行われ、自動的に更新が適用されないこと。
- **補足**: バージョン監視（検出・通知）は自動。更新実行のトリガーはユーザーが引く。

#### REQ-M15: 2つのセットアップ方式の並立

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、以下の2つのセットアップ方式を並立させなければならない。
  - **方式A（タスクトレイアプリ方式）**: フル機能。インストール・初期設定・プラグイン管理・バージョン管理・更新通知・将来のdesk-agents対応を提供する。非エンジニア向けの推奨方式。
  - **方式B（git clone方式）**: superpowersと同じ手法でaide-powersをセットアップするシンプルな方式。バージョン管理・更新通知・desk-agents等は非対応。エンジニアが手軽にaide-powersだけを使いたい場合の方式。
- **受入基準**: 方式A・方式Bの両方でaide-powersのセットアップが完了し、オーケストレーターが正常に動作すること。方式Bはsuperpowersと同等のセットアップ体験であること。

#### REQ-M16: プロジェクトルート管理と開発ツールランチャー

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: タスクトレイアプリは、aide-powersを使用するプロジェクトフォルダ（ワークスペース）のパスを記憶し、そのプロジェクトを指定して開発ツール（Kiro IDE、VSCode等）を起動できなければならない。起動時には社内プロキシ対応に必要な環境変数（証明書パス等）を自動設定すること。環境変数はGUIで管理（追加・編集・削除）可能であること。
- **受入基準**: タスクトレイアプリからプロジェクトを選択し、開発ツールを起動した際に、管理されている環境変数が正しく設定された状態でツールが起動すること。複数プロジェクトを管理できること。環境変数の一覧をGUIで確認・編集できること。
- **補足**: 現在はkirop.bat等のバッチファイルで環境変数を設定してからKiroを起動しているが、タスクトレイアプリがこの役割を担う。デフォルトで京セラ証明書関連の環境変数がプリセットされるが、ユーザーが自由にカスタマイズ可能。

#### REQ-M17: グローバル環境の非汚染

- **EARS分類**: Constraint（制約）
- **要件文**: aide-powersの開発・実行に必要なパッケージ・ライブラリは、グローバル環境にインストールしてはならない。Python依存はプロジェクトフォルダ内のvenv + requirements.txtで、Node.js依存はプロジェクトフォルダ内のnode_modules + package.jsonで管理すること。
- **受入基準**: グローバルのPython環境やNode.jsグローバルモジュールに変更を加えずに、aide-powersの全機能が動作すること。

#### REQ-M18: セットアップ時の証明書設定

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: 初期設定ウィザードにおいて、社内プロキシ対応に必要なCA証明書ファイルのパス設定を必須ステップとして含めなければならない。証明書ファイルの存在検証を行い、設定が完了するまで次のステップに進めないこと。
- **受入基準**: 初期設定ウィザードで証明書ファイルパスの設定ステップが存在し、ファイルの存在検証が行われること。証明書が正しく設定されないとセットアップが完了しないこと。
- **補足**: 証明書設定はMinIOストレージ接続や開発ツールランチャーの正常動作に必須であるため、セットアップの必須ステップとする。

### 2.2 Should（推奨要件）

#### REQ-S01: コンテキスト効率の向上

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: aide-powersは、kiro版AIDEと比較してコンテキスト効率が同等以上であるべきである。スキルのオンデマンド読み込みやサブエージェントへのコンテキスト隔離により、不要な情報のコンテキスト消費を抑制すること。
- **受入基準**: kiro版AIDEと同等かやや減少するトークン消費量であること（PoC実施時に実測）。

#### REQ-S02: 再構成工程のドキュメント化

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: 再構成工程自体をドキュメント化し、将来の更新や拡張に活用できるようにすべきである。
- **受入基準**: 再構成の設計判断・手順が記録され、同様の再構成を再現できること。

#### REQ-S03: 複数観点の並列レビュー

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: コードレビュー時に、複数の観点（コード品質、アーキテクチャ、テスト、要件準拠、パフォーマンス、セキュリティ等）を並列で実施できるべきである。
- **受入基準**: 既存AIDEのレビュー観点にsuperpowersの良い視点（パフォーマンス・セキュリティ等）が統合されていること。

#### REQ-S04: 将来のdesk-agents追加への拡張性

- **EARS分類**: Ubiquitous（常時適用）
- **要件文**: タスクトレイアプリの設計は、将来kiro-desk-agentsを追加できる拡張性を持つべきである。desk-agents追加時には、aide-powers機能なしでdesk-agents単体利用もあり得ることを考慮すること。
- **受入基準**: タスクトレイアプリのアーキテクチャが、aide-powers以外の製品（desk-agents等）を追加管理できる拡張ポイントを持つこと。
- **補足**: kiro-desk-agentsは確実に後から追加するが、今回のスコープ外。設計時に拡張性を考慮する程度でよい。

### 2.3 Could（希望要件）

#### REQ-C01: プラットフォーム間のコスト差異の可視化

- **EARS分類**: Event-driven（イベント駆動）
- **要件文**: 各プラットフォームでのAIDE実行時のトークン消費量・コストの差異を可視化できると望ましい。
- **受入基準**: PoC実施時に主要プラットフォームでの実測データが取得されること。

### 2.4 Won't（対象外）

#### REQ-W01: パブリック配布

- aide-powersは社内限定であり、パブリックへの展開は本プロジェクトのスコープ外とする。

#### REQ-W02: kiro版AIDEとの並行運用

- aide-powersが安定稼働した時点でkiro専用AIDEは完全に移行する。並行運用の仕組みは設けない。

#### REQ-W03: 運用費用の具体的金額試算

- 定額契約のため、具体的な金額の試算は不要とユーザーが判断。超えたらそのとき対応する方針。

| RISK-03 | 大量ファイル再構成時の品質低下 | 高 | 工程を細かく分割し、各ステップで検証を実施する |
| RISK-04 | オーケストレーター自動選択の誤選択 | 中 | スキルの説明文の記述精度を高め、メタスキルで補完する |
| RISK-05 | ストレージサーバーの可用性 | 高 | ストレージサーバーがダウンした場合、新規インストール・更新ができなくなる。git clone方式を補助経路として維持する |
| RISK-06 | 非エンジニアユーザーのトラブルシューティング困難 | 中 | セットアップ中のエラーに対して、わかりやすいエラーメッセージとログ出力を実装する |
