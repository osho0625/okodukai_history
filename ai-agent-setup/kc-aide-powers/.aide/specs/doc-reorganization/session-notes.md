# セッションメモ

## フェーズ1: 初期情報収集（ドキュメント整理）

### 確定事項

- 目的: aide-powers を他の人に引き渡せる状態にする + 社内展開で利用者が自力で使い始められるようにする
- 動機: 機能が安定してきた + 開発中のゴミが溜まって自分でも把握しづらい
- 対象ユーザー: 全員（開発引き継ぎ者・利用エンジニア・非エンジニア）
- 自発的な判断（外部依頼ではない）
- 出来上がりイメージ: リポジトリを渡せばREADMEと手順書を読むだけで開発を始められる状態

### 必要な成果物（確定）

1. **設計資料の作り直し**: 古い内容を一掃し、最新で見やすくわかりやすい構成に再構成
2. **利用者向け解説資料**: README拡充、使い方ガイド等
3. **開発者向け更新手順書**: フェーズスキルの作り方、共通スキルの作り方、カスタムエージェントの作り方
4. **履歴ファイルの一掃**: changes/、レビュー結果、セッションファイル等の削除

### 利用場面

- aide-powers を初めてインストールして使い始めるとき
- aide-powers にスキル・エージェントを追加・修正するとき
- aide-powers の設計思想や全体構造を理解したいとき

### 確定事項（追加）

- [サイクル2] 開発者向けドキュメント生成方式の精緻化:
  - 章別エージェント定義ファイルは作成しない（agents/ 配下に4種を新設しない）
  - task-orchestration の実行計画フェーズで、章ごとに general-task-execution サブエージェントへ渡すプロンプトを定義する
  - 実行フェーズで並列ディスパッチ（依存関係のない章は同時起動）
  - 各章プロンプトは aide-powers 構造（skills/agents/setup等）を入力として担当章の設計書を生成する

- [サイクル2] 利用者向けドキュメント生成方式の精緻化:
  - 文章整形エージェントもエージェント定義ファイルとしては作らない
  - task-orchestration の実行計画フェーズで「ユーザー素材を読みやすく整形する」プロンプトを用意し、サブエージェントへ渡す（一時的、再利用なし）
  - 制約: ユーザー主旨の改変禁止、事例の数値・固有名詞の改変禁止、抽象化による情報の希薄化禁止

- [サイクル2] ドキュメント陳腐化対策（観点6・観点7-3 への対応）:
  - 既存の `doc-sync` スキルを活用する（aide-powers の標準仕組み）
  - aide-powers 自身の変更・バグ修正・リファクタリング時に、各WFの最終フェーズで doc-sync が実行される
  - これにより、aide-powers のコード変更が docs-dev/ や docs/ に自動反映される運用となる
  - 新しい仕組みの追加は不要

- [サイクル2] 章間の重複・矛盾防止策（観点7-4 への対応）:
  - **共通用語辞書を先に作成**し、各章プロンプトに共有させる
    - 配置: `docs-dev/glossary.md` または `.aide/specs/doc-reorganization/glossary.md`
    - 内容: aide-powers 固有の用語（フェーズスキル、ハブスキル、共通スキル、Iron Law、ワークフロー名 等）の定義
    - 章別プロンプトでこの辞書の用語と定義を厳守させる
  - **章間レビューエージェントを並列生成後に1回走らせる**
    - 入力: 4章すべての生成済みドキュメント
    - 役割: 章をまたぐ用語のブレ、内容重複、責務境界の侵犯を検出
    - 検出した問題は該当章の修正タスクとして task-orchestration の修正サイクルに戻す

- [サイクル2] 文章整形時の主旨改変防止策（観点7-5 への対応）:
  - プロンプトに「主旨改変禁止・数値や固有名詞の改変禁止・抽象化禁止」を明記
  - **ユーザー素材原文と整形後の差分をユーザーに提示し、ユーザー自身がチェックする**
  - 主旨改変を発見したらユーザーが指摘して修正させる（AIによる自動チェックではなく、ユーザー目視による最終ゲート）

- [サイクル2] 観点1（進歩性）・観点9（充足度）への対応:
  - 企画書には「進歩性」「処理フロー図」等の追加節を**作らない**
  - ここまでの確定事項を企画書に淡々と反映するのみ
  - 進歩性の演出や全体像の図解はドキュメント整備の本題ではないため、企画書の充実より実作業に進む方を優先する

### 作業順序（確定）

削除は新ドキュメント完成後に実施。途中の参考資料が消えないように注意。

1. 既存ドキュメントを `old/` に退避（参考資料化）
2. **開発者向け一式作成**
   - 章別サブエージェント（4種類: 00-overview / 01-system-platform / 02-ai-agent / 03-how-to）を作成
   - task-orchestration で開発者向けドキュメント（docs-dev/）を生成
3. **利用者向け一式作成**
   - 「文章整形」カスタムエージェントを作成
   - 利用者向けドキュメント（README + docs/）を作成（ユーザーが素材→エージェントが整形）
4. **すべて完成・確認後**、`old/`、`references/`、`changes/` をまとめて削除
