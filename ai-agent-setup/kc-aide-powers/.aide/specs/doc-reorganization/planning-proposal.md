# 開発企画書: aide-powers ドキュメント再整備

## 1. プロジェクト概要
- **プロジェクト名:** aide-powers ドキュメント再整備
- **一言説明:** aide-powers を他者に引き渡し可能な状態にし、社内展開で利用者が自力で使い始められるようにするためのドキュメント整備プロジェクト
- **背景・動機:** 機能が安定してきた一方で、開発中に蓄積されたゴミ（古い設計資料、履歴ファイル等）が溜まり、開発者自身でも把握しづらい状態になっている。自発的な判断による整備であり、外部依頼ではない。
- **ゴール:** リポジトリを渡せば README と手順書を読むだけで開発を始められる状態にする

## 2. 対象ユーザー
- **ユーザー像:**
  - 開発引き継ぎ者（aide-powers の開発を引き継ぐエンジニア）
  - 利用エンジニア（aide-powers を自分のプロジェクトで使うエンジニア）
  - 非エンジニア（aide-powers の概要や設計思想を理解したい人）
- **ユーザーの課題:**
  - 初めて触る人がどこから読めばよいかわからない
  - 設計資料が古く、現状と乖離している
  - スキルやエージェントの追加・修正手順が明文化されていない
  - 不要な履歴ファイルがノイズとなり、本質的な情報にたどり着きにくい

## 3. スコープ
### 含まれるもの
- 設計資料の再構成（古い内容の一掃、最新で見やすい構成への再編）
- 利用者向け解説資料の作成（README 拡充、使い方ガイド等）
- 開発者向け更新手順書の作成（フェーズスキル・共通スキル・カスタムエージェントの作り方）
- 履歴ファイルの一掃（changes/、レビュー結果、セッションファイル等の削除）
- ドキュメント生成プロンプトの設計（章別4種 + 文章整形1種 + 章間レビュー1種、エージェント定義ファイルは作らない）
- 共通用語辞書（glossary.md）の作成

### 含まれないもの
- aide-powers の機能追加・仕様変更
- コードのリファクタリング（ドキュメント整備に伴わないもの）
- 社内展開の実施そのもの（展開用資料の作成まで）

## 4. 成果物一覧

### 4.1 開発者向けドキュメント（docs-dev/ 4層構造）

aide-powers の構造（skills/、agents/、setup.bat 等）を入力として、章別サブエージェントが生成する。

```
docs-dev/
├── 00-overview.md                      機能概要 + 構成概要
├── 01-system-platform/                 システム・プラットフォーム視点
│   ├── 00-architecture.md              全体アーキテクチャ
│   ├── 01-hub-skill-activation.md      ハブスキル方式・スキル発見
│   ├── 02-multiplatform.md             マルチプラットフォーム対応
│   ├── 03-platform-bootstrap/          プラットフォーム別起動処理
│   ├── 04-skill-map.md                 スキルマップ
│   ├── 05-dynamic-rules.md             ルールファイル動的生成
│   └── 06-execution-units.md           実行部隊構成
├── 02-ai-agent/                        AI Agent 構成詳細
│   ├── 00-overview.md
│   ├── 01-workflows/                   7ワークフロー
│   ├── 02-phase-skills/                フェーズスキル詳細
│   ├── 03-common-skills/               共通スキル詳細
│   └── 04-agents/                      共通エージェント詳細
└── 03-how-to/                          開発手順書
    ├── add-phase-skill.md
    ├── add-common-skill.md
    ├── add-agent.md
    ├── add-workflow.md
    └── release.md
```

### 4.2 利用者向けドキュメント（README + docs/）

ユーザーが書いた素材（事例・要点メモ・伝えたい主旨）を、文章整形カスタムエージェントが読みやすい文章に整形する。

- `README.md`
- `docs/01-about.md` — aide-powers とは（特徴・他Agentとの違い・モデル別任せ度・メリット/デメリット・向き不向き・ライセンス/動作要件 全部入り）
- `docs/02-getting-started.md` — インストールと初期設定
- `docs/03-usage.md` — 使い方
- `docs/04-faq.md` — よくある質問
- `docs/05-troubleshooting.md` — トラブルシュート

抽象 → 具象の流れで構成する（「特徴」という抽象テーマの下に「違い・モデル別・メリデメ・向き不向き」を具象として配置）。

### 4.3 ドキュメント生成プロンプト（task-orchestration 内で使用）

エージェント定義ファイルとしては作成しない。task-orchestration スキルの実行計画フェーズで章ごとにプロンプトを定義し、サブエージェント（general-task-execution）へ渡す。一時的・再利用なしの方式とする。

- **章別プロンプト（4種類）** — 開発者向けドキュメントの章ごとに用意
  - `00-overview` 担当
  - `01-system-platform` 担当
  - `02-ai-agent` 担当
  - `03-how-to` 担当
- **文章整形プロンプト（1種類）** — ユーザー素材を読みやすい文章に整形
- **章間レビュープロンプト（1種類）** — 4章生成後に並列レビュー（用語ブレ・重複・責務境界の侵犯を検出）

### 4.4 履歴ファイル一掃

- `.aide/specs/aide-powers/changes/` 配下の41個の変更履歴フォルダを削除
- `.aide/specs/aide-powers/` 配下の設計書類は `old/` に退避後、新ドキュメント完成後に削除
- `.kiro/specs/aide-powers/` の重複コピーも `old/` 退避 → 削除
- プロジェクトルートの `references/`（kiro-agents、superpowers 等の外部参照コピー）は `old/` 退避なしで削除
- **`.aide/references/` は削除しない**（aide-powers のスキルが参照しており、削除するとAI動作が壊れる）

## 5. 作成方法

### 5.1 開発者向けドキュメント

- 章別エージェント定義ファイルは作成しない
- task-orchestration の実行計画フェーズで章ごとにプロンプトを定義
- 実行フェーズで並列ディスパッチ（依存関係のない章は同時起動）
- 入力: `skills/`、`agents/`、`setup.bat` 等の実体（aide-powers のコード相当）
- 既存ドキュメントは参考資料として扱う（主入力ではない）
- **共通用語辞書（glossary.md）を先に作成**し、各章プロンプトに共有させる
- 4章生成後、章間レビュー（用語ブレ・重複・責務境界の侵犯を検出）を1回実施
- 検出問題は task-orchestration の修正サイクルで該当章を再生成

### 5.2 利用者向けドキュメント

- 文章整形エージェント定義ファイルも作成しない
- task-orchestration の実行計画フェーズでプロンプトを用意
- 入力: ユーザーが書いた素材（事例・要点メモ・伝えたい主旨）、章立てテンプレート
- 出力: 整形済みドキュメント（README.md / docs/01-about.md 等）
- 制約: ユーザー主旨の改変禁止、事例の数値・固有名詞の改変禁止、抽象化による情報の希薄化禁止
- **ユーザー素材原文と整形後の差分をユーザーに提示し、ユーザー目視で最終チェック**

## 6. 関連ビジネスロジック
### 利用場面
- **初回利用時:** aide-powers を初めてインストールして使い始めるとき
- **拡張・修正時:** aide-powers にスキル・エージェントを追加・修正するとき
- **理解・学習時:** aide-powers の設計思想や全体構造を理解したいとき

### 想定ワークフロー
1. リポジトリを clone する
2. README を読んで全体像を把握する
3. 使い方ガイドに従ってインストール・初期設定を行う
4. 必要に応じて開発者向け手順書を参照し、スキルやエージェントを追加・修正する

## 7. 作業順序

削除は新ドキュメント完成後に実施。途中の参考資料が消えないように注意。

1. **既存ドキュメントを `old/` に退避**（プロジェクトルート直下の `old/`、参考資料化）
2. **開発者向け一式作成**
   - 章別サブエージェント（4種類: 00-overview / 01-system-platform / 02-ai-agent / 03-how-to）を作成
   - task-orchestration で開発者向けドキュメント（docs-dev/）を生成
3. **利用者向け一式作成**
   - 文章整形カスタムエージェントを作成
   - 利用者向けドキュメント（README + docs/）を作成（ユーザーが素材を書く → エージェントが整形）
4. **すべて完成・確認後**、`old/`、`references/`、`changes/` をまとめて削除

## 8. 制約・前提条件
- aide-powers の機能自体は安定しており、大きな機能変更は予定していない
- 既存の設計思想・アーキテクチャは維持する（ドキュメントの整理であり、設計の変更ではない）
- ユーザーは AI による創造的な文章生成にセンスを期待しない（具体事例はユーザー側で書く）
- ドキュメント整備中も aide-powers 自体は通常運用可能であること（`.aide/references/` 等は維持）

## 9. リスク・懸念事項
- 設計資料の再構成時に、必要な情報を誤って削除するリスク
  - **対策**: old/ 退避 + 新ドキュメント完成確認後の削除ゲート
- 履歴ファイル一掃時に、まだ参照されているファイルを削除するリスク
  - **対策**: 削除前に grep で被参照を確認、`.aide/references/` は削除対象から除外
- ドキュメント整備後も、機能変更に追従してドキュメントが陳腐化するリスク
  - **対策**: 既存の doc-sync スキル（変更/バグ修正/リファクタリング各WFの最終フェーズで自動実行）で対応
- 章別サブエージェント間で記述の重複や矛盾が発生するリスク（章境界の調整が必要）
  - **対策**: 共通用語辞書を先に作成 + 章間レビュープロンプトで並列生成後に検出
- 文章整形エージェントがユーザーの主旨を抽象化して薄めてしまうリスク
  - **対策**: プロンプトで主旨改変禁止を明記 + ユーザー素材原文と整形後の差分をユーザー目視で最終チェック
- `old/` 退避後、新ドキュメント完成前に誤って `old/` を削除するリスク
  - **対策**: 削除前のユーザー最終確認ゲート（最終フェーズで明示的にユーザー合意を得る）
