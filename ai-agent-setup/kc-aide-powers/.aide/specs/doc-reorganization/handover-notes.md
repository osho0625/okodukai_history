## 引き継ぎ先ワークフロー

**次のセッションでは aide-powers のワークフローを使わず、普通に企画書を参照しながら実作業を進める。**

理由:
- ドキュメント整備は「振る舞いを変えない内部資産の整理」であり、aide-powers のWFを通すと過剰
- 企画書がリファクタリング計画として既に十分機能している
- ユーザーの判断: 普通にやる方が早い

## A. 特に注意すべき点

| 項目 | 内容 |
|---|---|
| 削除タイミング | 削除は「すべて完成・確認後」に実施。途中で `old/`、`references/`、`changes/` を消さない。新ドキュメント作成中の参考資料として残す |
| `.aide/references/` 削除禁止 | aide-powers のスキルが参照しており、削除するとAI動作が壊れる。削除対象から明示的に除外する |
| 共通用語辞書の先行作成 | 章別プロンプトに渡す前に `glossary.md` を先に作る。後付けにしない |
| ユーザー目視チェック必須 | 文章整形は AI による自動チェックではなく、ユーザー素材原文と整形後の差分をユーザー目視で確認。主旨改変はユーザーが指摘 |
| 事例・キャッチー表現 | 利用者向けドキュメントの具体事例・キャッチー表現はユーザーが書く。AIは整形のみ。AIにセンスを期待しない |
| エージェント定義ファイル不作成 | 章別エージェント・文章整形エージェント・章間レビューエージェントはすべて task-orchestration 内のプロンプト方式。`agents/` 配下に永続的なエージェント定義ファイルは作らない |

## B. ユーザーの意思決定の経緯

| 判断内容 | 選択肢 | 決定理由 |
|---|---|---|
| 開発者向けドキュメント構成 | ユーザー案3層 / 4層構造（提案A）/ 読み手別（提案B） | 提案A（4層構造）を採用。「読む順番」が一目瞭然で、引き継ぎ者が即座に手を動かせるため |
| 利用者向けドキュメント章立て | 章を分散 / 1ファイル集約 | 抽象→具象の流れで `docs/01-about.md` に集約。「特徴」という抽象テーマの下に「違い・モデル別・メリデメ・向き不向き」を具象として配置。観点4・5を観点1に含める設計 |
| 設計資料の作り直し方針 | 既存ドキュメント整理 / コードから逆生成 / 両方 | コードから逆生成（設計逆引きWFベース）。既存ドキュメントは参考資料扱い。理由: 既存資料が古くゴチャゴチャしているため、コードを正源として作り直す方が早くて正確 |
| サブエージェントの粒度 | 1つの汎用 / 章ごと / 1ファイル毎 | 章ごとに分割し、task-orchestration 内のプロンプトとして実行。エージェント定義ファイルは作らない（一時的・再利用なし） |
| 履歴ファイル一掃の範囲 | changes/のみ / 全部 | 当初「全部」だったが、ユーザー指摘により `.aide/references/` 削除を回避。最終的には `changes/` + 旧設計書 + 重複コピー + プロジェクトルートの `references/` を削除 |
| `old/` フォルダの配置 | プロジェクトルート / `.aide/specs/` / `.archive/` | プロジェクトルート直下の `old/`（一番見やすい、削除し忘れない） |
| 進歩性節・処理フロー図の追加 | 追加 / 追加せず | 追加せず。ドキュメント整備が本題で、企画書の見栄えを充実させるより実作業に進む方を優先 |

## E. ユーザー技術レベルの所感

| 項目 | 内容 |
|---|---|
| コミュニケーションスタイル | 全軸4〜5のエキスパート。aide-powers 企画者本人。判断が早く、選択肢を提示すると即座に番号で返答する。曖昧な選択肢や抽象的な提案を嫌う |
| 得意・不得意 | 抽象と具象の階層構造に敏感。AIが抽象化して情報を薄めると即座に指摘する。具体的な事例・数値・固有名詞を重視する |
| 対話のコツ | 番号付き選択肢で簡潔に提示。各選択肢の違いを具体的に書く。「他もそう」と言われる抽象表現は避ける。事例の文言はユーザーが書くため、AIは構成・骨格に専念する |
| 注意点 | 「その他（自由記述）」を選択肢に含め忘れない（グローバルルール §1-1）。質問は1つずつ（複数まとめて投げない）。task-orchestration を「並列実行屋」ではなく「プロセス定義」として扱う。doc-sync スキルなど既存資産があるか先に確認してから新規仕組みを提案する |
