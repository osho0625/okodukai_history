# 03. aide-powers の使い方

aide-powers をインストールしたあと、実際にどう使うかを説明します。
利用エンジニアがプロジェクトで aide-powers を使い始めるときの実用的なガイドです。

セットアップ手順は本書では扱いません。インストールが済んでいない場合は、
README.md のクイックスタートを参照してください。

---

## 1. 基本の流れ

aide-powers をインストールしたあとは、AI Agent に **普通に話しかけるだけ** で
ワークフローが起動します。利用者側で「この機能を使いたい」と意識する必要はありません。

裏側ではハブスキル方式が動いています。AI Agent はセッション開始時に
ハブスキル（`using-aide-powers`）を読み込み、ユーザーの発話内容から
適切なワークフローを自動で選択します。

```
ユーザーの発話
   ↓
ハブスキル（using-aide-powers）が受け取る
   ↓
Quick Routing で該当ワークフローのエントリポイントを特定
   ↓
エントリポイントスキルを起動 → ワークフロー開始
```

利用者から見ると次の流れになります。

1. 普通に話しかける（例: 「ログイン機能を追加して」）
2. AI Agent が「変更ワークフローで進めます」と確認してくる
3. フェーズに沿って質問・確認に答える
4. 設計書・コード・レビュー結果が順次でき上がる

ワークフローのフェーズ番号や内部ルールを利用者が覚える必要はありません。
AI Agent が必要なときに必要な質問をしてきます。

---

## 2. ワークフロー選択（Quick Routing）

ハブスキルは Quick Routing という仕組みで、ユーザーの発話に含まれるキーワードから
最初に呼ぶべきフェーズスキルを判断します。

| ユーザー発話の例 | 起動するワークフロー |
|---|---|
| 「作りたい」「新しいアプリ」「アイデアがある」 | 企画ワークフロー |
| 「要件は決まっている」「設計して」「仕様書」 | 設計ワークフロー |
| 「実装して」「コードを書いて」「タスクリスト」 | 実装ワークフロー |
| 「バグ」「動かない」「エラー」「クラッシュ」「壊れた」 | バグ修正ワークフロー |
| 「機能追加」「仕様変更」「振る舞いを変えたい」 | 変更ワークフロー |
| 「リファクタ」「内部構造」「コード品質」「技術的負債」 | リファクタリングワークフロー |
| 「設計書がない」「既存コードから設計書」「構造把握」 | 設計逆引きワークフロー |

英語の発話（"build X", "bug", "refactor" など）にも対応します。

判断に迷うケースでは、AI Agent が **番号付き選択肢** で確認してきます。
利用者は自由文で意図を補足してもよく、「その他」を選んで自由記述することもできます。

## 3. 対話例

実際の発話とワークフロー起動の対応例です。

### 例1: アイデア段階から始める

```
ユーザー: 「Pythonでじゃんけんアプリ作って」

→ 企画ワークフローが起動し、要件確認から始まる
```

ハブスキルは「作って」「アプリ」というキーワードからアイデア段階と判断し、
企画ワークフローのエントリポイントを起動します。AI Agent はまず初期ヒアリング
（誰が使うか、何を実現したいか、制約は何か）を行い、企画書をまとめていきます。

### 例2: バグを直す

```
ユーザー: 「このバグ直して」

→ バグ修正ワークフローが起動し、原因分析から始まる
```

「バグ」というキーワードでバグ修正ワークフローが選択されます。
このワークフローは HEARING FIRST（ヒアリング最優先）の原則で、症状・再現手順・
期待動作を最初に聞き取ります。困っている人を待たせない設計です。

### 例3: 機能追加する

```
ユーザー: 「ログイン機能を追加して」

→ 変更ワークフローが起動し、影響範囲分析から始まる
```

「追加して」というキーワードで変更ワークフローが選択されます。
既存コードへの追加なので、AI Agent はまず既存設計書とコードを読み、
影響範囲を洗い出してからユーザーと対応方針を合意します。

---

## 4. 判断に迷うケース

「修正して」「改善して」のように、複数のワークフローに当てはまりそうな発話があります。
このとき AI Agent は確認ポイントに沿って質問してきます。

| 発話 | 確認ポイント | 振り分け先 |
|---|---|---|
| 「修正して」 | バグか、それとも仕様変更か？ | バグ → バグ修正ワークフロー / 仕様変更 → 変更ワークフロー |
| 「改善して」 | 振る舞いが変わるか？ | 変わらない → リファクタリングワークフロー / 変わる → 変更ワークフロー |
| 「設計書を作って」 | 既存コードがあるか？ | ある → 設計逆引きワークフロー / ない → 設計ワークフロー |
| 「実装して」 | 設計書があるか？ | ある → 実装ワークフロー / ない → まず設計ワークフロー |
| 「新機能を追加」 | 既存コードベースがあるか？ | ある → 変更ワークフロー / ない → 企画ワークフロー |

利用者は YES/NO ではなく、内容を簡潔に答えれば AI Agent が適切なワークフローを
選びます。例えば「修正して」と言ったあと「期待した結果が返ってこない」と
補足すれば、バグ修正ワークフローが起動します。

不明な場合は AI Agent から番号付き選択肢で確認してきます。利用者は番号で
答えるか、「その他」を選んで自由記述してください。

## 5. 各ワークフローの動き

7つのワークフローについて、利用者視点で「何を入力すると何が起きるか」を説明します。
各ワークフローのフェーズ番号や内部ルールの詳細は本書では扱いません。
仕組みを深く知りたい場合は `docs-dev/02-ai-agent/` を参照してください。

### 5.1 企画ワークフロー（アイデア → 企画書）

漠然としたアイデアを、設計に進める粒度の **開発企画書** にまとめます。

| 入力 | 出力 |
|---|---|
| ユーザーのアイデア・既存資料（あれば） | `planning-proposal.md`（開発企画書）、`handover-notes.md`（設計WFへの引き継ぎメモ）、`user-profile.md`（利用者の技術レベル記録）など |

利用者は AI Agent との対話を繰り返しながら、誰が何のために使うのか、
どんな技術で実現するのか、どこまでをスコープにするのかを少しずつ確定していきます。
AI Agent が必要に応じて Web で技術調査もしてくれます。

最終レビューで READY 判定が出てユーザー合意が取れたら、企画書を確定させて
設計ワークフローへ引き継ぎます。

### 5.2 設計ワークフロー（要件 → 設計書一式、4 QAゲート）

要件から **実装可能なレベルの設計書一式** を作ります。11フェーズで構成され、
品質を担保するために4つの QAゲートが置かれています。

| 入力 | 出力 |
|---|---|
| 企画書または明確になった要件 | ユーザー要件・システム要件・開発計画書・アーキテクチャ・GUI設計・ユースケース分析・レイヤードアーキテクチャ・オブジェクト設計・インフラインターフェース設計・プログラム構成 |

QAゲートは設計書の節目ごとに動き、QAレビューアーエージェントが
APPROVED / REJECTED を判定します。REJECTED の場合は対応するフェーズに戻って
修正してから再 QA を行うため、利用者は「設計書はもうレビュー済み」という
状態でワークフロー完了を迎えられます。

利用者の役割は、各フェーズで AI Agent からの確認に答えること、
QAゲート通過時の最終合意を出すことです。

### 5.3 実装ワークフロー（設計書 → コード、設計書ゲート + 多段階コードレビュー）

完成した設計書をもとに、コードを実装します。

| 入力 | 出力 |
|---|---|
| 完成済みの設計書一式 | 実装コード、テストコード、動作確認試験書、README.md、`docs/`配下の開発者向けドキュメント |

入口で **設計書ゲート** が動き、設計書がすべて完了状態であることを機械的に
確認します。設計書が揃っていない場合は実装に進めません。AI Agent は設計
ワークフローへ誘導します。

実装中は1タスクごとに **多段階コードレビュー** が動きます。実装担当・設計準拠
レビュー担当・コード品質レビュー担当の3つのサブエージェントが分業し、
書いたコードが設計通りで品質基準を満たしているかを毎回検査します。
利用者は仕上がりを確認するだけで、レビュー指摘の往復は AI Agent 内で完結します。

GUI がある場合、本格実装の前に静的なモックアップを先に作って利用者が
レイアウトを確認できるようにします。

### 5.4 設計逆引きワークフロー（既存コード → 設計書）

既にあるコードベースから **設計書を逆生成** します。理想を書くのではなく、
コードの現実をそのまま記録するワークフローです。

| 入力 | 出力 |
|---|---|
| 既存のコードベース | プログラム構成・開発環境定義・システム要件・ユーザー要件（必要に応じてアーキテクチャ・オブジェクト設計・インフラIF・GUI設計） |

AI Agent はコードを機械的に解析してフォルダ構成・依存関係・技術スタックを
抽出します。ユーザー要件はコードの挙動から推測したうえで、利用者へのヒアリングで
確定させます。

設計書がない既存プロジェクトに対して変更や実装を行いたい場合、まずこのワークフローで
設計書を整えてから他のワークフローへ進む流れになります。

### 5.5 変更ワークフロー（影響範囲分析 + 差分設計）

既存コードに **機能追加・仕様変更** を加えます。

| 入力 | 出力 |
|---|---|
| 変更要求、既存設計書、既存コード | 変更要件、影響範囲分析、差分設計書（before → after）、差分実装、既存設計書への反映 |

このワークフローは「設計と実装の両方」に変更を反映するのが特徴です。
入口で設計書ゲートが動き、設計書が揃っていることを確認します。
そのあと既存設計書とコードを読み込んで影響範囲を洗い出し、対応方針を
利用者と合意してから差分設計書を作成します。

差分設計書は QAレビューアーエージェントの審査を必ず通り、APPROVED が出て
初めて差分実装に進みます。実装が終わったら差分設計書の内容を既存設計書に
マージして、ワークフローを完了します。

利用者は変更要求を伝え、影響範囲のレビュー時と差分設計の最終合意時に
意思決定するだけで進められます。

### 5.6 リファクタリングワークフロー（外部振る舞い保持 + セーフティネット）

外部から見える振る舞いを変えずに、**内部構造を改善** します。

| 入力 | 出力 |
|---|---|
| リファクタリング要求または「気になっているコード」、既存設計書、既存コード | リファクタリング候補分析、差分設計書、改善後のコード、既存設計書への反映 |

入口で設計書ゲートを通したあと、既存テストを全実行して PASS / FAIL / スキップ数を
**セーフティネット基準** として記録します。リファクタリング実装がすべて完了した後の
動作確認Stepで既存テストを再実行し、基準値と比較することで「外部振る舞いが変わっていない」
ことを機械的に保証します。

利用者からリファクタリング要求が出ていない場合でも、AI Agent が6観点
（重複・巨大化・命名・結合度・依存方向・テスタビリティなど）でコードを分析して
候補を提案します。利用者は候補を見て優先順位を決めるだけで進められます。

### 5.7 バグ修正ワークフロー（HEARING FIRST + 原因分析）

既存コードのバグを修正します。**HEARING FIRST** が大原則で、
他のワークフローと違って設計書ゲートはヒアリングの後に置かれています。

| 入力 | 出力 |
|---|---|
| バグ症状の報告、再現手順、期待動作 | バグ報告書、原因分析、修正方針、差分設計書（リグレッションテスト設計含む）、修正コード、既存設計書への反映 |

最初に AI Agent が症状・再現手順・期待動作・実際の動作・環境情報を
聞き取ります。困っている人を待たせないため、コード調査や設計書確認はその後です。

ヒアリング後にコードとテストを調査して根本原因を特定し、原因 / 修正方針 /
修正種別の三つ組を利用者と合意します。差分設計書には **リグレッションテスト**
（バグ再現テスト）の設計を必ず含め、実装完了後の動作確認Stepで **既存テスト全実行** を
1 回実施し、他の機能を壊していないことを確認します。

利用者は症状を伝えれば、原因特定から修正・テストまで AI Agent が一貫して
進めてくれます。

## 6. セッション切替

長時間のワークフローでは、AI Agent のコンテキストウィンドウが大きくなりすぎて
新しいセッションに切り替えたくなる場面があります。aide-powers では
`session-handover` というメタスキルが、この切り替えを自動で支えます。

仕組みは次のとおりです。

1. ワークフローのフェーズ完了時など節目のタイミングで、AI Agent が
   `session-handover.md` に作業状態を書き出します（完了済み作業、未完了作業、
   次のアクション、読むべきファイル、確定した設計判断、ユーザー指示など）。
2. 利用者が新しいセッションを開始すると、ハブスキルが
   `session-handover.md` の存在を検出し、内容を読み込んで作業状態を復元します。
3. AI Agent が前回の続きから作業を再開します。

利用者から見ると、セッションを切り替えても **作業の続きから自然に再開** できます。
コンテキストが溢れそうになったり、別の日に作業を再開したりするとき、
新しいセッションを開いて「続きをやって」と伝えれば、AI Agent が
引き継ぎファイルを読んで状況を把握してから話しかけてきます。

引き継ぎファイルは1世代前まで `session-handover-old.md` として保持されるため、
直前の引き継ぎ内容を後から確認することもできます。

## 8. トークン消費の目安

aide-powers のトークン消費は、ベースの AI Agent 単体利用と比べて増えます。要件定義・設計・QA レビュー・多段階コードレビュー・ドキュメント同期の工程が走るためです。具体的な消費量はモデルとプロジェクト規模に依存しますが、利用前に押さえておきたい傾向は次のとおりです。

### 8.1 ワークフロー別の傾向

各ワークフローで消費が増える主な要因は次のとおりです。実数値はモデル・プロジェクト規模・対話の往復回数で大きく変わるため、本書ではレンジは示しません。

| ワークフロー | 消費が増える主因 |
|---|---|
| 企画ワークフロー | 初期ヒアリング、Web 技術調査、企画書の繰り返し改訂 |
| 設計ワークフロー | 11 フェーズの設計書生成、4 つの QA ゲートでのレビュー往復 |
| 実装ワークフロー | 多段階コードレビュー（実装 + 設計準拠 + コード品質 + テスト網羅性 + テスト品質 + テスト実行）の 1 タスクあたり複数往復 |
| 変更ワークフロー | 影響範囲分析、差分設計、差分設計 QA、差分実装、ドキュメント同期 |
| バグ修正ワークフロー | 原因分析、リグレッションテスト設計、動作確認Stepでの既存テスト全実行、ドキュメント同期 |
| リファクタリングワークフロー | セーフティネット記録、動作確認Stepでの既存テスト全実行 |
| 設計逆引きワークフロー | 既存コード全体の解析、各レイヤーの設計書再構成 |

### 8.2 消費を抑えるポイント

- **ワークフローを使い分ける** — 「アプリ全体を作り直す」ではなく、影響範囲が局所的な修正は変更ワークフローやバグ修正ワークフローに切り分けて、必要な工程だけ回す。
- **セッション切替を活用する** — フェーズ完了の節目で `session-handover` メタスキルが状態を書き出します。コンテキストが膨らんだら新セッションに切り替えると、過去の対話履歴を持ち越さずに済みます。
- **対話を簡潔に** — AI Agent からの確認に冗長に答えると、その分のトークンが各フェーズで積み上がります。番号付き選択肢には番号で答えるのが最も効率的です。
- **モデルを選ぶ** — 任せられる範囲はモデルによって変わります。詳細は [01-about.md §5 AI モデル別の任せ度](01-about.md#5-ai-モデル別の任せ度) を参照してください。

## 9. 実例集

aide-powers を実プロジェクトで使ったときの記録欄です。ワークフローの組合せ、所要時間、対話回数、うまくいった点、想定外だった点を蓄積していくことで、利用判断の材料になります。

各事例は以下のフォーマットで追記してください。

```
### 事例 N: タイトル

- プロジェクト規模: （ファイル数 / 機能数 / コード行数など）
- 利用モデル: 
- 採用ワークフロー: 
- 所要時間: 
- 対話ターン数の概算: 
- 結果: 
- うまくいった点: 
- 想定外だった点: 
- 学び・工夫したこと: 
```

実例の追記はユーザーが運用に応じて行います。AI Agent が推測値で埋めることはしません。
