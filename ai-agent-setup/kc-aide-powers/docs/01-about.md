# aide-powers とは

aide-powers を「使うかどうか」を判断するために必要な情報を 1 ページにまとめています。本ページを通読すれば、aide-powers の特徴、他の AI Agent との違い、メリット・デメリット、向き不向きが俯瞰できる構成です。

抽象から具象の順で並べており、§1〜§3 で aide-powers が何であるか（抽象）を、§4〜§8 でその具体的な特徴（違い・モデル別の任せ度・メリット・デメリット・向き不向き）を扱います。§9 はライセンスと動作要件です。

§5 の AI モデル別の任せ度は、実プロジェクトでの検証結果に基づいてユーザーが所感を記入する欄になっています。それ以外は本ページ内で完結します。

---

## 1. 一言で言うと

aide-powers は、AI Agent にドキュメント駆動開発を強制し、「動くけれど期待と違うものができる」状態を防ぐためのフレームワークです。

## 2. 解決したい問題

AI Agent に「アプリを作って」と指示するだけでも、コードは生成されます。しかしその生成物は、しばしばユーザーの期待と乖離します。要件の取りこぼし、設計の薄さ、エラーハンドリングの欠落、エッジケース未考慮、テスト不足。コードは動くけれど、ユーザーが本当に欲しかったものではない、という状態が起きやすいのが実情です。

aide-powers は、要件定義 → 設計 → 実装 → レビューの工程を AI Agent に強制することで、この「動くけれど期待と違う」問題の発生を抑えます。各工程で必ずドキュメントを作成・確認しながら進めるため、AI Agent の判断が暴走したり、ユーザーの意図から外れたりする兆候を段階的に検知できます。

## 3. 主要機能

aide-powers は次の 5 つの機能で AI Agent の振る舞いを規定します。

### 3.1 7 つのワークフロー

開発プロセスを用途別に 7 種類のワークフローに分割し、ユーザー発話に応じて適切なワークフローが自動で選択・起動されます。

| ワークフロー | 用途 |
|---|---|
| 企画ワークフロー | アイデアから企画書を作る |
| 設計ワークフロー | 要件から設計書一式を作る |
| 実装ワークフロー | 設計書からコードを作る |
| 設計逆引きワークフロー | 既存コードから設計書を作る |
| 変更ワークフロー | 既存コードに機能追加・仕様変更を加える |
| リファクタリングワークフロー | 振る舞いを変えずに内部構造を改善する |
| バグ修正ワークフロー | バグを再現・原因分析・修正する |

### 3.2 QA ゲート

設計ワークフローには 4 つの QA ゲートが配置されており、各ゲートで専任の QA レビューアーエージェントが設計書の品質を判定します。基準を満たさない設計書は次フェーズに進めません。

| ゲート | 検証対象 |
|---|---|
| ゲート1 | ユーザー要件 / システム要件 / 開発計画書 / 開発環境定義 |
| ゲート2 | レイヤードアーキテクチャ / GUI 設計 |
| ゲート3 | オブジェクト設計 + ユビキタス言語辞書 |
| ゲート4 | インフラインターフェース設計 / プログラム構成 + 全設計網羅性確認 |

変更・バグ修正・リファクタリングの各ワークフローでは、差分設計書に対しても同等の QA を実施します。

### 3.3 多段階コードレビュー

実装系ワークフロー（実装・変更・バグ修正・リファクタリング）では、1 タスクの実装ごとに 3 つのエージェントが連携してレビューを行います。

- `micro-impl-agent` — 実装・修正・テスト作成・テスト実行を担当
- `design-review-agent` — 設計書との整合性を検証する「外を見る」レビュー
- `code-review-agent` — 命名・型・SOLID・エラーハンドリング等を検証する「中を見る」レビュー

### 3.4 設計書ゲート

実装系ワークフローの入口には設計書ゲートが置かれています。doc-index.md に登録された設計書がすべて完了状態になっていない限り、実装に進めません。「設計なしの実装」を機械的に防ぐ仕組みです。

### 3.5 ハブスキル方式

AI Agent が会話開始時に必ずハブスキル（`using-aide-powers`）を起点として読み込み、ユーザー発話から適切なエントリポイントスキルへ Quick Routing で遷移します。AI Agent が自分でスキルを探し回るのではなく、ハブを起点に確実にルーティングする方式です。これにより、ワークフロー選択のブレを抑えています。

## 4. 他の AI Agent との違い

aide-powers と、AI Agent プラットフォーム単体（Claude Code / Cursor / GitHub Copilot 等）をそのまま使う場合との違いをまとめます。aide-powers が「上に乗せて使うフレームワーク」である以上、ベースとなる AI Agent そのものの能力を否定するものではありません。本節は、単体利用時に AI Agent が個別判断で済ませる領域を、aide-powers が **どこまで規定するか** の差を整理したものです。

| 観点 | AI Agent 単体 | aide-powers |
|---|---|---|
| ドキュメント駆動 | 任意。AI Agent が必要と判断したときだけ作る | 強制。要件 → 設計 → 実装 → レビューの各工程で必ず文書化する |
| 要件定義の構造 | 自然文での箇条書きが中心 | EARS 構文 + MoSCoW 分類で構造化を強制 |
| 設計レイヤーの分割 | AI Agent の判断に依存 | アーキテクチャ → レイヤード → オブジェクト → インフラ IF → プログラム構成の 5 段階を固定 |
| 設計書の品質審査 | 利用者が目視で確認 | 4 つの QA ゲートで専任 QA レビューアーエージェントが APPROVED / REJECTED を判定 |
| 実装後のレビュー | 単一エージェントによる一括レビュー | 設計準拠（外を見る）と コード品質（中を見る）を別エージェントに分離した多段階レビュー |
| 実作業の担当 | 同じ AI Agent が方針決定と実作業を兼ねる | 方針決定はワークフロー本体、実作業は専任サブエージェントに委譲 |
| フェーズ省略 | AI Agent の判断で省略可 | Iron Law として禁止。緊急度・修正の単純さ・時間制約は省略の根拠にならない |
| 設計なしの実装 | 防止策なし | 設計書ゲートで機械的にブロック |
| 変更時の影響範囲分析 | AI Agent の判断で実施 | 変更ワークフローの必須フェーズ |
| バグ修正のリグレッションテスト | 任意 | バグ修正ワークフローで必須化 |
| マルチプラットフォーム対応 | 単一プラットフォームに閉じる | Kiro IDE / Claude Code / Cursor / OpenCode / GitHub Copilot / Gemini CLI / Codex で同一スキル群が動作 |
| チーム間のプロセス均質化 | 利用者の練度に依存 | 同一スキル群を全員が使うため、AI Agent の出力品質が個人差を吸収 |

差の本質は「AI Agent の判断に任せる範囲を、利用者側のプロセス定義で狭めている」ことです。AI Agent 単体の自由度が高いほど、利用者の指示の質と監視の手間に出力品質が依存します。aide-powers はその振れ幅を、ワークフロー・QA ゲート・サブエージェント分業で機械的に押し下げます。

## 5. AI モデル別の任せ度

aide-powers は AI Agent プラットフォームに乗せて使うフレームワークのため、ベースとなる AI モデルの能力で出力品質と任せられる範囲が変わります。実プロジェクトで検証したモデルごとの所感を以下にまとめます。

### 5.1 モデル別の所感

| モデル | 任せ度 | 観察される傾向 |
|---|---|---|
| Claude Opus 4.7 | 高 | 要件定義が正しければ、ほぼ自律的にプログラムが作れる |
| Claude Opus 4.6 | 中 | 一部プロセスを勝手に省略して品質低下が見られる。設計に異常系の考慮が少ない |
| Claude Sonnet 4.6 | 中（やや低） | Opus 4.6 のデメリットがさらに少し大きくなる |
| GPT-4o | 不可 | まともに作れない |

### 5.2 要求分析と設計の重要性

Opus 4.6 / Sonnet 4.6 でも、**要求分析と設計が正しく仕上がっていれば、実装フェーズは自立実装で安定** します。逆に言えば、これらのモデルでは前段（要件定義・設計）の品質が成果物の品質を直接左右するということです。

aide-powers の 4 段階の QA ゲートと多段階コードレビューは、モデル単体の品質低下を吸収するための機構でもあります。Opus 4.7 ほどの自律性が出ないモデルでも、ワークフローの強制と QA レビューを組み合わせることで、最終成果物の品質を一定水準に保てます。

## 6. メリット

aide-powers を採用すると、AI Agent 開発で次の効果が得られます。

### 6.1 期待と一致した成果物が得られやすくなる

要件 → 設計 → 実装 → レビューを工程化し、各工程で利用者の合意を取ります。意図と乖離した方向に AI Agent が走り出した場合、合意フェーズで止まる構造です。「動くけれど期待と違う」が出にくくなります。

### 6.2 設計書という形で意図が残る

最終成果物がコードだけでなく設計書一式（ユーザー要件・システム要件・アーキテクチャ・GUI・ユースケース・レイヤード・オブジェクト・インフラ IF・プログラム構成）として残ります。後続の保守・引き継ぎ時に「なぜこの実装になっているか」を辿れます。コメントやコード読解で意図を推測する手間が減ります。

### 6.3 レビュー観点が抜けにくい

実装レビューを「設計準拠（外を見る）」と「コード品質（中を見る）」に分離し、別エージェントが担当します。観点が混在しないため、片方の指摘がもう片方を打ち消す現象が起きにくくなります。テストレビュー（網羅性 / 品質）とテスト実行も独立工程です。

### 6.4 仕様変更の影響範囲が把握しやすい

変更ワークフローは差分設計書（before → after）を作成してから実装に進みます。何を変えると何に波及するかが、コードを読む前に文書化されます。レビューや承認の判断材料が揃うため、変更を入れる前に意思決定が完結します。

### 6.5 リファクタリングで外部振る舞いを壊さない

リファクタリングワークフローは入口で既存テストの PASS / FAIL / スキップ数を **セーフティネット基準** として記録します。各タスク完了ごとにテストを再実行して基準値と比較するため、外部振る舞いの変化が機械的に検出されます。

### 6.6 バグ修正時にリグレッションテストが必ず残る

バグ修正ワークフローは差分設計書にリグレッションテスト（バグ再現テスト）の設計を必ず含めます。修正と同時に再発防止が成果物として組み込まれるため、同じバグが再発したときに気付ける状態でリリースできます。

### 6.7 チーム展開時の品質均質化

利用エンジニアが全員同じスキル群（ハブスキル、ワークフロー、共通スキル、共通エージェント）を使うため、AI Agent 経由で出てくる成果物の品質が個人差を吸収して平準化します。新しいメンバーがチームに入っても、aide-powers をインストールするだけで同じ手順を踏めます。

### 6.8 マルチプラットフォームで同一成果

7 種類のプラットフォーム（Kiro IDE / Claude Code / Cursor / OpenCode / GitHub Copilot CLI + VSCode / Gemini CLI / Codex）で同じスキル群が動作します。プラットフォームを切り替えても、ワークフローと成果物の構造は変わりません。

## 7. デメリット

aide-powers の採用には次のコスト・制約が伴います。

### 7.1 トークン消費が増える

要件定義・設計・QA レビュー・多段階コードレビュー・ドキュメント同期の各工程で AI Agent が動くため、AI Agent 単体に「アプリを作って」と指示する場合と比べてトークン消費は増えます。具体的な増加量はプロジェクト規模・モデル・ワークフローの組合せに依存します。

### 7.2 1 タスクあたりの完了時間が伸びる

工程数が増えるため、1 つの機能を実装し終えるまでの所要時間は AI Agent 単体利用よりも長くなります。各 QA ゲート・各レビューステージで AI Agent と利用者の合意確認が入るため、対話のターン数も増えます。

### 7.3 学習コスト

利用エンジニアは 7 つのワークフローと、各ワークフローのフェーズ構造、QA ゲート・設計書ゲートの存在を把握する必要があります。基本的にハブスキルが Quick Routing で自動選択するため日常利用では意識不要ですが、トラブル時や特殊ケースで自分でワークフローを選びたい場合に学習が必要になります。

### 7.4 小規模・短命なコードに対する過剰品質感

使い捨てスクリプト、1 ファイルで完結する単純なツール、検証用プロトタイプなど、もともと設計書もテストも不要なケースでは、aide-powers の工程は重く感じられます。本来であれば数十秒で終わる作業に対して、要件 → 設計 → 実装 → レビューの工程を踏むため、コストパフォーマンスが見合わない場合があります。

### 7.5 フェーズ省略が許容されない

aide-powers のフェーズ省略は Iron Law として禁止されており、AI Agent からユーザーへの省略提案も禁止されています。緊急修正・小規模変更でも同じワークフローを通します。柔軟性を捨てて品質均質化を取った設計です。

### 7.6 サブエージェント並列実行に伴うコンテキスト管理の煩雑さ

ワークフローは方針決定をワークフロー本体、実作業をサブエージェントに委譲する構造です。並列実行されるサブエージェント間で出力をどう統合するか、各サブエージェントへ渡すコンテキストをどう絞り込むかは、ワークフロー側のスキルが管理します。プロセス自体が複雑になるため、振る舞いの不具合が起きたときの原因切り分けは AI Agent 単体利用よりも難しくなります。

## 8. 向き不向き

aide-powers が効果を発揮しやすいプロジェクトと、コストが見合わないプロジェクトを整理します。

### 8.1 向くプロジェクト

- **仕様が複雑で、要件取りこぼしのリスクが大きい**
  EARS 構文 + MoSCoW 分類で要件を構造化し、QA ゲートでレビューするため、ヒアリング段階での漏れに気付きやすい構造です。
- **長期保守を前提としており、設計書が後で必要になる**
  実装と同時に設計書一式が成果物として残るため、半年・1 年後の保守担当者がコード理解の起点を持てます。
- **複数人で開発・引き継ぎを行う**
  プロセスが固定されているため、個人差が出にくく、引き継ぎ時の説明コストが下がります。
- **品質要件が高い（業務システム / 本番運用前提）**
  4 段階の QA ゲート、設計準拠レビュー + コード品質レビューの分離、リグレッションテスト必須化など、品質担保のための仕組みが組み込み済みです。
- **チーム間で AI Agent 利用の練度差が大きい**
  ハブスキル経由でプロセスが統一されるため、練度の低いメンバーでも一定品質の成果物が出ます。
- **既存コードに対して継続的に変更・バグ修正を入れる必要がある**
  変更・バグ修正・リファクタリングの 3 ワークフローは差分設計を介して既存設計書を最新化するため、コードと設計書の乖離が抑えられます。

### 8.2 向かないプロジェクト

- **使い捨ての実験コード・プロトタイプ**
  動けばよく、保守も引き継ぎもしないコードに対しては、設計書一式の作成コストが目的に対して過剰です。
- **1 ファイルで完結する単純なスクリプト**
  数十行で終わる処理に対してワークフロー全体を回すと、AI Agent 単体に直接書かせる方が早く終わります。
- **厳しいトークン予算の制約下にある**
  工程数が多い分トークンを使います。予算上限の運用が必要なら、対象範囲を絞るか、AI Agent 単体利用と aide-powers を案件ごとに使い分ける方が現実的です。
- **「とりあえず動くもの」を最短で出したいフェーズ**
  ハッカソン、PoC の初期、デモ準備など、設計書品質よりスピードが優先される場面では、ワークフローの工程数が足枷になります。

迷ったら判断軸はシンプルです。**そのコードを 3 か月後に他人が触る可能性があるか**。あるなら aide-powers が効きます。ないなら AI Agent 単体利用で十分です。

## 9. ライセンス・動作要件

### ライセンス

MIT ライセンスで提供しています。

### 動作要件

- **Git** — リポジトリの取得とセットアップに必要です。Windows の場合は Git for Windows（bash 同梱）を使用します。
- **AI Agent プラットフォーム** — 以下のいずれかが必要です。
  - Claude Code
  - Kiro IDE / Kiro CLI
  - Cursor
  - OpenCode
  - GitHub Copilot（CLI / VSCode 拡張）
  - Gemini CLI
  - Codex
- **Node.js** — visual-companion 機能（モックアップ・図表のブラウザ表示）を使う場合のみ必要です。使わない場合は不要です。

インストール手順は [02-getting-started.md](./02-getting-started.md)、日常的な使い方は [03-usage.md](./03-usage.md) を参照してください。
