# よくある質問（FAQ）

aide-powers を利用する際に、利用エンジニアが疑問に持ちやすいポイントを Q&A 形式でまとめます。

機能事実から確実に答えられる Q&A と、実運用に関する Q&A の 2 構成です。実運用に関する Q&A は実プロジェクトで蓄積した事例の参照先（[03-usage.md §8 トークン消費の目安](03-usage.md#8-トークン消費の目安) / [03-usage.md §9 実例集](03-usage.md#9-実例集) / [05-troubleshooting.md](05-troubleshooting.md) など）にリンクする形でまとめています。

## 動作の基本

### Q: aide-powers をインストールしたら、毎回ハブスキルから始まるのですか？

はい。会話開始時にハブスキル（`using-aide-powers`）が起動し、AI Agent はそこからワークフロー選択を行う仕組みです。これを「ハブスキル方式」と呼びます。

各プラットフォームのブートストラップファイル（Kiro IDE の `steering/aide-powers-bootstrap.md`、Copilot の `aide-powers.instructions.md`、Codex / OpenCode の `AGENTS.md` 等）が、AI Agent をハブスキルに誘導するように構成されています。

### Q: AI Agent がスキルを読まずに勝手に動くことはないですか？

`rules-distribute` スキルが、aide-powers のグローバルルールをプラットフォームのルールファイル機構（Kiro の `.kiro/steering/`、Claude Code の `.claude/rules/`、Cursor の `.cursor/rules/`、Copilot の `.github/instructions/` 等）に直接配置します。

配置されたルールはプラットフォームによって自動でコンテキストに注入されるため、AI Agent がスキルを明示的に読まなくてもグローバルルールが強制適用されます。

### Q: 同じプロジェクトを別のプラットフォームから開いても動きますか？

動きます。ハブスキルの初期アクションでワークスペース内の `.aide/references/` に全プラットフォーム分のツールマップ（`kiro-ide-tools.md` / `claude-code` 系 / `copilot-tools.md` / `gemini-tools.md` / `codex-tools.md` 等）がコピーされます。

別セッションで別プラットフォームから同じワークスペースを開いても、対応するツールマップを参照して Claude Code 標準ツール名を自プラットフォームのツール名に変換できます。

## ワークフローの進め方

### Q: ワークフローを途中でやめたいときはどうすればよいですか？

途中で別ワークフローに切り替えることはできません。フェーズ進行中に別の問題を発見した場合は、`.aide/specs/{feature_name}/pending-issues.md` に記録した上で、現在のワークフローを最後まで完遂してから次の対応に移る運用です（グローバルルール §3-3）。

これは、フェーズ途中で別ワークフローを起動すると成果物の整合性が崩れるためです。

### Q: フェーズ省略はできますか？

できません。Iron Law です。

緊急度・修正の単純さ・時間的制約・コンテキストの大きさ、いかなる理由もフェーズ省略の根拠になりません（グローバルルール §3-1）。量が多い場合は `task-orchestration` スキルで並列処理し、正式な手順を全件に適用します。AI Agent からユーザーへフェーズ省略を提案することも禁止されています。

### Q: 設計書がないコードに変更ワークフローを使うとどうなりますか？

設計書ゲート（`design-gate` 共通スキル）で FAIL となり、先に進めません。設計書が存在しない場合は、設計逆引きワークフロー（エントリポイント: `fs-reverse-phase1-program`）で既存コードから設計書を生成してから、変更ワークフローに戻る流れになります。

詳細は [02-getting-started.md](02-getting-started.md) と [03-usage.md](03-usage.md) を参照してください。

## 実装・テスト・品質

### Q: テストコードはどう生成されますか？

実装ワークフローの多段階コードレビューの一環で、`micro-impl-agent` がテストコードを生成します。`unittest` 形式で、モック禁止・境界値・異常系を含む方針です。

生成されたテストコードはステージ2（テスト網羅性レビュー + テスト品質レビュー）とステージ3（テスト実行）でレビュー・実行されます。テスト方針は `impl-coding-standards` スキルで定義されています。

### Q: 既存コードが汚くてもリファクタリングワークフローで綺麗になりますか？

外部振る舞いを変えない範囲で内部構造を改善する設計です。リファクタリングワークフロー（エントリポイント: `fs-refactoring-phase1-status`）はセーフティネットとして既存テストの保持を機械的に確認し、外部振る舞いの変化を抑えます。

仕様変更を伴う改善は変更ワークフロー（`fs-change-phase1-analysis`）で扱います。

## 拡張・チーム展開

### Q: aide-powers のスキルを自分でカスタマイズできますか？

開発引き継ぎ者向けの手順が用意されています。フェーズスキル・共通スキル・カスタムエージェントの追加・修正手順は `docs-dev/03-how-to/` 配下のドキュメントを参照してください（`add-phase-skill.md` / `add-common-skill.md` / `add-agent.md` / `add-workflow.md` / `release.md`）。

利用エンジニアは、まず提供されているスキル群をそのまま使う運用を推奨します。

### Q: チームで使う場合の共有方法は？

ローカルインストール（`setup-local.bat` / `setup-local.sh`）を使い、プロジェクトリポジトリに aide-powers を組み込んでコミットすることで共有できます。

```bash
cd ~/aide-powers
./setup-local.sh /path/to/your/project
```

リポジトリ単位で aide-powers のバージョンを固定したいチームに向いています。グローバルインストール（`setup.bat` / `setup.sh`）はユーザーのホーム配下に配置し、全プロジェクトから利用する形態です。詳細は [02-getting-started.md](02-getting-started.md) を参照してください。

## 実運用に関する Q&A

### Q: トークン消費はどれくらいですか？

AI Agent 単体に「アプリを作って」と指示する場合と比べて増えます。要件定義・設計（11 フェーズ + 4 QA ゲート）・多段階コードレビュー（実装 + 設計準拠 + コード品質 + テスト網羅性 + テスト品質 + テスト実行）・ドキュメント同期で AI Agent が動くためです。

具体的な数値はモデル・プロジェクト規模・対話の往復回数で大きく変わるため、本書では一律の数値は示していません。実測値の蓄積欄は [03-usage.md §8.3](03-usage.md#83-実測値について) に用意しています。

消費を抑えるポイントは [03-usage.md §8.2](03-usage.md#82-消費を抑えるポイント) を参照してください。要点は「ワークフローを使い分ける（変更 / バグ修正で局所化）」「セッション切替を活用する」「番号付き選択肢には番号で答える」「モデルを使い分ける」の 4 つです。

### Q: どのモデルで使うのが推奨ですか？

実検証に基づく推奨は [01-about.md §5 AI モデル別の任せ度](01-about.md#5-ai-モデル別の任せ度) を参照してください。

一般論としては次の傾向があります。

- 要件抽出・設計フェーズはモデルの推論能力が品質に直結するため、上位モデルを使うほど成果物の質が上がります。
- 実装フェーズはサブエージェント並列実行のためトークン消費が増えやすく、コストとのバランスでモデルを使い分ける運用が現実的です。
- 低コストモデルほどスキル呼び出しを省略する傾向があり、aide-powers のようにスキル経由の動作を前提とするフレームワークでは、モデルが下がるほど挙動が崩れやすくなります。

### Q: Cursor 単体や Copilot 単体と何が違いますか？

差の本質は「AI Agent の判断に任せる範囲を、利用者側のプロセス定義で狭めている」点です。詳細な対比表は [01-about.md §4 他の AI Agent との違い](01-about.md#4-他の-ai-agent-との違い) を参照してください。

要点を抜粋すると次のとおりです。

- ドキュメント駆動を **強制** する（任意ではない）
- 要件は EARS 構文 + MoSCoW 分類で構造化を強制
- 設計は 5 段階レイヤー（アーキテクチャ → レイヤード → オブジェクト → インフラ IF → プログラム構成）に固定
- 設計品質は 4 段階の QA ゲートで専任エージェントが APPROVED / REJECTED 判定
- 実装後レビューは設計準拠（外を見る）と コード品質（中を見る）を別エージェントに分離
- フェーズ省略は Iron Law として禁止
- 同一スキル群がマルチプラットフォーム（Kiro IDE / Claude Code / Cursor / OpenCode / GitHub Copilot / Gemini CLI / Codex）で動作

Cursor / Copilot 単体の自由度の高さが必要な場面（PoC、小規模スクリプト等）では aide-powers を使わない選択もあります。判断軸は [01-about.md §8 向き不向き](01-about.md#8-向き不向き) を参照してください。

### Q: 1 ワークフロー完了までどれくらい時間がかかりますか？

AI Agent 単体利用と比べると長くなります。各 QA ゲート・各レビューステージで AI Agent と利用者の合意確認が入るため、対話のターン数も増えるためです。

実測の所要時間と対話ターン数は、プロジェクト規模・モデル・利用者の意思決定速度で大きく変わるため、本書では一律の数値は示していません。実例の蓄積欄は [03-usage.md §9 実例集](03-usage.md#9-実例集) に用意しています。

### Q: 実際の成功事例はありますか？

事例の蓄積欄は [03-usage.md §9 実例集](03-usage.md#9-実例集) に用意しています。プロジェクト規模・利用モデル・採用ワークフロー・所要時間・うまくいった点を運用しながら追記する形になっています。

### Q: 失敗事例（嵌まりやすいポイント）はありますか？

機能的に再発しやすい嵌まりポイントは [05-troubleshooting.md](05-troubleshooting.md) に「症状 / 原因 / 対処」の 3 点セットでまとめています。代表例は次のとおりです。

- インストール後にスキルが認識されない（Claude Code の手動コピーで SessionStart hook が登録されないケース）
- VSCode GitHub Copilot で hooks が動かない（settings.json 未設定）
- Codex / OpenCode で AGENTS.md の参照行が反映されない（rules-distribute の global モード未実行）
- 古いワークフロー構造が残っている（フラット化前のディレクトリ構造の残骸）
- ワークフローが途中で別のワークフローに切り替わる（AI Agent がグローバルルール §3-3 を破るケース）
- 設計書ゲート FAIL でワークフローが進まない（設計書欠落）

実運用で気付いた嵌まりポイントは [05-troubleshooting.md §11 実運用で発生したトラブル](05-troubleshooting.md#11-実運用で発生したトラブル) に追記する形になっています。

### Q: 学習コスト（チーム導入時）はどれくらいですか？

利用エンジニアの場合、日常的にハブスキルが Quick Routing で自動的に適切なワークフローを選ぶため、ワークフロー名・フェーズ番号・QA ゲートの存在を覚える必要は基本的にありません。AI Agent に普通に話しかければ動きます。

ただし次の場面では学習が発生します。

- トラブル対応で自分でワークフローを切り替えたい場合 → [03-usage.md §2 ワークフロー選択](03-usage.md#2-ワークフロー選択quick-routing) を読む
- インストールでつまずいた場合 → [02-getting-started.md](02-getting-started.md) と [05-troubleshooting.md](05-troubleshooting.md) を読む
- 設計書の読み方を覚えたい場合 → 該当プロジェクトの設計書一式（ユーザー要件・システム要件・アーキテクチャ・GUI・レイヤード・オブジェクト・インフラ IF・プログラム構成）を読む

aide-powers 自体をカスタマイズする立場（開発引き継ぎ者）の学習コストは別物です。`docs-dev/` 配下のドキュメントを読む必要があり、利用エンジニアよりも大きく増えます。チームの全員が開発引き継ぎ者になる必要はないため、利用エンジニアと開発引き継ぎ者は分けて運用するのが現実的です。
