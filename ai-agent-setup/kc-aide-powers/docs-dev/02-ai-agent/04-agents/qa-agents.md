# QAレビューアーエージェント詳細

設計書 / 差分設計書の品質を判定する 5 つのエージェント。設計ワークフローの 4ゲート、
および差分系ワークフロー（変更 / バグ修正 / リファクタリング）の差分設計 QA で動く。
呼び分けは [共通スキル `design-qa-dispatch`](../03-common-skills/infrastructure.md#design-qa-dispatch) が担う。

## 共通の判定基準

| 判定 | 条件 |
|---|---|
| `APPROVED` | FAIL 0 件 かつ WARNING 0 件 |
| `REJECTED` | FAIL 1 件以上、または WARNING 1 件以上 |

WARNING も「修正必須」として扱う。REJECTED 後の修正には**再 QA を必ず実施する**（設計ワークフローの
Iron Law）。

QAレビューアーエージェントは指摘の修正自体を行わない（呼び出し元の責務）。出力フォーマットは全エージェント共通で、
検証結果一覧テーブル / FAIL 項目の修正指示テーブル / WARNING 項目テーブル / 総合判定 を返す。

## requirements-qa-agent

### 役割

要件定義QAレビューアーエージェント。設計ワークフロー **ゲート1** で呼ばれる。
変更 / バグ修正ワークフローの差分設計 QA で要件レイヤーに影響がある場合にも呼ばれる。

### 入力

- レビュー対象: `user-requirements.md` / `system-requirements.md` / `development-plan.md` / `dev-environment.md`

### 主な検証観点

- 要件の網羅性（Must 要件 → システム要件の対応）
- ユーザー要件とシステム要件の矛盾
- EARS 構文準拠（Ubiquitous / Event-driven / State-driven / Unwanted / Optional）
- MoSCoW 分類の妥当性
- エラーハンドリング方針（分類 / 伝播ルール / ログ方針の 3 要素）
- 開発環境定義の完全性（言語バージョン / 仮想環境パス / 依存管理 / テスト実行コマンド）
- ユーザー要件の作成ルール（目的と手段の分離、抽象表現、否定された手段の不記載）
- 開発計画書の整合性
- 例外・ルール回避の検出（設計原則を「不要」「適用対象外」等で無効化していないか）

### 行動規範

- 基準を満たさない設計は絶対に承認しない。
- 修正指示は「何を」「どう直すか」を明記する。
- 検証は成果物のテキストを実際に読んで行う（推測判定禁止）。

## architecture-qa-agent

### 役割

アーキテクチャQAレビューアーエージェント。設計ワークフロー **ゲート2** で呼ばれる。
変更ワークフローの差分設計 QA でアーキテクチャに影響がある場合にも呼ばれる。

### 入力

- レビュー対象: `gui-design.md` / `layered-architecture.md`
- 前提成果物: `user-requirements.md` / `system-requirements.md`

### 主な検証観点

- GUI 設計の要件充足（Must 要件と画面・UI 要素の対応）
- DDD 採用判断とアーキテクチャパターン選択の妥当性（論理的根拠の有無）
- レイヤー間依存方向（DDD 採用時はドメイン層の独立性、各レイヤーの責務分離）
- ドメイン層の独立性（外部ライブラリへの直接参照禁止）
- 依存性逆転の適用（インフラがドメインのインターフェースを実装する構造）
- テスト用ダミー実装方針（DI 切り替え方式の定義）
- ユビキタス言語のトレーサビリティ（DDD 採用時）
- ドメインモデル貧血症を防ぐ設計方針（DDD 採用時）
- 集約設計方針（DDD 採用時、境界の決め方・ID 参照ルール）
- ユビキタス言語辞書の存在確認（DDD 採用時）
- 例外・ルール回避の検出

### 行動規範

- DDD 不採用の場合、ドメイン層固有・DDD 固有の検証項目（独立性・ユビキタス言語等）はスキップする。
- 設計原則の例外・回避を検出した場合は無条件で FAIL とする。

## object-design-qa-agent

### 役割

オブジェクト設計QAレビューアーエージェント。設計ワークフロー **ゲート3** で呼ばれる。
変更ワークフロー / リファクタリングワークフローの差分設計 QA でオブジェクト設計に影響がある場合にも呼ばれる。

### 入力

- レビュー対象: `object-design-domain.md` / `object-design-application.md` /
  `object-design-infrastructure.md` / `object-design-presentation.md` / `ubiquitous-language.md`
- 前提成果物: `user-requirements.md` / `system-requirements.md` / `gui-design.md` / `layered-architecture.md`

### 主な検証観点（A〜I）

- **A. ドメイン層への技術浸食**: DB 型 / ORM 制約 / ライブラリ依存の混入禁止
- **B. レイヤー間依存違反**: 具象クラスへの直接依存禁止、インターフェース経由を強制
- **C. ドメインモデル貧血症**: エンティティ・値オブジェクトに振る舞いがあるか / ドメインサービスの肥大化検出
- **D. テスト容易性**: ドメイン層がモック・スタブなしでテスト可能か / インフラ層のテスト用ダミー実装の有無
- **E. ユビキタス言語の整合性**: 要件の用語と設計の命名の 1 対 1 対応 / `~Data` `~Manager` 等の技術命名混入禁止
- **F. SOLID 原則**: SRP（使う人の目的が 1 つに限定されているか） / OCP / LSP / ISP / DIP
- **G. 集約と整合性の境界**: 集約のサイズ / 集約間の ID 参照 / 集約ルート経由アクセス
- **H. オブジェクト定義の品質**: 役割の具体性 / 属性のまとまり / 不変条件の定義
- **I. 例外・ルール回避の検出**

### 行動規範

- DDD 不採用の場合、C / E / G はスキップする。
- SRP 判定は「使う人の目的」で行い、メソッド数やコード量で判定しない。
- 設計原則の例外・回避を検出した場合は無条件で FAIL とする。

## final-design-qa-agent

### 役割

最終設計QAレビューアーエージェント。設計ワークフロー **ゲート4** で呼ばれる。
変更ワークフローの差分設計 QA でインフラ IF / プログラム構成に影響がある場合にも呼ばれる。

### 入力

- レビュー対象: `infra-interface-design.md` / `program-structure.md`
- 前提成果物: `object-design-*.md` / `layered-architecture.md` / `user-requirements.md` /
  `gui-design.md` / `system-architecture.md`

### 主な検証観点

- インフラ IF 設計の整合性（オブジェクト設計のリポジトリインターフェースとの対応）
- **プログラム構成の網羅性**: オブジェクト設計の全クラスをファイル配置と 1 件ずつ突き合わせる（抜き取り禁止）
- import ルールの定義（許可 / 禁止パスが具体的に明記され、レイヤー依存方向と整合）
- ファイル命名規則の一貫性
- 例外・ルール回避の検出（6 パターンを文字列ではなく意味で判定）
- **設計網羅性確認**: ユーザー要件 → オブジェクト設計までトレースできるか（ゲート4の最後の砦）

### 行動規範

- 全クラスのファイル配置漏れを 1 件でも検出すれば FAIL（抜き取り禁止）。
- 設計原則の例外・回避を検出した場合は無条件で FAIL とする。

## delta-design-qa-agent

### 役割

差分設計QAレビューアーエージェント。差分系ワークフロー（変更 / バグ修正 / リファクタリング）の
差分設計 QA で **常に呼ばれる**。差分が触る領域の専門QAレビューアーエージェント（要件 / アーキ / オブジェクト /
最終）と組み合わせて使う。

### 入力

- レビュー対象: `delta-design.md` / `fix-design.md` / `refactoring-design.md` のいずれか
- 関連ファイル: `approach.md` / `fix-plan.md` / `refactoring-plan.md`
- 既存設計書群（差分の前提となる設計書すべて）

### 主な検証観点

- **before → after の妥当性**: 「変更前」記述が既存設計書の実際の内容と一致するか
- **影響範囲外への変更検出**: 影響分析で特定された範囲を逸脱していないか
- **既存設計書との矛盾チェック**: 名前衝突 / インターフェース利用箇所への影響漏れ
- **差分設計の完全性**: 必要な変更が全て差分設計書に含まれているか
- **レイヤー依存方向の整合性**
- 差分設計書の記述品質（曖昧表現の検出）
- **不変条件の保全**: 既存設計書の不変条件が維持されるか
- **OCP 原則の準拠**: 既存の拡張ポイント活用 vs 既存コード直接変更
- **「更新が必要な設計資料」セクションの整合性**: 必要なのに欠落していれば FAIL
- 例外・ルール回避の検出

### 行動規範

- before → after チェックは差分設計書の記述を鵜呑みにせず、既存設計書の実際の内容と必ず突き合わせる。
- 設計原則の例外・回避を検出した場合は無条件で FAIL とする。
- 各設計領域の専門的な正しさは担当外（`requirements-qa-agent` 等が並行して判定する）。

## manual-test-review-agent（試験書品質レビューアー、参考）

> 本エージェントは上記5エージェントとは判定文字列が異なる（`APPROVED` / `NEEDS_FIX`）ため、
> 厳密な「QAレビューアーエージェント」カテゴリの外側だが、動作確認試験書の品質を判定する
> レビューアーとして密接に関連するため本ファイルに併記する。

### 役割

動作確認試験書 品質レビューアーエージェント。4WF（実装 / バグ修正 / 変更 / リファクタリング）の
動作確認Stepで生成された試験書が「ユーザー視点で全動作を検証しているか」をレビューする。
試験書作成直後・試験実行前の品質ゲートとして機能し、PASSするまで試験実行に進めない。

### 入力

- `wf_type`（`impl` / `bugfix` / `change` / `refactoring`）
- 試験書パス（`testing/test-{機能名}-test-plan.md`）
- WF固有入力ファイル（usecase-analysis.md / bug-report.md・fix-plan.md / change-requirements.md / refactoring-plan.md）

### 主な検証観点

- 共通4観点: ユーザー操作シナリオか／ユーザー視点の網羅性（質的）／目視可能な期待結果か／内部視点混入検出
- WF別基準: `wf_type` に応じた追加基準（再現手順の未再現確認、受入基準の検証等）

### 判定

- `APPROVED`（指摘0件）/ `NEEDS_FIX`（指摘1件以上）

### test-coverage-audit-agent との責務境界

| 軸 | test-coverage-audit-agent | manual-test-review-agent |
|---|---|---|
| 主眼 | 量的網羅性（要件ID×試験項目の1対1照合） | 質的視点（ユーザー視点・操作シナリオ・目視可能な期待結果） |
| 実行タイミング | 実装WF最終チェック | 4WFの動作確認Step（試験書作成直後） |
| 対象WF | 実装WFのみ | 実装・バグ修正・変更・リファクタリングの4WF |
