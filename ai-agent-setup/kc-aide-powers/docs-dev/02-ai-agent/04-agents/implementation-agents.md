# 実装系エージェント詳細

実装ループ（多段階コードレビュー）の実作業を担うホワイトリスト3エージェントの詳細をまとめる。
パイプラインの呼び出し関係は [共通スキル `multi-stage-code-review`](../03-common-skills/impl.md#multi-stage-code-review) を参照。

## micro-impl-agent

### 役割

マイクロ実装エージェント（実装専任）。1 つの実装タスクを受け取り、実装コードとテストコードを書く。
レビューは担当外（`design-review-agent` と `code-review-agent` が担当）。
レビュー指摘に基づく修正もこのエージェントが行う。

### 入力

呼び出し元から以下を受け取る:

- タスク番号とタスク内容
- 対象ファイルパス / テストファイルパス
- 設計書ファイルパス（読むべき設計書のパス。1 つ以上）
- 設計参照セクション（設計書内の該当セクション番号・名前）
- テスト観点（設計書から抽出したテストケース一覧）
- 依存先（既に実装済みのクラス / モジュールのファイルパス）
- 開発環境情報（Python バージョン、venv パス、依存管理方針等）
- 実行モード（次節）

### モード（5 種）

| モード | 用途 | 出力 |
|---|---|---|
| `implement` | 新規実装。設計書を読み込み、規約に従って実装コードを書く。動作確認試験書を更新する | 実装ファイル |
| `fix` | レビュー指摘修正。受け取った指摘に基づき実装コードを修正する | 修正済み実装ファイル + 修正件数報告 |
| `write_test` | テスト作成。設計書のテスト観点に基づき unittest 形式のテストを書く（モック禁止 / 境界値・異常系含む） | テストファイル |
| `fix_test` | テストレビュー指摘修正。指摘に基づきテストコードを修正する | 修正済みテストファイル + 修正件数報告 |
| `run_test` | テスト実行。ユニットテストを実行し、結果を報告する。失敗時は実装またはテストを修正。既存テスト全実行（リグレッションテスト）は動作確認Stepで1回実施する設計に統一されている | テスト結果報告 |

`implement` モードには特殊形態として **親タスク完了チェック** があり、全サブタスク完了後に
設計書セクション全体と実装コードを照合して漏れを検出する。

### 出力

- 実装コード / テストコード（指定パスへ書き込み）
- 各モードの完了報告（タスク番号、ファイルパス、ステータス、修正内容等）

### ステータス運用

各モード完了時に必ず以下のいずれかを返す。詳細は [overview](./00-overview.md#ステータス-4-種) を参照。

- `DONE`
- `DONE_WITH_CONCERNS`
- `NEEDS_CONTEXT`
- `BLOCKED`

### 行動規範

1. 設計書を読まずに実装を始めない（全モードの前提条件）。
2. 1 回の呼び出しで変更するファイルは 1 つだけ。複数ファイルが必要なら報告する。
3. テストが通るまで完了としない（`run_test` で全パスを確認）。
4. 設計と実装の乖離を発見したら自分で設計を変更せず報告する。
5. レビューは行わない。品質判断は `code-review-agent` / `design-review-agent` に委ねる。
6. ダミー実装の原則禁止。ライブラリが必要なら自分でインストールする。
7. 開発環境情報が渡されていない場合は、実装を開始せず「開発環境情報が不足しています」と報告する。
8. テストファイルが「なし」と指定されている場合、`write_test` / `fix_test` / `run_test` はスキップして報告する。
9. 50 行超のファイルは分割書き込み（先頭 50 行 Write + 残り Append）。

### REQUIRED SUB-SKILL

`impl-coding-standards`（粒度ルール / コーディング規約 / 動作確認試験書更新 /
親タスク完了チェック / 5 モード報告テンプレート / テスト関連ルール / テスト実行ルール）。

## design-review-agent

### 役割

設計準拠レビューエージェント（「外を見る」レビュー担当）。
実装コードが設計書に準拠しているか、レイヤー間の import ルールが守られているかを検証する。
内部ロジック意図検証を最優先とし、クラス名・シグネチャが一致していても中身が空・スタブ・別ロジックの
ケースを必ず検出する。

タスク種別（`normal` / `bugfix` / `change` / `refactoring`）に応じた追加検証を行う。

### 入力

- 対象ファイルパス（実装コード or テストコード）
- 設計書ファイルパス（1 つ以上）と設計参照セクション
- レビューモード（`implementation` または `test`）
- タスク種別（`normal` / `bugfix` / `change` / `refactoring`）
- バグ修正タスクの場合: `fix-plan.md` / `fix-design.md` のパス
- 変更タスクの場合: `delta-design.md` のパス
- 過去不具合修正の保持検証用: `bugfix/` ディレクトリパス

### モード

| モード | 用途 |
|---|---|
| `implementation` | 実装コードの設計準拠レビュー。`import-review` 共通スキルを必ず読み込み import 違反を検証 |
| `test` | テストコードの網羅性レビュー。`test-review` 共通スキルを `coverage` モードで読み込む |

### 出力

差分一覧テーブル（ファイル / クラス / 項目 / 設計書 / 実装 / 種別）と判定。

| 判定 | 条件 |
|---|---|
| `PASS` | 差分 0 件 |
| `FAIL` | 差分 1 件以上（種別未確定。明らかな実装誤りは即 fix 指示） |

差分の種別: ロジック未修正 / 対策未反映 / 過去不具合修正の喪失 /
クラス欠落 / メソッド欠落 / シグネチャ不一致 / 不変条件欠落 / 処理フロー逸脱 / 未定義の追加。
乖離種別（実装誤り / 設計漏れ）の確定は、実装完了または依存ブロック時にユーザーと行う。

PASS 時は 1 行で出力（`判定: PASS（検査クラス数: N, 差分: 0）`）。FAIL 時のみ詳細テーブルを出力する。

### ステータス運用

判定そのものは `PASS` / `FAIL` を返す（`micro-impl-agent` の 4 ステータスとは別軸）。
設計漏れと確定された場合は `design-sync` 共通スキルに設計書更新を依頼する。

### 行動規範

1. 内部ロジック意図検証を最優先で実施する。クラス名・シグネチャの一致だけで PASS としない。
2. 「設計書のコード例はあくまで参考」を理由に内部ロジック検証をスキップしない。特にバグ修正・変更タスク。
3. 設計書を必ず読んでから照合する。
4. コード内部の品質には言及しない（`code-review-agent` の担当）。
5. 判定は差分が 1 件でもあれば FAIL。種別確定はレビュー中に行わない。
6. 過去不具合修正の保持検証はテスト結果で判断せず、`fix-design.md` と実装コードの目視確認で判断する。
7. レビュー結果の修正は行わない（`micro-impl-agent` に委ねる）。
8. ダミー実装の検出は必須。`pass` のみ・スタブ・モック代替は FAIL。
9. レビュースキルを読み込んでからレビューを実行する（`import-review` または `test-review`）。

### REQUIRED SUB-SKILL

- mode: implementation → `import-review`
- mode: test → `test-review`（coverage モード）

## code-review-agent

### 役割

コード品質レビューエージェント（「中を見る」レビュー担当）。
コード自体の品質（命名 / 型ヒント / SOLID / エラーハンドリング / テスト方針）を検証する。
設計書整合性や import 方向性は担当外。

### 入力

- 対象ファイルパス（実装コード or テストコード）
- 設計書ファイルパス（エラーハンドリングの `Raises` セクション確認用）
- レビューモード（`implementation` または `test`）

### モード

| モード | 用途 |
|---|---|
| `implementation` | 実装コードの品質レビュー。`code-quality-review` + `error-handling-review` を必ず読み込む |
| `test` | テストコードの方針準拠レビュー。`test-review` を `policy` モードで読み込む |

### 出力

指摘一覧テーブル（ファイル / 種別 / 行 / 内容 / 重要度）と判定。

| 判定 | 条件 |
|---|---|
| `APPROVED` | ERROR 0 件 かつ WARNING 0 件 |
| `NEEDS_FIX` | ERROR が 1 件以上、または WARNING が 1 件以上 |

APPROVED 時は 1 行で出力（`判定: APPROVED（検査ファイル数: N, ERROR: 0, WARNING: 0）`）。
NEEDS_FIX 時のみ詳細テーブルを出力する。

### ステータス運用

判定そのものは `APPROVED` / `NEEDS_FIX` を返す。WARNING も修正必須として扱う。

### 行動規範

1. 設計書整合性（クラス定義 / メソッドシグネチャ等）には言及しない（`design-review-agent` の担当）。
2. import のレイヤー間依存方向には言及しない（同上）。
3. 判定は ERROR が 1 件でもあれば NEEDS_FIX。WARNING も同じ。
4. ダミー実装の検出は必須:
   - unittest.mock の import がある（テストコード含む）
   - `pass` のみのメソッド実装（抽象メソッド除く）
   - 「暫定 / 仮実装 / 後で修正」等のコメント付きコード
   - TODO / FIXME / HACK 先送りマーカー
   - try/except で握りつぶしてダミー戻り値を返している
5. レビュー結果の修正は行わない（`micro-impl-agent` に委ねる）。
6. レビュースキルを読み込んでからレビューを実行する。

### REQUIRED SUB-SKILL

- mode: implementation → `code-quality-review` + `error-handling-review`
- mode: test → `test-review`（policy モード）
