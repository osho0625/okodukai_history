# 共通スキル: 配布・運用系

ワークフロー横断で動く基盤スキル群。ルール配布、進捗管理、コミット、ドキュメント管理、
ゲート判定、QA ディスパッチ、ユーザー情報管理等を担う。

各スキルの記載は「目的 / 呼び出し元 / メインプロセスの要点 / Iron Law」の 4 観点で統一する。

## rules-distribute

### 目的

aide-powers のルールを各プラットフォームのルールファイル機構に直接配置することで、
AI Agent がスキル本体を読まなくてもプラットフォームが自動でコンテキスト注入する状態を作る。

### 呼び出し元

- ハブスキル（`using-aide-powers`）の初回起動時 → **global モード**
- 全フェーズスキル / 全共通スキルの開始時 → **skill:deploy モード**
- 全フェーズスキル / 全共通スキルの完了時 → **skill:cleanup モード**

### メインプロセスの要点

`global-rules.md` をプラットフォーム別のルールファイル機構に配置する。
skill モードはスキルごとの Iron Law / ルール / 完了条件 / 禁止事項を一時ファイルとして配置 / 削除する。
プラットフォーム別の配置先（`.kiro/steering/` / `.claude/rules/` / `.cursor/rules/` /
`.github/instructions/` / `AGENTS.md` / `GEMINI.md` 等）と形式特徴の詳細は
[第1章 `05-dynamic-rules.md`](../../01-system-platform/05-dynamic-rules.md) §3.2 配置先（プラットフォーム別）を参照。

### Iron Law

- skill:deploy 後、ルールファイルが実際に作成されていることを確認するまでメインプロセスへ進まない。
- skill:cleanup を呼ばずにスキルを終了してはならない（ルールファイルが残り続ける）。

## task-orchestration

### 目的

複雑タスク・大量の繰り返しタスクを系統的に分解し、サブエージェントに並列委譲して実行する。
スクリプトによる一括処理を禁止する代わりに、各サブエージェントがコンテキストを理解した上で
処理する仕組みを提供する。

### 呼び出し元

- 任意のフェーズスキル / 共通スキル（タスクが複雑または量が多いと判断したとき）
- 出力が切れる・大量ファイル処理が必要等の場面で、新セッション切り替えを避けるための分割実行に使用

### メインプロセスの要点

タスクを子サブエージェントに分解し、独立した粒度で並列実行させ、結果をマージする。
各サブエージェントは独自コンテキストで動作する（親の会話履歴を渡さない）。

### Iron Law

- スクリプト一括処理を禁止。各ファイルの内容を読んでから処理する。
- 出力が切れた / コンテキストあふれを理由に新セッション切り替えを安易に提案しない（§7-4）。

## session-handover

### 目的

セッション切り替え時に作業状態を引き継ぐための `session-handover.md` を管理する。
コンテキスト肥大時の安全な引き継ぎを保証する。

### 呼び出し元

- 各ワークフローのフェーズ完了時（自動更新）
- ユーザーからの明示的な引き継ぎファイル生成指示
- セッション切り替え推奨時

### メインプロセスの要点

最新の `session-handover.md` を生成し、1 世代前を `session-handover-old.md` として保持する。
プロセス 4（新セッション用プロンプトの提示）は省略禁止。

### Iron Law

- プロセス 4（新セッション用プロンプト提示）を絶対に省略しない。

## progress-resume-check

### 目的

ワークフローのフェーズ先頭で、進捗ファイルから「次に実行すべきフェーズ」を判定する。

### 呼び出し元

- 全フェーズスキルの先頭（メインプロセス開始前）

### メインプロセスの要点

`progress-file-format.md` の共通フォーマットに従って進捗ファイルを読み、戻り値に基づき分岐する。

| 戻り値 | 意味 | 呼び出し元の動作 |
|---|---|---|
| RESUME_FROM N | フェーズ N から再開 | 該当フェーズスキルへ遷移、または自フェーズなら処理続行 |
| START_FRESH | 進捗ファイル未作成 | 新規作成してメインプロセスへ |
| ALL_COMPLETED | 全フェーズ完了済み | ユーザーに案内し終了 |

### Iron Law

- 進捗ファイルを読まずに作業を開始しない。

## doc-index-maintenance

### 目的

プロジェクトのドキュメント一覧（`doc-index.md`）と各ドキュメントの状態を管理し、
設計書ゲートが正しく機能する状態を維持する。

### 呼び出し元

- 設計書・成果物の作成・更新・削除のたびに、フェーズスキル / 共通スキルから呼ばれる

### メインプロセスの要点

新規追加 / 更新 / 削除のいずれかをエントリ単位で実行する。状態列（`✅ 完了` / `⚠️ 作成中` /
`⏭️ スキップ` 等）を機械的に管理し、設計書ゲートが読める状態を保証する。

### Iron Law

- 成果物の作成・更新後の `doc-index.md` 反映を省略しない。

## git-commit-workflow

### 目的

git コミットを安全に実施する。コミット対象の選別・メッセージ生成・ユーザー承認・
コミット実行の一連を集約する。

### 呼び出し元

- 全フェーズスキルのフェーズ完了時 / QA APPROVED 後 / ワークフロー完了時

### メインプロセスの要点

ステージング対象を提示してユーザー承認を取り、適切なメッセージプレフィックスでコミットする。
**ワークフロー1件 = コミット1回**。複数ワークフローのまとめコミットを禁止する。

### Iron Law

- AI Agent が直接 `git commit` / `git push` を実行することを禁止する。本スキル経由のみ可。
- 強制プッシュ / `--no-verify` / `reset --hard` 等の破壊的操作はユーザー明示許可が必要。

## user-profile-management

### 目的

ユーザーの技術レベル（ドメイン知識 / プログラミング / システム・インフラの 3 軸 ×5 段階）を
記録・更新し、AI Agent の説明粒度や用語選択に反映する。

### 呼び出し元

- 各ワークフローの初期対話後
- 対話中にプロファイルとのギャップを感じたとき
- ワークフロー完了時のレビュー / セッション間引き継ぎ時

### メインプロセスの要点

`user-profile.md` を作成・更新する。プロファイルが存在しない時点では全軸スコア 0（不明）とし、
安全側の挙動（専門用語を避ける / 平易な言葉で確認する）を取る。

### Iron Law

- ユーザーに技術レベルを直接聞かない。会話内容から推定する。

## pending-issues-management

### 目的

ワークフロー実行中に発見したスコープ外の問題を `pending-issues.md` に記録し、現在の作業を
中断せずに最後まで完遂する仕組みを提供する。

### 呼び出し元

- スコープ外の問題発見時 / ワークフロー開始時（既存問題の提示） / 完了時（書き戻しチェック）

### メインプロセスの要点

問題を発見・記録・提示・解決のサイクルで管理する。問題発見を理由に別ワークフローを起動することは
禁止（§3-3）。

### Iron Law

- ワークフロー進行中に別ワークフローを起動して対処してはならない。

## design-gate

### 目的

実装系ワークフロー（実装 / 変更 / リファクタリング / バグ修正フェーズ2）の入口に置かれる
ハードゲート。`doc-index.md` を機械的に確認して PASS / FAIL を判定する。

### 呼び出し元

- `fs-impl-phase1-gate`、`fs-change-phase1-analysis`、`fs-refactoring-phase1-status`、
  `fs-bugfix-phase1-analysis`（フェーズ1と2の間）

### メインプロセスの要点

`doc-index.md` の全エントリを読み、`✅ 完了` または `⏭️ スキップ` であれば PASS、
それ以外があれば FAIL を返す。FAIL 時の対応は呼び出し元（設計ワークフローまたは設計逆引きワークフローへ
ユーザー誘導）が担う。

### Iron Law

- 設計書ゲートを通過しないまま実装に進んではならない。
- ユーザーが「設計書なしで進めたい」と要求しても、設計書完成を先に行うことを説明し合意を得る。

## design-sync

### 目的

実装が設計書と乖離した際に、どちらを正にして整合性を取り戻すかをユーザーと合意して反映する。

### 呼び出し元

- coding-test-2review の乖離種別確定フローで「設計漏れ」と確定された場合
- `design-review-agent` が「設計書側を更新する必要がある」と報告した場合（種別確定後に起動）

### メインプロセスの要点

乖離内容を提示し、ユーザーの判断で「実装側を直す」「設計書側を直す」を選んでもらう。
設計書を修正する場合は該当する設計系共通スキル（`object-design` の fix モード等）に委譲する。

### Iron Law

- 乖離発見時に黙って実装と設計を不一致のまま放置しない。

## doc-sync

### 目的

差分系ワークフロー（変更 / バグ修正 / リファクタリング）の最終フェーズで、差分設計書
（`delta-design.md` / `fix-design.md` / `refactoring-design.md`）の内容を既存設計書にマージする。

### 呼び出し元

- `fs-change-phase9-completion`、`fs-bugfix-phase6-doc`、`fs-refactoring-phase6-doc`

### メインプロセスの要点

差分設計書の「更新が必要な設計資料」セクションに従い、対象設計書をマージ更新する。
更新後 `doc-index.md` を反映する。

### Iron Law

- 差分設計フェーズ中（QA 前）に既存設計書を直接変更してはならない。マージは本スキル経由のみ。

## design-qa-dispatch

### 目的

設計書 / 差分設計書のレビューが必要な場面で、影響領域を判定して適切なQAレビューアーエージェント
（`requirements-qa-agent` / `architecture-qa-agent` / `object-design-qa-agent` /
`final-design-qa-agent` / `delta-design-qa-agent`）を呼び分ける。

### 呼び出し元

- 設計ワークフローの 4ゲート（`fs-design-phase3-dev-plan` / `fs-design-phase7-ddd` /
  `fs-design-phase8-object` / `fs-design-phase10-program`）
- 差分系ワークフローの差分設計 QA（`fs-change-phase5-delta-design` / `fs-bugfix-phase4-design` /
  `fs-refactoring-phase4-design`）

### メインプロセスの要点

差分系ワークフローでは `delta-design-qa-agent` を**常に呼ぶ**。差分が触る設計領域に応じて
追加のQAレビューアーエージェントを呼ぶ。設計ワークフローのゲートではゲート位置に対応するエージェントを呼ぶ。
REJECTED 時は再 QA を必須とする。

### Iron Law

- REJECTED 後の再 QA を省略してはならない。
- 差分系ワークフローで `delta-design-qa-agent` の呼び出しを省略してはならない。

## folder-merge-check

### 目的

変更 / バグ修正 / リファクタリングの分析フェーズで、起因元ドキュメントフォルダ（git blame の
`Docs:` フッターから特定）が判明した場合に、現在の作業フォルダを起因元フォルダにマージするか
判定する。

### 呼び出し元

- `fs-change-phase1-analysis`、`fs-bugfix-phase1-analysis`、`fs-refactoring-phase2-candidates`

### メインプロセスの要点

git blame の `Docs:` フッターをトリガに起因元を特定し、フォルダ統合の必要性をユーザーに提示する。
統合時に同名ファイルが衝突した場合は、ファイルの性質で 2 分岐する: (a) 恒久的設計資産
（`user-requirements.md` / `object-design-*.md` 等、常に最新が正）は既存ファイルへ追記・更新し、
(b) その時用の設計資料・進捗ファイル（`delta-design.md` / `*-progress.md` 等、WF 完了後は履歴）は
統合先の既存ファイルを `old/{日付}/` に退避してから今回 WF の成果物を正規名で配置する。
`old/{日付}/` に退避したファイルは履歴保全用とし、以降のフェーズの入力対象から除外する。
旧方式（`~1` / `~2` サフィックス）は採用しない。

### Iron Law

- 起因元の検出を意図的に無視してはならない（履歴の追跡が切れる）。

## toolmap-verifier

### 目的

現在のプラットフォームで実際に利用可能なツールを確認し、ツールマップ
（`.aide/references/{platform}-tools.md`）との整合性を検証する。

### 呼び出し元

- ツールマップ更新時、プラットフォーム移行検証時、ツール名の不整合が疑われる場面

### メインプロセスの要点

ツールマップに列挙された各ツール名と、現プラットフォームで実行可能なツールを突き合わせる。
不一致があれば修正提案を出す。

### Iron Law

- ツールマップを読まずに「そのツールは存在しない」と判断してはならない（§10）。

## visual-companion

### 目的

ブラウザベースの視覚的提示機構を提供する。モックアップ・図表・選択肢を WebSocket サーバ経由で
表示する。

### 呼び出し元

- 設計フェーズ（システム構成図、GUI モックアップ、技術比較表、依存関係図の提示）
- 企画フェーズ（アーキテクチャ構成図、技術比較表）
- ユーザー対話で「文字より図のほうが伝わる」場面

### メインプロセスの要点

ローカル WebSocket サーバを起動し、ブラウザで図を表示してユーザーに確認してもらう。
合意取得 / 修正反映の対話に活用する。

### Iron Law

- 視覚的表現が有効な場面で本スキルの活用を躊躇しない（§12）。
