# リリース手順

aide-powers リポジトリの新バージョンをリリースし、利用エンジニア側で `git pull && setup.*` で取り込めるようにする手順をまとめる。

機構の説明（配布構造、setup スクリプトの内部処理、グローバル / ローカルインストールの違い）は本書では扱わない。次を参照。

- 配布物の構造とインストール方式 → [第1章 アーキテクチャ](../01-system-platform/00-architecture.md)
- 各プラットフォームの配置先 → [第1章 03-platform-bootstrap](../01-system-platform/03-platform-bootstrap/)
- ルール配布機構 → `skills/rules-distribute/SKILL.md`

本書は「やり方」だけを書く。

## 1. 成果物

1リリースで作成・更新するもの:

- 更新: `README.md`（バージョン記載がある箇所、互換性メモ等）
- 更新: 必要に応じて `docs-dev/00-overview.md`（構成変更があれば）
- 必要に応じて新規 / 更新: `docs/` 配下のユーザー向けドキュメント
- 新規: git タグ（`v{major}.{minor}.{patch}` 形式）
- ユーザー向け: 取り込み手順の案内（リリースノートまたは内部展開）

## 2. リリース前チェック

リリース作業を始める前に、以下が満たされていることを確認する。

- [ ] 全ワークフローが最低1サイクル動くことを確認済み（回帰テスト）
- [ ] 新規追加 / 変更したスキルの skill:deploy / skill:cleanup が正常動作することを確認済み
- [ ] `setup.bat` / `setup.sh` を実機（少なくとも Windows + Linux/WSL）で再実行し、対象プラットフォームに正しく配布されることを確認済み
- [ ] `cleanup-kiro-agent.bat` / `cleanup-kiro-agent.sh` 等のクリーンアップスクリプトが新バージョンの旧構成削除を網羅していることを確認済み
- [ ] `setup-local.bat` / `setup-local.sh` でローカルインストールも動作することを確認済み（チーム共有利用想定）
- [ ] 共通用語辞書 `.aide/specs/aide-powers/ubiquitous-language.md` が最新の用語と一致していることを確認済み
- [ ] `README.md` の「対応プラットフォーム」表と実際の `setup.bat` 対応プラットフォームが一致していることを確認済み

## 3. バージョン番号付け

aide-powers はセマンティックバージョニングに準じる。

| 種別 | 上げる対象 | 該当例 |
|---|---|---|
| MAJOR | 互換性のない変更 | 既存スキル名変更 / 既存ワークフロー削除 / 配置先ディレクトリ構造の破壊的変更 |
| MINOR | 後方互換ありの機能追加 | 新ワークフロー追加 / 新フェーズスキル追加 / 新共通スキル追加 / 新エージェント追加 |
| PATCH | バグ修正・誤字修正 | プロンプトテンプレートの誤記修正 / SKILL.md 内の表記揺れ修正 |

直前のバージョンは `git tag --list` で確認する。タグが1件もない場合は `v0.1.0` から始める。

## 4. リリース手順（リリース担当者作業）

### 4-1. ブランチとコミット

- [ ] リリース用ブランチを切る（例: `release/v{X.Y.Z}`）。`main` への直 push は禁止
- [ ] 全変更が `git-commit-workflow` 経由でコミット済みであることを確認
- [ ] ローカルで `git status` がクリーンであることを確認

### 4-2. ドキュメント最終更新

- [ ] `README.md` の互換性メモ（必要なら）を更新
- [ ] `docs-dev/00-overview.md` を新ワークフロー / 新スキル追加に合わせて更新
- [ ] バージョン番号を記載しているファイルがあれば更新（aide-powers は基本的に git タグでバージョン管理し、コード内バージョン文字列を持たない方針）

### 4-3. PR とレビュー

- [ ] `release/v{X.Y.Z}` から `main` への PR を作成
- [ ] タイトル: `release: v{X.Y.Z}`（70 文字以内）
- [ ] 説明に以下を記載
  - 含まれる変更（新スキル / 変更スキル / 削除スキル / 新エージェント等）
  - MAJOR / MINOR / PATCH の判定理由
  - 動作確認したプラットフォーム
  - 既知の互換性影響（あれば）
- [ ] レビュアーから approve を得る
- [ ] `main` にマージ

### 4-4. タグ付け

- [ ] `main` を最新化: `git checkout main && git pull`
- [ ] タグ作成: `git tag -a v{X.Y.Z} -m "Release v{X.Y.Z}"`
- [ ] タグ push: `git push origin v{X.Y.Z}`
- [ ] タグが GitHub / 配布リポジトリ側で参照可能になったことを確認

### 4-5. リリースノート（任意 / 推奨）

GitHub Releases などホスティング側のリリースノート機能を持つ場合、以下を含めて公開する。

- 主要変更（新ワークフロー / 新スキル / 新エージェント / 互換性影響）
- ユーザー側の取り込み手順（§5）
- 既知の問題と回避策

## 5. ユーザー側の取り込み手順案内

リリースノート / 内部展開には、以下の取り込み手順を含める。利用エンジニアはこれをそのまま実行する。

### 5-1. グローバルインストール環境

#### Windows

```cmd
cd %USERPROFILE%\aide-powers
git pull
setup.bat
```

#### Linux / Mac / WSL

```bash
cd ~/aide-powers
git pull
./setup.sh
```

`setup.bat` / `setup.sh` を再実行すると、旧バージョンのファイル（旧スキル / 旧フェーズフォルダ等）は自動でクリーンアップされる（`cleanup_legacy_skills` 処理）。利用エンジニアが手動で削除する必要はない。

#### Gemini CLI のみ追加で利用している場合

```bash
cd ~/aide-powers
gemini extensions link .
```

エクステンションは link で参照しているため `git pull` した時点で内容が反映される。

### 5-2. ローカルインストール（チーム共有）環境

プロジェクトリポジトリに `setup-local.bat` / `setup-local.sh` で組み込んでいる場合は、ホスト側 aide-powers を更新した後、各プロジェクトで再度ローカルインストールを実行する。

```bash
cd ~/aide-powers
git pull
./setup-local.sh /path/to/your/project
```

### 5-3. 取り込み後の確認

利用エンジニアが取り込み後に確認すべき項目を案内する。

- [ ] 対象プラットフォームのセッションを再起動
- [ ] ハブスキル経由でいずれかのワークフローを起動できることを確認
- [ ] 旧フォルダ構造（古い `*-workflow/` 等）が削除されていることを確認
- [ ] `.aide/references/` が最新化されているか（不安なら `.aide/references/` を一旦削除して再起動すると `using-aide-powers` が再配置する）

## 6. リリース後チェック

- [ ] 自身のワークスペースで `git pull && setup.*` を実行し、リリース内容が想定通り反映されることを実機確認
- [ ] 主要プラットフォームで新規セッションを開始し、Quick Routing が新内容で動作することを確認
- [ ] 既存ワークフローが回帰していないことを確認（最低1ワークフロー）
- [ ] ドキュメント（README / docs-dev / docs）が新バージョン内容と一致していることを確認

## 7. 注意事項・落とし穴

- **タグ前のコミット忘れ**: `git tag` は HEAD に対して打たれる。マージ前のブランチに打っても利用エンジニアの `git pull` で取得できない。必ず `main` マージ後の HEAD でタグ付けする。
- **旧構成削除の網羅性**: `setup.bat` の `:cleanup_legacy_skills` セクションは旧ワークフローフォルダ（`design-workflow/` 等）の削除を行う。新リリースで旧フォルダを生んだ場合、ここに削除対象を追記しないと利用エンジニアの環境にゴミが残る。
- **rules-distribute の自動再実行は走らない**: グローバルルール（`global-rules.md`）を更新した場合、利用エンジニアのワークスペースに既に配布済みのルールファイル（`.kiro/steering/aide-powers-global-rules.md` 等）は自動更新されない。`using-aide-powers` 起動時の STEP 3 で「いずれか存在する → スキップ」になるため、古いルールが残り続ける。リリースノートで「ルール変更を反映するには `.kiro/steering/aide-powers-global-rules.md` 等を一旦削除してセッション再起動」と案内するか、利用エンジニアに明示的に rules-distribute 再実行を依頼する。
- **互換性破壊の即時影響**: スキル名やフェーズ名を変更すると、進行中のワークフローが `progress-resume-check` で `START_FRESH` 扱いされる。MAJOR バージョンとして扱い、リリースノートに移行手順を必ず記載する。
- **チーム共有環境での反映遅延**: ローカルインストール環境では、リポジトリ管理者が `setup-local.*` を再実行しないと反映されない。リリース通知の送付先にプロジェクトリポジトリ管理者を含める。
- **gitコミットルールはリリース作業にも適用**: リリース時のコミット（README 更新 / ドキュメント最終更新等）も `git-commit-workflow` 経由で行う。手動 `git commit` の直接実行を禁止する（global-rules §4-2）。
- **タグ削除は原則禁止**: 利用エンジニアが既に `git pull` 済みの場合、タグ削除すると参照が壊れる。タグ訂正が必要な場合は新しい PATCH タグを切る。
- **第1章 / 第2章のドキュメント**: 配布構造の説明や setup スクリプトの内部処理解説は第1章。本書（第3章）には書かない。
