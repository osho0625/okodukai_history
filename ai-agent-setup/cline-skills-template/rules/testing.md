# テスト方針

プロジェクトに配置する場合は `.clinerules/testing.md` にコピーする。

## テスト原則

- 新機能には必ずテストを書く
- バグ修正時は、そのバグを再現するテストを先に書く（TDD的アプローチ）
- テストが落ちたまま次の作業に進まない

## テストの粒度

| レベル | 何をテストするか | 頻度 |
|--------|-----------------|------|
| ユニットテスト | 個々の関数・メソッド | 全変更 |
| 統合テスト | モジュール間の連携 | 機能追加時 |
| E2Eテスト | ユーザー操作フロー | 重要フロー |

## テストの書き方

- テスト名は「何が、どうなるべきか」を日本語or英語で明確に書く
- Arrange → Act → Assert パターンに従う
- 1テスト = 1アサーション（可能な限り）
- テスト間の依存を作らない（独立して実行可能に）

## テスト対象の優先順位

1. ビジネスロジック（計算、判定、変換）
2. エッジケース（0、null、空配列、境界値）
3. エラーケース（異常入力、タイムアウト）
4. 正常系のハッピーパス

## テストが書けない場合

テストフレームワークがない、またはテストが困難な場合でも、スキップは許可しない。
以下を必ず記載すること:

- 書けない理由: {具体的な理由}
- 代替確認方法: {どう動作確認するか}
- 手動確認手順: {ステップバイステップ}
- 確認結果: OK / NG

「テストが書けないので省略します」は禁止。理由と代替を示すこと。
