# Detailed Rules（必要時のみ参照）

## フェーズ判定

| 発話パターン | 開始フェーズ | Skill |
|-------------|-------------|-------|
| 「〇〇を作って」「新機能」「追加して」 | Requirements | `01-requirements.md` |
| 「この仕様で設計して」 | Design | `03-design.md` |
| 「実装して」（設計書あり） | Task Planning | `04-task-planning.md` |
| 「バグ直して」「エラー」 | 即実装 | ※省略条件を満たす場合のみ |
| 「リファクタして」 | 即実装 | ※省略条件を満たす場合のみ |
| 軽微修正 | 即実装 | 省略可 |

## Architecture Review の実施条件

以下のいずれかに該当する場合のみ:
- DBテーブルの追加・変更
- APIエンドポイントの追加
- ディレクトリ構成の変更
- 新規ライブラリの導入
- 認証・認可方式の変更
- 状態管理の変更
- イベントフロー・キャッシュ方式の変更
- 外部サービスの追加
- 既存設計パターンへの影響

## Decision Log

`docs/specs/{feature-name}/decision-log.md` に記録するのは **設計変更を伴う判断のみ**。
記録しない: 命名変更、リファクタ、微修正、コメント修正。

## 要求外の改善案

実装しない。報告のみ:
- Issue化を提案する
- 「提案: ○○。スコープ外なので実装しない」と報告する

## 成果物の保存先

- `docs/specs/{feature-name}/` に保存（ケバブケース）

## コミットメッセージ

`feat:` / `fix:` / `docs:` / `refactor:` / `test:`
