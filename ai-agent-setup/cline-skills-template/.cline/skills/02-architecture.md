# Skill: Architecture Review（アーキテクチャレビュー）

## 実施条件

以下のいずれかに該当する場合のみ実施する:
- 新規機能の追加
- DBテーブルの追加・変更
- APIエンドポイントの追加
- ディレクトリ構成の変更
- 新規ライブラリの導入
- 既存設計パターンへの影響がある

該当しない場合はスキップしてDesignに進む。

## 目的

既存システムとの整合性を確認し、設計の方向性を早期に定める。

## 手順

1. 前フェーズのサマリを整理する:
   - 目的: {この機能で何を実現するか}
   - 決定事項: {確定した要件}
   - 未決事項: {まだ決まっていないこと}
   - 制約: {技術的・ビジネス的制約}
2. 既存コードベースを確認する
3. チェックを実施する
4. 結果を `docs/specs/{feature-name}/architecture-review.md` に記録する
5. ユーザーに報告し、設計フェーズへ

## チェック観点

### 既存構成との整合性
- 既存のディレクトリ構成に収まるか
- 既存のデータフローに乗せられるか
- 既存の命名規則・パターンに合うか

### 新規ライブラリ・技術の必要性
- 既存の技術スタックで実現可能か
- 新しいライブラリが必要な場合、その理由は十分か

### 影響範囲
- 変更が影響する既存ファイルの範囲
- 既存機能へのデグレリスク
- 共有リソース（DB、localStorage、CSS）への影響

### 技術的負債
- この実装が将来の保守性を下げないか

## 出力フォーマット

```markdown
# {機能名} - アーキテクチャレビュー

## サマリ
- 目的: ...
- 決定事項: ...
- 未決事項: ...
- 制約: ...

## 既存構成との整合性
- ✅ / ⚠️ {判定と理由}

## 新規技術の要否
- {不要 / 必要: {理由}}

## 影響範囲
- {ファイル一覧と影響度}

## 推奨方針
- {設計フェーズで採るべきアプローチの方向性}

## リスク・懸念
- {あれば}
```

## Decision Log への記録

重要な判断があれば `docs/specs/{feature-name}/decision-log.md` に記録する:
- 日時
- 判断内容
- 理由
- 採用案 / 却下案

## 禁止事項

- このフェーズでコードを書かない
- アーキテクチャの問題を無視してDesignに進まない
