# Skill: Requirements（要件定義）

## トリガー

ユーザーが新機能や大きな変更を依頼した時。

## 手順

1. ユーザーとの会話内容をサマリにまとめる:
   - 目的: {ユーザーが実現したいこと}
   - ユーザー要求: {具体的に言われたこと}
   - 不明点: {まだ分からないこと}
   - 制約: {言及された制約}
2. 不明点を質問する（下記「確認すべき観点」参照）
3. `docs/specs/{feature-name}/requirements.md` を作成する
4. ユーザーに提示し「この要件でOKか？修正・追加はあるか？」と確認する
5. 修正があれば反映 → 再確認
6. OKが出たら次のフェーズへ（Architecture Review実施条件を確認）

## 確認すべき観点

要件を書く前に、以下が不足していればユーザーに質問する:

- 誰が使うのか（ユーザーの種類・権限）
- 何ができればゴールなのか（最小限のスコープ）
- どの画面/ページに配置するか
- 既存機能との関係（連携するか、独立か）
- エラー時にどうすべきか
- 対応デバイス（PC/スマホ/両方）
- データの永続化が必要か（DB保存 vs メモリのみ）

全部聞く必要はない。文脈から明らかなものは省略し、本当に不明な点だけ質問する。

## 出力フォーマット

```markdown
# {機能名} - 要件定義

## 概要
何を作るのか、何が解決されるのか。1-3文で。

## ユーザーストーリー
- {誰}として、{何}がしたい。なぜなら{理由}。

## 機能要件
- [ ] FR-1: {具体的かつテスト可能な記述}
- [ ] FR-2: ...

## 非機能要件
- パフォーマンス: {応答時間、同時アクセス数等}
- セキュリティ: {認証、権限、データ保護}
- 対応環境: {ブラウザ、デバイス、OS}

## 受入条件
- AC-1: {操作}した時に{結果}が得られること
- AC-2: {条件}の場合に{表示/動作}すること

## スコープ外（今回は対応しない）
- {明示的に除外するもの}

## 前提・制約
- {技術的制約、既存システムの制約}
```

## 品質基準

- テスト可能（「使いやすい」ではなく「3クリック以内で完了する」）
- 曖昧さがない（「適切に」「必要に応じて」を避ける）
- スコープが明確（やることとやらないことの境界が分かる）

## 禁止事項

- 要件が確定する前にコードを書かない
- ユーザーの確認なしに次のフェーズに進まない
- 要件を勝手に追加・削除しない
