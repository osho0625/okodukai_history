# Skill: Final Review（最終レビュー）

## トリガー

全タスクの実装が完了した後（tasks.md の全チェックボックスが `[x]`）。

## 手順

1. 前フェーズのサマリを整理する:
   - 目的: {実装した機能}
   - 決定事項: {実装中に決めたこと}
   - 未決事項: {残った課題}
   - 制約: {発見された制約}
2. `docs/specs/{feature-name}/requirements.md` を読み込む
3. `docs/specs/{feature-name}/design.md` を読み込む
4. 実装されたコードを確認する
5. 以下の観点でチェックする
6. 結果をユーザーに報告する
7. 問題の重要度に応じて対応する

## チェック観点

### 1. 要件との整合性
- 全ての機能要件（FR-*）が実装されているか
- 受入条件（AC-*）を全て満たしているか
- スコープ外のものが紛れ込んでいないか

### 2. 設計との整合性
- 設計書のファイル構成通りか
- データ設計通りか
- 処理フロー・エラーハンドリングが設計通りか

### 3. コード品質
- 不要なコード（console.log、コメントアウト）が残っていないか
- セキュリティリスクがないか
- パフォーマンス問題がないか

### 4. 統合動作
- 複数タスクの実装が正しく連携しているか
- 正常系が端から端まで動作するか
- エラーケースでクラッシュしないか

### 5. Decision Log との整合性
- 記録された設計判断が実装に反映されているか
- 判断の理由が妥当か（状況が変わっていないか）

## 出力フォーマット

```markdown
# 最終レビュー結果

## サマリ
- 目的: ...
- 決定事項: ...
- 未決事項: ...
- 制約: ...

## 要件充足状況
| 要件ID | 状態 | 備考 |
|--------|------|------|
| FR-1 | ✅ | |
| FR-2 | ⚠️ | {具体的な不足点} |

## 設計との乖離
- {あれば具体的に。なければ「なし」}

## 品質上の問題
- {あれば具体的に。なければ「なし」}

## 総合判定
✅ 完了 / ⚠️ 要修正（{修正内容の概要}）
```

## 問題発見時の対応

| 重要度 | 対応 |
|--------|------|
| 軽微な未充足（コード修正のみで対応可） | 即修正する |
| セキュリティ問題 | 即修正する |
| 設計変更が必要な未充足（DB変更、API追加等） | ユーザーに確認してから対応 |
| 設計との軽微な乖離 | ユーザーに確認 |
| 改善提案（nice-to-have） | 報告のみ |

## 禁止事項

- レビューをスキップしない
- 問題を見つけても放置しない
- 設計変更を伴う修正をユーザー確認なしで行わない
- 要件にない改善を勝手に実施しない
