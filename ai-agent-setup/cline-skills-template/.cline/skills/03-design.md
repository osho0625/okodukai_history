# Skill: Design（設計）

## トリガー

Requirements確定後（Architecture Reviewがあればその後）。

## 手順

1. 前フェーズのサマリを整理する:
   - 目的: {要件の核心}
   - 決定事項: {確定した方針・制約}
   - 未決事項: {設計で決めるべきこと}
   - 制約: {アーキテクチャレビューからの制約}
2. 設計を検討する
3. `docs/specs/{feature-name}/design.md` を作成する
4. ユーザーに提示し「この設計でOKか？」と確認する
5. OKが出たら Task Planning フェーズへ

## 複数案の比較について

設計に複数の合理的な選択肢が存在する場合のみ、2案以上を比較する。
単純な変更（ボタン追加、バリデーション追加等）では1案で十分。

### 複数案が必要なケース
- アーキテクチャに複数のアプローチがある（例: SPA vs MPA）
- データ構造の選択肢がある（例: 正規化 vs 非正規化）
- パフォーマンスとシンプルさのトレードオフがある

### 1案で十分なケース
- 既存パターンの踏襲で明らかに正解がある
- 要件がシンプルで選択肢が実質1つ
- UIの軽微な追加・変更

## 設計時の判断原則

1. 既存アーキテクチャに合わせる
2. 最小限の変更で要件を満たす
3. 判断に迷ったらユーザーに選択肢を提示する
4. YAGNI（将来のための設計はしない）

## Decision Log への記録

設計判断を `docs/specs/{feature-name}/decision-log.md` に記録する:
- 日時
- 判断内容
- 理由
- 採用案 / 却下案（複数案比較した場合）

## 禁止事項

- 設計確定前にコードを書かない
- 要件にないものを設計に含めない
- 既存アーキテクチャと矛盾する設計をしない
