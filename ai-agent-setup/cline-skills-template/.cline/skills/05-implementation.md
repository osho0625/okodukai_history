# Skill: Implementation（実装 + ミニレビュー）

## トリガー

Task Planningが完了し、タスク一覧が確定した後。

## 手順（1タスクごとに繰り返す）

### 準備（実装前に必ず実施）

1. tasks.md から次のタスクの内容を確認する
2. 対象ファイルの全体を読み込み、現状を把握する
3. 関連ファイル（import先、呼び出し元）も確認する

### 実装

4. コードを書く
5. 動作確認する:
   - テストフレームワークがある → テスト実行
   - ない → エラーなく動作することを確認
6. 問題があれば修正する（下記「失敗時の対応」参照）

### ミニレビュー（タスク完了ごとに実施）

7. Definition of Done を確認する:
   - [ ] 完了条件を満たしている
   - [ ] Build/実行エラーなし
   - [ ] 既存テストが壊れていない
   - [ ] Requirementと矛盾なし
   - [ ] Designに準拠
   - [ ] デバッグコードが残っていない
   - [ ] 次タスクへの悪影響がない
8. tasks.md のチェックボックスを `[x]` に更新する
9. コミット案を生成する（コミットメッセージのみ、実行はしない）
10. 次のタスクに進む

### 全タスク完了後

11. 「全タスク完了しました。最終レビューに進みます」と報告する

## 実装ルール

### 実装前の確認（必須）
- 変更対象の関数・クラス全体を読んでから書き始める
- 関連ファイル（呼び出し元、共通モジュール）を確認する
- 既存のパターンを把握してから書く

### コード品質
- 既存コードのスタイル・パターンに合わせる
- 1関数 = 1責務
- 複雑な判定ロジックにはコメントで「なぜ」を書く
- マジックナンバーは定数化する

### エラーハンドリング
- ユーザー操作起因のエラーは必ず捕捉してメッセージ表示
- API/DB失敗時は適切なフォールバック
- エラーメッセージはユーザーが次のアクションを取れる内容にする

## 失敗時の対応（3回ルール）

同じアプローチで2回失敗したら、3回目の前に以下を整理する:

```
## 失敗分析
- 原因: {なぜ失敗したか}
- 試した方法: {何をしたか}
- なぜダメだった: {根本原因の推定}
- 次に試す方法: {別アプローチ}
```

別アプローチでも失敗した場合、上記をユーザーに報告し判断を仰ぐ。

## Decision Log（実装中の判断記録）

実装中に設計変更を伴う判断をした場合、`docs/specs/{feature-name}/decision-log.md` に記録する:
- 日時
- 判断内容（例: API仕様を変更した）
- 理由
- 採用案 / 却下案

軽微な実装判断（変数名の選択等）は記録不要。

## 禁止事項

- 対象ファイルを読まずにいきなり書き始めない
- 複数タスクを一度に実装しない（1つずつ確実に）
- ミニレビュー（Definition of Done確認）をスキップしない
- 設計書にない機能を勝手に追加しない
- 同じアプローチで3回以上失敗を繰り返さない
- テストが落ちたまま次のタスクに進まない
